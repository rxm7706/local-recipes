- (decision) Paradigm: two-plane architecture. Build-time plane = pipes-and-filters (recipes -> pixi-locked env -> pixitainer OCI assembly -> SBOM/sign). Run-time plane = hexagonal with exactly ONE true port: the LLM provider, already defined by upstream llmai's CUSTOM_LLM_URL/CUSTOM_LLM_API_KEY contract, with three tier adapters (Tier1 internal proxy / Tier2 llama.cpp sidecar / Tier3 init-container GGUF fetch). This mirrors AD-3 in the pyforge-herald spine (transport-agnostic core) applied to the LLM seam instead of a design-tool transport.
- (decision) AD-1 Build pipeline composition: single pixi.toml environment assembles the five confirmed recipes (presenton-export-node, pptx-assembler, pptx-thumbnail-inject, playwright-with-chromium, llmai) as pinned conda dependencies; pixitainer consumes that locked environment to produce the OCI image. ALL channel/package resolution during this build MUST route through the *_BASE_URL env-var family (docs/reference/enterprise-deployment.md sec 6) - no recipe or build step may hardcode a public URL. Prevents: one recipe author's build reaching a public CDN while another routes through JFrog, silently breaking the air-gap hard constraint per-recipe instead of enforcing it once at the pipeline level.
- (decision) AD-2 LLM provider port is the ONLY swappable seam in the running app. Presenton app code and Helm chart never branch on which tier is active beyond setting CUSTOM_LLM_URL/CUSTOM_LLM_API_KEY (+ optional OPENAI_BASE_URL/ANTHROPIC_BASE_URL passthrough) to point at: Tier1 = an operator-supplied external endpoint (no in-cluster resource), Tier2 = a llama.cpp Service in the same namespace (OpenAI-compatible HTTP, sidecar or dedicated Deployment), Tier3 = same llama.cpp Service but its Pod carries an init-container that fetches the GGUF from an internal registry before the main container starts. Prevents: a Tier2-specific code path or in-process llama-cpp-python binding creeping into the app instead of staying at arm's length over HTTP like Tier1/3.
- (decision) AD-3 Recipe/image boundary: image-assembly layer (this architecture's pixi.toml + Helm chart) only ever consumes published, versioned conda artifacts by name+pin; it never vendors or patches recipe internals. Recipe content itself is conda-forge-expert-governed (CLAUDE.md Rules 1&2), out of this architecture's scope. Prevents: image-build-layer forks of recipe logic that silently diverge from the upstream-merged recipe.
- (decision) AD-4 Chromium sandbox default (resolves Risk R9): default to --no-sandbox in the playwright-with-chromium invocation inside the OCP pod, as an explicit, Helm-values-documented security decision (not a silent default) - standard container-Chromium practice, compatible with restricted-v2/v3's allowPrivilegeEscalation:false. Escape hatch: a Helm values flag (chromiumSandboxMode: none|namespace) lets a Phase-0/architecture spike swap in unprivileged-namespace sandboxing later IF empirically validated against a real OCP restricted-v3 cluster; ships as an unexercised code path (documented, not built) until that spike runs. Prevents: two deployers independently guessing a sandbox posture and producing inconsistent security postures across customer clusters.
- (decision) AD-5 Provenance pipeline: syft (1.49.0, conda-forge-verified) scans the assembled OCI image (post-pixitainer, pre-registry-push) producing CycloneDX (primary format) + SPDX (secondary export) in one deterministic step; cosign (3.0.4) signs the resulting image digest and attaches the SBOM as an in-toto attestation. Single tool, single step, runs once per image build - prevents two different SBOMs (e.g. one lockfile-derived, one image-introspected) existing for the same image tag.
- (decision) AD-6 Fixture-set phase boundary is a hard CI-topology split, not just a doc convention: tests/fixtures/upstream-baseline capture (Set 1) and tests/drift (Set 2) run ONLY in a separate, explicitly-online GitHub Actions workflow (network egress allowed) that never shares a runner/environment with the air-gapped build pipeline; the air-gapped pipeline workflow has no network egress at all (enforced at the CI-runner/network-policy level, not just by convention) so an accidental Set-1/Set-2 invocation inside it fails loudly instead of silently reaching out. tests/operational (Set 3) and tests/install (Set 4) ship inside the OCI image and run air-gapped by construction.
- (decision) AD-7 Memory-subsystem fork (Phase 0 exit 6b) is pre-wired, not blocking: pixi.toml carries a feature flag (presenton-memory feature, default OFF) toggling whether mem0ai+fastembed-vectorstore are in the locked environment; Helm chart carries a matching values.memory.enabled (default false) that sets the env var Presenton needs to no-op the subsystem IF that no-op path is confirmed clean (open question from PRD exit 6b - if it requires a source patch instead, this AD's default-OFF shape still holds, the patch just becomes part of the presenton-export-node/pptx-assembler patch set already in scope). Prevents: image-build work blocking on the Phase-0 decision, and prevents the eventual answer from requiring an architectural rework - both shapes are already the same toggle.
- (decision) AD-8 OCP SCC target: Helm chart's PodSecurityContext/SecurityContext defaults are restricted-v2-compatible (all capabilities dropped, seccompProfile runtime/default, allowPrivilegeEscalation false, non-root arbitrary UID via GID-0/chmod-g=u convention on writable paths) as the floor every cluster supports; restricted-v3 (hostUsers:false) compatibility is asserted but not separately branch-tested until the AD-4 spike runs. No hardcoded UID/GID anywhere in the image or chart.
- (constraint) Consistency convention: Helm values.yaml carries one top-level llmProvider.tier enum (tier1|tier2|tier3) selecting a values sub-block; no separate chart-per-tier, no separate values-file-per-tier fork that could drift. Writable-path convention: only /app_data and /tmp are writable (emptyDir or PVC), everything else read-only-root-filesystem-compatible as an opt-in hardening flag (readOnlyRootFilesystem: false by default per PRD's note that Restricted SCC doesn't mandate it, true available for hardened clusters).
