## Intent

**Problem:** `board.py::_check_project_chain_completeness`'s INV-A check (`chain-completeness`)
decides "this open Spec is decomposed" with `if bare not in prose and slug not in prose` — a
bare substring test over the concatenated PRD+epics prose blob. Once ANY epic mentions a Spec's
name once, it reads as fully decomposed forever, no matter how many capabilities are later added
to it with zero stories against them (`DW-CHAIN-COMPLETENESS-1`: proven live — `spec-deferred-work-visibility`
grew from 3 to 10 capabilities on 2026-08-15 and the check still reported `ok` while 7 of 10 had
no story anywhere).

**Approach:** Parse the Spec's own declared `CAP-N` ids from its `## Capabilities` section
(format: `- **CAP-<N> — <title>.**`), parse every `CAP-` reference actually cited in the
project's PRD/epics prose (three live citation shapes confirmed by grepping every tracked
`epics.md` fleet-wide: bare `CAP-N`, inclusive range `CAP-N..M`, and slash-grouped `CAP-N/M/...`),
and report the specific uncovered CAP ids as one INV-A finding per Spec, instead of a single
pass/fail boolean for the whole Spec.

## Boundaries & Constraints

**Always:** A Spec with declared `CAP-N` ids is judged by CAP-id coverage, not by whether its
slug/name string appears in prose. The finding for an incompletely-decomposed Spec names the
specific missing CAP ids (e.g. `CAP-4, CAP-6..10`), not just "not decomposed." All 30 existing
tests in `test_sources_board_chain_completeness.py` for INV-B/C/D (everything except INV-A)
continue to pass unmodified — this story touches INV-A only.

**Block If:** none identified — this is a self-contained, well-scoped bug fix in one function
with no cross-story dependency.

**Never:** Do not touch INV-B, INV-C, or INV-D logic in the same function/module. Do not change
`OPEN_SPEC_STATUSES` or `DEFERRED_SPECS` semantics. Do not introduce a new CLI flag or config
option — this is a pure detector-logic fix, same signature, same call site.

| Zero-CAP Spec, slug NOT in prose (existing test `test_open_undecomposed_spec_reports_fail`) | SPEC.md has no `## Capabilities` section; slug never appears in any PRD/epics prose | One `spec-not-decomposed` FAIL finding, same shape as today | N/A |
| Multi-CAP Spec, partial coverage (the DW-CHAIN-COMPLETENESS-1 repro) | SPEC.md declares `CAP-1`..`CAP-10`; epics prose cites only `CAP-1..3` | One FAIL finding naming the uncovered ids `CAP-4..10` (or an equivalent explicit list) — never `ok` | N/A |
| Multi-CAP Spec, full coverage via mixed citation shapes | SPEC.md declares `CAP-1`..`CAP-5`; epics prose cites `CAP-1`, `CAP-2/3`, `CAP-4..5` | No finding — every declared id is covered by at least one citation shape | N/A |

| CAP citation with a malformed range (e.g. `CAP-10..4`, reversed) | Epics prose contains a range where the end is less than the start | Treat as citing no ids from that malformed token (do not silently invert or crash) — the uncovered-id list is unaffected by a token that resolves to nothing | Never raise |

## Design Notes

**Round 1 fallback design decision (still valid, KEEP):** a Spec with zero parseable `CAP-N` ids falls back to the original bare-substring behavior rather than, say, always failing or always passing. Rationale: a Spec authored before the `## Capabilities` convention existed, or one that genuinely has no capability breakdown, has nothing for a coverage test to compare against — the substring test is the only signal available, and both pre-existing tests already encode this exact expectation. This preserves 100% of current INV-A test semantics for the zero-CAP case while adding real coverage-gap detection for the common case. **This part of Round 1's implementation worked correctly and needs no change** — keep `_parse_declared_cap_ids`'s design, the `_format_cap_ids` range-collapsing formatter's design, and the overall two-parsers-plus-a-set-diff architecture. Also KEEP the `test_sources_board_chain_completeness.py` fixture-extension pattern (`_write_spec` gaining an optional `capabilities` param) -- it worked well and matched the file's existing style.

**Round 2 rejection (bad_spec loopback, triggered by adversarial + edge-case review):** Round 1's `_parse_cited_cap_ids(prose)` built ONE flat set of cited CAP ids for the whole project's concatenated prose, and every Spec in that project was checked against that same pooled set. Since virtually every SPEC.md numbers its own capabilities starting at CAP-1, two open Specs in the same project with overlapping declared ids cross-contaminate: citing `spec-bar`'s `CAP-1..3` in epics.md silently "covers" `spec-foo`'s identically-numbered, genuinely-undecomposed `CAP-1..3` too. Verified live against real fleet data during review: `pyforge-marshal` has two open Specs (`spec-pyforge-core`, `spec-surface-drift-reconciliation`) that both declare `CAP-1..6`-ish ranges; Round 1's code reported only `spec-pyforge-core`'s CAP-7 as uncovered even though `spec-pyforge-core`'s own prose never cites a bare `CAP-N` token at all -- the "coverage" for its CAP-1..6 was bled in from the *other* Spec's citations elsewhere in the same project's epics.md. This is the exact "reports OK while missing most of what it claims to check" defect class `DW-CHAIN-COMPLETENESS-1` exists to fix, reintroduced one level down. **The required fix: citations must be scoped to the specific Spec they belong to, not pooled project-wide.** The fleet's real epics.md convention gives a reliable scoping anchor: an Epic's own prose names which Spec it decomposes, via a "Decomposes `<spec-slug>`" or "**Spec binding.** Decomposes `<spec-slug>`" phrase near the top of that Epic's section (confirmed live across doctor/steward/herald epics.md files -- e.g. this very Epic 12's own header: "Decomposes `spec-fleet-hygiene-verification-exemplar-program` CAP-1..5"). Design the scoped parser around segmenting a project's epics/PRD prose into per-Spec windows using this "Decomposes `<slug>`" anchor (however you choose to detect the window boundary -- next such anchor, or next top-level Epic heading, whichever the real data supports most robustly; investigate a handful of real epics.md files across 2-3 projects before finalizing the exact boundary rule), and only counting a `CAP-N` citation found inside a Spec's own window as covering that Spec. A project whose prose contains no such anchor at all for a given Spec (i.e. it cannot be scoped) must NOT fall back to pooling -- treat it the same as if no citation was found for that Spec (safer to under-report coverage than to risk cross-contamination). Also confirmed live during review: the citation regex must additionally accept the `CAP-N..CAP-M` prefixed-range shape (5 real occurrences: `pyforge-marshal/prd.md` ×2, `pyforge-atlas/epics.md` ×3) -- Round 1's regex silently dropped this shape entirely, contradicting its own docstring's "grepped fleet-wide" claim.

**Round 2 zero-cost hardening (folded in, not separately justified by a live occurrence):** while rewriting the citation regex for the `CAP-N..CAP-M` shape above, also anchor its leading `CAP-(\d+)` with a trailing `\b` (matching `_parse_declared_cap_ids`'s own existing `\b` boundary) so a token like `CAP-10x` cannot be mistaken for a citation of `CAP-10` -- checked live, no such token exists in the fleet today, but the fix is a one-character addition to a regex already being rewritten, so there is no reason not to include it.

**Round 3 rejection (bad_spec loopback, review pass 2):** Round 2's `_cited_cap_ids_by_spec` anchored a citation window on ANY literal occurrence of a Spec's own slug text anywhere in the project's prose -- including a purely narrative aside with no decomposition intent at all. Live-reproduced during review: `pyforge-marshal/prd.md` line 8 mentions `spec-surface-drift-reconciliation` inside a dated changelog/comment block, near the top of the file, well before that file's first `## ` heading (line 34) -- Round 2's code opens a citation window there and sweeps in an unrelated `CAP-9` token from the same changelog block (about a different capability entirely), wrongly crediting CAP-9 to `spec-surface-drift-reconciliation`. This did not flip today's actual reported finding only by luck (CAP-9 isn't in that Spec's own declared set) -- it is nonetheless a live-reproducible instance of the SAME cross-contamination defect class Round 2 was supposed to close, just relocated to a narrower trigger (an anchor sitting in header-less preamble/changelog prose, with no heading nearby to cap it and no other anchor close enough to end the window early). **The required fix, scoped narrowly to close exactly this reproduction, not a full redesign:** an anchor occurrence must NOT open a citation window when it appears before the document's first `## ` heading -- a changelog/currency-review/frontmatter-adjacent preamble is never where a real "Decomposes `<slug>`" binding statement or a real inline `spec-<slug> CAP-N` citation lives in this fleet's actual convention (confirmed by every real example examined across both rounds), so excluding pre-first-heading anchors closes the reproduced leak without weakening the legitimate any-slug-occurrence design that Round 2 correctly established for the two real citation conventions (Epic-level "Decomposes" binding AND inline per-story `spec-<slug> CAP-N` citation) discovered during Round 2's own investigation. Do not attempt a more elaborate redesign (e.g. requiring "Decomposes" text specifically, or a tight per-paragraph proximity match) -- that would re-litigate Round 2's correctly-scoped investigation for no live-justified gain; this one narrow rule closes the one reproduced bug.

**Round 3 additional required hardening (both real, both cheap, fold into the same pass):**
1. **Missing regression test for the heading-cap branch.** Review proved by mutation (disabling `if h + 1 < len(headings): end = min(end, headings[h + 1])` and re-running the full suite) that ALL 49 existing tests still pass -- the single most heavily-documented piece of new logic (the "cap at the second heading, allow coasting across exactly one" rule, with a multi-paragraph docstring justifying it from two real live cases) has zero test coverage proving it actually does anything. Add at least one test that: (a) constructs a fixture where a Spec's own citations legitimately continue past ONE un-anchored `## ` heading (the real `spec-deferred-work-visibility` Epic 8→9 shape) and must still count as covered, AND (b) constructs a fixture where an unrelated anchor TWO OR MORE headings past the first Spec's own anchor must NOT leak into that Spec's window (the real Epic-14-to-Epic-16 marshal shape that motivated the cap in the first place). Both fixtures must fail if the cap logic is removed or the "second heading" bound is changed to "first heading" or "unbounded."
2. **Deterministic multi-file prose concatenation.** The pre-existing `prose` build (`list(pa.glob("prds/*/prd.md")) + list(pa.glob("epics*.md"))`, unchanged by this story until now) concatenates files with no separator and in filesystem-dependent glob order -- harmless for the old plain-substring check, but the new anchor/window logic is now position-sensitive, so a boundary-adjacent token across two files could fuse or split unpredictably depending on iteration order. Sort each glob result before concatenating (e.g. `sorted(pa.glob(...))`, already the pattern this file uses elsewhere for `specs/spec-*/SPEC.md`) and join files with an explicit blank-line separator so no token can span a file boundary.
3. **Redundant file read.** `_frontmatter(spec_md)` and the INV-A block's own `spec_md.read_text(...)` each independently open and read the same SPEC.md file per open Spec per project. Read once, pass the already-read text to both, or parse frontmatter from it directly -- avoids doubling file I/O for every open Spec, at zero behavior risk.

**Round 4 rejection (bad_spec loopback, review pass 3) -- SIMPLIFY, don't add more special-casing:** Round 3's preamble exclusion computed ONE "first `## ` heading" position over the WHOLE concatenated `prose` blob, not per source document. It only protects whichever file happens to sort first in the concatenation (`prds/*/prd.md` before `epics*.md`); any later-concatenated file's own header-less preamble is still exploitable by the identical leak Round 3 claimed to close. Both reviewers independently reproduced this LIVE, in two different real projects: Edge Case Hunter found `pyforge-marshal`'s general shape, and Blind Hunter found a live instance in `pyforge-doctor`'s OWN `epics.md` (the `currency_review` frontmatter field, before that file's first `## ` heading, contains a changelog-style aside naming `spec-deferred-work-visibility`'s CAP ids) -- currently inert (confirmed by a redaction test: removing that occurrence doesn't change today's live findings, because the same ids are separately, legitimately cited elsewhere via the normal coast-across-one-heading path), but a targeted synthetic repro proves it would silently suppress a real finding once that redundancy doesn't exist.

**The required fix is a SIMPLIFICATION, not another special case bolted onto `_cited_cap_ids_by_spec`:** strip each source document's own preamble (everything before ITS OWN first `## ` heading) at PROSE-BUILD TIME, in `_check_project_chain_completeness`, before any document is concatenated into `prose` -- not as an anchor-exclusion check inside the citation-window function. Concretely: for each file read while building `prose_parts`, if that file's own text contains a `## ` heading, slice the text to start AT that heading (discard everything before it); if the file has no `## ` heading anywhere, keep its text whole, unchanged (mirrors Round 3's own existing "nothing to exclude when there's no heading" fallback, just applied per-file instead of globally). Concatenate the (now per-file-preamble-stripped) pieces exactly as Round 3 already does (sorted, `"\n\n"`-joined). Because no preamble text ever enters the searchable `prose` string in the first place, `_cited_cap_ids_by_spec` and its heading-cap logic need NO special-casing for "is this anchor before the first heading" at all -- delete that check entirely; the function goes back to reasoning about one already-clean prose string, exactly like Round 2's design, just fed cleaner input. This is simpler than Round 3's fix, not more complex, and it composes correctly with a project that has one headed file and one headerless file (each is handled independently, correctly, with no cross-file leakage possible either way) -- which is the exact shape both reviewers' live reproductions actually needed to work.
