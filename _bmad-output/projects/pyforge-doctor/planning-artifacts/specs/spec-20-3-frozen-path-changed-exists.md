## Intent

**Problem:** Architecture spine fnd:AD-22 (`_bmad-output/projects/pyforge-steward/planning-artifacts/architecture/architecture-pyforge-steward-2026-07-25/ARCHITECTURE-SPINE.md:225`) says a capability entering `rebuilding` or `moving` freezes its source paths in `local-recipes` at once, and names a `frozen-path-changed` detector as the enforcement mechanism -- but nothing has built it (`cutover-readiness.md` G11: "never built"). Until the actual python-foundry cutover begins, no capability ledger exists at all (`docs/foundry/` is empty today), so this detector spends most of its life reporting "nothing to check yet" -- but it must exist and be correct before the first capability enters `rebuilding`/`moving`, not be built reactively after a frozen path is silently broken.

**Approach:** A new Doctor source, `sources/frozen_path.py`, reads a capability ledger at `docs/foundry/manifest.{yaml,yml,json}` (first found wins; **`[ASSUMPTION: schema]`** -- see Design Notes, this exact file shape is not fixed anywhere yet, including in the architecture spine itself, which marks its own manifest location `[ASSUMPTION: location]`) listing each capability's `state` and `frozen_paths` (path prefixes). For every capability whose `state` is `rebuilding` or `moving`, diffs `origin/main..HEAD` (via `cli_bridge.run_git`, the package's sole subprocess site) and reports a `fail` Finding per (capability, changed path) pair that falls under a frozen prefix. No ledger at all -- true for every real invocation until cutover begins -- is `ok`.

## Boundaries & Constraints

**Always:**
- Read-only: reads the capability ledger file and runs `git diff --name-only` only -- no writes, no `git` mutation, no other subprocess (AD-5: `cli_bridge` is the sole subprocess site; this module's own `_git` wrapper mirrors `sources/ledger.py`'s own `_git` helper exactly).
- No ledger found at any of the three candidate paths is `ok`, naming "no capability ledger found (pre-cutover)" -- this is the dominant, expected outcome for every real invocation today.
- A found-but-malformed ledger (unparseable YAML/JSON, not a table, missing `capabilities` list) is treated as a TRACKED-contract-file defect, not silent absence: it raises inside `_gather` and is caught by the outer `degrade_on_exception` wrapper into one generic WARN -- mirrors `bmad_method.py`'s CAP-1/CAP-2 "raise on a tracked file, degrade at the outer net" style, not the fail-open-per-layer style Story 20.2 used for gitignored/optional config layers (a capability ledger, once it exists, is a real contract file whose corruption is worth flagging).
- An unresolvable `origin/main`/`HEAD` git ref, or any other git failure, is a WARN ("could not diff") -- mirrors `sources/ledger.py`'s own "unresolvable base ref... yields a WARN Finding" precedent for the identical `origin/main..HEAD` shape.
- A genuine frozen-path violation is a `fail` `DoctorStatus`, one Finding per (capability, changed path) pair, naming both -- literal AC text ("a change under a frozen path is a `fail` naming the capability and the path"). This is a deliberate, documented departure from Epic 20's own general framing paragraph ("HARD boundaries: every finding stays advisory -- `warn` at most") -- see Design Notes for why the more specific, per-story AC governs here, consistent with this package's own extensive existing precedent of FAIL-capable sources (`LEDGER_REGRESSION`, `PLATFORM_POLICY_SUITE`, `SPEC_SURFACE`, ...).
- `scope="repo"` (reads only tracked files + git history, runs anywhere) -- eligible for `detectors-ci` membership per the story's own Surface line, added to `scripts/detectors.py`'s `_DOCTOR_SOURCE_TASKS` following the same "offline, deterministic, no budget concerns" bar `platform-policy-suite`/`bmad-render-config-ambiguity` already cleared.

**Never:**
- Never write to `docs/foundry/**`, never run a mutating git command, never invoke `steward cutover plan` or import any steward/marshal package -- this source is structurally independent of the mechanism it inspects, same rule every sibling source in this package follows.
- Never treat a capability whose `state` is anything other than `rebuilding`/`moving` (`planned`, `verified-in-foundry`, `cut`, or unrecognized) as frozen -- only those two states freeze paths per fnd:AD-22's own rule.
- Never invent a second manifest-discovery mechanism beyond the three-extension `manifest.{yaml,yml,json}` probe -- if the real cutover work lands a different shape, that is a follow-on story's fix, not something to pre-guess further here.

## Design Notes

**Why `[ASSUMPTION: schema]` is unavoidable here, and how this spec resolves it.** The architecture spine (fnd:AD-22, Consistency Conventions table) defines TWO separate, only loosely related schemas: a per-FILE manifest row (`path · kind · owner · coupling[] · destination · reason · source_sha · status · foundry_commit`, explicitly `[ASSUMPTION: location]` at `docs/foundry/manifest.*`, JSONL/CSV) and a per-CAPABILITY row (`capability · owner spec · mode · state · depends_on[] · signals · decided_by · decided_on`, no file format stated at all). Neither one, as literally documented, carries a path-list field a detector could diff against — fnd:AD-22's own prose ("freezes its source paths") requires one to exist for `frozen-path-changed` to be checkable at all, but no artifact today defines where it lives. This spec makes the minimal, clearly-labeled synthesis needed to build something real: one YAML/JSON file at `docs/foundry/manifest.{yaml,yml,json}` holding a `capabilities:` list, each entry carrying `capability`, `state`, and a `frozen_paths` list — the capability-row fields fnd:AD-22 already names, plus the one field (`frozen_paths`) its own freeze rule requires. If steward's own cutover work later lands a different concrete shape, updating `_find_manifest`/`_load_capabilities` to match is that later story's job, not a defect in this one — the detector's dominant real behavior (no ledger → OK) is unaffected by this choice and is what nearly every invocation will exercise until cutover begins.

**Why `fail`, despite Epic 20's own "HARD boundaries: warn at most" framing.** That framing paragraph describes CAP-9's two NEW detectors as a pair in prose; Story 20.2's own detector genuinely is warn-only, matching it. Story 20.3's own Given/When/Then, written specifically for THIS capability, explicitly says "a change under a frozen path is a `fail`" — a more specific, deliberately-worded contract for a structurally different violation (an active breach of a hard invariant mid-cutover, not an informational risk signal). This package already has extensive FAIL-capable precedent (`LEDGER_REGRESSION`, `SPEC_SURFACE`, `PLATFORM_POLICY_SUITE`, ...) proving "advisory, never a second PR gate" means never competing with Warden's own PR-approval mechanism — not a categorical ban on any Doctor source ever reporting FAIL. The specific, capability-scoped AC governs over the general framing sentence.

**Why real git-repo fixtures, never a mocked subprocess.** `sources/ledger.py`'s own test file already established this convention for every `origin/main..HEAD`-shaped check in this package: build an actual git repo in `tmp_path`, commit real content, and create a LOCAL branch literally named `origin/main` (`git branch origin/main <sha>` — slashes are legal in branch names, so this resolves via `git rev-parse`/`git diff` with no real remote needed). This module's own tests follow the identical pattern rather than inventing a mocking seam.
