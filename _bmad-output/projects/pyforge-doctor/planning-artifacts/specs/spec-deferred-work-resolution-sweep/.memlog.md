- (direction) Source: docs/dreams/deferred-work-resolution-sweep.md (owner: doctor, status: dreamt). Sibling of deferred-work-audit-completeness.md (folded into spec-deferred-work-visibility as CAP-4..7): that Dream gets a finding INTO tracked storage; this one periodically re-confirms it is still TRUE once there. Dream's own text: the two are different enough in kind (parsing vs. code-comprehension) to be scoped as separate stories, not one -- kept as its own standalone Spec rather than folded into spec-deferred-work-visibility again.
- (decision) Why: a tracked ledger entry is a claim about code truth AT AUTHORING TIME; nobody re-checks it once it lands. Proven valuable exactly once, by hand, never made repeatable: PR #147 (2026-07-30) individually re-verified 145 entries across 5 stations and found 12 already-resolved-but-still-marked-open (one root cause independently fixed 3x across 3 projects, 2 of 3 ledger entries still read open), 2 that got WORSE since authoring, 5 that understated their own scope, and 1 (atlas DW-I5-1) only verifiable by reading a DIFFERENT project's code. That gap has since grown, not shrunk: mason/steward/scribe (should be ~150+ entries) have never been verified once, and every entry promoted since (including tonight's fresh promotions) is unverified from day one.
- (capability) CAP-1 -- due-for-verification selection. intent: a sweep can select tracked entries needing verification -- no verified: line at all, or a verified: date older than a staleness threshold -- batched per project, without a human enumerating them by hand. success: given the fleet's current ~400+ tracked entries, running the selector returns exactly the entries with no verified: line or a stale one -- demonstrated against the current ~150+ never-verified entries (mason/steward/scribe plus all promotions since the 2026-07-30 campaign).
- (capability) CAP-2 -- churn-based cost filtering. intent: entries whose named file/path has had zero commits since their last verified date (or since authoring, if never verified) are deprioritized, since nothing could have changed. success: given an entry whose named path has zero commits since its last-verified date, the sweep does not select it for agent verification (or flags it skip-reason: no-churn); given commits since, it is selected. Structural cost bound, not discipline -- ~400+ entries and growing means a full LLM re-read every run does not scale.
- (capability) CAP-3 -- tiered verification, mechanical first. intent: a sweep attempts a cheap structural/grep-level check first for mechanically-checkable claims (a raised exception, an absent try/except, an unused function, a call-site count), escalating to an agent read only when the claim genuinely requires judgment. success: given an entry whose claim is grep-recomputable (e.g. 'N call sites of X'), the mechanical check alone produces a verdict with no agent invocation; given a judgment-requiring claim, it escalates. Mirrors spec_surface_check.py's own two-tier shape (hash-drift mechanical, drift-presumed needs a human) -- reuse that shape, do not invent a new one.
- (capability) CAP-4 -- evidence-grounded verdict recording, four verdicts. intent: for entries needing judgment, a verification agent reads the entry, locates the named code, and writes a verified: <date> -- <verdict> line backed by cited evidence (a file:line or a reproduced/measured fact), never a restatement of the entry's own prose -- and the verdict is one of four: still-open, resolved, moot/superseded (code deleted/replaced/project archived, cited), or pending-on-precondition (genuinely undecidable, e.g. blocked on a named future story) -- never a forced false confirm just to close the loop. success: every verified: line written cites a file:line or a reproduced/measured fact; a scope correction (entry claims 2 packages, sweep finds 8) is written as the corrected number, not left stale; an entry whose code no longer exists closes as moot/superseded citing what replaced/removed it, not left open and not silently dropped.
- (capability) CAP-5 -- cross-project reach. intent: whatever selects and verifies work for a batch can read any project's source tree, not just the owning project's -- a per-project-only sweep structurally cannot catch a fix that landed in a sibling project's code. success: given an entry in project A whose defect was actually fixed by a commit in project B (the precedent's real atlas DW-I5-1 case, resolved in marshal's core/policy.py), the sweep's verification step is able to read project B's tree and correctly close the entry.
- (capability) CAP-6 -- cross-entry, cross-project correlation. intent: the sweep actively looks for near-duplicate entries (same file/symbol named across different projects' ledgers, or closely similar summary text) and surfaces them as one defect-class group, not independent low-priority entries nobody connects. success: given two or more tracked entries across different projects naming the same file/symbol or near-identical summary text, the sweep's report groups them as a single defect class rather than listing them as unrelated findings -- this is the shape of the precedent's sharpest finding (one root cause hit 3x across 3 projects, found only by a human noticing the pattern while reading).
- (capability) CAP-7 -- fleet-wide staleness signal. intent: fleet_picture.py's ATTENTION block (which already aggregates cross-cutting fleet health) surfaces '% of tracked entries verified within N days, per project' as an ongoing signal, so a verification gap is visible incrementally instead of requiring another pointed user challenge to notice it went quiet again. success: after the sweep has run at least once, fleet-picture's ATTENTION block includes a per-project staleness percentage line, sourced from each project's tracked ledger's verified: dates.
- (capability) CAP-8 -- backlog-intake check (natural complement, scope boundary open). intent: when a new story/spec is drafted for an epic, tracked deferred-work entries whose owner:/prose names that same epic or story are surfaced as candidate acceptance criteria, so closing an entry does not depend entirely on someone remembering to grep the ledger by hand. success: given a story/spec draft naming epic E, tracked entries whose owner:/prose names epic E (or a story within it) are surfaced in the drafting flow as candidates. Scope-boundary question: this is write-adjacent to story-drafting, a different subsystem than the read-only sweep CAP-1..7 -- see Open Questions on whether it ships in the same wave or as its own follow-on Spec.
- (constraint) Must reuse, not re-solve, the heading-less-entry parser fix that deferred-work-audit-completeness.md's Spec (CAP-4..7, folded into spec-deferred-work-visibility) already addresses -- shared root-cause bug between promotion-side detection and this Spec's own resolution-side status tracking (normalize_deferred_ledgers.py's blind spot). Fix once, consumed by both, per the sibling Dream's own explicit note.
- (constraint) Verification must be code-grounded -- a cited file:line or a reproduced/measured fact, never a restatement of the entry's own claim back at itself. Three entries in the 2026-07-30 precedent were only correctly resolved by actually running the code (AST-evasion, dict-key collapse, schema-gap reproduction) -- reading alone was insufficient for those.
- (constraint) Must not silently narrow a scope claim on correction -- if an entry claims impact to 2 packages and verification finds 8, the corrected number is the finding to record, not a reason to leave the stale 2 uncorrected.
- (non_goal) Not a fully mechanical/parseable capability -- 'is this defect still in the code' is explicitly not a fact the way 'does this id exist in file X' is; this Spec is agent-driven for judgment-requiring claims by design, never claims full automation (CAP-3 only mechanizes the subset that genuinely is mechanical).
- (non_goal) Not deciding which Tier-3 findings get promoted into tracked storage in the first place -- that is deferred-work-audit-completeness's (folded into spec-deferred-work-visibility) territory, not this Spec's.
- (non_goal) Not a full ledger data-quality audit of pre-existing issues -- warden DW-1-4-1's still-unsplit shared id and atlas's own entries: count self-consistency gap are pre-existing cleanup items this Spec does not itself fix, though CAP-4's own evidentiary discipline would catch new instances of both classes going forward.
- (assumption) Assumed this Spec stays independent from deferred-work-audit-completeness (already folded into spec-deferred-work-visibility as CAP-4..7) rather than being folded in too -- the source Dream's own 'Relationship to the sibling Dream' section states the two problems (parsing vs. code-comprehension) differ enough in kind to warrant separate stories when this reaches bmad-spec, which this Spec takes as direction to stay standalone.
- (question) CAP-8's scope boundary: should it ship in the same story wave as CAP-1..7, or as its own follow-on Spec, since it is write-adjacent to story-drafting (a different subsystem) rather than read-only sweep verification like the rest of this Spec? Operator/architecture call.
- (question) CAP-1's exact staleness threshold (how many days before a verified: date counts as stale enough to re-select) is undecided -- the source Dream does not name a number. Needs a decision at architecture or story-definition time.

- (decision) CAP-3 widening was REQUESTED by the operator and then DROPPED on measurement: the only genuinely mechanisable shape (an absence claim naming both a token and a path) exists in exactly 2 of 1410 entries, so widening would move it from 0 to 2. Recording the measurement was chosen over building. The binding constraint is not the parser -- it is that entries do not cite the code they are about; every citation added during this sweep is worth more to the next run than any parser change.
