## What went well

- **The MCP-first/CLI-fallback pattern, established once, reused cleanly three times.** Story 2.1 proved the `doctor.sources.atlas` MCP-first-with-CLI-fallback shape on the staleness axis; Story 2.2 extended it verbatim to cve and the abandonment composite; Story 4.3 (adoption axis, Epic 4) reused the *identical* `_fetch_rows`/`_FetchFailed`/degrade pattern with zero new exception classes and zero new swallow sites (per its own self-review: "this story is a mechanical, well-precedented extension of Story 2.1/2.2's already-reviewed machinery"). This is a genuine example of an architectural decision (AD-6) paying for itself three times over instead of being re-derived or drifting.
- **The frozen Epic 1 contract held for the whole build.** `Finding`/`DoctorReport`/`Source`/`DoctorStatus`, frozen in Story 1.1, absorbed every later epic's additions (new `Source` members for cve/abandonment/adoption, the `Prescription` shape for diagnose, the health-grade and safe-upgrade fields for Epic 4) without a schema-breaking retrofit — the same "contract froze early and held" pattern Warden's Epic 1 retro flagged as foundational.
- **AD-4's purity boundary on `prescribe`/`score` was real, not aspirational.** Every review pass across Stories 3.1–3.4 and 4.1/4.4 explicitly re-verified (via `git diff` + the sanctioned-import-set meta-test) that no subprocess/MCP import crept into the pure-function layer. Zero findings against this boundary across the whole build — a constraint that was checked, not just claimed.
- **Self-review before the test suite ran caught real bugs cheaply**, most visibly in Story 3.2: the first draft's `rank()` embedded `Finding` objects directly in sort tuples, which raises `TypeError` on any tie (no `__lt__`) — caught and fixed in self-review before any test observed the broken code, alongside an undeclared-`packaging`-dependency bug (mirroring `behind_upstream.py` too literally, discovered only by cross-checking `pyproject.toml`). Story 2.3 caught an analogous class of bug the same way: a first-draft `NameError` from a placeholder parser reference (`_MONITOR_PARSER_FOR_DISPATCH`) that never existed, caught by re-reading the draft against the actual parser return shape before running anything.
- **Speed-budget discipline (NFR-4) resisted a vacuous pass.** Story 1.5's first review pass caught that the 5-second benchmark could pass trivially if warden degraded to one instant sentinel Finding ("fast" and "broken-and-therefore-fast" indistinguishable) — fixed by asserting a minimum findings count, not just wall-clock.

## What was harder than expected

- **Hand-written AST guards needed repeated widening passes to close alias/import-surface bypasses.** This is the clearest systemic pattern in the whole build, recurring across at least three stories:
  - Story 1.2's "no-warden-reimplementation" guard was hardened across **three separate review passes on the same story**: pass 1 fixed `from pyforge import warden` and bare `os.system`/`os.popen`; pass 2 added relative-import resolution (`from .. import warden`) since `pyforge` is a namespace package and the package's own house style is relative imports; pass 3 found the guard was still module-granular where the spec's contract is symbol-granular (`from pyforge.warden.engines import subprocess as sp` laundered a forbidden name through the sanctioned module) and finally closed it with a positive allowlist (`_SANCTIONED_IMPORTS`) instead of an ever-growing denylist.
  - Story 1.4's env-hygiene AST scanner needed alias resolution for `import os as o` / `from os import environ` / `from os import *`, added only after an initial pass that hard-coded literal names `"os"`/`"environ"`/`"getenv"`.
  - Story 1.1's own NFR-1 read-only guard needed extending from the `Name`-form `open(...)` to the attribute-form `Path(...).open("w")` in its very first review pass.
  
  The lesson each individual patch drew ("mirrors the sibling idiom," "closes this bypass") was correct locally, but the pattern recurring three times independently suggests the fix belongs one level up: a shared alias/import-resolution helper for AST meta-tests, not a per-guard patch each time a new call shape is discovered.

- **Guard-polarity blindness in conditional analysis, found twice in the same story.** Story 1.4's credential-injection visitor applied a host-referencing `if`-guard to *both* branches of an `if`/`else` (missing the exact inverse-condition leak the check exists to catch) in its first review pass, then — after that was fixed — a second, independent review pass found the fix had only handled one polarity direction (`if host != safe: leak` was still silently suppressed, the TRUE-branch inverse of the first bug). Two independent adversarial passes each found a real, live false-negative in the same function, in complementary directions. This says the "guard applies to the wrong branch" bug class is genuinely easy to get half-right and needs deliberate polarity-both-directions test design from the start, not just adversarial review after the fact.

- **A "clean/OK finding gets treated as if it needs action" bug shipped independently in two layers of the same pipeline.** The Epic 2+3 batch adversarial pass (2026-08-07) found that `_partition_one` correctly classifies a clean (`DoctorStatus.OK`) Finding as `ACTIONABLE` (per Story 3.1's "every Finding lands somewhere" design), but **both** downstream consumers of that partition independently failed to special-case it: Story 3.2's `rank()` gave clean Findings a real 1-based rank/`rank_factors` as if they needed prioritizing, and Story 3.4's `_action_text` unconditionally rendered "address {check} ({source})" for them, discarding the finding's own `reason="clean — no remediation needed"`. Same root cause (partition semantics assume "actionable" means "needs action," but here it means "no further gate blocks it"), manifesting identically in two independently-written consuming modules. Neither story's own self-review pass caught it — it took a fresh, context-free adversarial pass across both files together to see the pattern.

## Corrections/refinements to carry forward

- **Epic 2's story-count doesn't match the epics.md narrative exactly** — Story 2.1 shipped alone via PR #290, then 2.2 and 2.3 shipped together with all of Epic 3 via PR #299 ("doctor: fix Epic 2+3 review findings"). This is a minor batching-of-merges pattern worth naming: stories don't always land 1:1 with PRs, and a retro reading PR titles alone would undercount Epic 2's real story completion (2.2/2.3 are real, reviewed, tested stories — just merged in the same PR as Epic 3's fixes).
- **Two "recover a deferred story" incidents, for different reasons.** Story 1.4 was recovered via a PR explicitly titled "deferred on review budget, not on merit" (#162) — a real signal that review-budget pressure can silently drop a completed story from the merge sequence if nothing catches it. Story 1.1 separately lost a full completed implementation to a worktree-rollback/token-budget-cap race (documented in its own Spec Change Log) and had to be re-derived from the intent-contract in a second pass. Both are process risks around the bmad-loop dev-auto pipeline, not story-content defects — worth flagging to Marshal/bmad-loop stewardship rather than Doctor's own skill files.
- **Doctor never got a per-epic retro during the build**, unlike Warden (which ran Epic 1 and Epic 3 retros mid-build). This whole-build retro is consequently thinner on "how did velocity/morale evolve epic to epic" than a series of per-epic retros would have been — the finding is entirely reconstructed from the Review Triage Logs and commit history, which is a faithful but narrower lens than a live per-epic retro would give.

## Lessons

1. **A pattern proven once (MCP-first/CLI-fallback, AD-6) is worth the up-front cost of designing it generically** — Doctor got three axes (staleness, cve+abandonment, adoption) out of one reviewed shape, with the third instance in Epic 4 needing essentially zero new review findings because it inherited a battle-tested pattern rather than re-deriving one.
2. **AST-based meta-test guards in this codebase have a recurring failure shape: they start literal/name-based and get bypassed by aliasing, relative imports, or symbol-level laundering until a positive allowlist replaces the denylist.** This happened independently in Story 1.1 (open-call detection), Story 1.2 (three full passes), and Story 1.4 (os-alias resolution). A shared, tested alias-resolution utility for future AST guards (in Doctor or any sibling package writing similar meta-tests) would likely prevent 2–3 of these from recurring per new guard.
3. **When one Finding-classification decision (e.g. "clean is technically actionable") has multiple downstream consumers, each consumer needs its own explicit test for the edge case — a correct decision at the classification layer does not imply correct handling everywhere it flows.** This bit Doctor once, in two places at once (3.2's ranking and 3.4's action text), and was only caught by a review pass spanning both files together rather than each story's own isolated self-review.
4. **Self-review immediately after drafting, before running any test, caught at least three real bugs cheaply** (Story 3.2's tie-comparison `TypeError` and undeclared `packaging` dependency; Story 2.3's placeholder-parser `NameError`) — cheaper than letting them surface as adversarial-review findings later, though adversarial review still found things self-review missed (the clean-finding bug, the guard-polarity residual, the false-correlation bug in Story 3.3).

## Action items

- **Extract a shared AST alias-resolution helper** (relative-import resolution + `import X as Y` / `from X import *` alias tracking) usable by any future `pyforge-doctor`/`pyforge-warden`-style meta-test guard, instead of re-deriving it per guard as happened three times in this build. `[new, open]`
- **When a partition/classification result has 2+ independent downstream consumers, require an explicit edge-case test per consumer for every non-obvious classification value** (e.g. "actionable but already clean") as a standing review checklist item for future Doctor/Warden-style pipelines. `[new, open]`
- **Run per-epic retros going forward, not just a closeout retro**, matching Warden's convention — this build's evidence base is exclusively Review Triage Logs and commit messages, which is workable but strictly narrower than a live per-epic retro would have captured (velocity trends, morale, mid-build course corrections).
- **File the guard-polarity-both-directions pattern as a standing review prompt** ("for any guard/conditional-suppression logic, prove both the TRUE-branch and FALSE-branch leak scenarios are covered, not just one") for any future credential/security-shaped AST scanner in this codebase, since it recurred within a single story here.
- **No CFE-skill retro triggered by this closeout.** Per the repo's Rule 2 (BMAD ↔ conda-forge-expert integration), a CFE-skill retrospective is required at the closeout of a BMAD effort that did conda-forge work. Doctor's scope is a pure Python CLI (`src/shared/packages/pyforge-doctor/`) with no recipe/`meta.yaml`/`recipe.yaml`/conda-forge-expert-skill touches anywhere in its 16 stories or its `pixi.toml` wiring — confirmed by re-reading the FR list, the AD list, and every story's Files-changed list above. Rule 2 does not apply to this closeout.
