- (capability) CAP-1 Authenticated Upload and WASI-Sandboxed Validation: a business user uploads an .xlsx via an OIDC-authenticated FastAPI endpoint, and structure/data-quality is checked inside a genuine WASI Preview 2 sandbox before any row reaches ingestion, with per-row failures reported precisely and valid rows queued independently of rejected ones; success = FR-1..4 - unauthenticated requests get HTTP 401 before the body is read, a structurally-invalid file is rejected in full (zero rows to Bronze), row-level failures name the specific column/rule without blocking passing rows, only validated rows reach dlt->DuckDB Bronze
- (capability) CAP-2 Bronze to Silver to Gold Transformation: dbt-duckdb transforms Bronze into schema-declared Silver and Gold models, emits column-level lineage for every model, and a failing dbt test blocks promotion of that model's output; success = FR-5..7 - every dbt run traces to the Bronze state it consumed, a lineage query for any Gold column returns its full upstream chain to Bronze, a dbt run with a failing test leaves the prior good table state queryable and does not update it
- (capability) CAP-3 End-to-End Observability and Provenance: one W3C trace ID minted once at the browser/API boundary correlates OTel spans and OpenLineage facets across every pipeline stage to Marquez via a per-pod Vector sidecar, so a single trace-ID lookup reconstructs the full upload-to-Gold journey with no gaps; success = FR-8..11 - the trace ID returned at upload time is the same one attached to the eventual Gold-table lineage record, a trace query returns spans for every stage with no gap, Marquez returns the full Bronze->Silver->Gold lineage graph, no container besides the Vector sidecar holds external telemetry egress
- (capability) CAP-4 Mechanically-Verified WASI Sandbox Isolation: an automated, non-hollow gate mechanically proves the WASI validation component cannot reach any capability beyond its WIT-declared surface, and a build-time check blocks denylisted imports from ever entering the component's dependency closure; success = FR-12,13 - the gate fails on any host interaction beyond declared WIT imports, deliberately widening capabilities without a matching WIT change makes the gate fail (proving it checks something), adding a denylisted import (numpy/pandas/pyarrow/pydantic/etc) fails pixi run build not a later runtime error
- (capability) CAP-5 One Toolchain - Local Dev, Digital Twin, Production OCP: one Pixi toolchain builds every artifact including the compiled WASI component, and the same security context runs identically under a Podman digital twin and OpenShift Restricted SCC, with DuckDB state persisted via a ReadWriteOnce PVC at a consistent mount path; success = FR-14..17 - a clean checkout + pixi install && pixi run build produces a runnable digital twin with no manual steps, every container starts as non-root UID 1001 with read-only rootfs in both environments, the Helm chart's securityContext matches Restricted SCC exactly with no anyuid exception, pipeline restarts do not lose Bronze/Silver/Gold data
- (constraint) Maturity verdict (load-bearing, from technical research): DuckDB's native engine has no WASI build and no WASI roadmap upstream, so dlt/dbt-duckdb/DuckDB itself cannot run in a genuine WASI component today - the WASI sandbox is scoped narrowly to the pure-Python upload-validation step only (AD-3); a future wasm32-wasi build target for ingestion/transform requires an ADR amendment citing new upstream evidence, not an incremental extension
- (constraint) AD-1: the validation component's WIT interface accepts/returns only primitive/record types (strings, numbers, booleans, lists, records) - never a host-shared-memory or buffer type (no Arrow buffers, no raw Excel bytes); Excel bytes are parsed into rows entirely outside the sandbox, in the FastAPI process, before the WIT call
- (constraint) AD-2: the FR-13 dependency denylist is enforced as a build gate, not a policy - pixi run build runs a static-import-scan against the validation component's source and resolved dependency closure, failing the build if numpy/pandas/pyarrow/pydantic or any other C-extension-backed or componentize-py-unproven package is imported directly or transitively
- (constraint) AD-4: the Isolation-Verification Gate must be non-hollow by construction - it ships from its first version with a meta-test that deliberately widens the component's declared WIT capabilities without a matching interface change and asserts the gate then FAILS; the gate runs on every build (resolves PRD OQ5/Q5 via PRD's own SM-2 success metric, cited verbatim - not deferred)
- (constraint) AD-5: exactly one trace-ID field, upload_trace_id, minted once at FastAPI ingress (or extracted from an inbound traceparent header) - always the bare 32-hex-character W3C trace-id, never the full traceparent string, never a UUID, never dashed; deliberately never conflated with OpenLineage's own separately-minted runId; no stage introduces a synonym field or re-encoded copy
- (constraint) AD-6: a single canonical securityContext definition (non-root UID 1001, readOnlyRootFilesystem true, no privilege escalation) is authored once under deploy/; both the Helm chart and the Podman compose file consume it via a generation step, neither hand-authors its own copy
- (constraint) AD-7: DuckDB is single-writer - each validated upload triggers exactly one dlt load followed by exactly one dbt run scoped to that load, 1:1 never batched, both steps invoked sequentially by the same owning process/Job (never two separately-scheduled triggers that could race); a move to concurrent/batched transforms is a scope change requiring an ADR amendment
- (constraint) AD-8: every build-time fetch (Pixi packages, DuckDB extensions, the componentize-py/Wasmtime toolchain) routes through the configured channel/mirror; no build script hardcodes a public URL, mirroring pyforge-atlas G1's vendored-extension pattern (air-gap-routable per the enterprise-airgap posture)
- (constraint) AD-9: POST /upload/excel is synchronous - it blocks through Excel parsing, the WASI validation call, and returns the full per-row validation result in the same HTTP response; the returned upload_trace_id is a correlation handle for observability/lineage lookups, NOT a polling handle - there is no V1 polling endpoint; a future file-size ceiling making synchronous blocking impractical is a scope change requiring an ADR amendment
- (constraint) AD-10: OIDC token validation happens at a sidecar/gateway boundary in front of apps/api/, never embedded per-request inside apps/api/ itself; apps/api/ trusts the identity the gateway attaches to the request and does not itself speak to the OIDC provider or validate JWKS
- (non-goal) A general-purpose Wasm-sandboxing framework for arbitrary third-party logic - the WASI component boundary in v1 is scoped exclusively to the Excel-upload validation step
- (non-goal) Running dlt, dbt, or DuckDB itself inside a WASI Preview 2 sandbox - blocked at the DuckDB-dependency level per the technical research, not a scoping choice to revisit without new upstream evidence
- (non-goal) Apache Arrow buffers as the host-to-WASI-component interchange format - deferred pending a confirmed pyarrow-in-WASI path or an Arrow-maintained WASM/WASI interchange primitive
- (non-goal) A browser-side query/dashboard surface onto Gold tables - v2, would reuse the pyforge-atlas G1 DuckDB-WASM/Pyodide pattern directly rather than reinvent it; explicitly out of this v1
