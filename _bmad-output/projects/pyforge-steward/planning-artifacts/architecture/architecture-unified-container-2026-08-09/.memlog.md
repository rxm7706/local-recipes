- (constraint) BROWNFIELD, verified in the shipped Containerfile rather than assumed: the checkout is BAKED (COPY . /pyforge in the builder, then COPY --from=builder /pyforge /pyforge into the runtime stage); /pyforge is a literal, deliberately SHORT root, not a build ARG, because a long root panics pixi-build-python at the bmad-loop worktree path-length limit; mutable state is declared via VOLUME for /pyforge/.steward, /pyforge/.claude/data/conda-forge-expert and /root/.bmad-loops; and Story 7.5 runs container-gates cli-smoke over all eight station CLIs at BUILD time so a missing or slow CLI fails the build, not a later run.
- (constraint) THE MECHANISM everything else follows from: pixi.toml composes pyforge-container from the eight pyforge-* features BY NAME with no-default-feature=true -- not by copied pins. The image therefore tracks each station deps automatically, and equally: any base dependency added to ANY station lands in the whole-Guild image with no story written and no review of that consequence. A per-station dependency decision is an image-wide decision.
- (decision) AD-1 (operator-decided 2026-08-09): the secure-live-dashboards ASGI stack -- django, channels, daphne, asgiref, and channels_redis -- ships as an OPTIONAL EXTRA, pyforge-steward[dashboard], never as a base dependency of pyforge-steward. The argument is correctness before size: Steward CLI is {keys, deploy, provision, budget} and deploy is a git reconcile-and-push; nothing in that surface imports django or daphne. Per the dashboard architecture AD-1 the library runs IN THE ADOPTER process, so the ASGI stack is a dependency of the library as an adopter consumes it, not of the station. Declaring it as a base dep would assert a runtime dependency the station never imports. Size confirms rather than drives it: daphne alone pulls twisted, autobahn, pyopenssl, service_identity and idna. Rejected: base dependency in pyforge-steward, which via composition-by-name would put Twisted in the lean whole-Guild image. Rejected: solving this by splitting the image into tiers, which answers a dependency-placement question with a packaging change.
- (decision) AD-2: ONE lean image stands. The two-tier split (pyforge-container plus a pyforge-factory-full carrying local-recipes/CFE) is DEFERRED, not rejected, with a named trigger: when recipe builds need to run INSIDE the container. Recorded honestly -- the tiering proposal was never driven by the dashboard; its real driver is the conda build toolchain and mason 373-file CFE surface, which is a separate question with its own demand signal and no adopter asking today. Deciding it now would pull mason into a decision nothing forces. Rejected: splitting tiers pre-emptively.
- (decision) AD-3: an optional extra that nobody exercises rots, so the extra is installed by default in the in-repo dev env and NEVER in the container. This is the atlas->warden precedent already in the tree: gate = [pyforge-warden] under project.optional-dependencies, "installed by default in the in-repo pyforge-atlas pixi env; external installs may omit it". Rejected: declaring the extra and leaving it uninstalled everywhere, which produces an untested code path that fails first for an adopter.
- (decision) AD-4: for the extra to be legal, the dashboard imports may NOT be unconditional at module level. dashboard architecture AD-13 deliberately keeps the module at pyforge.steward.dashboard INSIDE the pyforge-steward distribution, so an unconditional top-level import of django would make tests/packaging/test_dependency_completeness demand django in project.dependencies -- and it would be right to. The repo own test states the remedy: move the import behind a guard or into the function that needs it, and declare it as an extra. Rejected: relaxing the completeness test, which is the check that caught the bs4 gap hours ago.
- (decision) AD-5 (Q2, ratifying shipped reality): the BAKED checkout is the primary mode; a bind-mount over /pyforge is the development override. This is not a fresh choice -- the shipped Containerfile already bakes it, and A3.6 recommended exactly this. The invariant worth fixing is not baked-vs-mounted but that /pyforge stays a literal SHORT root either way: a long root panics pixi-build-python at the bmad-loop worktree path-length limit, which is why it is not a build ARG. Rejected: making the root configurable, which reintroduces the exact failure the literal was chosen to prevent.
- (decision) AD-6 (Q3/Q4): Mode I is deferred and Mode L must not foreclose it. Two things already point the way and are ratified rather than re-decided: /root/.bmad-loops is ALREADY a declared VOLUME, so an in-container loop runner would get its worktrees on a volume rather than the image filesystem; and Mode L continues to run loops against a mounted host checkout exactly as today. What WOULD foreclose Mode I, and is therefore forbidden: baking any station state into an image layer instead of a volume, and any assumption that the container is single-tenant or short-lived. Rejected: designing Mode I now, which its own Spec puts out of scope.
- (assumption) THE ASSUMPTION THAT WOULD OVERTURN AD-1: that adopters host their own dashboards and Steward only SCAFFOLDS. dashboard AD-1 and CAP-6 both read scaffold-not-serve -- steward deploy generates the ASGI runtime and edge, the adopter runs it. If Steward is ever meant to SERVE dashboards itself, one Steward-run ASGI process hosting the Guild boards, then the ASGI stack IS a station runtime dependency, AD-1 collapses, and the lean image is simply heavier than advertised. Written down so the reversal is cheap to spot rather than discovered late.
- (event) spine finalized: 6 ADs plus one recorded open assumption; Mode L ratified, Mode I and the second tier deferred with named triggers
