- (direction) Operator decision 2026-08-09 on Q3: support BOTH modes; DEFAULT is the zero-infrastructure path (no database, no hosted infra) with batch latency accepted; Mode B is the ADVANCED, opt-in, configurable option.
- (decision) LABEL MISMATCH RESOLVED. The intake doc's Mode A is 'real-time, zero-hosting-cost, serverless' (GitHub Actions + Jira Automations, webhook-triggered); Mode B is 'scheduled batch' but requires dlt + PostgreSQL. So 'batch cadence AND no database' is NEITHER mode as written. Resolved by decoupling TRIGGER from TRANSPORT: the default runs Mode A's mechanism under 'on: schedule' instead of 'on: project_v2_item'. Yields batch cadence at zero infrastructure and drops every webhook edge case (delivery retries, replay, ordering). Rejected: adopting Mode B as the default to get batch cadence — it buys the cadence with a PostgreSQL instance the operator explicitly excluded.
- (decision) Q2 RESOLVED — GitHub Projects V2 is the authoritative side on a simultaneous conflicting edit, per-field overridable. Rejected: last-writer-wins by timestamp — it makes correctness depend on comparing clocks across two vendors' APIs, which neither guarantees, and Jira Automation vs GitHub webhook timestamps are not commensurable. Determinism beats usually-right. GitHub wins by default because that is where the work happens and where this repo's build line already reads.
- (constraint) The TIME-based loop guard (item updated_at vs the engine's own last_sync_timestamp) is retained as the ZERO-LOOP mechanism (CAP-2) and is orthogonal to Q2's conflict authority. The intake doc argues it generalizes better than Mode A's bot-identity guard because it works by time, not identity, and a scheduled run has no per-update initiator to inspect. Identity-guard is additive, never the primary.
- (decision) Q4 RESOLVED — Mode B ships the NORMALIZED EAV schema plus the three-table control plane (sync_entity_mapping, sync_field_mapping, sync_value_translation). Rejected: the flat single-table shape. Its only advantage is a simpler diff view, and that advantage now belongs to the default zero-infrastructure path; a flat table cannot express per-field sync direction or value translation, which are precisely the capabilities that justify paying for Mode B's infrastructure at all. If you only need the flat view you should not be on Mode B.
- (decision) CENTRAL INVARIANT: ONE logical control-plane contract, TWO physical materializations. Both modes need the same three things — entity link, field mapping, value translation. The default materializes them IN THE TWO SYNCED SYSTEMS (GitHub custom field + Jira field); Mode B materializes them as the three control-plane tables. Same contract, so a board synced by the default and later migrated to Mode B needs no re-linking. This is what stops the two modes diverging into two products.
- (constraint) KNOWN VENDOR DEFECT, carried forward from the intake doc and binding on BOTH modes: GitHub's updateProjectV2ItemFieldValue updates the underlying data store but can fail to update the board view's grouping index, so a card moves logically while appearing stuck until a human drags it. Data is correct; display may lag. Implementers must budget for it as an accepted UX quirk and re-verify against GitHub's issue tracker at implementation time rather than assuming it still reproduces.
- (constraint) No third-party sync SaaS (Unito, Exalate). Two due-diligence findings are settled and not to be re-litigated: Steampipe rejected as the WRITE path (plugins read-only; possibly still useful read-side), Octosync rejected (unmaintained ~5 years, auth-incompatibility risk).

- (decision) AD-9 ADDED — webhook delivery is at-least-once and unordered, so the reversal reintroduces the three edge cases the schedule trigger had removed. Recording them as an invariant rather than leaving them to each story: a redelivered payload must be a no-op (CAP-3 already requires this and the reconciler paradigm still supplies it), an out-of-order arrival must not overwrite a newer state, and a dropped delivery must be recoverable. Rejected: leaving these to per-story defensive code — three stories would each invent a different answer, which is precisely the divergence an AD exists to prevent.
- (decision) PARADIGM AMENDED, not replaced: 'scheduled reconciliation' becomes 'EVENT-TRIGGERED reconciliation'. The reconciler is retained deliberately. A straight event-propagation pipeline (read payload -> transform -> write) would make idempotence (CAP-3) a defended property requiring payload dedupe; a reconciler that reads current state for the affected item and converges it is idempotent BY CONSTRUCTION, and re-reading is what makes an out-of-order or redelivered webhook harmless. Rejected: pure event propagation per the intake doc's Flow A1/A2 sketch — it is simpler per-event but pays for it with dedupe state, which AD-2 forbids storing anywhere.
- (constraint) AD-5 AMENDED: the time-based loop guard REMAINS primary. With webhooks an initiator IS present, so Mode A's identity guard (github-actions[bot]) becomes available and MAY be used as a cheap fast-path short-circuit — but not as the primary, because it does not survive a trigger change to schedule and does not exist in Mode B at all. Keeping time-based primary is what keeps one loop-guard contract across both triggers and both transports.

- (constraint) FACT VERIFIED AGAINST GITHUB DOCS 2026-08-09, surfaced by steward 8-1 dev session as an intent_gap: there is NO project_v2_item or projects_v2_item event usable in a GitHub Actions on: block. The projects_v2_item WEBHOOK is real but is deliverable only to an EXTERNAL receiver -- a GitHub App with org-level Projects read access, or an org/repo webhook endpoint -- which must then call repository_dispatch to reach a workflow file. repository_dispatch is a valid trigger and is the documented bridge for activity that happens outside GitHub. The Stack table line "GitHub Actions (on: project_v2_item webhook)" was therefore factually impossible as written.
- (decision) AD-1 AMENDED AGAIN (id stable, operator decision 2026-08-09 after the intent_gap): default trigger returns to SCHEDULE, with the webhook receiver as an OPT-IN advanced path. The reversal to webhook-by-default was made on the belief that webhooks were merely unearned complexity at zero infra; that belief was false -- true webhook Mode A CANNOT be zero-infrastructure, because GitHub cannot trigger a workflow from a Projects V2 event at all. Making webhook the default would therefore force every adopter to stand up and credential an external receiver. Schedule-by-default keeps the zero-infrastructure floor the operator wanted; trigger=webhook remains fully expressible for anyone who will run a receiver. The trigger/transport decoupling is untouched and is exactly what makes this a one-value change rather than a redesign. Rejected: keeping webhook default and mandating a receiver; rejected: deleting the webhook path, which would discard the near-real-time capability the operator explicitly asked for.

- (constraint) DEFECT ESTABLISHED BY TRACE, not by review opinion (steward 8-1 passes 2/5/6, cold-context Blind Hunter re-confirmed): AD-5's rule is structurally unimplementable under AD-2. The sync point is stored as a FIELD ON THE ITEM (AD-2), and writing that field advances the SAME item's aggregate updated_at past the value just recorded. Every reconcile after the first therefore reads updated_at > sync_point, misroutes into the 'both sides changed' branch, and lets AD-4's GitHub-wins default clobber genuine Jira-only edits. A 30s SYNC_POINT_GRACE forward tolerance was tried and does not hold: updated_at and sync_point are static server-recorded values that do not advance with wall-clock, so the offset is permanent, not a window. No grace value fixes it.
- (note) ROOT CAUSE, stated generally so it is not re-invented elsewhere: a change detector must not store its marker inside the object it observes. An item's aggregate updated_at cannot, for any tolerance, distinguish the engine's own bookkeeping write from a coincidental genuine edit in the same window, because both are simply 'a write to this item'. The mechanism is self-interfering by construction.
- (decision) AD-5 AMENDED IN PLACE (id stable, third amendment): the zero-loop guard becomes a LAST-SYNCED-VALUE comparison against a shared baseline -- resolution R2 of the three the 8-1 session named. 'Did this side change?' is answered by current_value != baseline_value, never by a timestamp. Self-interference is eliminated by construction rather than tolerated: writing the bookkeeping field does not change the STATUS value, so the signal the guard reads is untouched by the write that broke the old one. Adopted also because it makes the guard a three-way merge against a shared base, which is the first mechanism in this design that can genuinely DETECT a simultaneous conflicting edit -- the precondition AD-4 was always written against ('when both sides diverge').
- (decision) REJECTED R3 (accept a bounded data-loss window with operator telemetry distinguishing converged from may-be-pending). Two independent grounds. (1) It contradicts the Spec's own Constraints, which name CAP-2 and CAP-3 non-negotiable NFRs whose Success signal requires the operator to PROVE zero-loop on demand; a documented loss window cannot be proven away. (2) The premise is false anyway -- pass 6 established the misclassification is PERMANENT, not windowed, so there is no bounded window to document. R3 would have to be re-derived before it could even be honestly written down.
- (decision) R1 (per-field rather than per-item change signal) is NOT rejected but is DEMOTED to an optional fast-path, never load-bearing -- the same shape AD-5 already gives the bot-identity guard. R1 and R2 are not peers: R1 makes the change SIGNAL more precise, R2 changes what the signal IS, and R2 subsumes the failure R1 would work around. Demoting it also keeps the correctness path free of an unverified vendor claim: R1 depends on per-field updatedAt being exposed by GitHub's ProjectV2ItemFieldValue types and reconstructable from Jira's paginated changelog -- genuinely asymmetric, and unverified here. A value comparison depends only on values, which every API returns.
- (decision) TIMESTAMPS ARE RETAINED FOR CANDIDATE SELECTION ONLY, never for the decision. Under trigger=schedule the engine still needs to know WHICH items to reconcile without reading every baseline on a large board; item updated_at is fit for that and unfit for nothing else. The asymmetry is what makes it safe: a false positive candidate costs one wasted read and converges to a no-op, a false negative silently drops a change -- so the filter must be deliberately over-inclusive. Recording the split explicitly because 'we kept updated_at' would otherwise read as a partial reversal.
- (decision) AD-10 ADDED -- the baseline's storage contract and lifecycle, because five stories would each invent it. It materializes through AD-3's existing two-materialization split (no new store, so AD-2 is untouched): serverless writes one bookkeeping field per side holding a per-field value map, Mode B adds a column to sync_entity_mapping. Three lifecycle rules stories must not each answer: absent baseline is a FIRST LINK, not a loop candidate; the map must distinguish 'field cleared' from 'field never synced' via an explicit null sentinel, since a missing key and a null value mean opposite things; and exceeding the vendor field-size ceiling is AD-2's documented escape hatch to Mode B, not a reason to invent a sidecar store.
- (note) TERMINOLOGY ALIGNMENT ONLY, not a decision reversal: 'last sync point' becomes 'baseline' in the Paradigm prose, the Paradigm diagram, and AD-4's rule text. AD-4's authority rule is UNCHANGED -- GitHub wins, per-field overridable, resolution a pure function of (github_value, jira_value, field_mapping).
