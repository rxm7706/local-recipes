- (direction) Operator decision 2026-08-09: LIBRARY + SUBCOMMAND SPLIT. Verification ownership (Steward vs Doctor) explicitly delegated to this architecture run.
- (decision) AD-1 DELIVERY SPLIT ON THE PROCESS BOUNDARY. What runs inside the adopter's process per HTTP request — role extraction, RLS filtering, audit write, conditional navigation — is a LIBRARY (pyforge.steward.dashboard). What stands the deployment up and inspects it — container stack, edge policy, WSGI topology, security CI, wiring verification — is a STEWARD SUBCOMMAND under the existing verb. Rejected: a template repository. It has NO upgrade path (a diverged adopter never receives a fix, and the Spec's own open question names that as the case that matters), and it duplicates the genesis-installer role already consolidated into pyforge-marshal. Rejected: subcommand-only — a subprocess cannot filter a dataframe mid-request. Rejected: library-only — a library cannot provision Nginx.
- (decision) AD-2 THE LIBRARY PROVIDES, THE SUBCOMMAND VERIFIES — resolving the Spec's provide-vs-verify question as BOTH, split by half. The library provides so isolation is never reimplemented per dashboard; the subcommand verifies so an adopter that diverged is still caught. Rejected: provide-only (a diverged adopter is invisible) and verify-only (every adopter reimplements the pipeline, which is the wall this pattern exists to remove).
- (decision) AD-3 VERIFICATION IS STEWARD'S, with one carve-out to Doctor. Charter §6 bars a station being the final word on ITS OWN artifact; an adopter's dashboard is the ADOPTER's artifact, not Steward's, so verifying an adopter's wiring is not self-grading. Coupling decides the rest: verification is inseparable from deployment ( already exists and already means dashboard build/reconcile/status), and routing it through Doctor would put a cross-station dependency in every adopter's deploy path, so a Doctor problem would block a deployment. Doctor is also a repo-rooted diagnostic for THIS factory; making it a runtime dependency of external deployments inverts its role. CARVE-OUT: a verdict on whether STEWARD'S OWN pattern implementation is sound — as opposed to an adopter's wiring — is Doctor's under Charter §6, because that IS Steward grading itself. Rejected: routing all verification to Doctor. Technically possible (Doctor's sources take target: Path, so an external directory is reachable) but it buys Charter purity at the cost of coupling every adopter's deploy to a second station.
- (decision) AD-4 THE TRUST BOUNDARY IS DECLARED, NOT ASSUMED. The pattern consumes proxy-set identity headers and cannot itself distinguish a forged header from a real one. Rather than pretend otherwise, an adopter must DECLARE the trusted ingress (the address or interface the proxy connects from), and the library refuses to start when identity headers arrive from outside it. Rejected: silently trusting any header, which is the blueprint's behaviour and leaves the strongest guarantee resting on an undocumented network assumption. Rejected: mTLS or a shared secret as the v1 requirement — correct but raises the adoption floor beyond a pattern's remit; recorded as the upgrade path.
- (decision) AD-5 THE CACHE BACKEND IS PLUGGABLE, THE SHARING PROPERTY IS NOT. Redis is not mandated; a cache that cannot be shared across worker processes IS refused. The blueprint's own sample contradicts its Compose stack here — FileSystemCache under Gunicorn --workers 4 does not deliver the shared-cache guarantee Redis is provisioned to provide. Single-worker adopters may use an in-process cache. Rejected: mandating Redis (raises the floor for a small adopter) and accepting any cache (silently breaks the one-fetch-per-refresh property under concurrency).
- (decision) AD-6 FILTER THEN SEARCH, ENFORCED BY SIGNATURE not by discipline. Search operates on the already-role-filtered frame; the library exposes no entry point that can search the master set. The Spec's open question asks what ENFORCES the order — the answer is that the unfiltered frame is never passed to a searchable surface. Rejected: documenting the order and trusting adopters, which is exactly how the leak happens.
- (decision) AD-7 AUDIT RETENTION IS THE ADOPTER'S DECLARED POLICY, and the pattern refuses to default it. The trail accumulates per-user activity and is both a compliance asset and a privacy liability; a default retention would silently make that choice for an organisation with legal obligations the pattern cannot know. An adopter declares a retention period and the pattern enforces it. Rejected: an unbounded default (silently accumulates personal data forever) and a fixed default (imposes one jurisdiction's answer on all).
- (constraint) Secrets resolve through Steward's existing keys surface. No literal key and no default-key fallback may appear in pattern code or in adopter scaffolding — scripts/container-gates' secrets-scan already refuses this class and the blueprint's sample violates it.
- (constraint) Every isolation test must fail when its guard is removed, demonstrated rather than claimed. The blueprint's supplied test_admin_sidebar_visibility mocks a Viewer and asserts one page, so it would pass against an implementation that always restricts — a vacuous test is treated as a defect, not as coverage.
