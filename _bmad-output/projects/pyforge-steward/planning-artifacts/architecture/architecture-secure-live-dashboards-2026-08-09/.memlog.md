- (direction) Operator decision 2026-08-09: LIBRARY + SUBCOMMAND SPLIT. Verification ownership (Steward vs Doctor) explicitly delegated to this architecture run.
- (decision) AD-1 DELIVERY SPLIT ON THE PROCESS BOUNDARY. What runs inside the adopter's process per HTTP request — role extraction, RLS filtering, audit write, conditional navigation — is a LIBRARY (pyforge.steward.dashboard). What stands the deployment up and inspects it — container stack, edge policy, WSGI topology, security CI, wiring verification — is a STEWARD SUBCOMMAND under the existing verb. Rejected: a template repository. It has NO upgrade path (a diverged adopter never receives a fix, and the Spec's own open question names that as the case that matters), and it duplicates the genesis-installer role already consolidated into pyforge-marshal. Rejected: subcommand-only — a subprocess cannot filter a dataframe mid-request. Rejected: library-only — a library cannot provision Nginx.
- (decision) AD-2 THE LIBRARY PROVIDES, THE SUBCOMMAND VERIFIES — resolving the Spec's provide-vs-verify question as BOTH, split by half. The library provides so isolation is never reimplemented per dashboard; the subcommand verifies so an adopter that diverged is still caught. Rejected: provide-only (a diverged adopter is invisible) and verify-only (every adopter reimplements the pipeline, which is the wall this pattern exists to remove).
- (decision) AD-3 VERIFICATION IS STEWARD'S, with one carve-out to Doctor. Charter §6 bars a station being the final word on ITS OWN artifact; an adopter's dashboard is the ADOPTER's artifact, not Steward's, so verifying an adopter's wiring is not self-grading. Coupling decides the rest: verification is inseparable from deployment ( already exists and already means dashboard build/reconcile/status), and routing it through Doctor would put a cross-station dependency in every adopter's deploy path, so a Doctor problem would block a deployment. Doctor is also a repo-rooted diagnostic for THIS factory; making it a runtime dependency of external deployments inverts its role. CARVE-OUT: a verdict on whether STEWARD'S OWN pattern implementation is sound — as opposed to an adopter's wiring — is Doctor's under Charter §6, because that IS Steward grading itself. Rejected: routing all verification to Doctor. Technically possible (Doctor's sources take target: Path, so an external directory is reachable) but it buys Charter purity at the cost of coupling every adopter's deploy to a second station.
- (decision) AD-4 THE TRUST BOUNDARY IS DECLARED, NOT ASSUMED. The pattern consumes proxy-set identity headers and cannot itself distinguish a forged header from a real one. Rather than pretend otherwise, an adopter must DECLARE the trusted ingress (the address or interface the proxy connects from), and the library refuses to start when identity headers arrive from outside it. Rejected: silently trusting any header, which is the blueprint's behaviour and leaves the strongest guarantee resting on an undocumented network assumption. Rejected: mTLS or a shared secret as the v1 requirement — correct but raises the adoption floor beyond a pattern's remit; recorded as the upgrade path.
- (decision) AD-5 THE CACHE BACKEND IS PLUGGABLE, THE SHARING PROPERTY IS NOT. Redis is not mandated; a cache that cannot be shared across worker processes IS refused. The blueprint's own sample contradicts its Compose stack here — FileSystemCache under Gunicorn --workers 4 does not deliver the shared-cache guarantee Redis is provisioned to provide. Single-worker adopters may use an in-process cache. Rejected: mandating Redis (raises the floor for a small adopter) and accepting any cache (silently breaks the one-fetch-per-refresh property under concurrency).
- (decision) AD-6 FILTER THEN SEARCH, ENFORCED BY SIGNATURE not by discipline. Search operates on the already-role-filtered frame; the library exposes no entry point that can search the master set. The Spec's open question asks what ENFORCES the order — the answer is that the unfiltered frame is never passed to a searchable surface. Rejected: documenting the order and trusting adopters, which is exactly how the leak happens.
- (decision) AD-7 AUDIT RETENTION IS THE ADOPTER'S DECLARED POLICY, and the pattern refuses to default it. The trail accumulates per-user activity and is both a compliance asset and a privacy liability; a default retention would silently make that choice for an organisation with legal obligations the pattern cannot know. An adopter declares a retention period and the pattern enforces it. Rejected: an unbounded default (silently accumulates personal data forever) and a fixed default (imposes one jurisdiction's answer on all).
- (constraint) Secrets resolve through Steward's existing keys surface. No literal key and no default-key fallback may appear in pattern code or in adopter scaffolding — scripts/container-gates' secrets-scan already refuses this class and the blueprint's sample violates it.
- (constraint) Every isolation test must fail when its guard is removed, demonstrated rather than claimed. The blueprint's supplied test_admin_sidebar_visibility mocks a Viewer and asserts one page, so it would pass against an implementation that always restricts — a vacuous test is treated as a defect, not as coverage.

- (decision) AD-7 extended at the reviewer pass: the Spec asked for retention AND access policy; retention alone dropped half the question. The audit trail is itself role-isolated data and reading it is a recorded act -- otherwise the record of who-saw-what is the one dataset nobody's access to is governed.
- (decision) AD-8: the pattern binds at the WSGI/request layer, NOT to a dashboard framework. Forced by herald adoption -- herald is a stateless CLI plus a STATIC web dashboard, and its live-backend Spec explicitly refuses to commit a framework (Flask/FastAPI illustrative, not committed). A Vizro-bound pattern could not serve its own second adopter. Vizro demoted from Stack requirement to first-adopter choice. Rejected: keeping Vizro binding and telling herald to adopt Vizro -- that reshapes an adopter application to fit the pattern, inverting who serves whom.
- (decision) AD-9: machine callers authenticate by PROOF, not by ingress -- a carve-out to AD-4. Forced by herald LB-2: a CI webhook receiver is an inbound caller that is not a proxied human, so AD-4 as written (refuse identity headers from outside the declared ingress) would refuse every legitimate CI call. A machine caller presents a verifiable signature (HMAC) and is never granted a human role. Rejected: whitelisting CI source addresses at the ingress -- it re-treats the network path as the credential for a caller that CAN carry one, and CI egress addresses are neither stable nor narrow.
- (note) Both AD-8 and AD-9 were surfaced by naming a SECOND adopter, which is precisely the Spec success signal ("a second dashboard -- one that did not exist when the pattern was written"). Neither was visible while atlas was the only adopter, because atlas is Vizro and has no machine callers.
- (decision) AD-10: static export and role isolation are MUTUALLY EXCLUSIVE delivery modes; a dashboard that declares role isolation may not be delivered by static export. Operator supplied a Vizro-to-GitHub-Pages static workaround spec (export Plotly components with fig.to_html, inject into a grid template, optional client-side filtering via Plotly.react). Its own section 5.1 embeds the data for ALL possible states into the client JS layer -- so every role rows ship to every browser and the filter is presentation, which the Spec constraint already forbids as access control. The two modes are a legitimate CHOICE per dashboard, not a spectrum: public+unrestricted+zero-infra, or role-isolated+hosted. Rejected: treating static export as a cheap deployment option for the same dashboard -- it silently removes the guarantee CAP-2 exists to make.
- (note) Consequence for the named adopters: marshal wants an ALTERNATE live board precisely because its static GitHub Pages board cannot be secured in place. herald already ships a static-JSON-snapshot payload (claims.py Story 9.4), so its Moments data is client-visible today -- fine while that data is not role-sensitive, and a thing to check before any role vocabulary is declared for it.
- (direction) OPERATOR CONSTRAINT (2026-08-09, supersedes part of AD-8): the primary backend is a DJANGO service with Channels, on ASGI. The dashboard must be PLUGGABLE INTO Django. This makes AD-8 rule as first written (binds at the WSGI/request layer) wrong -- WSGI is the sync protocol, Django+Channels is ASGI -- and makes the blueprint Gunicorn gthread worker topology the wrong default.
- (decision) AD-8 AMENDED IN PLACE (id stable): the pattern binds at the ASGI application boundary and is mountable inside a Django project as a Django application, not at the WSGI layer and not to a dashboard framework. A WSGI-native dashboard (Vizro/Dash/Flask) is mounted through a WSGI-to-ASGI adapter rather than forcing the host to be WSGI. The original AD-8 reason survives untouched -- no adopter may be asked to change dashboard frameworks -- only its protocol layer moves. Rejected: keeping WSGI and running Django behind it, which would forfeit Channels entirely.
- (decision) AD-11: the identity SOURCE is pluggable; the no-authentication rule is not. The pattern consumes an established identity and still authenticates nobody, but the source is now either a trusted-ingress proxy header (AD-4) OR the host framework authenticated user -- with Django request.user plus its groups a first-class source, since a Django host already owns auth, sessions and permissions. The declared-not-assumed discipline of AD-4 applies per source. Rejected: proxy headers as the only source, which would ask a Django estate to bypass its own auth layer and re-establish identity at the edge; also rejected: the pattern owning authentication, which remains a Non-goal.
- (decision) AD-12: isolation and audit are per-MESSAGE on a persistent connection, not only per-request. Channels means a WebSocket lives across many messages, so a role captured once at connect would outlive a revocation for the life of the socket. The role is re-resolved per message, each message that returns data is audited with its row count like any request, and a connection whose identity can no longer be resolved is closed rather than served. Rejected: resolving the role once at connect handshake -- simpler and the standard shortcut, but it makes the socket a stale-privilege cache.
- (version) Verified on the web 2026-08-09: Django 6.0 reusable-app packaging (docs.djangoproject.com/en/6.0/intro/reusable-apps/). Load-bearing requirements taken from it -- AppConfig must name the module and set an explicit label; application labels MUST be unique in INSTALLED_APPS and must avoid contrib labels (auth, admin, messages); default_auto_field must be set on AppConfig so the reusable app migrations are not affected by the adopter DEFAULT_AUTO_FIELD; templates and static live namespaced under templates/<label>/ and static/<label>/; the URLconf is exposed for include() rather than wired to project routes.
- (decision) AD-13: the library half ships as a REUSABLE DJANGO APP, by Django own convention, and the adopter enables it through INSTALLED_APPS plus an include() of its URLconf. Concretely binding: an explicit AppConfig label that is unique and never collides with a contrib label; default_auto_field set on that AppConfig, which is load-bearing because this app ships an audit-trail MODEL WITH MIGRATIONS into someone else project and would otherwise mutate under the adopter DEFAULT_AUTO_FIELD; templates and static namespaced under the label. Deviation recorded: we do NOT take the django- / django_ name prefix, because the distribution is pyforge-steward and not a standalone Django package -- the prefix is a recommendation for identifying standalone Django distributions on PyPI, and the module stays pyforge.steward.dashboard. Rejected: a settings-configured middleware-only integration with no AppConfig -- it cannot ship models or migrations, which the audit trail requires.
- (version) Verified on the web 2026-08-09 (channels.readthedocs.io/en/latest): Channels extends Django past HTTP over ASGI; consumers receive a scope plus events and may be sync or async; ProtocolTypeRouter/URLRouter/ChannelNameRouter do routing; CHANNEL LAYERS carry cross-process messaging and groups, with channels_redis the backend for multi-process deployments; AuthMiddlewareStack populates scope["user"] for WebSocket connections; direct DB access from an async consumer requires database_sync_to_async wrapping.
- (decision) AD-11 SHARPENED (id stable): the identity source is protocol-specific, not one accessor. Over HTTP inside Django it is request.user plus groups; over a Channels WebSocket it is scope["user"], populated by AuthMiddlewareStack -- an adopter that wires AuthMiddlewareStack for HTTP only gets an anonymous scope on the socket and would silently serve unfiltered or empty data. The pattern reads the protocol-correct accessor and refuses a connection whose identity cannot be resolved.
- (decision) AD-5 GENERALIZED (id stable, rule amended): the sharing property now governs ALL cross-worker shared state, not the response cache alone. Channels adds a second piece -- the CHANNEL LAYER -- with the identical failure mode: the in-memory layer is single-process, so under more than one worker a group broadcast reaches only the workers holding those sockets and the dashboard silently updates for some viewers and not others. Any cross-worker state (response cache AND channel layer) must be genuinely shareable when workers > 1; channels_redis is the sanctioned layer backend there, still not mandated for a single-worker adopter.
- (constraint) ORM access from an async consumer goes through database_sync_to_async. Load-bearing here specifically because the audit write is a Django model write on the hot path of every data-returning message (AD-12): an unwrapped ORM call from an async consumer blocks the event loop, so the correctness rule and the performance rule are the same rule. A sync consumer needs no wrapping.
- (version) STACK NAMED BY OPERATOR 2026-08-09, all four verified available to this conda/pixi estate: channels (Django integration layer) and channels_redis (optional Redis channel-layer backend) and django already have LOCAL recipes in recipes/; daphne (conda-forge/daphne-feedstock, meta.yaml v0, BSD-3, noarch, pins asgiref >=3.5.2,<4) and asgiref (conda-forge/asgiref-feedstock, recipe.yaml v1, 3.11.1, BSD-3, noarch) exist upstream and are CONSUMED, needing no new recipe. Daphne is the HTTP and WebSocket TERMINATION server, which settles the earlier generic "an ASGI server" seed. asgiref is not merely transitive: it supplies the WSGI-to-ASGI adapter AD-8 requires and the sync/async bridge behind database_sync_to_async.
- (assumption) VERSION CAVEAT: AD-13 reusable-app rules were verified against the Django 6.0 doc the operator supplied, while this estate library catalog pins django 5.2 LTS (with channels 4.x, daphne 4.x). The reusable-app mechanics AD-13 binds -- explicit AppConfig label, default_auto_field, namespaced templates/static, include() URLconf -- are stable across 5.2 and 6.0, so the rules hold; bind to the estate 5.2 LTS pin and re-check only if the estate moves to 6.x.
- (decision) AD-14: SQLite for development and test, PostgreSQL for deployment, selected by connection configuration alone -- one Django DATABASES setting, two engines, never two code paths. This is the existing one-schema-across-environments constraint bound to a concrete pair. The NON-OBVIOUS consequence, and the reason this is an AD rather than a stack row: SQLite does not exhibit the concurrent-write contention production will, and AD-12 puts an audit write on the hot path of every data-returning message across many simultaneous sockets -- so the highest-contention path in the system is the one development exercises least. Contention behaviour is therefore proven against PostgreSQL in CI, not inferred from a green SQLite run. Rejected: PostgreSQL everywhere including dev, which raises the local floor the Spec deliberately keeps low; rejected: trusting the SQLite run, which is how a boundary holds in dev and fails in production.
