- (change) RECONCILES src/shared/packages/pyforge-steward/src/pyforge/steward/provision.py (2026-08-09, Story 6.1). CAP-1 delivered for its first backend: `_SUPPORTED_MODULES = {"bmb": ...}`, `provision_module()` and `_run_module()` wire `steward provision --module bmb [--json]` as the new top-precedence flag. It assembles an answers JSON from `module.yaml`'s own declared variable defaults, then drives BMB's own `bmad-bmb-setup` scripts — `merge-config.py`, `merge-help-csv.py` — as `uv run` subprocesses (AD-1: Steward never reimplements their merge/anti-zombie logic); `_materialize_module_output_dirs` `mkdir -p`s any `{project-root}`-prefixed output dir the module declares, reusing `merge-config.py`'s own template-substitution read-only (SKILL.md names this a caller responsibility). Deliberately never passes `--legacy-dir` and never invokes `cleanup-legacy.py`: this repo's `_bmad/core/config.yaml` is a *different*, already-governance-owned module's legacy config that `cleanup-legacy.py --module-code bmb`'s own hardcoded `[module_code, "core"]` removal list would `shutil.rmtree` as a side effect — the Spec's own "never absorb bmad-method's governance core" constraint. An unrecognized `--module` name is reported directly, never reaching `provision_module`/a subprocess call. Skill Forge intentionally NOT registered (its `install` has no non-interactive CLI flag as of v1.0.0 `STABILITY.md` — CAP-1's Skill-Forge half deferred, not dropped). CAP-2 (module discovery / installed-vs-available listing) and the rest of CAP-3 (deep post-install verification) remain open — Stories 6.2/6.3.
- (change) RECONCILES src/shared/packages/pyforge-steward/src/pyforge/steward/provision.py (2026-08-09, Story 6.2; also touches the sibling spec-pyforge-steward's own surface — src/shared/packages/pyforge-steward/src/pyforge/steward/cli.py and src/shared/packages/pyforge-steward/tests/conformance/test_provision_list_modules.py (new) — recorded in that Spec's own memlog). CAP-2 delivered: `module_install_states()` derives each registered module's `installed`/`available` state from `_bmad/config.yaml`'s own top-level keys — the exact anti-zombie key `merge-config.py`'s own `config[module_code] = module_section` writes (verified against the real script, Story 6.1's own evidence trail) — a pure filesystem read, no subprocess call, no new state file (derive-don't-declare, matching `--list`'s own `pixi.toml`-derived precedent). A missing `_bmad/config.yaml`, or one that parses to a non-mapping (e.g. a bare YAML list), both degrade to `{}` -> every registered module reports `available`, never an error; a genuinely malformed (unparseable) `_bmad/config.yaml` is NOT caught inside `module_install_states` — `yaml.YAMLError` propagates to `ProvisionDuty.run()`'s existing exception boundary (already catching that type since Story 6.1), honoring `--json` on the error path via the existing `_render_error`. `format_module_states()` mirrors `format_environments`'s own text/`--json` split. Wired as `steward provision --list-modules [--json]`, the new first precedence check ahead of `--module`. Two states only, by design (not a third for "backend directory missing"): that failure mode is already `provision_module`'s own distinct `FileNotFoundError` at provision time (CAP-3's territory); deep post-install verification remains Story 6.3's scope (rest of CAP-3).
- (change) RECONCILES src/shared/packages/pyforge-steward/src/pyforge/steward/provision.py (2026-08-09, Story 6.3; also touches src/shared/packages/pyforge-steward/tests/conformance/test_provision_module.py — recorded in the sibling spec-pyforge-steward's own memlog). CAP-3 delivered (its remaining half — "partial state is named, never silent"): `_run_module` no longer trusts `provision_module()`'s two subprocess steps at face value. A new `_format_called_process_error()` helper dedupes the `` `{cmd}` exited {code}: {stderr} `` formatting `ProvisionDuty.run()`'s own except block already applied inline, reused by both. A local `try/except (subprocess.CalledProcessError, RuntimeError)` around the `provision_module()` call compares a state snapshot taken BEFORE the call against one taken after it fails (both via the new `_module_install_state_or_none` wrapper around `module_install_states`, Story 6.2's own oracle, never re-derived) — a mid-chain `merge-help-csv.py` failure after `merge-config.py` newly landed its section (or a `RuntimeError` from `_materialize_module_output_dirs` after both scripts land) is named "already wrote a `<name>` section ... provisioning is INCOMPLETE"; a first-script (`merge-config.py`) failure is named "nothing was written to _bmad/config.yaml"; a failure against an ALREADY-installed module (state unchanged by this run) gets neither note, since nothing about THIS run's outcome is newly incomplete (review-pass fix: comparing only post-failure state, with no before-snapshot, misreported this last case as INCOMPLETE even though the run touched nothing). A read failure at either snapshot (malformed/unreadable `_bmad/config.yaml`) degrades to a neutral "could not confirm" note rather than letting a `yaml.YAMLError`/`OSError` from the recovery read itself mask the original stderr or crash past this boundary (review-pass fix; also applied to the post-success gate's own read). After a successful call, `module_install_states` is consulted once more before reporting `ok=True`: if `<name>` never actually landed in `_bmad/config.yaml` despite both scripts exiting 0, the run reports `ok=False` naming "not counted as provisioned" — FR-21's "succeeds while leaving the module unimportable" clause, previously entirely unguarded. `FileNotFoundError` (unregistered name / missing backend dir) stays out of the new local catch — both occur before any subprocess call, so Story 6.1's existing message still covers it via `ProvisionDuty.run()`'s outer boundary, unchanged. `--json` is honored on both new failure paths via the existing `_render_error`. The real `bmb` backend cannot exercise the post-success gate's failure branch today (`merge-config.py`'s own source always pairs `"status": "success"` with actually writing the section, per Story 6.1's own evidence trail) — it is reachable only via a simulated-backend test, a defensive contract for future backends and FR-21's literal wording, not a claim that `bmb` is unreliable. All three of this Spec's capabilities (CAP-1/Story 6.1, CAP-2/Story 6.2, CAP-3/Story 6.3) are now shipped.
