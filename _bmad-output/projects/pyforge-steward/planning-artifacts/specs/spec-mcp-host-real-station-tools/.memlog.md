- (capability) CAP-1 -- a station with a real in-process MCP app (e.g. django_marshal_portal.mcp_asgi) is reachable through the deployed mcp-host sidecar with its REAL tools, not the generic station_face() stub. - (capability) CAP-2 -- a station with no real in-process MCP app still gets the existing station_face() stub as a fallback, so today's slice-1 proof (the dual-era handshake) keeps passing unchanged for any station that never grows a real app. Success: spec-mcp-era-isolation's own CAP-1..3 acceptance criteria still hold after this Spec's change lands.
- (capability) CAP-3 -- the deployed proof: CAP-3's own CRC exercise (spec-run-state-one-publisher/verification-2026-09-12.md) is re-run and its 'NOT PROVEN' row (a live run appearing on /runs/, timing surviving workstation teardown) flips to PASS.
- (constraint) Must not change spec-mcp-era-isolation's shipped slices 1-3 sequencing or scope: the dual-era wire, the proxy dispatch, MCP_HOST_SIDECAR_BASE_URL wiring, CAP-4 cluster-required fail-loud, the stdio translator (slice 2), and the ImportError-skip retirement gate (slice 3) all stay exactly as they are.
- (constraint) A station's own portal package (django_<name>_portal) stays that station's surface; this Spec only owns how the sidecar discovers and mounts what already exists there -- it does not redesign any station's tool implementation.
- (non-goal) Not retiring the mcp 1.x/2.x ImportError skip in the web image (slice 3 -- gated on an upstream FastMCP 4 / unpinned-Langflow release, tracked in spec-mcp-era-isolation/retire-skip.md).
- (non-goal) Not the factory stdio wire-format translator (spec-mcp-factory-stdio-translator, slice 2) -- a different, already-specced problem (modern MCP clients vs FastMCP 3 stdio tools).
- (question) Open: how does the sidecar get Django ORM access for stations whose real app needs it (e.g. django_marshal_portal.mcp_asgi calling into django_pyforge.supervisor)? The sidecar image today runs no Django at all by design ('No Langflow. No FastMCP.'). Candidate shapes: (a) a minimal settings module registering only the portal AppConfigs + DB connectivity, no Langflow; (b) each station's real app builder takes its own ORM-free path; (c) something else. Not resolved by this Dream -- the Spec needs research before this can leave open_questions.
