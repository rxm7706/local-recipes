- (note by claude) Story 45.2 build, empirical (real `claude -p` invocations against opus, 2026-09-06/07, ~$2 total spend): the mutated arm reliably resolves `caught` (AD-33 `witness-matched`) when the review cites the planted line, and a genuine miss reliably resolves `missed` / FAIL / exit 2 (verified by hand-constructing both outcomes against the real `eval-quality score` CLI before wiring the driver). BUT the clean arm is a persistent, reproducible false-positive source with the current fixture: across three independent live runs (two different driver revisions, one with `fixture-intent.md` inlined as the Step-5 claims file), edge-case-hunter's exhaustive-enumeration methodology found a DIFFERENT legitimate boundary concern at the same `pkg/discount.py:17` every time — float-accumulation rounding at the threshold, NaN handling, and (once) a same-hunk "constant referenced but not defined" note — never the planted `>=`-to-`>` flip itself, since the clean diff doesn't have it. The `covers-by-key` oracle matches by `file:line` only, so any of these resolves as `false-positive` (AD-33 `clean-control-false-positive`) indistinguishably from a true catch of the actual planted defect. This is a scope limit of location-only matching for a numeric-threshold defect class, not a driver bug — a numeric comparison line is close to always going to draw SOME edge-case finding from this reviewer. Left as-is per the epics AC's own oracle mandate (`covers-by-key` on file:line); a future contract revision wanting a quieter clean arm would need a defect class less structurally attractive to exhaustive boundary enumeration, or a stronger key (e.g. also matching `trigger_condition` text), which the current `covers-by-key` operator cannot express.
