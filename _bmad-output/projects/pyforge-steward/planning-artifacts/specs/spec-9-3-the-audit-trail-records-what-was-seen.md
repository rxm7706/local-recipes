## Intent

**Problem:** CAP-4 requires every data load, filter, navigation, and export to write a durable, role-isolated audit record naming who saw how many rows of what; today `pyforge.steward.dashboard` has no store for it at all, and two Story 9.1 deferrals (verbatim, un-normalized identity/role values; an sld:AD-13 scaffold shipped early with no real model to prove it) explicitly name this story as their first consumer.

**Approach:** Add `AuditEntry` — this package's first Django model with migrations — plus a small `audit.py` write/read/retention API: `record_audit_entry` (the CAP-4 primitive), `query_audit_entries` (which itself audits its own read, per AD-7), and `purge_expired_entries`, which takes a required `AuditRetention` declaration (new in `declarations.py`, mirroring `AccessDeclaration`'s style) with no default — AD-7's "refused rather than run unbounded," enforced by signature the same way AD-6 enforces filter-then-search.

## Boundaries & Constraints

**Always:**
- `record_audit_entry` requires a non-blank `actor`; blank/`None` raises `ValueError` — CAP-4's "who saw" must never be unanswerable by construction. `role` may legitimately be `None` (Story 9.1's "no role established" scope state) and is stored as `NULL`, never coerced to `""`. `target` (the "of what") is optional — a caller with nothing more specific than the action itself may omit it — and defaults to `""`, never `None`.
- `actor`/`role`/`target` are stored **verbatim** — no trim, case-fold, or Unicode normalization. The trail's job is recording what was actually presented; normalizing would substitute this pattern's own reinterpretation for what was seen. This is the identity-model decision Story 9.1's review pass 3 deferred here.
- Each of `actor`/`role`/`target` is length-capped and validated **in Python before any DB write**, not left to the column type: SQLite (dev) does not enforce `VARCHAR(n)`, PostgreSQL (deployment) does — relying on the backend would make the boundary hold in production and silently not in development, the inverse of sld:AD-14's intent.
- `purge_expired_entries(retention: AuditRetention, ...)` has no default for `retention` and no module-level fallback constant — there is no call path that expires entries without one.
- `query_audit_entries` calls `record_audit_entry(..., action=AuditAction.AUDIT_READ)` for its own invocation — reading the trail is itself a recorded act (AD-7).
- `models.py`, `migrations/*`, and `audit.py` require Django, same tier as `apps.py`/`cache.py`. The new `AuditRetention` in `declarations.py` stays import-free of `django`/`channels`, consistent with its two existing dataclasses.

**Block If:**
- If `django.setup()` + `call_command("migrate")` against an in-memory SQLite `DATABASES` cannot produce a working `AuditEntry` table inside a plain pytest process (no `pytest-django` installed) — HALT and report.

**Never:**
- Wire `record_audit_entry` into `navigation.py`, `filtering.py`, `views.py`, or an export endpoint — none of those files exist in this worktree (Stories 9.2/9.4 are in-flight in sibling worktrees of this same bmad-loop run). This story ships only the primitive their call sites will use once merged.
- Ship a Channels consumer or any per-message/WebSocket handling — sld:AD-11/sld:AD-12's per-message re-resolution and closing-on-unresolvable-identity belong to whichever story ships the first persistent-connection consumer, matching this epic's established pattern of deferring consumer-side concerns to their first real caller.
- Prove sld:AD-14's PostgreSQL contention claim — no PostgreSQL CI service exists in this repo's pixi environments yet. Tests validate against SQLite only; the contention proof is a new deferred-work entry, not attempted here.
- Wire retention verification into `steward deploy` — that surface is Story 9.5's, per the identical precedent DW-FU-9-4-5 already set for export-gating verification.
- Reconcile DW-FU-9-2-3 (the whitespace-role inconsistency between `filter_by_role` and `build_navigation`) — both live in files absent from this worktree.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Normal write | `actor="alice"`, `role="east"`, `action=LOAD`, `row_count=42` | one `AuditEntry` row with those fields + `occurred_at` | No error expected |
| Write with no role | `actor="alice"`, `role=None`, `action=NAVIGATE`, `row_count=0` | row created with `role` NULL | No error expected |
| Blank actor | `actor=""` | — | `ValueError` naming `actor` as blank |
| Actor exceeding the length cap | `actor="x" * 300` | — | `ValueError` naming the field and the cap; no row written |
| Negative row count | `row_count=-1` | — | `ValueError` (not left to the DB) |
| Read the trail | 3 prior entries; `query_audit_entries(reader_actor="bob", reader_role="auditor")` | returns the 3 rows **and** writes a 4th entry, `action=AUDIT_READ` | No error expected |
| Purge with a declared retention | entries older/newer than the cutoff; `AuditRetention(days=30)` | only entries older than the cutoff are deleted; return value equals the deleted count | No error expected |
| Purge called with no retention | caller omits the argument | — | `TypeError` from Python itself — proves the refusal is a signature property, not a skippable runtime check |
| Retention declared non-positive | `AuditRetention(days=0)` or `days=-5` | — | `ValueError` naming the invalid value |

## Design Notes

**Verbatim storage over normalization.** Story 9.1's review pass 3 explicitly named this story as the place to decide identity/role trimming, case/Unicode normalization, and a length cap. This spec resolves it: store verbatim (CAP-4's contract is "records what was actually seen," and normalizing at write time would silently substitute a reinterpretation), cap length only as a robustness bound, and reject rather than truncate an overlong value so evidence is never silently corrupted.

**Length caps enforced in Python, not the column type.** SQLite performs no `VARCHAR(n)` enforcement at all; PostgreSQL does. A cap expressed only as `models.CharField(max_length=255)` would therefore hold in production and silently not in development — backwards from sld:AD-14's "proven, not inferred" intent, and the same class of dev/prod asymmetry sld:AD-14 already warns against for a different mechanism (contention). Explicit `len()` checks in `audit.py` close this regardless of backend.

**`purge_expired_entries` takes no default retention, ever.** This mirrors AD-6's already-established pattern in this epic ("enforced by signature, not by discipline") applied to AD-7: a Python function with a required positional parameter and no module-level fallback cannot be called into silently expiring nothing (or everything) the way a defaulted parameter or an implicit setting could.

**Why no Channels consumer here.** sld:AD-11/sld:AD-12 describe per-message re-resolution and audit on persistent connections, but no consumer exists anywhere in this codebase yet to call into. Every prior story in this epic (9.1's async cache variant, 9.4's async webhook call) deferred its own async-context concern to "whichever story first puts this on an async hot path" rather than inventing a caller; this story follows the same precedent for the write API's first per-message caller.
