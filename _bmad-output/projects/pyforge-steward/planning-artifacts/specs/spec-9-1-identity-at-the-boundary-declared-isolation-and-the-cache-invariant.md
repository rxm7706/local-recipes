## Intent

**Problem:** Every dashboard that needs role-based access today reinvents identity extraction, row isolation, and caching from scratch, or ships without them; the reusable secure-dashboard pattern this epic delivers has zero implementation yet, and it needs its foundation piece before any other story in the epic can build on it.

**Approach:** Stand up `pyforge.steward.dashboard`, a Django app shipped only behind a new `pyforge-steward[dashboard]` extra, with (1) an ASGI middleware that extracts identity/role from configured proxy headers and refuses to start the ASGI response cycle when those headers arrive from outside a declared trusted ingress, (2) a small declaration schema an adopter fills in (access column + role vocabulary) instead of hand-writing filtering, and (3) a single-flight cache layer over Django's cache framework that fetches the master dataset once per cache miss and never writes a role-filtered frame back.

## Boundaries & Constraints

**Always:**
- `pyforge.steward.dashboard` ships only via the `pyforge-steward[dashboard]` optional extra (`pyproject.toml`'s `[project.optional-dependencies]`), never a base `dependencies` entry, and never in the member `pixi.toml`'s `[package.run-dependencies]` (mirrors the existing `pyforge-atlas`→`pyforge-warden` `[gate]`-extra precedent verbatim).
- No file outside `pyforge/steward/dashboard/` imports `pyforge.steward.dashboard`, `django`, or `channels` at module top level.
- The trusted ingress (proxy address) and the identity/role header names are adopter-declared config, never hardcoded. (Interface-based ingress declaration, e.g. for Unix-domain-socket deployments, is deferred to Story 9.5 — see `deferred-work.md`.)
- When an identity header arrives on a connection whose peer address is outside the declared trusted ingress, the middleware raises before any ASGI `send()` call — the response never "starts" — rather than completing a normal (e.g. 403) response cycle.
- The role-filtered slice is computed only after the master dataset leaves the cache; the cache never stores a role-filtered frame, and concurrent misses for the same cache key collapse to exactly one upstream fetch.
- The `AppConfig` follows AD-13 now (explicit non-colliding label, `default_auto_field` set) even though this story ships no model — so Story 9.3's audit model inherits a compliant scaffold instead of retrofitting one.

**Block If:**
- The chosen ASGI refusal mechanism (raising before any `send()` call) proves untestable against a fake ASGI transport, or the fake harness can't distinguish "zero sends" from "a send that happened to fail" — HALT and report; do not silently reinterpret AD-4's "refuse the start, not the request" as an ordinary 403 response.

**Never:**
- Implement navigation filtering (9.2), the audit trail (9.3), export gating (9.4), the deployment perimeter (9.5), the proof suite (9.6), or static export (9.7) — this story is foundation only.
- Add `channels`, `channels_redis`, or `daphne` as dependencies — nothing in this story imports them (they land with the stories that do).
- Add a `steward deploy` CLI verb for any of this — no CLI/argparse surface change in this story.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Trusted-ingress request with identity header | `scope["client"]` inside declared ingress, identity header present | middleware populates identity/role onto `scope`, passes through to the wrapped app | No error expected |
| Untrusted-ingress request with identity header | `scope["client"]` outside declared ingress, identity header present | middleware raises before any `send()` call — no ASGI response ever starts | Connection aborted, never a 403 response body |
| No identity header at all | `scope["client"]` anywhere, header absent | pass-through with no identity set; ingress check never triggers | No error expected |
| Concurrent cache miss, two roles | two callers request the master dataset under the same cache key at once | exactly one upstream fetch call; each caller computes its own role-filtered slice after the shared fetch returns | No error expected |
| Cache inspection after a fetch/hit cycle | any point after `get_master_dataset()` returns | the cache backend holds only the unfiltered master frame under the declared key | Never a role-scoped key or role-filtered value in the backend |
| Declaration missing access column or roles | adopter constructs `AccessDeclaration` with an empty/absent column or role map | construction raises immediately, at config time | `ValueError` naming the missing field |

**Acceptance Criteria:**
- Given a request whose identity header arrives from outside the declared trusted ingress, when the middleware processes it, then no ASGI response event is ever sent and a distinct exception type is raised.
- Given two concurrent callers requesting the same cache key with different declared roles, when both race a cache miss, then the underlying fetch function is called exactly once and each caller receives its own role-filtered result.
- Given any successful fetch/hit cycle, when the cache backend is inspected directly, then it contains only the unfiltered master frame under the declared key -- never a role-scoped variant.
- Given the whole `pyforge-steward` package, when `tests/meta/test_invariants.py` runs, then no module outside `dashboard/` imports `pyforge.steward.dashboard`, `django`, or `channels`.
- Given `pyforge-steward` installed without the `[dashboard]` extra, when `steward --version` or any existing duty runs, then it succeeds unchanged.

## Design Notes

**"Refuse the start, not the request" (AD-4).** ASGI's HTTP flow only becomes a real response once `send()` is called with `http.response.start`. This story treats "refuse the start" literally: the middleware raises before calling `send()` at all for a connection whose identity header arrives from an untrusted ingress, so the connection is aborted rather than completing a polite 403 response cycle — a behavior the test asserts directly (`send` was never invoked), not a status-code check.

**What the ingress check actually compares — corrected in review pass 3.** The check reads `scope["client"]`, and `scope["client"]` is the ASGI *server's* claim about the peer, not necessarily the TCP peer. Verified against the installed daphne 4.2.3: `daphne.utils.parse_x_forwarded_for` (reached via `--proxy-headers`) replaces `scope["client"]` with `X-Forwarded-For.split(",")[0].strip()` and validates no hops at all; uvicorn does the same with `proxy_headers=True`, which is its default. Behind a proxy that *appends* to `X-Forwarded-For` (standard nginx `$proxy_add_x_forwarded_for`) that leftmost entry is client-supplied, which both refuses legitimate traffic and lets a caller name any address it likes. So AD-4's refusal is only as sound as the server's client-address reporting: the deployment must either leave proxy-header parsing off or terminate `X-Forwarded-For` at a controlled hop. This story documents that precondition in `middleware.py` and `TrustedIngress`; enforcing it is Story 9.5's deployment perimeter and Story 9.6's to prove end-to-end (both on the deferred-work ledger). The earlier wording here and in those docstrings asserted `scope["client"]` simply *is* the peer address, which is not true of the servers the architecture's Stack table names.

**Django version — corrected in review pass 1.** The first draft pinned the `[dashboard]` extra to `>=4.2,<5`, reasoning that the only `django` *local recipe* on disk (`recipes/django/meta.yaml`) built 4.2.15. That check was too narrow: `pixi.toml`'s existing `[feature.local-recipes.dependencies]` already pins `django = ">=5.2.15,<6.0"` alongside `channels`/`daphne` at the exact versions the architecture Stack table names — proving 5.2 LTS is already resolved and used elsewhere in this estate (wagtail/coderedcms), not merely aspirational. The `[dashboard]` extra now pins `>=5.2,<6`, matching the Stack table and that existing feature dependency exactly, in both `pyproject.toml` and root `pixi.toml`.

**Cache single-flight — corrected in review pass 3.** `cache.add(lock_key, ...)` is the acquire-if-absent primitive for "concurrent misses collapse to one fetch" without committing to a specific backend: AD-5 mandates the sharing *property* when workers>1, never a specific implementation, and nothing in this story requires standing up Redis to prove it. But it is **not** atomic against every Django backend — review pass 2 disproved that by execution and corrected `cache.py`'s docstring accordingly, while this Design Note was left asserting the disproven claim. The accurate statement: `LocMemCache` and Redis do provide an atomic `add()`; `FileBasedCache.add()` is an unlocked check-then-set, so concurrent processes can both win; `DummyCache.add()` returns `True` unconditionally and stores nothing, so every caller "wins" and caching is off by definition. Single-flight is also bounded by `lock_timeout` rather than absolute — a fetch slower than the lock loses exclusivity partway through (measured: 3 fetches for a 3s fetch at `lock_timeout=1`). Choosing a backend that carries the property, and refusing one that cannot when workers>1 (AD-5's other half), is the deployment perimeter's job (Story 9.5); both gaps are on the deferred-work ledger.

**The single-flight loop can now give up — added in review pass 4.** Two states the loop could not distinguish are now separated. A lock that is *visibly held* is a working backend and is waited on, as before. A lock that can be neither acquired nor observed — `cache.add()` reporting failure while the lock key reads as absent — is not a race at all: no working backend produces it, and Django's `DatabaseCache` produces it under ordinary write contention, because `_base_set` ends in a bare `except DatabaseError: return False`. That state was an unbounded busy loop (no `sleep` runs on that path; measured at ~500k backend operations per second, indefinitely, without ever calling `fetch()`), so the module now sleeps there like every other wait and raises `LockUnavailableError` once `2 * lock_timeout` has passed without progress. Only the WAIT/RETRY path is bounded — a `fetch()` this call started always runs to completion. This is a narrower change than it looks: it does not bound single-flight's *degradation* past `lock_timeout` (still deferred, still needing the backend decision), only the case where the function could never return at all.
