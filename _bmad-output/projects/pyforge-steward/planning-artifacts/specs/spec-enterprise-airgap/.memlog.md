- (decision) Kernel describes the shipped posture: ALL enterprise routing is runtime-driven via _http.py (truststore + JFrog/GitHub/.netrc auth chain), env vars only, never committed config; read-side atlas CLIs offline-safe; current_repodata.json path chosen over rattler sharded protocol partly for air-gap/JFrog reuse
- (question) OPEN (known issue, Doctor->Steward): JFROG_API_KEY injects unconditionally on every outbound request regardless of host - cross-resolver credential leak; fix = host-gate the header in _http.make_request
- (event) Self-validate 1+2: PASS - known credential-leak deviation NAMED as open question (never false-green); all posture claims grounded in shipped code/docs
- (event) Surface reconcile, 2026-08-20: `.claude/skills/conda-forge-expert/scripts/_http.py` changed by the pyforge-mason Story 5.5 Rule-2 CFE retrospective (spec `spec-5-5-rule-2-conda-forge-expert-retrospective`), an unrelated BMAD project's closing retro that is the one commit its whole effort is permitted to touch the CFE surface with. This is not incidental drift — the change RESOLVES the open question above: `auth_headers_for` now gates the JFrog credential branches on `_configured_enterprise_hosts()`, a set derived from every currently-set `*_BASE_URL` env var, closing the unconditional cross-resolver leak without an SSRF-style denylist (which would block the very enterprise mirrors this kernel's own routing exists to reach). Open question closed in SPEC.md frontmatter; baseline re-stamped scoped to this spec only (`python scripts/spec_surface_check.py --write-baseline --spec pyforge-steward/spec-enterprise-airgap`).
- (event) Follow-up, same commit, 2026-08-20: a same-pass adversarial review (Blind Hunter + Edge Case Hunter) found the entry above's fix incomplete when first landed — `_configured_enterprise_hosts()` read only `*_BASE_URL` env vars, missing the hosts this project's own `docs/reference/pixi-config-jfrog.example.toml` documents as project-local `.pixi/config.toml` (no env vars at all), THE RECOMMENDED enterprise setup — a functional auth regression for that documented path, not merely a residual leak. Also found and fixed in the same commit, still inside `_http.py`'s surface: the JFrog/GitHub-token branches shared one `if/elif` chain with no host-type distinction, so a `*_BASE_URL` resolving to github.com/api.github.com could shadow `GITHUB_TOKEN`; and host comparison did not strip the port. All three patched before landing — `_configured_enterprise_hosts()` now unions env-var- and pixi-config-derived hosts, github.com/api.github.com are unconditionally excluded from the JFrog gate, and host comparison is port-stripped (`netrc_credentials`'s own convention). This kernel's posture claim (`_http.py`'s routing is the shipped enterprise-auth mechanism) holds more completely now than the entry above alone reflected; no SPEC.md change needed beyond the open-question closure already recorded (the fix is more complete, not differently scoped). Two SIBLING scripts outside this spec's surface (`dependency-checker.py`, `inventory_channel.py`) had their own independent copies of the same leak — fixed in the same commit but reconciled under `pyforge-mason/spec-conda-forge-expert-rebuild`'s own memlog, not here (out of this spec's declared surface).
- (event) Follow-up review pass, 2026-08-20 (v8.82.0 → v8.82.1): an independent review of the landed change found the host gate — the mechanism that closed this kernel's open question — parsing hosts with `urlparse().netloc.split(":")[0]`. That returns the USERNAME for `https://svc:tok@artifactory.corp/api/conda/cf`, which is a routine Artifactory `*_BASE_URL` form, so the enterprise mirror this kernel exists to describe would never have entered the allowlist and would have silently stopped receiving its credential — a functional auth regression for the shipped posture, and the direct inverse of the leak the gate closed. It also collapsed every IPv6 literal to `[2001`, so an unrelated same-prefix address matched and received the credential instead. Both fixed via `urlparse().hostname`. Two further gaps in the same mechanism: public default hosts could enter the allowlist through the env-var half (a redundant `PYPI_BASE_URL=https://pypi.org/simple` re-opened the leak), now subtracted from both halves via `_public_default_hosts()` derived from `_http`'s own `_DEFAULT_*` globals; and `_pixi_configured_hosts()` let `read_pixi_config()`'s `Path.home()` RuntimeError (no HOME — rootless/arbitrary-UID containers, an air-gap-adjacent deployment shape this kernel cares about) raise through every outbound request, since the gate had newly put that call on the request path. Now guarded. The open-question closure recorded in the entries above still holds and holds more completely; no SPEC.md change needed. Baseline re-stamped scoped to this spec only.

- (event) Third review pass, 2026-08-20 (v8.82.1 → v8.82.2): a second independent review of the same mechanism — the host gate that closed this kernel's open question — found two further defects in `_http.py` itself, both reproduced before triage. (1) `netrc_credentials` still derived its host with `urlparse().netloc.split(":")[0]`, the very form the previous pass's constraint bans, left behind because it is not on the allowlist path. For `https://svc:tok@artifactory.corp/api/conda/cf` — the routine Artifactory form this kernel's posture describes — it yields `svc`, the USERNAME, which matches no `machine` line, so `netrc.authenticators` falls through to any `default` entry: the operator's correct `.netrc` credential for their mirror is silently bypassed and an unrelated one sent in its place. Now `_host_of`, the same parse the gate uses. (2) Closing the JFrog branch made the generic `.netrc` branch REACHABLE in a state it never ran in before: with `JFROG_API_KEY` set, the first `if` used to match unconditionally, so an operator with both a JFrog key and a `default` `.netrc` entry now sends those Basic credentials to unconfigured hosts where they previously sent the JFrog header. That is `default`'s documented netrc semantics and so is the operator's own declared intent rather than a leak the function invents, but it is a behaviour change on the enterprise-auth path this kernel documents, and it is now stated in `auth_headers_for`'s own docstring and in SKILL.md as a general rule (guarding one branch of an `if/elif` chain hands its traffic to the next). Also recorded here because this kernel's surface is where an operator would look: a GHES / self-hosted GitLab host named by `GITHUB_API_BASE_URL` / `GITLAB_API_BASE_URL` enters the allowlist and takes the JFrog branch, so `GITHUB_TOKEN` is not attached to it — behaviour that predates the gate (the unconditional branch did the same), verified live, and now tracked as a deferred item rather than changed here, because the safe form must first be checked against `resolve_github_api_urls`'s real call sites. The open-question closure recorded above still holds. No SPEC.md change needed. Baseline re-stamped scoped to this spec only.
