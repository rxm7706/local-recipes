- (question) Where does the pattern live: a steward subcommand that scaffolds and verifies, a library the dashboard imports, or a template repository? Each implies a different upgrade story when the pattern improves, and a diverged adopter is the case that matters.
- (question) Does the pattern PROVIDE the RLS pipeline and audit writer, or VERIFY that an adopter has an acceptable one? Provide is reusable and rigid; verify tolerates dashboards that already chose.
- (question) Proxy headers are trusted implicitly — anything that can reach the app directly can forge X-Forwarded-Roles. The blueprint configures header NAMES but never defends the trust boundary. Needs a defence or an explicitly recorded assumption.
- (question) Is Redis mandated or one pluggable cache backend? The blueprint's sample uses FileSystemCache, which contradicts its own Compose stack: with Gunicorn --workers 4, a filesystem cache does not deliver the shared-cache guarantee Redis exists to provide.
- (question) Does the audit trail have a retention and access policy? It accumulates per-user activity and is therefore both a compliance asset and a privacy liability.
- (question) What enforces that search runs AFTER role filtering? The blueprint's sample gets the order right but nothing binds it, and reversing it leaks.

- (capability) CAP-8 static delivery mode (operator direction 2026-08-09, second intake doc vizro-static-github-pages-workaround.md): the same dashboard definition can ALSO be published as a free static GitHub Pages site -- Plotly components exported via fig.to_html, injected into a responsive grid, rebuilt by CI to gh-pages. intent: one dashboard definition, two delivery modes, no fork. success: the same board is published both ways from one definition without hand-re-deriving its charts, and the static build REFUSES when the board has declared role isolation.
- (constraint) Choosing a delivery mode is choosing a SECURITY POSTURE, not a hosting preference. The static mode optional client-side filtering embeds the data for all possible states in the page, so every role rows reach every browser; the static mode also has no server, therefore no audit trail is possible at all. A board that declares an access column may not be delivered statically, and the static build must refuse rather than warn.
- (question) OPEN, from the second intake: what keeps the two modes from DIVERGING? If the static export re-derives charts from vm.Graph(figure=...) by hand, two deliveries of the same dashboard drift into two different dashboards. Also open: include_plotlyjs=cdn fetches a third-party runtime at load time, which does not work air-gapped and executes code from a host the estate does not control -- relevant next to spec-enterprise-airgap.
- (constraint) HOST CONSTRAINT (operator 2026-08-09): the primary backend is a Django service with Channels on ASGI, and the dashboard must be pluggable into it. Consequences carried into the architecture: the pattern binds at the ASGI boundary and mounts as a Django application; identity may come from Django request.user and groups rather than only proxy headers; role isolation and audit apply per WebSocket MESSAGE, not only per HTTP request; the audit store is Django ORM with migrations when hosted inside Django, and the worker topology is an ASGI server, not Gunicorn gthread.
- (constraint) DATABASE PAIR (operator 2026-08-09): SQLite for local development and testing, PostgreSQL for deployment, differing by connection configuration only. Carried into the architecture as sld:AD-14 with its caveat -- SQLite does not reproduce production write contention, and the audit write sits on the hot path of every data-returning message, so contention is proven against PostgreSQL in CI rather than inferred from a green SQLite run.
