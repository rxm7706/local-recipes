Two findings from the same review pass are worth recording here because they constrain
future edits to `[feature.python-agent-platform]` specifically:

1. **The pip layer must exclude every package the LOCK provides, not every package the
   feature DECLARES.** The exclusion list was derived from the feature's nine declared
   dependencies, so five requirement lines whose packages arrive transitively in the
   395-package solve were silently replacing their conda builds — `pillow` 12.3.0→11.3.0,
   `celery` 5.6.3→5.5.3, `uvicorn` 0.52.3→0.35.0, `gunicorn` 26.0.0→23.0.0, and
   `argon2-cffi` same-version. conda-forge packages ship real `.dist-info`, so pip
   uninstalls them first. The celery one was actively out of spec: pip's 5.5.3 declares
   `kombu<5.6` against this env's `kombu 5.6.2`, a constraint `--no-deps` suppresses.
2. **`uvicorn` and `uvicorn-worker` are now a coupled pair in this env.** Fixing (1)
   exposed that `requirements/base.txt`'s `uvicorn-worker==0.3.0` calls
   `uvicorn.Config.setup_event_loop()`, removed in uvicorn 0.36.0 — a hard gunicorn
   worker-boot failure against the conda `uvicorn 0.52.3`. The old pip downgrade had been
   masking it. The image now installs `uvicorn-worker>=0.4.0`. Any future uvicorn bump
   across an API break needs the matching worker release; the failure mode is a boot loop.

## 2026-08-15 — Story 10.3 follow-up review pass (second pass on a `done` spec)

An independent follow-up review of Story 10.3 landed six further changes under this spec's
surface. Two of them are behavioural fixes to the image; the rest tighten what CI can
actually catch.

Paths changed under this spec's surface in this pass:

- `src/platform/Containerfile` — CHANGED, three substantive edits.
  1. **`$HOME` moved off `/app` onto a dedicated `/app/.home`.** The previous pass gave an
     arbitrary UID a writable `$HOME` with `chgrp 0 /app && chmod g+rwX /app`. On POSIX,
     permission to unlink or rename an entry comes from the DIRECTORY, so that grant let the
     runtime user `rm /app/entrypoint.sh` and write its own in place, and rename `/app/config`
     — reproduced live under `--user 24680:0` before the fix, against the Containerfile's own
     comment asserting the source tree stayed read-only. `/app` is now back to root:root 0755
     and `$HOME` is a group-0-writable subdirectory. Re-verified live: gunicorn 26's control
     socket lands at `/app/.home/.gunicorn/gunicorn.ctl` owned by the arbitrary UID,
     `entrypoint.sh` is no longer removable, `config/` is no longer renameable.
  2. **`STATIC_ROOT` is now group-READ-ONLY (`g+rX`), not group-writable.** Nothing writes it
     after the build — WhiteNoise serves it read-only from a baked manifest — and it is the one
     tree whose contents reach every visitor's browser as executable JS. Consequence recorded
     in the file: `collectstatic` can no longer be re-run inside a running container, which is
     the intended posture for an immutable image.
  3. **The nine explicitly-named pip extras are now exact `==` pins, not floors.** They were
     the only packages in the image resolved live from PyPI at build time, so rebuilding the
     same commit could produce a different image — and this file already documents that a wrong
     version here (the uvicorn/uvicorn-worker pair) is a gunicorn boot loop, not an import
     error. Versions captured from the verified build: `django-timezone-field==7.2.2`,
     `python-crontab==3.3.0`, `cron-descriptor==2.1.0`, `django-appconf==1.2.0`, `rjsmin==1.2.2`,
     `text-unidecode==1.3`, `fido2==2.2.1`, `qrcode==8.2`, `uvicorn-worker==0.4.0`. The cost is
     deliberate: a security bump to `fido2`/`qrcode` now needs a manual edit here.
     Two comment corrections rode along: the exclusion-filter count ("14 kept, 10 excluded" was
     stale by one — it is 13/11), and the `psycopg[c]` note, which cited a deferred-work entry
     that lives only in this story's gitignored Tier-3 ledger and is therefore unreadable from a
     clone; the gap is now written out in full at the point of use instead of cited.
- `src/platform/config/urls.py` — CHANGED, comment only. Records what `/ht/` does and does not
  prove: `health_check.Database` is a CONNECTIVITY probe under both pinned versions, not the
  `TestModel` write/read/delete round-trip the removed `health_check.db` sub-app registered, so
  a 200 does not mean the schema is migrated or that writes succeed. Prior passes corrected this
  claim in the story spec's Design Notes; it had never been recorded in the repo itself, where a
  future reader of the endpoint would look.
- `src/platform/tests/test_health_endpoint.py` — NEW. The `/ht/` route had zero runtime coverage
  on the pip-pinned `django-health-check==3.24.0` leg that `platform-ci.yml`'s `test` job runs.
  That matters because `config/urls.py` documents a real trap — 3.24.0's `get_plugins()` catches
  only `ValueError` on its per-entry unpack, so passing raw CLASSES instead of dotted strings
  raises an uncaught `TypeError` — and `get_plugins()` is reached only from an actual HTTP
  request, never from `as_view()` or URLconf loading. Proven, not assumed: with the raw-class
  form injected, `manage.py check` still reported "no issues" while the new tests failed. The
  container job cannot cover this either; it runs the conda 4.5.0 side, which catches both.

Verified live in this pass (docker engine; this sandbox still has no podman, so
`platform-ci.yml`'s podman matrix leg remains the first automated proof of the dual-engine
claim): a fresh `docker build` clean with `secrets-scan: clean (2 root(s))`; `pip list` inside

5.6.3, uvicorn 0.52.3, gunicorn 26.0.0, argon2-cffi 25.1.0, psycopg2 2.9.12) and the nine extras
