## Intent

**Problem:** The Artifactory/consumption map — which OpenTeams-universe packages are
verified on PyPI, conda-forge, both, or neither, plus the staged-recipes/board-issue gap
— exists only as `jfrog-workbook.canvas.tsx`, generated by `scripts/openteams_identity_
dashboards.py::write_workbook_canvas` from TWO sources: the identity records AND the
`CDO-ENT-JFROG` tab of the legacy Excel workbook. Almost every number that canvas renders
(`jfrogMap` bucket counts, `neitherRows`, `needPr`, `boardGap`) is JFROG-derived — the
Atlas-side equivalent of that Excel tab, `enterprise_jfrog_consumption.parquet`, is Story
23.2's deliverable and **does not exist yet** (confirmed: zero `enterprise_jfrog_
consumption` hits anywhere under `src/`/`conf/` as of this drafting).

**Approach:** Add the `identity-workbook` Vizro page now, wired to a genuine two-Parquet
join (`identity_ranked_export.parquet` for PyPI/conda-forge verification identity ⋈
`enterprise_jfrog_consumption.parquet` for JFROG telemetry) — proven correct against a
FIXTURE pair where both files exist, but shipping today against production data where
only the ranked export exists. Per this story's explicit scope, that is not a defect: the
page must degrade to an honest empty shell + a "Data gap" note when the enterprise overlay
is absent (DW-D2-2), and reach real parity once Story 23.2 lands the overlay — this story
does not block on 23.2, it builds the join logic ready for it.

## Boundaries & Constraints

**Always:**
- Absent EITHER `identity_ranked_export.parquet` OR `enterprise_jfrog_consumption.parquet`
  → the page renders an empty typed grid + a Card explicitly naming WHICH file is missing
  (not a generic "data unavailable" — an operator reading the page today must be able to
  tell this is "waiting on Story 23.2," not a bug).
- When BOTH files are present (fixture today; real data after Story 23.2 ships), the join
  and bucket classification (`both`/`pypi_only`/`cf_only`/`neither`) are proven correct
  against `write_workbook_canvas`'s own `jfrogMap` output on a shared fixture.
- The join happens in `dashboard/data.py` (the existing "wire a Parquet path to an Ibis
  table" responsibility) via two `models.duckdb_table_from_parquet` reads on ONE shared
  DuckDB connection; the bucket-classification LOGIC itself is a declared `semantic/
  models.py`/`metrics.py` expression (AD-8) — `data.py` plumbs table sources, it does not
  compute the classification.
- The parity test imports `write_workbook_canvas` unmodified.

**Block If:** Story 22.1 is not `status: done` (same as 22.2/22.3). Story 23.2 is
explicitly NOT a blocker — this story ships the honest-shell v1 regardless of 23.2's
status, per `stories.yaml`'s `invoke_dev_with: "enterprise JFROG export deferred — empty
shell acceptable v1"`.

**Never:**
- Do not fabricate JFROG data, a mock overlay Parquet checked into the repo, or any
  stand-in for `enterprise_jfrog_consumption.parquet` to make the page "look" populated in
  production before Story 23.2 ships — the honest-shell state IS this story's correct v1
  production behavior, not a placeholder to be embarrassed about.
- Do not reproduce `write_workbook_canvas`'s `workbookTabs` section (per-sheet row/name
  counts across the ENTIRE legacy `.xlsx`) — there is no Parquet-catalog equivalent of
  "enumerate every sheet in a workbook"; this is explicitly a legacy-Excel-only concept
  with no Atlas-side analog (see Design Notes).
- Do not block this story on Story 23.2 landing — see `Block If`.
- Do not add a new `PageDef.kind` value — reuse `"bsl-shell"`.
- Do not build the cross-page canvas-vs-Vizro CI harness (Story 22.5's job).

## Design Notes

**Why this story does NOT block on Story 23.2.** `stories.yaml`'s own `invoke_dev_with`
note for 22.4 is explicit: "enterprise JFROG export deferred — empty shell acceptable v1."
Building the join logic now (proven against a fixture) and shipping the honest-shell state
against production data is strictly better than either (a) deferring the whole page until
23.2 ships, or (b) shipping a page that silently shows wrong/partial numbers today. The
`Never` boundary against fabricating a stand-in overlay Parquet exists precisely to prevent
option (b) from creeping in during implementation.

**Why `workbookTabs` is out of scope, not deferred.** `write_workbook_canvas`'s `sheet_
stats` loop (L1044-1071) enumerates every sheet in the legacy `.xlsx` and counts rows/
distinct names per sheet — a property of "how many tabs does THIS Excel file have," which
has no Kedro/Parquet-catalog analog (a catalog has typed DATASET entries, not workbook
sheets). Porting it would mean either keeping a live read of the legacy `.xlsx` inside the
Vizro dashboard (reintroducing exactly the dual-source-of-truth problem CAP-1-4 exists to
retire) or inventing a fabricated Parquet-catalog equivalent with no real referent. Neither
is acceptable; this is a genuine capability gap between the two systems, not a shortcut.

**Why the join lives in `data.py`, not a new `semantic/` primitive.** AD-8 draws the line
at METRIC/dimension LOGIC (must be declared, in `models.py`/`metrics.py`) versus TABLE
SOURCING (already `data.py`'s job via `duckdb_table_from_parquet`). Joining two Ibis tables
on a key column before handing the result to a `SemanticModel` is table sourcing — the
classification of what a joined row MEANS (`match_bucket`) is the declared metric logic
that stays in `metrics.py`/`models.py`. This mirrors how `_bsl_query_or_empty` already
resolves ONE table before binding a model to it; this story's loader resolves TWO.

**Same `status: ready-for-dev` / Story 22.1 dependency reasoning as spec-22-2/22-3** — see
spec-22-2's Design Notes; not repeated in full here. Story 23.2 is explicitly NOT a
dispatch blocker for this story (see `Block If` above).
