## Intent

**Problem:** The operational view of the identity universe (Priority/Work distribution,
packaging-issue coverage gap, local build health, feedstock/staged-recipe census) exists
only as `identity-ops.canvas.tsx`, generated by `scripts/openteams_identity_dashboards.py
::write_ops_canvas`, and as the parallel `render()` markdown gist mirror in
`scripts/conda-forge-packaging-inventory-operations_openteams_identity.py`. Neither is
reachable from `dashboard-serve`, has no CI parity gate, and is Cursor-only.

**Approach:** Add one multi-pane Vizro page, `identity-ops`, to `dashboard/app.py`'s
`PAGE_INVENTORY`, with FOUR small BSL-driven panes (Priority, Issues, Builds, Census) on a
single page — a genuinely richer layout than every existing single-grid page, but built
from ONE shared `semantic/models.py::build_identity_ops_model` over `identity_ranked_
export.parquet` (Story 22.1's confirmed bridge export), queried four different ways (one
`dimensions`/`measures` combination per pane), following the same `_bsl_query_or_empty`
seam every other page uses. Parity is proven against `write_ops_canvas`'s own `DATA` blob
on a shared fixture, scoped to the THREE aggregates that blob actually carries (Priority/
Work counts, Issues have/miss-by-P, Builds status totals) — not `render()`'s markdown-only
Census cross-tab, which `write_ops_canvas` itself does not export into JSON today (see
Design Notes for why the Census pane still ships, just outside the binding parity gate).

## Boundaries & Constraints

**Always:**
- The page is wired into `dashboard/app.py`'s existing `PAGE_INVENTORY` + `build_
  dashboard()` — one page, four components, not four separate `PageDef` entries.
- Every pane's loader routes through `_bsl_query_or_empty` against the SAME shared
  `build_identity_ops_model` (AD-8) — no raw SQL, no pandas-level metric arithmetic in
  `dashboard/data.py`, no filesystem scan of `recipes/` at read time (that is a dataset-
  layer concern per AD-2, and `Local_Build_Status` is already a STORED column on the
  ranked export per `GIST_SCHEMA` — no live recompute needed).
- Absent `identity_ranked_export.parquet` → all four panes render empty typed grids/cards
  + one shared "Data gap" note (DW-D2-2), never fabricated rows or counts.
- The parity test imports `write_ops_canvas` **unmodified** via the same importlib-by-path
  technique `tests/packaging/test_openteams_handoffs.py` uses; it is not rewritten.

**Block If:** Story 22.1 is not `status: done` (same dependency as 22.2/22.4).

**Never:**
- Do not implement the recipe-type breakdown dimension on the Builds pane (canvas's
  `buildByType` is `[recipe_type, total, success, blocked, failed, not-attempted, blank]`
  per-type). `recipe_type` classification is computed live from `recipes/` filesystem
  contents by `write_ops_canvas`'s own `row_recipe_type`/`load_local_recipe_type` helpers
  (`openteams_identity_dashboards.py` L870-873) and is NOT a stored column on the ranked
  export — reproducing it would require either a filesystem scan at dashboard read time
  (forbidden, AD-2) or Story 22.1 exporting a new `recipe_type` column (out of this
  story's scope to demand). Ship the Builds pane as `Local_Build_Status` totals only (see
  Design Notes); do not silently drop the pane instead, and do not add a live filesystem
  scan to work around the gap.
- Do not build the "Census: feedstock, staged-recipes, local build" full-cube markdown
  table (`render()` L492-508, "Full cube (P × work × feedstock × needs staged)") — the
  Census pane here is the flat presence/absence counts only (feedstock exists / needs
  staged / staged PR filed / local recipe URL present), not the 10-column cube.
- Do not build the cross-page canvas-vs-Vizro CI harness (Story 22.5's job).
- Do not add a new `PageDef.kind` value — reuse `"bsl-shell"`.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| `identity_ranked_export.parquet` absent | No file at the resolved relpath | All four panes render empty typed grids + one shared Data-gap Card; `AD-17` "unavailable" | Never raise, never fabricate |
| Parquet present, well-formed | Fixture matching the ranked-export shape | Priority pane: `P`×`Work` counts. Issues pane: `P`×has-issue have/miss counts. Builds pane: `Local_Build_Status` totals. Census pane: feedstock/staged-PR/local-recipe presence counts | N/A |
| Parity check — Priority/Issues/Builds | Shared `records` fixture fed to both `write_ops_canvas` and a matching Parquet | Priority pane totals per `P` equal `DATA.priorityCounts`; Issues pane have/miss per `P` equal `DATA.issues.byP`; Builds pane totals per status equal the SUM across `DATA.buildByType`'s per-type rows for that status column | A mismatch on any of these three fails the story |
| Census pane | Same fixture, columns present | Renders real presence/absence counts | Documented as OUTSIDE this story's binding parity gate (no canvas JSON key to diff against yet) — must still be genuinely BSL-driven, not fabricated |

## Design Notes

**Why the Census pane ships without a binding parity target.** `write_ops_canvas`'s own
docstring (`openteams_identity_dashboards.py` L854-861) names "Priority/Work, Issues gap,
Builds/Census" in its one-line summary but then scopes what it ACTUALLY restructures into
JSON to "(Priority and work / Packaging-issue gap / Local build sections)" — three groups,
not four. The Census cross-tab (`render()` L455-508) is a markdown-only aggregate computed
by the gist generator, never exported into `write_ops_canvas`'s `DATA` blob. Since this
story's `done_checkpoint` is "Pane totals match write_ops_canvas on fixture" (not "match
render()"), the binding parity gate is scoped to the three aggregates that blob actually
carries. The Census pane is still built (matches the task's four-section framing and the
`GIST_SCHEMA` columns already support it cheaply) but is verified independently
(BSL-driven, not fabricated) rather than diffed against a canvas value that does not exist
yet. If Story 22.5's parity gate later wants Census parity too, that is 22.5's or a
follow-up's job to extend `write_ops_canvas` itself to export it first — not something this
story should reverse-engineer from the markdown mirror.

**Why the Builds pane drops the recipe-type dimension.** See the `Never` boundary — `recipe_
type` is a live filesystem classification, not a stored ranked-export column. This is a
genuine, cited scope-narrowing decision (not a silent omission): the `invoke_dev_with`
instruction for this story is explicitly "defer exact Cursor component parity," and a
status-only Builds pane is materially simpler while still being a real, BSL-driven,
parity-checked (at the status-total level) aggregate.

**Same `status: ready-for-dev` / Story 22.1 dependency reasoning as spec-22-2** — see that
spec's Design Notes; not repeated in full here. Whoever picks this story up should confirm
Story 22.1's live status before dispatch.
