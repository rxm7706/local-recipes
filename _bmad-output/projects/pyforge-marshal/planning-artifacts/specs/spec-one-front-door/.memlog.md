- (decision) Source: docs/dreams/one-front-door.md (owner marshal, status dreamt, explicitly marked Draft for refinement -- inventory derived from the tree, boundaries left open for operator refinement). Why: the Charter says execution has one owner, Marshal -- true of accountability, false of interface. What is installed is a toolbox (11 conda packages, 51 bmad-* skills, 16 skf-* skills, 10 detectors, an engine, a dashboard, a multi-project switch) used by remembering which piece is needed in what order with which project active. Verified 2026-08-01: no composed marshal entry-point verbs (run/status/check/land) exist yet on disk -- src/shared/packages/pyforge-marshal/src/pyforge/marshal/cli/ has only init.py (init/homes/preflight/teardown) and config.py (config), all Epic-1 delivered work already governed by spec-pyforge-marshal.
- (decision) Verified 2026-08-01 the Dream's own evidence scenario: driving one fleet run end to end required hand-invoking bmad-loop run/status, tmux capture-pane, seven detectors individually, dashboard-gen, dashboard-watch, spec-surface-check --write-baseline, git push across nine homes, and gh pr create/edit/merge five times -- none composed, all separately documented. The failure modes observed were seams: dashboard-watch never started because nobody thought of it, the push window reopened because nothing owned it (see durable-runs), PR #170 merged broken because the landing path asked nothing (see pr-lifecycle).
- (decision) Surface ownership check performed before drafting capabilities: spec-pyforge-marshal already claims src/shared/packages/pyforge-marshal/** in full (the whole CLI package, including the four already-shipped verbs). spec-factory-console claims docs/dashboard/**. spec-bmad-loop-governance claims .bmad-loop/**. spec-multi-loop-isolation claims scripts/bmad-switch + scripts/bmad-loop-worktree. This Spec therefore claims NO surface of its own (surface: []) -- its new verbs will land inside spec-pyforge-marshal's existing claim when built, and this Spec is the composition/design contract for what those verbs must do, not a second claim on the same files. Matches the Dream's own explicit framing: every row keeps its owner and its interface; the front door composes them, it does not replace them.
- (capability) CAP-1 marshal run -- wraps the engine, never absorbs it. Intent: a single verb drives a story or epic through bmad-loop (run/resume/status internally) without the operator hand-invoking bmad-loop directly, supplying active project + loop home + policy layer + story key from context rather than requiring them repeated per call. Success: driving one story from the Dream's evidence scenario collapses bmad-loop run + status + tmux capture-pane into one marshal run invocation with no loss of the context bmad-loop itself needs.
- (capability) CAP-2 marshal status -- one composed answer. Intent: a single verb answers is marshal's work saved and how is it going across fleet state, dashboard board, the detector registry, and unpushed-work-check (durable-runs CAP-5's reported-property) -- today that answer required four separate commands, per the Dream's own evidence scenario. Success: marshal status reports fleet health, unpushed-work findings, and detector state in one call; the operator no longer has to ask twice to get an honest answer (the durable-runs precedent this Spec composes rather than duplicates).
- (capability) CAP-3 marshal check -- the detector registry as a verb. Intent: scripts/detectors.py's derived registry becomes reachable as marshal check rather than a separate pixi task the operator must remember exists. Success: marshal check produces the same output as pixi run -e local-recipes detectors, invoked through the front door instead of beside it.
- (capability) CAP-4 marshal land -- the last mile, routed. Intent: once [[pr-lifecycle]]'s Spec exists and specifies what landing requires (linter gates, maintenance label, environment.yaml sync, PR lifecycle), marshal land is the one verb behind that door -- this Spec records the routing contract only; the landing behavior itself is pr-lifecycle's to specify. Success: marshal land invokes pr-lifecycle's specified behavior rather than this Spec re-specifying it -- a clean route, not a second definition of what landing requires.
- (capability) CAP-5 context supplied once. Intent: the active project, loop home, policy layer, and story key are resolved once by the front door and threaded through every routed call, rather than each of the composed tools (bmad-switch, bmad-loop, the detector registry, dashboard-gen) independently requiring the operator to supply them. This is the actual value of the Dream per its own text -- not shorter commands, context held once. Success: a single marshal invocation carries project/home/policy/story context to every tool it routes to without the operator re-specifying any of them mid-sequence.
- (constraint) Wrap, never absorb (Marshal doctrine, restated by this Dream as its central rule). The moment marshal CONTAINS a skill's logic instead of invoking it, this rule is broken one level up -- CAP-1..4 route to bmad-loop, the detector registry, and pr-lifecycle; none reimplement them.
- (constraint) Each craft stays with its owning station -- row 14 of the Dream's inventory is a named boundary test: conda-forge-expert is Mason's craft (Rule 1: any BMAD agent doing conda work must wield it), and Marshal routing a call to it is fine while Marshal knowing conda-forge internals is not (Charter, each station works one craft).
- (constraint) Install-time and run-time stay two Dreams, not one. [[genesis-installer]] owns greenfield init / brownfield adopt / the write guard / managed regions; this Spec is scoped to the runtime half -- who drives the surface once installed. Merging them would give one Dream two jobs, which the source Dream explicitly rejects.
- (constraint) New verbs land inside spec-pyforge-marshal's existing package surface (src/shared/packages/pyforge-marshal/**) -- this Spec introduces no new package and claims no surface of its own (see the Why decision entry on the surface-ownership check performed before drafting).
- (non-goal) Not a replacement for bmad-loop's engine, any of the 51 bmad-* skills, or any of the 16 skf-* Skill Forge skills -- every row in the Dream's inventory keeps its own owner and interface.
- (non-goal) Not the install/init surface -- greenfield and brownfield installation is genesis-installer's Spec, not this one.
- (non-goal) Not a decision on row 6's triage (bmad-manticore, bmad-labs-skills, bmad-utility-skills, bmad-method-wds-expansion, bmad-module-template) -- the Dream poses keep/wrap/remove as genuinely open and this Spec does not invent an answer (see Open Questions).
- (question) Q1 -- exact verb surface. The Dream lists run/status/check/land/switch(shipped)/homes(shipped)/doctor(delegate) as candidates it explicitly says to argue with, not a decided list. CAP-1..4 capture the verbs the Dream's own evidence scenario most directly supports; whether additional verbs are needed, or these four should be named differently, is open.
- (question) Q2 -- row-6 triage. Five installed packages (bmad-manticore, bmad-labs-skills, bmad-utility-skills, bmad-method-wds-expansion, bmad-module-template) are largely unexercised in this repo. Keep, wrap, or remove is unresolved; an unexercised dependency is surface area with no owner until this is decided.
- (question) Q3 -- the route-versus-contain boundary, per skill. Context is the product (CAP-5), but the Dream does not state where supplying context once becomes containing a skill's logic, across the 51 bmad-* skills. Precedent will need to be set skill-by-skill as CAP-1..4 are implemented.
