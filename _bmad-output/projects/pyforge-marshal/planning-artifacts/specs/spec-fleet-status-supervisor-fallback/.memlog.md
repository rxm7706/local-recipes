- (note) Governs core/status.py::derive_home_state and cli/status.py's supervisor_alive probe (pyforge-marshal, 2 candidate files). Source: docs/dreams/fleet-status-supervisor-fallback.md, captured 2026-08-11.
- (capability) CAP-1 a fallback liveness signal when supervisor_alive is False -- before derive_home_state's first branch returns unsupervised, a second signal (engine pid liveness / the run's tmux session / state.json or journal freshness -- design left to the downstream story) is consulted so a dead sidecar behind a live engine is distinguishable from a run that actually needs a re-spin.
- (capability) CAP-2 the two failure shapes read differently in the report -- an operator or an automated fleet-picture consumer never again needs the ps / tmux ls / state.json cross-check by hand to tell 'sidecar died, engine fine' from 'engine is actually gone too.'
- (constraint) The FLEET_STATES five-value vocabulary and the existing rule that a dead supervisor is never reported as healthy both stay intact -- this narrows a false positive, it never softens a real one.
- (constraint) Whatever the fallback checks must itself be derived from journals/process state per AD-5, never a hand-maintained flag or an operator override.
- (note) Non-goal (from the Dream): not a redesign of the state model; no implementation detail is prescribed -- which process to probe, tmux vs state.json, how it surfaces on the row are all left open for the downstream story.
- (question) Which concrete fallback signal (a recorded engine/launch pid liveness probe, the run's own tmux session name, or state.json/journal mtime freshness, or some combination) is undecided -- a story-level design decision, not resolved by the Dream.
