## Intent

**Problem:** Today one hand-edited `.bmad-loop/policy.toml` conflates repo-wide policy with per-project settings and per-story model tiering (the "HARD-STORY BATCH PROCEDURE" comment block), so switching projects or escalating a model tier means editing a shared tracked file — the F-1 cross-project bleed. Nothing yet composes Marshal's *own* effective policy with per-field provenance, so `EffectivePolicy` doesn't exist for Story 1.10 to render from.

**Approach:** Add `core/policy.py`: a bounded, closed 9-key policy vocabulary (traceable to FR-49/50/51/53/54) composed `defaults -> project -> flags`, last wins, pure; every field wrapped in a `PolicyField{value, layer, raw_source}`; static fields as public attributes, seed fields reachable only via `EffectivePolicy.seed_view()` (AD-26/F-8); a deterministic `content_hash` (AD-35's naming primitive); FR-53 shape/range validation emitting registered findings; a secret-redaction mechanism. `cli/config.py` wires `marshal config` (FR-54) as the package's first real subcommand.

## Boundaries & Constraints

**Always:**
- `core/policy.py` stays pure (AD-4): `compose(*, project_slug: str, project: Mapping, flags: Mapping) -> tuple[EffectivePolicy, tuple[Finding, ...]]` takes already-parsed layer mappings; it never reads a file or an env var. File I/O and `BMAD_ACTIVE_PROJECT` resolution live in `cli/config.py` (the CLI boundary) — AD-2's one sanctioned env var.
- Precedence fixed: Marshal defaults -> project -> flags, last wins, no fourth layer, no per-key reordering (AD-16). `compose()` is pure: identical inputs produce a byte-identical `content_hash`.
- Exactly 9 fields, closed set. **Static** (public `EffectivePolicy` attributes): `verify_commands`, `worktree_seed_paths`, `merge_subject_template`, `model_tier_map`. **Seed** (epics.md's own named examples — "frozen surfaces, gate mode, attempt counts"): `gate_mode`, `frozen_surfaces`, `max_dev_attempts`, `max_review_cycles`, `max_followup_reviews`. Seed fields live ONLY in a private `_seed: Mapping[str, PolicyField]`; `seed_view()` is the sole whitelisted accessor (AD-26, closing F-8: it is what lets `marshal config`/FR-54 and FR-53 validation range over every key without contradicting "reading a seed field outside the fold fails a meta-test").
- `worktree_seed_paths` is GENERATED, never literal (FR-50): `compose()` derives the base two paths from `project_slug` (`_bmad-output/projects/<slug>/implementation-artifacts`, `_bmad/custom/.active-project`) and appends any extra paths the project layer declares. Its winning layer is `"project"` only if the project layer contributed an extra path, else `"default"`.
- FR-53 validation is shape/range only (not filesystem/PATH resolution — FR-53 itself assigns that to preflight, Story 1.7): unknown top-level key in the project/flags layer -> `MRS-POLICY-001`; a non-string `verify_commands` entry, a `model_tier_map` stage name outside `{dev, review, triage}`, or a non-string model name -> `MRS-POLICY-002`; `gate_mode` outside `{none, per-epic, per-story-spec-approval}` or a negative/non-int attempt-count -> `MRS-POLICY-003`. All three classify `Verdict.UNEVALUABLE` (mirrors Story 1.2's `MRS-IDENT-*` reasoning: Marshal cannot determine operator intent, not that a gate failed). `compose()` never raises on malformed input — same "reported, not raised" convention as `resolve_feed`: an unknown key is excluded from composition (no field to fall back on); a known field with an out-of-range/malformed value falls back to Marshal's default value for that field. Either way, one `Finding` names the layer that introduced the problem.
- `content_hash` (a `sha256` hex digest over a canonical sorted-key JSON serialization of every field's value, static and seed) is `EffectivePolicy`'s AD-35 naming primitive. `cli/config.py` (the I/O boundary; `core/policy.py` stays pure) provides `materialize(policy, target_dir) -> Path`: writes `<target_dir>/policy-<content_hash>.json` via write-to-temp-then-`os.replace` and is a no-op if that exact path already exists — content-addressing makes write-once correct by construction, since an identical hash can only carry identical content. `target_dir` is caller-supplied (any directory), not a resolved "loop home" path — that resolution, the per-home `current` pointer file, and the "refuses when a live run holds an older hash" check all need the loop home (Story 1.4) and the run journal (Epic 3), neither of which exists yet.
- `marshal config` (`cli/config.py`, wired as `main.py`'s first subcommand): composes defaults + an optional `--project-policy PATH` TOML file (`tomllib`, read at the CLI boundary) + repeatable `--set KEY=VALUE` flags, resolves `project_slug` from `--project` or `BMAD_ACTIVE_PROJECT`, and prints every field (key, effective value, winning layer) via `seed_view()` + the static attributes, through the `Envelope` (AD-14), redacting any secret-shaped field. An optional `--materialize DIR` flag calls `materialize()` and reports the written (or already-present) path — giving the write-once mechanism a real caller rather than dead code.
- Secret redaction: a `SECRET_KEY_SUFFIXES` frozenset (`_TOKEN`, `_KEY`, `_SECRET`, `_PASSWORD`, case-insensitive suffix match against the field name) renders a fixed sentinel instead of the value. None of the 9 real fields match today; the mechanism is proven via a synthetic fixture, mirroring `findings.py`/`verdict.py`'s own "empty registry, mechanism proven via injected synthetic entries" precedent.
- `schemas/policy.json` mirrors `envelope.v1.json`'s style (draft 2020-12, `additionalProperties: false`, per-field `description`) and documents the 9-key closed shape plus the `{value, layer, raw_source}` `PolicyField` shape.
- `MRS-POLICY-001/002/003` are added to `findings.REGISTERED_CODES` and classified `Verdict.UNEVALUABLE` in `verdict._CLASSIFY_TABLE` — the registry's third real registrations (after Story 1.2's two), append-only.
- A meta-test (`tests/meta/test_ad26_seed_field_access_guard.py`, mirroring the AD-23 guard's AST-scan technique) fails the build if any module other than `core/policy.py` accesses the private `_seed` attribute directly instead of through `seed_view()`; a synthetic-violation fixture proves the detector fires (non-vacuous, matching every prior meta-test's convention).

**Block If:** None identified.

**Never:**
- Do not resolve an actual loop-home path, implement the per-home `current` pointer file, or the "refuses when a live run holds an older hash" check — those need the loop home (Story 1.4) and the run journal (Epic 3), neither of which exists yet. `materialize()` only writes a content-addressed file into a caller-supplied directory; deciding WHICH directory is a loop home is Story 1.4's job.

**Acceptance Criteria:**
- Given Marshal defaults, a project layer, and invocation flags, when `compose()` runs, then precedence is defaults -> project -> flags, last wins, with no fourth layer and no per-key reordering
- Given the same three inputs, when `compose()` runs twice, then both calls produce an `EffectivePolicy` with an identical `content_hash`
- Given a composed `EffectivePolicy`, when `marshal config` renders it, then every one of the 9 keys prints its effective value and winning layer, with any secret-shaped field redacted
- Given a composed `EffectivePolicy`, when any module outside `core/policy.py` accesses a seed-tagged field other than through `seed_view()`, then the AD-26 meta-test fails the build
- Given an active project slug, when `compose()` runs, then `worktree_seed_paths` is generated from that slug, never read as a literal -- switching projects requires no edit to any shared file
- Given a project or flags layer with an unknown key, an out-of-range value, or a malformed `model_tier_map` entry, when `compose()` runs, then the offending entry is excluded (unknown key) or its field falls back to the Marshal default (out-of-range/malformed value), and one registered finding names the layer that introduced it
- Given a composed `EffectivePolicy` and a target directory, when `materialize()` runs twice in a row, then the first call writes `policy-<content_hash>.json` and the second is a no-op that returns the same path (write-once, AD-35)

## Design Notes

**Why 9 fields, not the full `.bmad-loop/policy.toml` surface.** The real file (`~/.bmad-loops/pyforge-marshal/.bmad-loop/policy.toml`) carries ~25 keys across `[gates]`/`[limits]`/`[verify]`/`[notify]`/`[review]`/`[adapter]`/`[sweep]`/`[cleanup]`/`[scm]`/`[plugins]`/`[tui]`. Modeling all of them now would be Story 1.10's rendering-mapping job done backwards, and epics.md's own Deps line (`S-1.1` only) and Effort (`M`) don't support that scope. The 9 chosen keys are the ones FR-49/50/51/53/54 and AD-26's own parenthetical name explicitly: 4 static (`verify_commands`, `worktree_seed_paths`, `merge_subject_template`, `model_tier_map` -- FR-50/51's named examples) + 5 seed (`gate_mode`, `frozen_surfaces`, `max_dev_attempts`, `max_review_cycles`, `max_followup_reviews` -- AD-26's literal "frozen surfaces, gate mode, attempt counts"). Story 1.10 maps this bounded vocabulary onto the harness's larger key set; it does not require this story to have anticipated every harness key first.

**Why `seed_view()` already exists in the architecture text (F-8).** The 2026-07-25 adversarial review flagged AD-26 ("reading a seed field outside the journal fold fails a meta-test") as directly contradicting AD-16/FR-54 ("`marshal config` prints every key") and FR-53 ("validation ranges over every field") in the *same* acceptance-criteria block. The architecture's own resolution added `EffectivePolicy.seed_view()` as the whitelisted display/validation accessor before this story was ever drafted -- this story is what actually builds and meta-test-guards it, not a design decision made here from scratch.

**Static/seed storage split, not a uniform tag on one flat mapping.** A single `fields: Mapping[str, PolicyField]` with a `tag` attribute per entry would make the AD-26 guard's AST scan need to know WHICH keys are seed-tagged -- brittle, and it would have to special-case every new seed key added later. Splitting storage (public attributes for static, a private `_seed` mapping for seed) makes the guard's job purely structural: flag any non-`core/policy.py` access to the literal attribute name `_seed`, exactly mirroring the AD-23 guard's "flag a structural shape, not a semantic judgment" style.

**`compose()` returns `(EffectivePolicy, findings)`, not a raising function.** Matches `resolve_feed()`'s exact "malformed entries are reported, never raised" convention (Story 1.2) rather than inventing a second error-handling style in the same package.
