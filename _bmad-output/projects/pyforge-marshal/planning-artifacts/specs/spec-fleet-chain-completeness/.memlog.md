- (note) Source: docs/dreams/fleet-chain-completeness.md, reassigned 2026-08-02 from Herald to Marshal ownership — it is BMAD-chain governance machinery (Dream->Spec->Research->Brief->PRD->Architecture->Epics regeneration), Marshal's harness/governance domain per AGENTS.md, not Herald's communication-face scope.
- (capability) CAP-1 orchestrated chain regeneration: from a consolidated Dream, run bmad-spec -> bmad-prd -> bmad-architecture -> bmad-create-epics-and-stories in sequence, each phase's output feeding the next, non-interactively. Success: a single invocation against a consolidated Dream produces a coherent Spec/PRD/Architecture/Epics chain with no manual hand-off between phases.
- (capability) CAP-2 code-status preservation: regenerating the planning chain must not clobber existing Code implementation status (shipped versions, v1.0 markers, story completion state) recorded in epics.md. Success: re-running the workflow against an already-partially-implemented project leaves every story's done/in-progress/backlog status exactly as it was before the run.
- (capability) CAP-3 chain-completeness audit mode: a verify-only pass, independent of regeneration, answers whether a project's 8-layer chain (Dream/Spec/Research/Brief/PRD/Architecture/Epics/Code) is complete, coherent, and free of orphaned or stale artifacts, without generating or changing anything. Success: run in audit mode against any of the 8 stations and get a pass/fail per contract checkpoint, matching what a manual dream-chain-check + reading would find.
- (capability) CAP-4 orphan detection with review-gated cleanup: identify artifacts the regenerated chain no longer references (old spec folders, epics from replaced specs, dream-deleted references) and stage their removal for human review -- never auto-delete, never auto-commit or auto-push. Success: after a consolidation run, the operator sees a named list of orphan candidates and an unstaged/reviewable diff, and nothing is deleted or committed without their explicit action.
- (capability) CAP-5 configurable per-project invocation: project_slug, dream_path, preserve_code_status (default true), auto_commit (default false), delete_orphans (default true-with-review-pause) are parameters, not hardcoded per station. Success: the same workflow definition runs unmodified against any of the 8 stations by varying only its parameters.
- (constraint) Wrap, never absorb: this workflow orchestrates bmad-spec/bmad-prd/bmad-architecture/bmad-create-epics-and-stories in sequence; it must never reimplement any of their derivation logic itself.
- (constraint) The memlog-derivation invariant is not bypassed. bmad-spec/bmad-prd derive SPEC.md/prd.md from an append-only .memlog.md and re-render on each run; this workflow must drive that same append-then-rerender path per phase, never hand-overwrite a downstream artifact directly, or it breaks the exact invariant fleet-chain-completeness exists to protect.
- (constraint) Derive completeness signals, do not declare them (EXEMPLAR-STANDARD.md provenance rule). CAP-3's audit-mode pass/fail per layer must be computed by checking real artifact presence and cross-references each run, never a cached or hardcoded per-station table.
- (constraint) If a future implementation regenerates more than one station's chain in the same run, each station's phases must be addressed by literal _bmad-output/projects/<slug>/planning-artifacts/... paths with BMAD_ACTIVE_PROJECT=<slug> passed per invocation, never by concurrent scripts/bmad-switch calls (CLAUDE.md parallel-agent physical-path rule) -- within one station's own chain the 8 phases are inherently sequential (each phase's output feeds the next) so this constraint only bites at the cross-station level.
- (constraint) Never auto-commits or auto-pushes. Cleanup (CAP-4) stages orphan removal for review; regeneration output (CAP-1) is left for the operator to review and commit, matching the Dream's own explicit non-goal.
- (note) Non-goals carried verbatim from the source Dream's own What This Is Not section: not a code generator (Code stays hand-written); not an auto-committer; not a replacement for human judgment on specs/epics; not a one-way pipeline (re-runnable whenever the Dream changes).

The Dream names the 4 skills to orchestrate (bmad-spec, bmad-prd, bmad-architecture, bmad-create-epics-and-stories) but not how the orchestrator itself is invoked non-interactively -- a new bmad-* skill, a Workflow tool script, or a subagent chain is undecided.
- (question) Q2 -- error/resume semantics undefined. If a mid-chain phase (e.g. PRD generation) fails or needs human clarification, the Dream does not specify whether the run halts, retries, or resumes from that phase on a second invocation.
- (question) Q3 -- Phase 8's git integration is unspecified. Dream says cleanup 'stages for human review in IDE' but does not say whether that means git add without commit, an unstaged working-tree diff, or something else -- concrete git-integration behavior is undecided.
- (question) Q4 -- Phases 2 (Research Generation) and 3 (Brief Generation) have no confirmed 1:1 skill mapping.
