- (note) CORRECTION on the record (2026-09-08, found by CI on PR #1082). CAP-5's rationale as written -- 'no environment in this repo has ever installed, built or exercised this package on 3.12' -- was WRONG. Three workflows did: pyforge-core.yml, pyforge-steward-five-tier.yml and pyforge-steward-fresh-clone.yml each ran actions/setup-python at 3.12 and pip-installed the packages OUTSIDE pixi, so raising requires-python made pip refuse with "Package 'pyforge-core' requires a different Python: 3.12.14 not in '>=3.14'". The claim was derived from pixi.toml alone and never checked against .github/workflows/, which is exactly the kind of unverified assertion CAP-5 exists to stop. The finding itself stands -- those three lanes were testing a floor the estate does not ship, and detectors.yml already ran 3.14 -- so the fix is to bump them to 3.14 rather than restore >=3.12.
