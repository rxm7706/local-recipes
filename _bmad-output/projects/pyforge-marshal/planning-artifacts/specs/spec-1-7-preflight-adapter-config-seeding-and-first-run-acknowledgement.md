## Intent

**Problem:** `marshal init` (1.4/1.5) provisions a loop home but never proves it can actually RUN one: the harness binary might be missing, the configured adapter's CLI might not be on PATH, its gitignored config (MCP servers, hook settings) is absent from the fresh worktree, and nobody has confirmed the adapter's first-run trust dialog was ever answered -- discovered today only when an unattended session times out 90 minutes in.

**Approach:** A new `marshal preflight <slug>` command resolves the composed policy (S-1.3) and the configured adapter's declarative profile (via `adapters/harness_bmadloop.py`, AD-3/AD-19 -- the sole module permitted to invoke the `bmad-loop` binary or import its package), reports six presence/resolvability facts, copies the adapter's declared gitignored seed files into the home (real copies, never symlinks -- ports `bmad_loop.install.provision_worktree`'s own copy-when-absent semantics one layer up, from Marshal's loop home to the main checkout), and blocks on an unacknowledged adapter first-run requirement, recording acknowledgement in a new machine-scoped (not git-tracked) state file per AD-37's fourth write target.

## Boundaries & Constraints

**Always:**
- `marshal preflight <slug>` (mirrors `init`'s slug-argument convention) reports, in `data`: `harness_version`, `multiplexer` (`{backend, available}`), `adapter` (`{name, binary_present}`), `story_feed` (`{resolvable, error}`), `verify_commands` (per-command `{command, resolvable}`), `main_checked_out_once` (bool), `seed_files` (per-file `{path, status: copied|skipped|failed}`), `first_run_acknowledged` (bool). Every check populates `data` regardless of outcome; only a FAILING check also emits a registered finding.
- `effective` (the composed `EffectivePolicy` S-1.3's ACs require) is obtained by calling `policy.compose(project_slug=slug, project=<parsed TOML>, flags={})`, where `<parsed TOML>` comes from the SAME lookup `cli/config.py` already uses (`conventional_project_policy_path(slug)`, i.e. `planning-artifacts/marshal-policy.toml`) -- reused via import, never re-derived; preflight passes no flag layer (`--acknowledge` is not a policy field).
- The configured adapter's NAME is resolved by calling the existing pure `adapters.harness_bmadloop.render_policy_toml(effective)` (Story 1.10, unchanged) in-memory and reading `[adapter].name` from the parsed result -- never a second, independent guess at which adapter is configured. This does NOT write `.bmad-loop/policy.toml`; `marshal config --write-harness-policy` remains the only writer of that file (Story 1.10's own surface, untouched).
- Seed files and their first-run note come from `bmad_loop.adapters.profile.get_profile(name, project=home)` (packaged profile TOML, overlaid by the home's own `.bmad-loop/profiles/*.toml` if present) -- never a hard-coded per-adapter list (AD-19, FR-7). Harness presence/version, adapter-binary presence, and verify-command resolvability are all one generic `shutil.which`-backed primitive (`HarnessPort.binary_present`) -- no adapter-specific branching.
- Multiplexer backend availability and story-feed resolvability reuse the harness's OWN detection (`bmad_loop.adapters.multiplexer.get_multiplexer`/`bmad_loop.sprintstatus.load` respectively) rather than a parallel reimplementation (FR-52: one seam) -- both calls live in `adapters/harness_bmadloop.py` only.
- Seed-file copying is reconcile-then-act (AD-21): a file already present at the home's destination path is reported `skipped`, never overwritten -- an operator's local edit to a seeded file survives a re-run. Copies are REAL bytes (`shutil.copy2`), never symlinks, matching `bmad_loop.install.provision_worktree`'s own semantics for the identical class of gitignored config.
- The first-run acknowledgement is a single combined gate per adapter (first-run trust requirement + a Marshal-authored sustained-automation caveat, shown together): `marshal preflight <slug> --acknowledge <adapter-name>` records it (idempotent) in a NEW machine-scoped, gitignored JSON file (AD-37's fourth write target; default `~/.local/state/pyforge-marshal/adapter-acknowledgements.json`, overridable via `MARSHAL_STATE_HOME`) BEFORE the check runs in the same invocation, so one command can both acknowledge and pass. An adapter absent from that file is unacknowledged.
- `bmad-loop` becomes a declared runtime dependency of `pyforge-marshal` as of this story (`pyproject.toml`, range `>=0.9.0,<0.10` matching AD-3/Story 1.9's planned conda pin) -- `adapters/harness_bmadloop.py` now hard-imports it (lazily, inside the functions that need it) to read profiles/multiplexer/story-feed data per AD-19; `pyforge-deps-test` (already one of this project's own verify_commands) fails on an undeclared hard import, making this a correctness requirement, not a style choice. Update the stale `pyproject.toml` comment claiming "no runtime dependency on bmad-loop exists yet."
- `main` checked out twice reuses `VcsPort.list_worktrees` (Story 1.6): a violation if any worktree OTHER than the repo root itself has `branch == "main"`.
- Policy validation (S-1.3) runs as part of preflight: `policy.compose()`'s own `MRS-POLICY-*` findings merge into preflight's finding list and its own verdict tier -- reused, never reclassified.
- Every check must complete well inside NFR-14's 10s budget: presence/resolvability checks only (`shutil.which`, one `--version` subprocess call, one YAML parse) -- never launch the adapter CLI itself.
- New finding codes `MRS-PREFLIGHT-001..009`, all classify `Verdict.ERROR` (a real prerequisite check ran and failed -- same tier as `MRS-INIT-003/004/005`/`MRS-HOMES-*`, not "could not evaluate").

**Block If:** none -- every decision here (adapter-name resolution path, seed-copy semantics, ack persistence location, dependency declaration) ports an already-adjudicated convention (Story 1.10's render function, `bmad_loop.install`'s own copy semantics, AD-37's enumerated fourth write target, `pyforge-deps-test`'s existing rule) rather than requiring a new product decision.

**Never:**
- Never invoke the adapter CLI itself (only `shutil.which` presence + the harness's OWN `--version`) -- launching it could itself trigger the very first-run dialog this story exists to gate ahead of time.
- Never treat "harness version outside the declared `>=0.9.0,<0.10` range" as anything but blocking -- the range IS the boundary of supported; there is no reachable "outside range but non-major" input for a pre-1.0 pin to justify a second, non-blocking tier (a simplification from FR-57's "prominent warning vs. major mismatch" wording, recorded here since nothing narrower is falsifiable today).
- Never resolve "stories mode" (`--spec`/`[stories].source == "stories"`) story feeds -- Marshal's own policy composition has no field driving that mode; only the default `sprint-status.yaml` path is checked.
- No remediation beyond naming the gap (mirrors `marshal homes`): preflight never fixes a missing binary, never auto-answers a first-run dialog, and the `--acknowledge` flag records ONLY the operator's own explicit assertion, never an inferred one.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Fully converged home, adapter already acknowledged | Harness + adapter binary on PATH, in-range version, tmux available, valid sprint-status.yaml, all verify commands resolvable, seed files already present, ack file has the adapter | Exit 0, all `data` fields report success, zero findings | n/a |
| Harness binary absent | `shutil.which("bmad-loop")` is `None` | Exit non-zero, `MRS-PREFLIGHT-001` | n/a |
| Harness version outside `>=0.9.0,<0.10` | `bmad-loop --version` reports e.g. `0.10.2` | Exit non-zero, `MRS-PREFLIGHT-002` naming both versions | n/a |
| Adapter binary absent | Configured adapter's `binary` (e.g. `claude`) not on PATH | Exit non-zero, `MRS-PREFLIGHT-004` naming the adapter and binary | n/a |
| Unacknowledged adapter, no `--acknowledge` given | Adapter absent from the ack state file | Exit non-zero, `MRS-PREFLIGHT-008` naming the adapter's first-run note + the sustained-automation caveat text | n/a |
| `--acknowledge claude` supplied this run | Same as above, plus the flag | Ack recorded first, `data.first_run_acknowledged = true`, that check passes this and every future run | n/a |
| Seed file already present | `.mcp.json` exists in the home | `data.seed_files` reports that entry `skipped`; no write | n/a |
| Seed file copy fails (unwritable home) | `fs.copy_file` raises `FsError` | Exit non-zero, `MRS-PREFLIGHT-009` naming the path | Command halts after reporting the failure |
| `main` checked out twice | A second worktree also has `branch == "main"` | Exit non-zero, `MRS-PREFLIGHT-007` naming both paths | n/a |
| Story feed missing/unparseable | No `sprint-status.yaml`, or invalid YAML shape | Exit non-zero, `MRS-PREFLIGHT-005` with the harness's own error text | n/a |
| Loop home not provisioned | `<loop-home-root>/<slug>` is not a directory | Exit non-zero, `MRS-PREFLIGHT-009` telling the operator to run `marshal init` first; no further checks run | n/a |

## Spec Change Log

**2026-07-31, implementation.** Two discoveries during implementation, neither touching the intent-contract's Intent/Boundaries & Constraints/I/O matrix (both are Code Map / tooling-configuration level, recorded here for the next reader rather than reinterpreted silently):

1. **`HarnessPort` needed a seventh method, `adapter_binary`, beyond the Code Map's literal six (`binary_present`, `harness_version`, `multiplexer_backend_available`, `adapter_seed_files`, `adapter_first_run_note`, `story_feed_error`).** The intent-contract's own `data.adapter.binary_present` fact requires the adapter's REAL binary name -- and two of the six packaged profiles diverge from their adapter name (`antigravity` -> binary `agy`, `opencode-http` -> binary `opencode`). The Always bullet also pins `binary_present` as the ONE generic, adapter-blind presence primitive shared by the harness/adapter/verify-commands checks, so resolving the binary NAME needed its own seam rather than overloading `binary_present` with adapter-specific logic. `adapter_binary(name, project) -> str` closes this, symmetric with the two sibling profile-derived methods.
2. **The AD-3 import-linter contract (`pyproject.toml`) needed `allow_indirect_imports = true` added.** Its default (indirect chains checked) never mattered before this story, because `harness_bmadloop.py` carried zero real `import bmad_loop` statements until now (Story 1.10 only ever rendered a vendored template). The moment `BmadLoopHarness`'s methods added real, lazy `bmad_loop` imports, the PRE-EXISTING `cli.config -> harness_bmadloop` edge (Story 1.10's `write_policy_toml` wiring) became a transitive "cli imports bmad_loop" violation under strict checking, even though `cli.config`/`cli.init` never write that import themselves. AD-3's own wording ("only ... may invoke the harness binary, import its package") is about direct import authorship, not about calling into the seam's public API -- the whole point of having one -- so this flag makes the contract's enforcement match its stated intent (`cli`/`core`/`ports`/`supervisor` still may never themselves write `import bmad_loop`) rather than loosen it.

## Design Notes

**Why adapter-name resolution goes through `render_policy_toml` rather than a new field.** Marshal's `EffectivePolicy` deliberately owns only 9 keys (Story 1.3); `[adapter].name` is not one of them -- today it is always the vendored template's baseline (`"claude"`), and the only code path that could ever diverge from that baseline is the SAME rendering function preflight now calls in-memory. Reusing it (rather than re-deriving "which adapter" from a second source) guarantees preflight and `marshal config --write-harness-policy` can never disagree about which adapter is configured.

**Why seed-file copies are real bytes, never symlinks.** `bmad_loop.install.provision_worktree` already established this exact semantics for the identical problem one layer down (bmad-loop's own per-story worktrees needing the main repo's gitignored MCP/CLI config) -- a symlinked `.claude/settings.json` would mean an edit inside the loop home silently mutates the main checkout's copy, the opposite of the isolation Epic 1 exists to guarantee.

**Why the first-run acknowledgement is machine-scoped, not per-loop-home.** The underlying fact -- "has the operator answered this adapter's trust dialog on this machine" -- is a property of the OPERATOR'S MACHINE and the ADAPTER, not of any one project's loop home (the same `claude`/`codex` binary is shared across every home). AD-37 already enumerates exactly one further write target beyond the loop home / Tier-3 store / promotion targets for this class of fact ("a single declared machine-scoped path... raw, per-host, per-adapter observations"); recording the acknowledgement there means acknowledging `claude` once covers every project's loop home, matching FR-47's "presented once per adapter" (not "once per home").
