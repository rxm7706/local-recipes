## Intent

**Problem:** `marshal factory spin` (Story 3.3) launches `bmad-loop run` detached and then walks away — its own Never clause says so explicitly ("nothing watches the process after this story"). FR-11 requires every started run to get a supervisor for its lifetime, and NFR-4/NFR-5 require that supervision be a *structural* property (a separate OS process with no control channel back into it), not a convention nobody enforces. Today `supervisor/__init__.py` is an empty Story-1.1 stub and nothing ever spawns it.

**Approach:** Give the `supervisor/` package a real, launchable entry point that `cli/spin.py` detach-spawns as the last step of a successful launch (mirroring `harness.spin`'s own detach recipe). The supervisor verifies it is watching a run Marshal actually started, journals its own attach/heartbeat/detach (liveness is journaled, never silent), and gathers clock/process/pane-content/mtime samples as plain injected values each tick — proving the seam AD-20's pure decision core will consume, without yet making any decision (that is Story 3.5's `core/supervise.py`, explicitly out of this story's Surface).

## Boundaries & Constraints

**Always:**
- `ports/process.py::ProcessPort` gains two methods (docstring updated to say "Story 3.4 adds two more"): `is_alive(pid: int) -> bool` (never raises — a probe that finds no such process returns `False`, one that exists but isn't ours still returns `True`) and `spawn_detached(argv: Sequence[str], *, cwd: Path, log_path: Path) -> int` (returns the spawned pid; mirrors `adapters/harness_bmadloop.py::spin`'s exact recipe — `Popen(..., start_new_session=True, stdin=DEVNULL, stdout=stderr=log_file)`, never waited on; raises `ProcessError` only when the process could not be launched at all — the same split `run()` already documents). Implemented solely by `PosixProcess` (AD-4).
- `ports/clock.py` (NEW): `ClockPort` Protocol, one method `now() -> datetime` (tz-aware UTC). `adapters/clock_system.py` (NEW): `SystemClock`, backed by `datetime.now(timezone.utc)`.
- `ports/observer.py` (NEW): `SessionObserverPort` Protocol — `pane_content(session: str) -> str | None` (a named multiplexer pane's captured text, passed through `core.egress.to_redacted` before returning — AD-34 requires pane-derived content redacted at capture, before it enters `core`; `None` if the session/pane can't be found) and `mtime(path: Path) -> float | None` (a path's last-modified Unix timestamp, `None` if absent). `adapters/observer_mux.py` (NEW): `MultiplexerObserver` — shells out to `tmux capture-pane -t <session> -p` via its own `subprocess` call (adapters never import each other, AD-4 — this cannot reuse `process_posix.py`) and `Path.stat().st_mtime`; never raises, matching every other observation-only port.
- `supervisor/__init__.py` (EDIT) drops the "reserved for a later story" docstring; `supervisor/__main__.py` (NEW) is the sidecar: `python -m pyforge.marshal.supervisor <home> <slug> <run_id> <watched_pid> <log_path>`. On start it reads the run's `journal.jsonl` once (`FsPort.read_text` + `core.journal.fold`); if no `phase: outcome`, `kind: "run-launch"` entry exists for that run directory, it exits immediately (code 0, no write) — the AC's "inert on a run it did not start." Otherwise it appends one `observation` entry (`kind="supervisor-attach"`, payload `{pid, watched_pid}`) via the same `prepare_for_write`/`FsPort.append_line` path `cli/spin.py` already uses (no second write mechanism, `fsync=False` — `Phase.OBSERVATION` carries no `intent_id` and needs no write-before-act pairing). It then loops while `ProcessPort.is_alive(watched_pid)`: sleep a fixed 60 s tick (no policy knob exists for this yet), sample `ClockPort.now()` plus `SessionObserverPort.pane_content`/`mtime` (proving the injection seam — none of these samples drive a decision in this story), and append one `observation` (`kind="supervisor-heartbeat"`, payload `{pid, watched_alive: true, sampled_at}`). When the watched process is no longer alive it appends one final `observation` (`kind="supervisor-detach"`, payload `{pid, reason: "watched-process-exited"}`) and exits.
- The supervisor reads its own argv once at start and touches no other externally-writable input for its own control flow — no `stdin` read, no socket, no named pipe, no re-polling of anything whose content could redirect its behaviour (the journal it reads once is Marshal's own prior write; the journal it appends to afterward is append-only, so its own future entries cannot be edited to control it). A new `forbidden`-type import-linter contract (`pyproject.toml`) forbids `pyforge.marshal.supervisor` from importing `pyforge.marshal.cli` — the session's own front door already has no way to call back into a separate OS process's internals; this makes that absence structural. `tests/meta/test_ad3_ad4_import_linter.py`'s `test_pyproject_declares_exactly_two_contracts` becomes `three`; a new `tests/meta/test_ad9_supervisor_no_control_channel.py` asserts the new contract's shape plus that the `supervisor` package imports no `socket`/`multiprocessing` module and calls neither `input()` nor `sys.stdin.read()`.
- `cli/spin.py::run_spin`'s detached path (never under `--foreground`, which journals nothing) calls a new, injectable `ProcessPort` (`process: ProcessPort | None = None`, default `PosixProcess()`, matching `fs`/`harness`'s own DI convention) to `spawn_detached([sys.executable, "-m", "pyforge.marshal.supervisor", str(home), slug, run_id, str(spin_result.pid), str(supervisor_log)], cwd=home, log_path=supervisor_log)` as the LAST step of `run_spin`, after the `run-launch` outcome entry append is attempted (whether or not that append itself succeeded) — never right after `harness.spin()` returns, which would race the supervisor's own inert-check against an outcome entry that isn't journaled yet. `data["supervisor_pid"]` is added to the envelope/text report. A spawn failure registers a NEW `MRS-SPIN-007` (`Verdict.WARN` — the harness launch itself already succeeded; losing supervision degrades the run to unsupervised, never invalidates the launch, matching architecture.md's "a supervisor crash degrades to an unsupervised run ... never to a corrupted one").
- Register `MRS-SPIN-007` in `core/findings.py`/`core/verdict.py` (`Verdict.WARN`), joining the six existing `MRS-SPIN-*` codes.

**Block If:** none — every decision here follows an explicit architecture rule (AD-9, AD-20, AD-25, AD-30, AD-34) or extends an already-shipped mechanism (`core.journal`'s append/fold, `cli/spin.py`'s own detached-launch recipe); no product ambiguity requires a human decision.

**Never:**
- Do not implement idle/budget/escalation decision logic (nudge, stop-and-retry, defer) — that is `core/supervise.py`, Story 3.5's own title and Surface, not this story's.
- Do not implement `marshal status`'s "dead supervisor" reporting — that command doesn't exist yet (a later epic's FR-36..40 scope). This story only ensures the journal carries what a future `status` needs (a `supervisor-heartbeat` timestamp plus the supervisor's own pid to check liveness against).
- Do not add a policy knob for the poll interval — no `EffectivePolicy` field exists for it; a fixed 60 s constant is the only defensible value with no real caller to size a knob against (mirrors this codebase's own "don't invent unused surface" precedent).
- Do not resolve the deferred concurrent-double-spawn question (`deferred-work.md`) — no AC here asks for it, and it is a genuine product decision, not a mechanical gap.
- Do not touch `core/journal.py`'s write/fold mechanism itself — reuse `prepare_for_write`/`append_line`/`fold` exactly as shipped; no new sidecar or entry-shape rule.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Normal attach | `spin` launches successfully | supervisor starts detached, journals `supervisor-attach`, then heartbeats until the harness exits | No error expected |
| Supervisor spawn fails | `spawn_detached` raises `ProcessError` | `MRS-SPIN-007`, `Verdict.WARN`; the harness run is unaffected, `spin` still returns | Non-blocking WARN, harness keeps running |
| Invoked against a run id Marshal never started | no `run-launch` outcome entry in that run's journal | supervisor exits immediately, code 0, writes nothing | Inert, not an error |
| Watched process already dead at first check | `ProcessPort.is_alive(watched_pid)` is `False` on the first loop iteration | supervisor journals `supervisor-attach` then immediately `supervisor-detach` (`reason: watched-process-exited`), exits | No error expected — a fast-exiting run is a valid outcome |
| Journal append fails mid-loop | `FsPort.append_line` raises `FsError` | supervisor logs to its own redirected log and exits rather than looping forever against a broken journal | Process exits non-zero; absence of further heartbeats plus a dead pid is later detectable |
| Multiplexer pane unavailable | no session by that name | `pane_content` returns `None`; the tick proceeds without it, never raises | No error expected |

**Acceptance Criteria:**
*(Story 3.4's ACs from `epics.md`, preserved as the contract of record.)*
- Given a run started by Marshal, when the supervisor attaches, then it runs as a separate OS process, parented to neither the agent session nor the invoking shell (AD-9)
- And it cannot be disabled, silenced, or reconfigured from inside the agent session -- a test asserts no control channel exists from session to supervisor
- And its inputs are externally observable only: multiplexer pane content, file modification times, process liveness, and adapter-written usage files
- And supervisor liveness is itself journaled; a dead supervisor is a reported condition surfaced by `status`, never silence, and degrades the run to unsupervised rather than corrupt
- And the supervisor is inert on a run it did not start
- And its only write is the journal
- And clock, process state and observations reach the decision core as injected values (AD-20)
