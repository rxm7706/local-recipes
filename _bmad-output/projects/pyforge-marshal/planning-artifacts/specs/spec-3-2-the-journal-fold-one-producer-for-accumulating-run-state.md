## Intent

**Problem:** Story 3.1 shipped only the journal's WRITE side (`core/journal.py`'s `mint_run_id`/`build_entry`/`prepare_for_write` + `FsPort.append_line`/`create_dir_exclusive`); nothing reads a run's journal back into a value any consumer can trust. `cli/gate.py`'s `--run` flag stays stubbed (`MRS-GATE-005`), and every future consumer (Story 2.3's frozen-surface scope check, Epic 4's spec-promotion/reconciliation stories) would otherwise be tempted to re-derive "what happened in this run" independently — exactly the two-consumers-disagree failure AD-5/AD-26 exist to prevent.

**Approach:** Add a pure `fold(lines, sidecars) -> FoldResult` to `core/journal.py`: parse each raw journal line, pair `outcome` entries to their `intent` by `intent_id` only (AD-28), quarantine any line that fails to parse/validate or references a missing sidecar blob — scoped to its own `(story, kind)`, or the whole run when neither recovers (AD-30) — and expose the result via a generic `by_kind`/`for_story`/`is_evaluable` query surface rather than inventing kind-specific accessors no real writer exists to populate yet (mirrors Story 3.1's own "pure mechanism, zero real caller" precedent).

## Boundaries & Constraints

**Always:**
- `fold(lines: Sequence[str], *, sidecars: Mapping[str, str | None] = MappingProxyType({})) -> FoldResult` lives in `core/journal.py`, importing only what that module (plus `.identity.normalize`/`MalformedStoryKeyError`, `dataclasses.replace`, `types.MappingProxyType`) already permits under AD-4 (enforced by the existing import-linter contract). `lines` is the run's journal file already split into individual JSON-line strings by the caller — no file I/O here. `sidecars` maps a `sidecar_ref` relative path to its already-read blob text, or is absent/`None` when the caller could not read it. A bare `str` for `lines` raises `TypeError` (mirrors `identity.resolve_feed`'s own bare-str guard).
- Each line is independently parsed and reconstructed into a `JournalEntry` via the SAME invariants `build_entry` already enforces (`id`/`intent_id` shape, `phase` vocabulary, timestamp pattern, story-key form via `identity.normalize` — never a second parser, AD-23). Any failure at any step quarantines that ONE line; it never aborts the fold or drops any other entry.
- A quarantined line's scope is a best-effort-recovered `(story, kind)` pair, read directly off the raw JSON even when full validation failed (e.g. a document missing `run_id` but carrying valid `story`/`kind` fields still scopes narrowly). When EITHER cannot be recovered, scope is `(None, None)` — the whole run (AD-30's explicit widening rule; no partial-recovery heuristic beyond this).
- Every quarantined line / missing sidecar / invalid-JSON sidecar produces one registered `Finding`: `MRS-JOURNAL-001` (an unparseable or invalid line) or `MRS-JOURNAL-002` (a missing or invalid-JSON sidecar blob) — register both in `core/findings.py::REGISTERED_CODES` and classify both `Verdict.UNEVALUABLE` in `core/verdict.py::_CLASSIFY_TABLE` (AD-8: unevaluable is failure, never silently dropped), following each module's existing docstring-narrative convention.
- `intent`/`outcome` pairing is EXCLUSIVELY by `id`/`intent_id` equality — a `set`/`dict` lookup over `JournalEntryId` (already hashable) — no positional, timestamp-adjacency, or ordinal pairing anywhere (AD-28). An `outcome` whose `intent_id` matches no known `intent` entry's `id` — including a forged/self-referencing outcome whose `intent_id` equals its own `id` (closing the Story 3.1 review's deferred self-reference gap, `deferred-work.md`) — surfaces in `FoldResult.orphaned_outcomes`, never silently paired or dropped.
- `FoldResult.entries` is every evaluable entry (sidecar-resolved where applicable) in AD-28's total order `(ts, writer_id, counter)` — a plain tuple sort, since `ts` is already Story 3.1's one canonical, string-sortable spelling. `FoldResult.open_intents` is every `intent`-phase entry whose id is never referenced by an `outcome.intent_id` — reported, never inferred closed. `FoldResult.by_kind(kind)` / `FoldResult.for_story(story)` / `FoldResult.is_evaluable(story, kind)` are the generic query surface a future real writer's consumer uses.
- Unit-test the full I/O & Edge-Case Matrix in `tests/unit/test_fold.py`, using SYNTHETIC entries for the 9 illustrative "run state" domains the epic names (story transitions, gate verdicts, escalations, deferrals, consumption, supervisor actions, frozen surfaces, attempt counts, gate mode) — proving the generic mechanism handles all of them structurally, mirroring `core/policy.py`'s own "mechanism proven synthetically" precedent for `SECRET_KEY_SUFFIXES` (none of the 9 has a real writer yet).
- Close the `deferred-work.md` entry recording the `intent_id` self-reference gap (now resolved via `orphaned_outcomes`); leave Story 3.1's other four deferred entries untouched (out of this story's scope).

**Block If:** none — every decision here follows an explicit architecture rule (AD-4/AD-8/AD-23/AD-26/AD-28/AD-30) or an established codebase precedent (synthetic-mechanism proof, bare-str guard, docstring registries); no product ambiguity requires a human decision.

**Never:**
- Do not wire `cli/gate.py`'s `--run` flag to call `fold()` — that stub (`MRS-GATE-005`) stays exactly as Story 2.1 left it. Wiring the frozen-surface scope check is Story 2.3's own title and scope (itself blocked ON this story, not the reverse).
- Do not invent kind-string vocabulary for story transitions, gate verdicts, escalations, deferrals, consumption samples, or supervisor actions — no story that would emit any of them (2.3, 3.3, 3.4, 3.6, 3.7, 3.8, every Epic 4 story) exists yet, and guessing their `kind` spelling now is the same unattended surface-widening Story 3.1's own Never clause refused for the `sessions/` namespace. `by_kind`/`for_story` are the generic surface those future stories call once they are real.
- Do not merge `EffectivePolicy.seed_view()`'s initial values into `FoldResult`. AD-26 requires the fold to be the sole producer of the LIVE value, but no story yet defines a `freeze-declared`/`gate-mode-changed` observation kind to fold on top of the seed — inventing one now has the identical no-real-caller problem as the kind vocabulary above. This story ships the fold that `core/journal`'s eventual seed-merging consumer (2.3) will call; it does not perform that merge itself.
- Do not add a new `FsPort`/adapter method. `fold()` takes already-read `lines`/`sidecars` as plain data; a future caller reads the run's journal file and any sidecar blobs via the EXISTING `FsPort.read_text` (already returns `None` for an absent path) — no new primitive needed.
- Do not detect or guard against a journal file mixing entries from more than one `run_id` — `fold()` trusts its caller passes exactly one run's own lines, the same "caller already gathered the right facts" convention every other pure-core function in this package follows.
- Do not add a NEW meta-test for "exactly one producer" (AD-26). The existing Story 1.3 guard (`test_ad26_seed_field_access_guard.py`) already fails the build if any module OTHER than `core/policy.py` accesses `_seed` directly; this story's `fold()` never touches `_seed`/`EffectivePolicy` at all, so it needs no exemption and the guard continues to hold unmodified — see Design Notes.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Matched intent+outcome | an `intent` line, then an `outcome` line whose `intent_id` equals the intent's `id` | both appear in `entries`; the intent's id is NOT in `open_intents` | No error expected |
| Lone unmatched intent | one `intent`-phase line, no closing outcome | the entry appears in `open_intents` | No error — reported, never inferred closed |
| Orphaned/self-referencing outcome | an `outcome` line whose `intent_id` matches no known `intent` id (including `intent_id == id`) | the entry appears in `orphaned_outcomes` | No error, no false pairing |
| Malformed JSON line | a line that is not valid JSON | excluded from `entries`; one `MRS-JOURNAL-001` finding scoped `(None, None)` (whole run) | Quarantined, never raised |
| Valid JSON, invalid shape, story+kind recoverable | dict missing `run_id` but with valid `story`/`kind` fields | excluded from `entries`; one `MRS-JOURNAL-001` finding scoped to that `(story, kind)`; other stories/kinds stay evaluable | Quarantined |
| Missing sidecar blob | payload is `{"sidecar_ref": "blobs/x.json"}`; `sidecars` has no entry (or `None`) for that path | excluded from `entries`; one `MRS-JOURNAL-002` finding scoped to that entry's `(story, kind)` | Quarantined, never "quarantine and continue" with the placeholder |
| Sidecar present and valid | payload references a sidecar; `sidecars[path]` is valid JSON text | the entry appears in `entries` with the original (large) payload restored | No error expected |
| Bare `str` for `lines` | `fold("not-a-list")` | — | `TypeError` |

*(Story 3.2's ACs from `epics.md`, preserved as the contract of record; parenthetical notes mark what this story satisfies.)*
- Given a journal, when the fold runs, then it produces queryable run state via `FoldResult` (generic `by_kind`/`for_story`/`is_evaluable` — no kind-specific accessor exists yet since no real writer emits story-transition/gate-verdict/escalation/deferral/consumption/supervisor-action entries, see Never)

- And `intent`/`outcome` pairing is by `intent_id` only — no positional or heuristic pairing exists anywhere (satisfied: `JournalEntryId` set/dict lookup; an unpaired outcome, including a self-reference, lands in `orphaned_outcomes`)
- And an unparseable line is quarantined, surfaced as a registered finding, and makes its own story key and decision domain unevaluable — records provably unaffected stay evaluable; when the line's story or kind cannot be recovered the scope widens to the whole run (satisfied: `MRS-JOURNAL-001`, `(story, kind)` or `(None, None)` scoping)
- And a reference to a missing sidecar blob is the same class and takes the same treatment (satisfied: `MRS-JOURNAL-002`, same unevaluable tier, never resolved-and-continued)
- And the fold is a pure function over entries with no I/O (satisfied: `lines`/`sidecars` are caller-supplied plain data; no import beyond AD-4's allowed set)
- And a lone intent is reported as open, never inferred closed (satisfied: `FoldResult.open_intents`)

## Design Notes

**Why no new AD-26 meta-test.** The AC's "any module reading them from `EffectivePolicy` fails a meta-test" describes the ALREADY-SHIPPED Story 1.3 guard (`test_ad26_seed_field_access_guard.py`): it fails the build if any module other than `core/policy.py` accesses `EffectivePolicy._seed` directly. This story's `fold()` operates entirely over journal entries and never references `_seed` or even imports `EffectivePolicy` — so the existing guard continues to pass, unmodified, with no exemption needed. A second, purpose-built guard for "only `core/journal.fold` may compute frozen-surface/gate-mode run state" would have no concrete violation shape to scan for yet: no other module in the tree attempts that computation today (the seed-merge itself is out of this story's scope — see Never), and inventing a detector with nothing to detect is exactly the speculative-code this project's conventions avoid.

**Why `orphaned_outcomes`, not a construction-time self-reference check.** Story 3.1's review deferred "does `intent_id == id` construct without error?" to "whichever story actually pairs `intent_id` against real prior entries" (`deferred-work.md`). Rather than adding a special-cased equality check in `JournalEntry.__post_init__` (which cannot see other entries), the fold's own pairing logic resolves it for free: an intent lookup keyed by `id` will never find a match for an outcome referencing its own id (or any other id that isn't a real `intent`-phase entry), so it surfaces in `orphaned_outcomes` structurally, without inventing new construction-time state.

**Why scope widens to `(None, None)` rather than a partial recovery.** AD-30's text is literal: "when the quarantined line's story or kind cannot be recovered, the scope widens to the whole run." A line that recovers `kind` but not `story` (or vice versa) still cannot be narrowly scoped — there is no meaningful partial key — so it takes the same whole-run treatment as a line that recovers neither.
