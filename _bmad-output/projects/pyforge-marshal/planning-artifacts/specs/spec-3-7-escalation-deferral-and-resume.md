## Intent

**Problem:** bmad-loop's own engine pauses a whole run when a session raises a CRITICAL escalation and quietly defers an individual story it could not land -- but neither fact is externally observable today (3.5/3.6's tick loop never reads `state.json`'s `paused_stage`/`Phase.DEFERRED`), and bmad-loop's own `resume` command does not itself refuse to re-drive a run whose escalated story was never resolved -- it silently abandons that story as "already handled" and moves on (FR-15/16/17).

**Approach:** add a new `HarnessPort.run_status_snapshot` (mirrors Story 3.6's `usage_snapshot`) reading bmad-loop's `state.json` for the run-level pause and every currently-`Phase.DEFERRED` task; a new pure `core/supervise.py::evaluate_escalation` classifying that read; supervisor tick-loop wiring that journals+notifies an escalation exactly once at loop-end (mirroring the existing `detach_reason or "watched-process-exited"` fallback site) and journals each newly-observed deferral per tick; a new `ports/notify.py`/`adapters/notify_file_desktop.py` pair (a durable file marker plus best-effort desktop notify, both AD-34 egress); and a new `marshal factory resume <slug>` CLI action that refuses on an unresolved escalation, otherwise detach-launches `bmad-loop resume` and re-attaches a supervisor, journaling an AD-45 back-reference.

## Boundaries & Constraints

**Always:**
- `run_status_snapshot` never raises (mirrors `usage_snapshot`'s exact `(OSError, ValueError, KeyError, TypeError, AttributeError, OverflowError, RecursionError)` guard, the tuple Story 3.6 arrived at only after three review passes -- reused verbatim, not re-derived narrower). Any pane/session-derived free text it reads (`state.paused_reason`, each deferred task's `defer_reason`) is redacted **at capture, before returning** -- the exact `to_redacted({"k": text}); json.loads(redacted.text)["k"]` wrap/unwrap round-trip `adapters/observer_mux.py::pane_content` already established for this same purpose (AD-34, F-16's `adapters -> core` authorization). Everything downstream (`core/supervise.py`, the supervisor, the journal payload) only ever sees the already-scrubbed plain `str`.
- Escalation is a **run-level** fact (`RunState.paused_stage`/`paused_story_key`/`paused_reason`), detected **once**, only when the tick loop discovers `watched_alive` has gone `False` with no other `detach_reason` already set by the idle ladder or a budget breach (those stay more specific and take precedence, matching the existing `detach_reason or "watched-process-exited"` fallback idiom exactly -- an escalation pause and a wedged/over-budget process are mutually exclusive causes of the same watched pid exiting). `core/supervise.py::evaluate_escalation(paused_stage, paused_story_key, task_phase) -> EscalationStatus` (`NONE | UNRESOLVED | RESOLVED`) is pure (AD-20): `UNRESOLVED` iff `paused_stage == "escalation" and paused_story_key is not None and task_phase == "escalated"`; anything else is `NONE` (not this kind of pause) or `RESOLVED` (paused for escalation, but the story's task already moved off `ESCALATED` -- only reachable at resume-time, see below). On `UNRESOLVED`, journal one `"escalation-detected"` observation (`story_key`, `reason`, `spec_file` -- the artifact needing a decision, from `tasks[paused_story_key].spec_file`) and call `NotifyPort.notify_file` (mandatory) then `NotifyPort.notify_desktop` (best-effort: any exception or `False` return is swallowed, never affects the detach outcome). `detach_reason` becomes `"escalation-paused"` instead of the generic fallback.
- Deferral capture is per-**story**, observed every tick while `watched_alive`: `run_status_snapshot`'s `deferred` tuple lists every task currently `Phase.DEFERRED`; the tick loop keeps a local `set[str]` of story keys already journaled this run and appends one `"story-deferred"` observation (`story_key`, `reason`, `attempt`, `branch`, `worktree_path`, `spec_file`) the first tick a key appears, never again. This is a **separate, budget/idle-independent** path -- it does not reuse `LadderRung`/`idle-defer` (Marshal's own idle-ladder giving up on a wedged *process*) or `evaluate_ceiling` (a budget *breach*); bmad-loop's engine deferring a *story* internally (verify exhaustion, a plugin veto) is a third, unrelated mechanism that merely shares the English word.
- `marshal factory resume <slug>` finds the most recent Marshal run directory for `slug` under the Tier-3 store (`<tier3>/runs/<slug>-*`, sorted -- AD-25's own "sortable chronologically within a slug"), folds its journal for `harness_run_id` (reusing `_resolve_harness_run_id`'s exact pattern), then calls `run_status_snapshot` **live** (never trusts the historical journal for the resolved/unresolved question -- only for discovering which `harness_run_id` to check). `EscalationStatus.UNRESOLVED` refuses with `MRS-SPIN-010` (ERROR) before any spawn. Otherwise it mints a fresh Marshal run id, journals a `"run-resume"` intent before spawn (AD-25), detach-launches `HarnessPort.resume` (the identical `Popen(..., start_new_session=True, ...)` recipe `spin` already uses -- AD-22), and spawns a new supervisor sidecar with the same 10-positional argv `spin` already constructs (idle threshold + 4 budget ceilings re-resolved from policy).
- The `run-resume` outcome payload carries AD-45's four fields: `story_key`, `reason` (the escalation's original, already-scrubbed reason, re-read live), `resolution_reference` (`bmad_loop.resolve.resolution_path(harness_run_dir, story_key).as_posix()` if that file exists on disk, else `None` -- `--no-interactive` resolves are never guaranteed to leave one), and `resolver` (`getpass.getuser()` -- attributable, not authenticated, exactly the trust model AD-27/F-4 already declares for every other "operator-attributed" entry in this codebase; no stronger identity primitive exists anywhere in Marshal to build on).
- `ports/notify.py::NotifyPort` is a new AD-34 egress port (`core/egress.py::EGRESS_PORTS["NotifyPort"] = True`); both methods accept only `Redacted`, never a bare `str` (`tests/meta/test_ad34_egress_registry_completeness.py` enforces this at build time). `adapters/notify_file_desktop.py::FileDesktopNotifier.notify_file` writes `<run_dir>/ESCALATION` via the same guarded `write_text_atomic(path, payload.text)` call `write_redacted_atomic` itself makes (no new atomic-write logic). `notify_desktop` is best-effort (a short-timeout `subprocess.run` to a platform notifier, e.g. `notify-send`), catches every exception, and returns `bool` -- never raises, never blocks the caller.

**Never:**
- No new Marshal policy/SEED key. "The run continues unless configured otherwise" (FR-16) describes bmad-loop's own existing continuation semantics, not a new Marshal stop-on-defer control surface -- Marshal's role here is observation and journaling only, never enforcement.
- No `reason_class` taxonomy invented for the deferral: bmad-loop's own `StoryTask.defer_reason` is free text at every one of its three call sites (no enum exists upstream); the journal field is named `reason` and carries it verbatim, matching this project's own precedent for not inventing structure bmad-loop itself doesn't provide.
- Resume does not accept `--epic`/`--story`/`--max-count`: `bmad-loop resume` itself ignores them, rebuilding the engine from **state-pinned** scope only.
- No new `HarnessPort.stop` return-shape widening (a `deferred-work.md` item already names this as a future story's concern) -- deferral capture reads `defer_reason` from `state.json` instead, which is sufficient for this story's own AC.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Escalation raised | Watched pid exits; `state.json` shows `paused_stage="escalation"`, `paused_story_key` set, that task's `phase="escalated"` | One `"escalation-detected"` observation; file marker written; desktop notify attempted; `detach_reason="escalation-paused"` | File-marker write failure -> `MRS-SUPV-007` (WARN), detach still proceeds |
| Ordinary finish | Watched pid exits; `state.json` has no `paused_stage`, or one unrelated to escalation (`spec-approval`, etc.) | No escalation entry; ordinary `"watched-process-exited"` fallback unchanged | No error expected |
| `run_status_snapshot` read failure | `state.json` missing/malformed/non-mapping field | Returns `None`; loop-end falls back to the ordinary detach reason exactly as if unread | Never raises |
| Story deferred mid-run | A task transitions to `Phase.DEFERRED` between two ticks | One `"story-deferred"` observation on the FIRST tick it's observed, never repeated | No error expected |
| Resume, unresolved escalation | `marshal factory resume <slug>`; live snapshot still shows the paused story's task `phase="escalated"` | Exit non-zero, `MRS-SPIN-010`, no spawn, no journal write | Refusal itself never raises |
| Resume, resolved escalation | Same, but a human ran `bmad-loop resolve` first (task `phase` back to `pending`) | `"run-resume"` intent/outcome journaled with AD-45 fields; detached `bmad-loop resume`; new supervisor spawned | Launch failure reuses `MRS-SPIN-003`'s existing shape |
| Resume, no prior run for slug | No `<tier3>/runs/<slug>-*` directory exists | `MRS-SPIN-011`, exit non-zero | Never raises |
| Resolution marker absent | Escalation resolved via `bmad-loop resolve --no-interactive` (no `resolution.json` written) | `resolution_reference: null` in the `run-resume` payload; resume still proceeds | Documented limitation, not a defect (AD-45/F-4) |

## Design Notes

**Why escalation detection happens once, at loop-end, not every tick.** bmad-loop's own `engine.run()` catches `RunPaused` internally and returns normally -- the harness CLI process (`bmad-loop run`/`bmad-loop resume`, whichever the supervisor is watching) exits exactly as it would on a clean finish. `state.json` is saved synchronously *before* that unwind (`engine.py`'s pause sites all call `self._save()` immediately before raising), so there is no race: by the tick the supervisor observes `watched_alive is False`, the pause fields are already durable. Polling for it on every tick while still alive would be pure waste -- nothing can be paused-for-escalation while the process supervised is still running.

**Why deferral capture is the opposite shape -- every tick, while alive.** `Phase.DEFERRED` does *not* pause the run (`engine._defer` returns normally; the loop picks the next story), so a deferred story is a fact that appears *during* a still-live run, potentially several times before the run itself ends. Missing one because the tick loop only checked at the end would silently drop every deferral but the last.

**Why `resume` re-checks live rather than trusting its own prior journal entry.** The AC's own framing -- "a paused run whose blocking condition a human resolved" -- describes an arbitrarily long gap between detection (this run's own `escalation-detected` observation, possibly hours old) and the resume attempt. Only a fresh `state.json` read can answer "is it *still* unresolved right now."

**Resolver attribution ceiling (documented, not a defect).** AD-45 itself carries F-4's caveat forward ("resolver attribution as the trust model defines it... not resolved") rather than promising authentication. `getpass.getuser()` is attributable, exactly like every other "operator-attributed" entry AD-27 already declares Marshal's ceiling to be (process isolation, the actual precondition for anything stronger, remains Deferred project-wide).

**2.
