## Intent

**Problem:** `bmad-loop run`/`resume` both call `engine.run()` synchronously and block the invoking shell for the run's entire lifetime (verified live in the installed 0.9.0 `cli.py`) — exactly the foreground-timeout class of failure (AD-22) that already killed a run mid-review in production. Marshal has no launch verb at all today: `core/journal.py`'s mint/append mechanism (Story 3.1) has zero real callers, and `deferred-work.md` names this story explicitly as "the first real caller" that must mint a run id, `create_dir_exclusive` a run directory, and `append_line` a journal entry before spawning anything.

**Approach:** Add `marshal factory spin <slug>` (`cli/spin.py`): resolve the provisioned loop home, resolve composable `--story`/`--epic`/`--max-count` selectors against the harness's raw story feed through a new read-only `HarnessPort` seam, verify AD-38 feed completeness via the already-shipped `core.identity.resolve_feed`, mint a Marshal run id (Story 3.1) and journal `intent` → detached spawn → `outcome` around one new `HarnessPort.spin` primitive that is the only code in the tree permitted to launch `bmad-loop run` (AD-3). Add `marshal factory attach <slug>` as the separate, non-destructive, interactive session-attach command the AC also requires.

## Boundaries & Constraints

**Always:**
- `ports/harness.py` gains three `HarnessPort` methods, implemented ONLY by `BmadLoopHarness` (AD-3): `story_feed_keys(project) -> tuple[str, ...]` (bmad_loop's `SprintStatus.stories[*].key` UNION `unknown_keys`, file order — "non-empty story records... before key parsing", AD-38, independent of Marshal's own `normalize()`); `spin(project, *, epic, story, max_count, log_path) -> SpinResult` (builds `["bmad-loop", "run"]` plus `--epic`/`--story`/`--max-stories` when given, launches via `subprocess.Popen(..., start_new_session=True, stdin=DEVNULL, stdout/stderr->log_path)`, never waited on, returns immediately); `attach(project) -> int` (execs `bmad-loop attach`, inherits stdio, returns its exit code — interactive by design). A new `SpinResult(pid: int, harness_run_id: str | None)` value type lives beside `HarnessPort` (mirrors `ports/process.py`'s `ProcessResult`).
- `spin` also reads back its own redirected log for the harness's self-minted id (`bmad-loop run`'s own "run {id} starting" stdout line) via a bounded poll (a few seconds, never indefinite); `harness_run_id` is `None` when the window elapses without a match. Only `adapters/harness_bmadloop.py` parses this text (AD-3).
- `spin`/`attach` raise `HarnessError` only when the process could not be LAUNCHED at all (missing binary, a launch-time `OSError`) — mirrors `ports/process.py::ProcessPort.run`'s convention, distinct from this same adapter's existing never-raises methods.
- `cli/spin.py::run_spin` order of operations: reuse the EXISTING `HarnessPort.story_feed_error` first (refuse early, `MRS-SPIN-005`, if the feed itself is unreadable) → `story_feed_keys` → `core.identity.resolve_feed` (AD-38: `total` is the whole raw population, independent of any selector) → refuse the launch (no spawn) if `unresolved` is non-empty, surfacing the EXISTING `MRS-IDENT-001` findings (already classified `Verdict.UNEVALUABLE` — no new code needed) → filter the RESOLVED `StoryKey`s by `--epic`/exact `--story` key/`--max-count` to build the echoed preview list → mint the Marshal run id (`core.journal.mint_run_id`, AD-25) → `create_dir_exclusive` its run directory → `append_line` an `intent` entry of kind `"run-launch"` whose payload carries the selector (`epic`/`story`/`max_count`, `null` where unset) AND the echoed preview `StoryKey` list (rendered via `core.identity.render_feed_key`) — this IS "the resolved story list ... recorded in the journal" — → call `HarnessPort.spin` → `append_line` an `outcome` entry (same `kind`, `intent_id` set to the intent's id) whose payload carries `pid` and `harness_run_id` (`null` when unconfirmed) as a plain correlation field, never a key/path/grouping value (AD-25) → print the same resolved list and run id to stdout/envelope.
- `writer_id` = a fresh, process-scoped, filesystem-safe token (e.g. `f"spin-{os.getpid()}"`, matching `_WRITER_ID_PATTERN`); `counter` starts at 0 and increments once per journal append made by this single CLI invocation — a bounded, sequential, single-process writer, so no cross-writer collision is possible by construction.
- `--foreground` (explicit boolean flag on `spin`) calls a synchronous, stdio-inheriting `HarnessPort` path instead of the detached one and relays its exit code; its help text documents it as unsafe for resumes (forward documentation only — resume itself is Story 3.7's scope).
- `cli/spin.py` reuses `cli/init.py`'s existing `_home_path`/`_loop_home_root` (imported, not duplicated — mirrors `cli/gate.py` already importing private helpers from `cli/config.py`) to resolve the provisioned loop home from the positional `slug`, matching every sibling loop-home command's own CLI shape.
- `spin` builds an `Envelope` via `build_envelope`/`compute_verdict`/`exit_code_for` exactly like every other command (text/json, `--format`); `attach` does NOT — it hands the terminal to the multiplexer and relays bmad-loop's own exit code directly, mirroring `cli/main.py --version`'s existing precedent for a command that legitimately bypasses the envelope.
- Register `MRS-SPIN-001` (malformed slug, pre-I/O) → `Verdict.UNEVALUABLE`; `MRS-SPIN-002` (loop home not provisioned) → `Verdict.ERROR`; `MRS-SPIN-003` (detached-spawn launch failure) → `Verdict.ERROR`; `MRS-SPIN-004` (harness_run_id unconfirmed within the poll window — spawn itself succeeded) → `Verdict.WARN`; `MRS-SPIN-005` (story feed missing/unparseable) → `Verdict.ERROR`. Wire `add_factory_subparser` into `cli/main.py`'s subparser tree.
- Any unresolved-feed refusal, provisioning gap, or spawn failure produces NO journal entries at all (nothing to mint a run id or spawn against yet) — only a genuinely attempted spawn gets `intent`/`outcome` entries.

**Block If:** none — every decision here follows an explicit architecture rule (AD-3, AD-6, AD-22, AD-25, AD-38) or reuses an already-shipped mechanism (`resolve_feed`, `story_feed_error`, `mint_run_id`/`append_line`/`create_dir_exclusive`); no product ambiguity requires a human decision.

**Never:**
- Do not implement `marshal factory resume` — FR-17's mechanics (re-attach a supervisor, refuse on an unresolved escalation) are Story 3.7's own title and scope.
- Do not add per-run selection to `attach` (e.g. `--run <id>`) — `bmad-loop attach` already defaults to the latest run, satisfying the AC's "a separate, non-destructive command"; disambiguating among multiple runs by Marshal's own run id needs a `core.journal.fold`-based lookup that is a real but undemanded capability — log it to `deferred-work.md` if review flags it.
- Do not attach a supervisor (Story 3.4) — `spin` launches and returns; nothing watches the process after this story.
- Do not wire AD-10's "policy composition materialized and journaled at spin" into this story — `marshal config --write-harness-policy` remains the one existing, operator-invoked mechanism for rendering `.bmad-loop/policy.toml`; adding journaled materialization touches `core/policy.py`/`cli/config.py`, outside this story's Surface — log to `deferred-work.md` if flagged.
- Do not implement an "approved spec" check before launch — no Epic 2 gate-approval dependency is declared (this story's own Deps are S-1.7, S-3.1 only); that precondition is operator-verified narrative.
- Do not reimplement `bmad_loop.sprintstatus.select_actionable`'s full matching grammar (slug fragments, a bare number needing `--epic`, etc.) inside `core/identity.py` or `cli/spin.py` — that duplicates harness-owned selection logic across the single-seam boundary (FR-52). Marshal's own echoed preview only needs epic-number/exact-key/count filtering over already-resolved `StoryKey`s; the harness's own `select_actionable` remains the sole authority for which stories the run actually executes.
- Do not pre-refuse a launch because the selector's preview count is zero (e.g. an epic with no actionable stories) — that judgment belongs to the harness's own engine at run time; Marshal blocking pre-emptively risks disagreeing with it. Launch anyway; the harness's own run reports the outcome.
- Do not block indefinitely waiting for `harness_run_id` — a bounded poll only, degrading to `MRS-SPIN-004`/`None`, never hanging the CLI invocation.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Happy path, whole feed | provisioned home, clean feed, no selectors | mints run id, journals intent+outcome, spawns detached, prints run id + resolved N of N, exit 0 | No error expected |
| `--epic`/`--story`/`--max-count` composed | provisioned home, clean feed | echoed preview filtered by all three; same flags passed to `bmad-loop run`; launch proceeds | No error expected |
| One raw feed key fails `normalize()` | e.g. malformed key anywhere in `story_feed_keys`, regardless of selector | `MRS-IDENT-001` finding(s), `Verdict.UNEVALUABLE`; launch refused, nothing spawned, no journal entries written | Refused before any I/O side effect |
| Loop home not provisioned | `fs.is_dir(home)` is `False` | `MRS-SPIN-002`, `Verdict.ERROR`; launch refused | Non-zero exit, no spawn |
| Malformed slug | slug fails `_is_valid_project_slug` | `MRS-SPIN-001`, `Verdict.UNEVALUABLE`, checked before any filesystem touch | Non-zero exit, no spawn |
| Story feed missing/unparseable | `story_feed_error(home)` returns non-`None` | `MRS-SPIN-005`, `Verdict.ERROR`; launch refused | Non-zero exit, no spawn |
| Detached spawn cannot launch | harness binary absent or `Popen` raises `OSError` | `MRS-SPIN-003`, `Verdict.ERROR`; run id already minted and directory created, but journaled as a failed `outcome`, never as a successful launch | Non-zero exit, no live process |
| `harness_run_id` unconfirmed | redirected log never shows the "starting" line within the poll window | spawn still counted a success (pid known); `outcome` entry records `harness_run_id: null`; `MRS-SPIN-004`, `Verdict.WARN` | Exit 0 (warn tier), CLI returns promptly regardless |
| `--foreground` | flag passed | `bmad-loop run` runs inline, inherits stdio, blocks; its exit code is relayed directly | Whatever `bmad-loop run` itself exits |
| `marshal factory attach <slug>`, a run exists | provisioned home, at least one run dir | execs `bmad-loop attach`, hands over the terminal, relays its exit code | No error expected |
| `marshal factory attach <slug>`, no run exists | provisioned home, no runs | `bmad-loop attach` itself prints "no runs found" and exits 1; relayed verbatim | Non-zero exit, no envelope built |

**Acceptance Criteria:**
*(Story 3.3's ACs from `epics.md`, preserved as the contract of record.)*
- Given an approved spec and a provisioned home, when `marshal factory spin` runs, then the harness process is detached from the invoking shell's session and lifetime, and the command returns promptly with the Marshal run id
- And the run survives the caller exiting
- And foreground execution exists only behind an explicit flag documented as unsafe for resumes, and nothing in Marshal blocks on a run's completion
- And attaching to a live run's session is a separate, non-destructive command

## Design Notes

**Why M/N is over the whole raw feed, not the selector-filtered subset.** AD-38's text is "M is the count of non-empty story records in the raw source, counted BEFORE key parsing" — unconditional. Determining "is this raw key inside the requested epic/story scope" itself requires parsing it, so scoping M to a filtered subset would be circular for exactly the malformed keys the rule exists to catch. `core.identity.resolve_feed` already implements this correctly and unconditionally (`total = len(raw_keys)`); `story_feed_keys` supplies its `raw_keys` as bmad_loop's own `stories` ∪ `unknown_keys` (every `development_status` entry that isn't an epic/retro/retro-item administrative key), independent of Marshal's `normalize()`.

**Why the echoed launch scope is a best-effort preview, not the authoritative selection.** The same `--epic`/`--story`/`--max-stories` flags are passed straight through to `bmad-loop run`, which re-derives the real selection itself via its own `select_actionable` at spawn time. Marshal's preview only needs to prove completeness (AD-38) and give the operator something to read before committing to a detached launch — it is not a second selection authority.
