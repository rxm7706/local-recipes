## Intent

**Problem:** Gate evaluation today only happens implicitly inside a live bmad-loop run — nobody can ask "would this pass?" for a tree with no run in flight, so an operator or CI cannot check before approving.

**Approach:** Add `marshal gate evaluate`: it resolves the active project's policy-declared `verify_commands` allowlist, runs each one through a new `ProcessPort`/`adapters/process_posix.py` seam, and folds the results into Marshal's existing verdict lattice (`core/verdict.py`) via a new pure aggregation function in `core/gate.py`.

## Boundaries & Constraints

**Always:** Verify commands run ONLY from `EffectivePolicy.verify_commands` (composed via `core/policy.compose()`) — no other command-input channel exists, so AD-17's allowlist-only rule holds structurally, not by a runtime check. Project scoping reuses `cli/config.py::run_config`'s exact `--project`/`BMAD_ACTIVE_PROJECT`-env/`conventional_project_policy_path` resolution (imported, not reimplemented), so "another project's gates never run" (FR-20) holds by construction. All process spawning goes through `ports/process.py::ProcessPort`, injected the same DI way `cli/init.py` already injects `VcsPort`/`FsPort`/`HarnessPort` (default-constructed from the real adapter when the caller passes `None`); `core/gate.py`'s aggregation function takes only already-obtained outcomes (a `ProcessResult` or a documented failure reason) and does no I/O itself (AD-4 — no `subprocess`/`os`/`time`/adapters import in `core/gate.py`). Every new finding code is added to `core/findings.py`'s `REGISTERED_CODES` and `core/verdict.py`'s `_CLASSIFY_TABLE` in the same change (both registries move together, per the existing convention). Verdict/exit-code assignment goes solely through `verdict.compute_verdict`/`exit_code_for` — never a hardcoded literal in `core/gate.py` or `cli/gate.py` (AD-7 sole-ownership meta-test). Output always carries an explicit `scope` field; with no `--run` supplied it is `"policy-seed-only"` plus a `mid-run freezes not visible` note (AD-26/F-3 — the story's own preamble flags this as the clause a developer reading only the ACs could otherwise miss). `marshal gate evaluate` performs no filesystem write itself (reading policy and spawning a read-only-from-Marshal's-perspective subprocess is the only I/O).

**Block If:** None. AD-26's own resolution text ("a standalone evaluation folds the policy seed alone... a complete, legitimate answer") and the epic's Cross-Story Dependencies note ("Epic 2 cannot fully close until S-3.2 lands; the epic boundary is a value boundary, not a scheduling barrier") together already resolve the one ambiguity this story would otherwise need a human for — see **Never**, below.

**Never:** Accepting an arbitrary/ad-hoc command to execute outside `policy.verify_commands` — there is deliberately no such flag (AD-17 is satisfied by having no other execution channel, not by a runtime allowlist check). Implementing the run-journal fold itself — that is `core/journal` (Story 3.1/3.2, both `backlog`, no code exists). `--run <id>` is accepted as a CLI flag for interface shape (matching the AC's stated eventual behavior), but since no journal exists to fold, supplying it produces an explicit `unevaluable` finding naming the gap rather than fabricating a run-scoped answer or crashing — a future story swaps this stub branch for a real `core/journal.fold` call once S-3.2 lands. Implementing `--scope-check` (referenced by the PRD's own `UJ-2` example invocation, `marshal gate evaluate --scope-check`) — that is Story 2.3, itself blocked on S-3.2. Implementing further verdict-lattice/never-false-green property tests beyond correct use of the existing `compute_verdict`/`classify` machinery — that is Story 2.2's scope. Redacting captured command output through `core/egress.py` — `ProcessPort` is explicitly carved out of AD-34's egress-port set (argv/environment to a child process, and CLI stdout, are inside Marshal's trust boundary, not a durable/third-party sink).

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| All commands pass | `verify_commands=(cmd1, cmd2)`, both exit 0 | `verdict=clean`, exit 0; each command's report shows `returncode=0` plus captured stdout/stderr | No error expected |
| One command fails | `verify_commands=(cmd1, cmd2)`, cmd2 exits 1 | `verdict=gate-failed` (`MRS-GATE-001`), exit 3; cmd2's report shows the non-zero code and captured output | Finding names the failing command |
| Command not resolvable | `verify_commands=("nonexistent-bin",)` | `verdict=unevaluable` (`MRS-GATE-002`), exit 1; report flags `resolvable: false` | Finding names the command; no crash |
| Malformed command string | `verify_commands=("'unterminated",)` | `verdict=unevaluable` (`MRS-GATE-003`), exit 1; no spawn attempted | Finding names the parse failure |
| Zero verify commands configured | `verify_commands=()` (bare defaults or an unresolvable project) | `verdict=warn` (`MRS-GATE-004`), exit 0 | Explicit "no verify commands configured" finding — never silently `clean` |
| `--run <id>` supplied | any | `verdict=unevaluable` (`MRS-GATE-005`); `scope` marker reflects the request could not be honored | Finding names the journal-fold gap explicitly |
| Wrong project never runs | `--project other-slug` while cwd is a different project | Only `other-slug`'s conventional policy path is read; the current tree's own commands never execute | N/A |
| `--project`/env both omitted | no flag, no `BMAD_ACTIVE_PROJECT` | Composes against Marshal's bare defaults (`verify_commands=()`) — same as the empty-allowlist row, plus the existing `MRS-POLICY-005` warn from `compose()` | Both findings surface together |

## Code Map

- `src/pyforge/marshal/core/gate.py` -- NEW. Pure aggregation: given each verify command's already-obtained outcome (a `ProcessResult` or a documented reason it never ran), classifies it into a per-command report dict plus zero-or-one `Finding`, via `core.verdict.classify`/`core.findings`. No I/O, no `ProcessPort` reference beyond the `ProcessResult` value type.
- `src/pyforge/marshal/cli/gate.py` -- NEW. `add_gate_subparser`/`run_evaluate`: resolves project slug + policy exactly like `cli/config.py::run_config` (reusing `conventional_project_policy_path`, `_read_project_policy`, `ENV_ACTIVE_PROJECT`), `shlex.split`s + spawns each configured command via the injected `ProcessPort`, hands outcomes to `core.gate`, builds the envelope, prints, returns the exit code. Mirrors `cli/init.py::run_preflight`'s DI-default-port + findings-list + `build_envelope` shape.
- `src/pyforge/marshal/ports/process.py` -- NEW. `ProcessPort` Protocol (one `run(argv, *, cwd, timeout_s=None) -> ProcessResult` method; never raises for a non-zero exit, raises `ProcessError` only when the process cannot be launched at all) plus the frozen `ProcessResult` dataclass. Mirrors `ports/vcs.py`'s docstring-specified Protocol style.
- `src/pyforge/marshal/adapters/process_posix.py` -- NEW. `PosixProcess`, the sole `ProcessPort` implementation, and `ProcessError`. Wraps `subprocess.run(argv, cwd=cwd, capture_output=True, text=True, encoding="utf-8", errors="replace", timeout=timeout_s)`, catching `FileNotFoundError`/`TimeoutExpired`/`OSError` into `ProcessError` — mirrors `adapters/vcs_git.py`'s `_run()` helper exactly.
- `src/pyforge/marshal/cli/main.py` -- EDIT. Register `gate_cli.add_gate_subparser(subparsers)` in `_build_parser()`, alongside the existing four.
- `src/pyforge/marshal/core/findings.py` -- EDIT. Register `MRS-GATE-001` through `MRS-GATE-005` in `REGISTERED_CODES`, with a docstring paragraph following the existing per-story convention.
- `src/pyforge/marshal/core/verdict.py` -- EDIT. Classify the five new codes in `_CLASSIFY_TABLE`: `MRS-GATE-001` -> `GATE_FAILED` (a command ran and failed — stronger than "could not evaluate"); `MRS-GATE-002`/`003`/`005` -> `UNEVALUABLE` (could not run at all — matches Story 2.2's own AC text: "a missing verify command... produces unevaluable"); `MRS-GATE-004` -> `WARN` (a legitimate, non-blocking bootstrap state, same tier as `MRS-POLICY-005`).
- `src/pyforge/marshal/cli/config.py` -- READ ONLY (no edit). `repo_root`, `conventional_project_policy_path`, `_read_project_policy`, `PolicyIOError`, `ENV_ACTIVE_PROJECT` are imported/reused by `cli/gate.py`, the same cross-module private-helper convention `cli/main.py` already uses for `config_cli._suppress_downstream_pipe_close`.

**Acceptance Criteria:**
- Given a project with `verify_commands` configured in its policy, when `marshal gate evaluate` runs with no run in flight, then each command runs via `ProcessPort` and pass/fail is reported per command with captured stdout/stderr
- Given `--project other-slug` (or `BMAD_ACTIVE_PROJECT=other-slug`) while invoked from a different project's tree, when `gate evaluate` runs, then only `other-slug`'s conventional policy path is read and only its commands execute
- Given any outcome, when the envelope is built, then `verdict`/exit-code assignment traces solely to `verdict.compute_verdict`/`exit_code_for` — no literal exit code or lattice-order sequence appears in `core/gate.py` or `cli/gate.py` (asserted by the existing `test_ad7_verdict_sole_ownership.py` meta-test, which needs no story-specific edit since it AST-scans the whole installed package)
- Given no run in flight, when `gate evaluate`'s envelope is built, then `data["scope"] == "policy-seed-only"` and a `mid-run freezes not visible` note is present
- Given `--run <id>` is supplied, when `gate evaluate` runs, then it reports `MRS-GATE-005` (`unevaluable`) naming the journal-fold gap rather than silently ignoring `--run` or crashing
- Given the same tree and the same configured commands, when `gate evaluate` runs twice in a row with no changes between runs, then both runs produce an identical verdict (NFR-1/FR-21 — no model call anywhere in the path)
- Given `gate evaluate` completes (any outcome), when the working tree is inspected before and after, then no file has been added, removed, or modified by Marshal itself

## Design Notes

**Why `core/gate.py` never calls `ProcessPort` directly.** The AC says the aggregation "lives in `core/gate.py` as a pure function over exit codes, with all process spawning behind `ProcessPort`" — read together with AD-4 (`core/**` forbids `subprocess`/`os`/`time`/`adapters` imports) and this package's established split (e.g. `core/policy.compose()`'s own docstring: "never reads a file or an env var... the CLI boundary does the I/O and calls this"), the spawning itself belongs in `cli/gate.py`. `core/gate.py` takes each command's *already-obtained* outcome — a `ProcessResult`, or a plain string reason it never ran (malformed/unresolvable) — and does only classification:

```python
# core/gate.py -- pure, no I/O
def classify_outcome(command: str, result: ProcessResult | None, *, failure_reason: str | None = None) -> tuple[dict, Finding | None]:
    if result is None:
        return {"command": command, "resolvable": False, "returncode": None}, Finding(code=..., severity=Severity.ERROR, message=failure_reason)
    if result.returncode != 0:
        return {"command": command, "resolvable": True, "returncode": result.returncode, "stdout": result.stdout, "stderr": result.stderr}, Finding(code="MRS-GATE-001", severity=Severity.ERROR, message=f"{command!r} exited {result.returncode}")
    return {"command": command, "resolvable": True, "returncode": 0, "stdout": result.stdout, "stderr": result.stderr}, None
```

`cli/gate.py` builds the `ProcessResult | None` per command (via `shlex.split` + `process.run`, catching `ProcessError`), then calls this per command and folds the returned findings with `verdict.compute_verdict`.

**Why zero configured commands is `warn`, not `unevaluable`.** `verify_commands=()` is Marshal's own literal `DEFAULT_POLICY` value — a brand-new project with no `marshal-policy.toml` override starts here. Treating that default as `unevaluable` (blocking, exit 1) would make every not-yet-configured project fail `gate evaluate` by default, which is a harsher bar than the identical-shaped precedent `MRS-POLICY-005` already sets for "no active project supplied" (classified `warn` — "a legitimate show-me-the-defaults invocation"). This is distinct from a *declared* command that turns out unresolvable (`MRS-GATE-002`, `unevaluable`) — there, an operator asserted a command exists and it does not, which Story 2.2's own AC text says must be `unevaluable`.

**Why `--run` is accepted but stubbed.** Omitting the flag entirely would leave one of the story's own literal ACs ("when a run is in flight and its id is supplied, the same command folds that run's journal instead") with no corresponding task, failing the Testable/Complete bar. Implementing it for real requires `core/journal.fold` (Story 3.1/3.2, `backlog`). AD-26's own resolution text says the no-run-in-flight path is "a complete, legitimate answer" on its own — so the honest, never-false-green move is to accept `--run`, and answer with an explicit `unevaluable` finding naming exactly why, rather than pretending the flag doesn't exist or silently ignoring it.
