## Intent

**Problem:** A session that stops producing output but never exits is invisible to Story 3.4's supervisor today -- it samples pane content and log mtime every tick but discards both, so a wedged run burns tokens to a multi-million-token cap instead of being caught in minutes (the exact incident FR-12 exists to prevent).

**Approach:** Add a pure decision core (`core/supervise.py`, AD-20) that turns the accumulating tick-sample sequence into a 3-rung ladder position (nudge -> stop-and-retry -> defer), wire it into the supervisor's tick loop to execute each rung and journal it as `intent`->`outcome`, and close the two placeholder gaps Story 3.4 explicitly left for this story: the tmux target passed to the observer (today a non-resolving placeholder) and the harness-log path sampled for mtime (today the supervisor's own log).

## Boundaries & Constraints

**Always:**
- Idleness is measured only from `SessionObserverPort.pane_content`/`.mtime` -- never the agent's self-report (AD-9).
- The ladder decision is a pure function over a `Sequence[Sample]` (AD-20): no port, no clock call, no I/O inside it. Every ladder transition has a millisecond synthetic-sequence test.
- Fresh output (pane content OR mtime changed since the previous sample) re-arms the window: idle-elapsed resets to zero AND the last-acted rung resets to `NONE`, so a session that responds to a nudge earns a full threshold before the next rung.
- Each ladder rung is journaled as one `intent` entry then one `outcome` entry, never a single combined entry (matches the existing `Phase` pairing rule).
- `stop-and-retry` uses `HarnessPort.stop`+`HarnessPort.resume` (new methods, backed by `bmad-loop stop <harness_run_id>` / `bmad-loop resume <harness_run_id>`) -- confirmed live as the intended, supported pairing (hard-stop works against an unresponsive engine; resume re-derives state from the same run_id and self-clears any stale tmux session). A bare re-`bmad-loop run` is never used as the retry primitive: it mints an unrelated run id with no in-flight lock, so it would double-dispatch the same story against the old run's leftovers.
- After a successful `stop-and-retry`, the supervisor's in-memory `watched_pid` is replaced by the new one and the sample history resets (the new engine attempt starts its own fresh idle window).
- `defer` is terminal: after its outcome is journaled the supervisor exits its tick loop via a new `supervisor-detach` reason (`"idle-deferred"`), alongside the existing `"watched-process-exited"`.
- The idle threshold is an operator-configurable value, not a buried literal: add `idle_threshold_minutes` (default 25) as a 10th key in the closed `EffectivePolicy` vocabulary (SEED-tagged, alongside `max_dev_attempts`/`max_review_cycles`/`max_followup_reviews`, the closest existing analogs), threaded through `compose()`, `schemas/policy.json`, and `cli/config.py::_FIELD_ORDER`. `cli/spin.py` (which already composes `EffectivePolicy` before spawning) resolves the effective value and passes it as a 6th positional on the existing supervisor spawn argv -- the same mechanism `watched_pid`/`log_path` already use -- rather than having the supervisor re-read the materialized policy file itself.
- The tmux session for a run is `f"bmad-loop-{harness_run_id}"` (a fixed upstream formula, confirmed live) -- but the WINDOW inside it is never persisted or formula-derivable, so `pane_content`/the new `send_text` resolve the live window id via `tmux list-windows` at call time, not a cached or guessed target.
- `harness_run_id` (recovered once at attach, from the existing `run-launch` journal entry the inert-check already reads) is required for every ladder action that touches the session or the harness (nudge, stop-and-retry). If it is unavailable, the ladder cannot act: journal a registered finding once and continue heartbeat-only supervision (no crash, no guess).

**Block If:** none identified -- every action in this story is either already-precedented upstream (stop/resume, send-keys) or a pure function; no decision here needs human input.

**Never:**
- Full FR-16 deferral capture (reason-class taxonomy, cross-run attempt counting, preserved-work location) -- Story 3.7's surface. This story's `defer` outcome only records that the idle ladder exhausted and the run was stopped.
- FR-13/14 budget/token ceilings -- Story 3.6.
- A Marshal-level `resume` CLI verb or operator-facing resume flow -- Story 3.7. `stop-and-retry` calls `HarnessPort.stop`/`resume` directly from inside the supervisor loop.
- Desktop/file-marker notification channels -- FR-15, Story 3.7.
- Policy-driven customization of the ladder's shape (only the threshold is configurable; nudge -> stop-and-retry -> defer is a fixed 3-rung sequence).
- Widening `core.egress`'s token-redaction vocabulary for arbitrary third-party pane text -- a real, already-logged AD-34 gap that this story makes LIVE (pane content is now genuinely read) rather than closing; update the existing deferred-work entry's status, do not fix the vocabulary itself here.
- A second multiplexer backend -- tmux only, matching Story 3.4.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Steady idle, no ladder yet | Samples show no pane/mtime change for < threshold | `evaluate_idle` returns `NONE`; no journal write, no action | No error expected |
| First threshold crossing | No change for >= 1x threshold, last acted rung is `NONE` | Ladder fires `nudge`: `idle-nudge` intent then outcome journaled; `send_text` called against the resolved window | `send_text` failure (no window resolves) is a registered finding, ladder still advances its own "last acted" bookkeeping so it doesn't retry nudge every tick |
| Fresh output after nudge | A later sample's pane/mtime differs from its predecessor | Idle-elapsed and last-acted rung both reset to zero/`NONE`; no further ladder action until a fresh full threshold elapses | No error expected |
| Second threshold crossing, still idle | No change for >= 2x threshold since last reset | Ladder fires `stop-and-retry`: `HarnessPort.stop` then `.resume`; `watched_pid` updated; `idle-stop-and-retry` intent/outcome journaled with `{old_pid, new_pid}`; sample history cleared | `stop` or `resume` raising `HarnessError` is caught, reported via a registered finding in the outcome payload, and the tick loop continues watching the (possibly still-wedged) original pid rather than crashing |
| Third threshold crossing, still idle | No change for >= 3x threshold since the last reset | Ladder fires `defer` (terminal): `idle-defer` intent/outcome journaled; supervisor writes `supervisor-detach` with `reason: "idle-deferred"` and exits its loop | No further ladder or heartbeat activity after detach |
| `harness_run_id` unavailable | The run-launch outcome entry's `harness_run_id` field is `None` | A registered finding is journaled once at attach; the tick loop continues heartbeats only, `evaluate_idle` is never consulted for this run | No crash |
| Window resolution finds zero or multiple candidates | `tmux list-windows` returns nothing, or more than one window with no clear active one | `pane_content`/`send_text` degrade to their existing documented `None`/`False` -- never raise | Logged via the existing "never raises" port contract, no new exception surface |

## Spec Change Log

### 2026-08-03 -- implementation-time deviations from the Code Map/Always bullet, verified against actual code

- **`cli/spin.py` did NOT already compose `EffectivePolicy` before this story.** The spec's own Always bullet states "`cli/spin.py` (which already composes `EffectivePolicy` before spawning) resolves the effective value and passes it as a 6th positional" -- verified live by reading the pre-existing `cli/spin.py` in full and grepping it for `compose`/`EffectivePolicy`/`seed_view`: none appear anywhere in the file before this story. `run_spin` only ever called `policy._is_valid_project_slug` (a shape check, not a composition). This story therefore ADDS the composition step itself: `run_spin` now reads the conventional project-policy file (mirroring `cli/config.py`'s own `conventional_project_policy_path`/`_read_project_policy` lookup, falling back to an empty project layer on a missing/unreadable file -- see the new deferred-work.md entry on why that fallback is silent rather than finding-bearing) and calls `policy.compose(project_slug=slug, project=project_policy_data, flags={})` immediately before building the supervisor's spawn argv. The resulting `idle_threshold_minutes` value is identical to what the (false) "already composes" premise would have produced; only the code path that gets there is new.
- **`adapters/harness_bmadloop.py::resume` does NOT literally call `ports.process.ProcessPort.spawn_detached`.** The Code Map's line for that file reads "`resume` detach-spawns `["bmad-loop", "resume", run_id]` via `ProcessPort.spawn_detached`, mirroring `spin`'s own detach recipe." Taken literally this would require `harness_bmadloop.py` to import `adapters/process_posix.py`'s `PosixProcess` (the sole implementation of `ProcessPort`) -- a direct violation of AD-4's "adapters never import each other" (already the explicit rationale `adapters/observer_mux.py`'s own docstring gives for NOT reusing `process_posix.py`, and the same constraint every other method on `BmadLoopHarness` already respects: `spin`/`attach`/`run_foreground` all call `subprocess`/`Popen` directly, never through an injected `ProcessPort`). Implemented instead as a raw `subprocess.Popen` call inside `resume` itself, reproducing `PosixProcess.spawn_detached`'s exact recipe (`start_new_session=True`, `stdin=DEVNULL`, both streams to `log_path`, `PYTHONUNBUFFERED=1`, never waited on) -- mirroring the MECHANICS `ProcessPort.spawn_detached` documents, not literally calling through that Protocol. `stop` is likewise a direct, synchronous `subprocess.run` call (mirroring `attach`'s own captured-output shape), not a call through `ProcessPort.run`.

### 2026-08-03 -- third follow-up review: Code Map deviations for the monotonic elapsed basis

- **`core/supervise.py::Sample` carries a FOURTH field, `monotonic_s: float | None`.** The Code Map specifies `Sample` as a frozen dataclass of exactly `moment: datetime`, `pane_content: str | None`, `log_mtime: float | None`. The third follow-up review found that measuring elapsed idle time from `moment` alone makes the ladder score wall-clock JUMPS as idleness: a host suspended for an hour mid-run (or an NTP step) advances `moment` across an interval in which the session was not running and could not have produced output, so at the shipped 25-minute default the first tick after wake nudged and the next one hard-stopped and relaunched a healthy engine. `moment` is kept -- it remains the journal's timestamp basis and the anchor `idle_since` returns -- and the new field is OPTIONAL with a `None` default, so `evaluate_idle` falls back to `moment` deltas whenever either endpoint lacks a monotonic reading. Every pre-existing synthetic-sequence test therefore keeps its exact previous semantics with no edit.
- **`ports/clock.py::ClockPort` grows a second method, `monotonic() -> float`** (implemented by `adapters/clock_system.py::SystemClock` over `time.monotonic`). The Code Map does not list either file. AD-20's injected-clock seam is the architecture-consistent home for the reading: the supervisor takes it once per tick alongside `now()` and passes it into the pure core as a plain value, never calling it from inside `core/**`.
- **`core/supervise.py` exports a new public `idle_anchor(samples) -> Sample | None`**, with `idle_since` delegating to it (so the two cannot disagree, the same discipline `evaluate_idle`/`idle_since` already share). The supervisor's post-nudge rebase needs BOTH of the anchor's time readings; pinning only `moment` while letting `monotonic_s` fall to the current tick's reading would restart the very elapsed count that rebase exists to preserve.
- **`supervisor/__main__.py` no longer records a `Sample` on a tick whose pane is unobservable.** The Code Map says the tick loop "accumulates into a `list[Sample]`" without qualification. Recording unobservable ticks made a flaked `capture-pane` read as two changes (text -> `None`, `None` -> text), re-arming the idle window every time it happened; dropping them keeps the history to genuine observations, which is also what makes the pane-keyed observability guard coherent.

## Design Notes

**Why `stop`+`resume`, never a raw kill or a bare re-`run`.** Verified live against this repo's own upstream `bmad-loop` install: a bare re-`bmad-loop run` mints an unrelated run id with no in-flight lock anywhere in the engine, so it would happily re-select and double-dispatch the very story the wedged run is still (nominally) working, racing against whatever worktree/branch/agent-window state that run left behind. `bmad-loop stop <run_id>` (hard path) SIGTERMs-then-force-kills without needing the target to cooperate, tears down its tmux session, and marks it stopped; `bmad-loop resume <run_id>` reloads that exact run's state, re-derives its original selectors, self-clears any stale session, and (under this repo's own `scm.isolation=worktree` policy) auto-recovers the abandoned in-flight task from its baseline commit. This is the one pairing upstream itself documents and exercises for exactly this scenario.

**Why the window target is resolved live, never cached or formula-derived.** The session name is a pure formula (`bmad-loop-{harness_run_id}`, verified live), but the window id is backend-assigned at creation and never persisted anywhere Marshal could read it back from -- confirmed by grepping a live `state.json`/`journal.jsonl` for `window_id`/`native_id` and finding neither. Querying `tmux list-windows` at call time is also what upstream's own multiplexer seam recommends over caching a native id.

**Why `idle_threshold_minutes` joins the closed policy vocabulary rather than a hardcoded constant (unlike Story 3.4's `_TICK_SECONDS`).** `_TICK_SECONDS` had no AC calling it configurable; FR-12's own AC explicitly does ("the threshold is configurable"). The three existing SEED fields (`max_dev_attempts`/`max_review_cycles`/`max_followup_reviews`) are the established home for exactly this shape of operator-tunable numeric ceiling -- extending that vocabulary is the precedented path, not new surface invented for this story alone.

**Why the ladder rung is derived by floor-division over elapsed-since-last-change rather than a stateful counter threaded through the loop.** AD-20 requires the DECISION to be a pure function over the sample sequence -- computing `rung = min(idle_elapsed // threshold, DEFER)` from the samples alone (no external mutable ladder state passed in) keeps `evaluate_idle` trivially replayable against any synthetic sequence. The supervisor's own tick loop is the only place that tracks "last rung acted on," purely to decide whether THIS tick's computed rung is new -- an ordinary imperative concern, not part of the tested pure contract.
