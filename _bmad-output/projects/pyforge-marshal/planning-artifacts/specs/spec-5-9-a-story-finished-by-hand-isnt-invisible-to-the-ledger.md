## Intent

**Problem:** a story completed and merged entirely via `bmad-quick-dev` (no `bmad-loop` run ever touches it) never gets its `sprint-status-ledger.yaml` key advanced out of `backlog` -- nothing in `pyforge.marshal` knows `bmad-quick-dev` exists (repo-wide grep: zero hits outside planning prose), and the only writer of that tracked file, `scripts/promote_sprint_status.py`, only ever promotes bmad-loop's own Tier-3 feed. Story 5.4 already reports the *converse* mismatch (`merged-not-done-in-ledger`) diagnostically but never rewrites either source.

**Approach:** a new `marshal deploy reconcile-completions --project <slug>` command detects, from git alone plus corroborating spec evidence, every story merged to `main` via a route Marshal itself did not drive, advances its ledger key to `done` in a dedicated commit, and promotes its Tier-3 spec (reusing Story 4.1's already-shipped, completion-path-agnostic promotion scan verbatim).

## Boundaries & Constraints

**Always:**
- **Completion path is derived, never journal-sourced (AD-5/AD-33).** `core.promotion.merged_story_keys` already classifies each `main` merge subject via 3 patterns: AD-24 templated (`deploy land-story`'s own signature -- confirmed live, `cli/deploy.py::run_land_story` calls `identity.render_merge_subject`), bmad-loop-native, and generic GitHub PR-merge. A NEW `core/promotion.py::marshal_native_merged_keys(subjects, template, project_slug) -> frozenset[StoryKey]` returns only the first two (both Marshal-driven). A key present in `merged_story_keys` but absent from `marshal_native_merged_keys` is labeled `"not-loop-native"`, never `"bmad-quick-dev"`: `marshal land` (`cli/land.py::run_land`) is ALSO Marshal-driven but merges via `forge.merge_pr` using GitHub's own auto-generated subject -- byte-identical in shape to a human's plain PR merge -- so this detection cannot, from git subjects alone, distinguish a `marshal land` landing from a genuine `bmad-quick-dev` one (AD-5 forecloses the one signal, `marshal land`'s own journal, that could tell them apart). The label reports "Marshal doesn't already know this from a templated or bmad-loop-native subject," never "a human ran `bmad-quick-dev`" -- the detection mechanism itself is unchanged and correct; only the reported label's causal claim narrows to what is actually knowable from git alone. No journal/run-state is ever read for this classification. (A follow-up story could change `marshal land` to render the templated subject, which would then let it split cleanly out of this bucket -- explicitly out of scope here.)
- **A git match alone never triggers a write.** `extract_story_key_from_github_merge_subject` has a documented, unscoped cross-project collision (`cli/status.py::_merged_keys_for_slug`'s own docstring: ~30 false keys per foreign station, measured live). A not-loop-native key is only eligible when it is ALSO corroborated by a valid, durable Tier-3 spec for THIS project's own slug -- reuse `cli/deploy.py::_scan_promotions`'s existing `plan.to_promote ∪ already_promoted` (Story 4.1, unchanged) as that corroboration, never a second spec check.
- **Ledger write is a targeted line rewrite, not a re-render.** A new pure `core/status.py::render_ledger_advancements(ledger_text, raw_keys) -> str` replaces only each named key's existing `  <raw-key>: <status>` line with `  <raw-key>: done`, byte-identical otherwise -- never invents a new key, never touches the header/comments/ordering `scripts/promote_sprint_status.py` and `generate.py::parse_sprint_status` both depend on.
- **The ledger write closes its own Tier-3 divergence, never leaves it for a human.** `sprint-status-ledger.yaml`'s header names `scripts/promote_sprint_status.py` as its sole regular writer, sourced from the gitignored Tier-3 `sprint-status.yaml` feed; this command is a second, feed-bypassing writer, so after a successful ledger commit the tracked twin says `done` while the Tier-3 feed still says `backlog` for that key -- exactly the "twin ahead of feed" state `promote_sprint_status.py::regressions` + its `--repair-feed` flag were built to repair (2026-08-08 incident). Rather than leave this for the next `sprint-ledger-sync` run to trip over (it `continue`s past the WHOLE project, blocking unrelated status propagation, until a human passes `--repair-feed`/`--allow-regression`), the ledger-commit step in this command's own write sequence closes the gap itself immediately afterward, scoped to only the keys this run just advanced -- reusing `promote_sprint_status.py`'s existing repair-feed logic (extracted into a shared function if not already callable outside `main()`, never re-derived) rather than shelling out where a direct call suffices. A failure to close the gap is reported (`MRS-DEPLOY-027`, WARN) but does not roll back the ledger commit already made -- the next `sprint-ledger-sync` run's own `--repair-feed` remains the fallback, and `dashboard-drift-check`'s existing twin-ahead-of-feed detector (`pyforge.doctor.sources.board`) still catches it either way.
- **Two dedicated commits, one per concern** (AD-29's "only promotion paths" precedent, applied symmetrically): the ledger advancement commits only the ledger path; spec promotion commits only the promoted spec paths, scoped to exactly the keys advanced this run (not every durable spec `deploy promote` would otherwise catch). The Tier-3 feed repair-write is part of the ledger-advancement concern (it is the other half of the same durable-ledger-signal guarantee), not a third commit.
- **Reuses, never re-derives:** `_scan_promotions`, `is_valid_spec_text`, `HarnessPort.ledger_story_statuses`, `VcsPort.commit_paths`/`commit_subjects`, `core.identity.normalize`, `promote_sprint_status.py`'s repair-feed logic.

**Block If:** none -- the detection signal, corroboration requirement, and write shape are all fully determined by already-shipped primitives; nothing here requires human adjudication.

**Never:**
- Never read or write any run journal, `state.json`, or harness process state (AD-5) -- the whole detection path is git + the tracked ledger + Tier-3 spec files only.
- Never advance a key absent from the ledger map entirely (report it, `MRS-DEPLOY-026`, never invent a row) or already `done`.
- Never touch `bmad-quick-dev` itself, and never decide whether Marshal invokes it (PRD Q-16 stays open).
- Never fold this into `marshal status`'s default view or `--reconcile-ledger` (still read-only, Story 5.4) -- an explicit, separate write verb.

## Design Notes

**Why `land-story`'s templated form counts as "Marshal-driven," not "not-loop-native."** The Dream's own framing is binary (bmad-loop vs. everything else), written before `deploy land-story` existed. `land-story` re-runs Marshal's own gate and renders the merge subject from policy (`identity.render_merge_subject`) -- Marshal orchestrated that merge, so grouping it with bmad-loop (both "Marshal already knows") against every other route is the accurate two-actor split.

**Why the completion-path label is `"not-loop-native"`, not `"bmad-quick-dev"` (resolved 2026-08-12, see Spec Change Log).** `marshal land` (`cli/land.py::run_land`) is also Marshal-driven, but its default `landing_merge_strategy: "merge"` calls `forge.merge_pr`, which lets GitHub write its own auto-generated subject -- a shape byte-identical to a human's plain PR merge. Measured against this repo's real history: of the 52 keys `merged_story_keys` finds outside the templated/bmad-loop-native patterns, the large majority are `marshal land` landings, not genuine `bmad-quick-dev` sessions. AD-5 (git + ledger + spec only, never journal-sourced) forecloses the one signal -- `marshal land`'s own run journal -- that could tell the two apart, so this story reports the honest, coarser fact ("Marshal doesn't already know this from a templated or bmad-loop-native subject") rather than the previously-claimed, false-for-most-of-its-instances fact ("a human ran `bmad-quick-dev`"). The detection mechanism (`marshal_native_merged_keys`) is unchanged; only the reported label narrowed to what git alone actually proves. A separate follow-up story to change `marshal land` so it renders the templated subject (matching `land-story`) would let `marshal_native_merged_keys` classify those landings correctly going forward, narrowing this bucket back down toward genuine quick-dev sessions with no further change to this story's own code -- tracked as backlog, not a prerequisite for this story.

**Why the Tier-3 feed repair-write happens inside this command, not left to a human (resolved 2026-08-12, see Spec Change Log).** `sprint-status-ledger.yaml`'s own header names `promote_sprint_status.py` as its sole regular writer; this command adding a second, feed-bypassing writer without closing the resulting divergence would leave every subsequent `sprint-ledger-sync` run for the project refusing to write anything (`regressions()`'s own `continue`/`return 1` path) until a human passes `--repair-feed`/`--allow-regression` by hand -- neither wired into the pixi task. That silent, whole-project-blocking failure mode contradicts this story's own stated purpose (a trustworthy ledger signal requiring "no operator hand-edit"), so the write sequence repairs the feed for its own advanced keys immediately, reusing `promote_sprint_status.py`'s existing repair-feed logic rather than re-deriving it. `dashboard-drift-check`'s own twin-ahead-of-feed detector remains a second, independent safety net if the repair-write itself ever fails.

**Why corroboration reuses `_scan_promotions` instead of a second spec check.** `classify_promotion_candidates` already answers "does a valid, durable spec exist for this key" with zero knowledge of completion path (verified: it only tests `merged_keys` membership + `is_valid_spec_text`). Calling it once and using its output for both CAP-1 (as collision corroboration) and CAP-3 (as the promotion plan) avoids a second, potentially-diverging implementation.
