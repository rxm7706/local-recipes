- (decision by claude) OPEN QUESTION 1 ANSWERED (selector grammar) -- both flags, both explicit in CI: --pixi-environment and --pixi-platform; the extractor constructor takes environment: str | None and platform: str | None, and None/None keeps today's union. The platform defaults to the host ONLY for interactive use, never in CI. Reason: the extractor has no selector to extend today (extract/lockfiles.py:180-206 returns every entry of the flat top-level packages: list), so the grammar is greenfield; the Spec's Assumptions and src/platform/Containerfile (FROM --platform=linux/amd64) both pin python-agent-platform/linux-64, and a host default would silently produce a different closure on an arm64 runner -- exactly the misrepresentation the Dream was written to kill. Rejected alternative: environment flag only with the platform always host-derived (smaller surface, re-opens the cross-arch drift). Operator-approved 2026-09-09, fleet-readiness-decision-batch-2026-09-09.md row warden-B1 / section 2.3 C9.
- (decision by claude) OPEN QUESTION 2 ANSWERED (provisioning) -- CI takes the osv-native --download-offline-databases route on the connected runner (the Story 1.4 decision record's section-1 order); the DB is cached with actions/cache keyed by the snapshot date, and the daily key roll owns the refresh cadence -- no human refresh owner. Reason: nothing provisions it today (OSV_SCANNER_LOCAL_DB_CACHE_DIRECTORY appears only in warden package code and tests; zero hits across .github/workflows/), and the conda-packaged-DB alternative the record allows does not exist yet, so this is the only route that can land now; a date-keyed cache makes the 7-day strict staleness rule self-enforcing (a stale key simply misses and re-downloads). Rejected alternative: conda-package the OSV DB first -- cleaner air-gap story (NFR-S2) but blocks CAP-3, and therefore CAP-4 and the whole Dream, behind a packaging effort with no recipe. Operator-approved 2026-09-09, fleet-readiness-decision-batch-2026-09-09.md row warden-B2 / section 2.3 C9.
- (decision by claude) OPEN QUESTION 3 ANSWERED (coverage floor) -- NO coverage floor: a clean rung alone is the promotion gate; --fail-under-coverage is NOT added. Reason: this Spec's first Constraint already forbids the failure mode a floor would guard ('a selector that cannot resolve a component's identity keeps withholding it (UNMAPPED_ECOSYSTEM); it never drops it from the denominator'), so an unassessed component cannot be clean and the floor would be a second, redundant expression of the same rule plus a second number to tune; CAP-4 already requires the record to name unassessed components and the reason. Rejected alternative: --fail-under-coverage 100 as belt-and-braces (a second knob and a second way for the gate to red for a non-security reason).
