## Intent

**Problem:** No extractor exists for conda/pixi SOURCE manifests (`recipe.yaml`, `meta.yaml`, `environment.yml`, `pixi.toml`) — the tool sees only `pyproject.toml` and lockfiles today. The fleet's majority shape (a bare feedstock recipe with no Python packaging manifest) is invisible to both axes: no components extract, and `hygiene.py`'s own docstring already flags that DEP001 trust-gating "can't be reliably correlated to one component without Story 2.2's synthesized front-door (not yet built)."

**Approach:** Add 4 format-specific extractors (`extract/recipe_v1.py`, `meta_v0.py`, `environment_yml.py`, `pixi.py`) that parse-as-data: literal deps pass through; bare `{{ VAR }}`/`${{ VAR }}` context-variable refs resolve to their captured literal; anything else (filters, control flow, selectors) degrades to `NAME_ONLY`/`RAW_MALFORMED` — never crashes, never evaluates Jinja (2.3 owns the full construct matrix). Factor `extract/lockfiles.py`'s conda-identity component builders into a shared `extract/_identity.py` so all 6 extractors share one path. `run_constrained`/`run_constraints` entries are excluded entirely (never become a `Component` — no schema change). Wire `discovery.py`/`routing.py`/`extract/__init__.py` the same additive way 2.6 did. Give `DeptryEngine` an unconditional synthesized front-door (`--requirements-files <tempfile>`) so conda-sourced hygiene works; deptry's own priority rule makes this a no-op for existing pyproject-native scans. Build the differential-oracle (`tests/conformance/test_extraction_oracle.py`) for recipe.yaml/meta.yaml against `rattler_build`/`conda_build`'s real renderers, skip-if-unavailable, on a fixture-scale common-case corpus (2.3 later ratchets complex-construct fixtures against this same harness).

## Boundaries & Constraints

**Always:**
- Parse-as-data only: no `jinja2` import, no execution primitive — the AST-denylist meta-test (`tests/meta/test_extract_no_execution.py`, auto-discovers every `.py` under `extract/`) covers all 4 new files for free.
- `{{ VAR }}`/`${{ VAR }}` substitution is BARE-token only — `VAR` must be a literal string/number already captured (meta.yaml v0: regex-strip `{% set NAME = "..." %}` lines before YAML load, since they aren't valid YAML; recipe.yaml v1: `context:` is itself valid YAML, so `yaml.safe_load` the whole document first, then string-substitute on the parsed scalars). No filter/expression/function-call evaluation (`{{ version.replace(...) }}` etc. is 2.3's job) — an unresolved/unrecognized template degrades that one dependency to `NAME_ONLY`+marked (best-effort name) or `RAW_MALFORMED`, never a crash, never a guess.
- Walk `requirements.{build,host,run}` (both spellings) + the v0 singular `test.requires` / v1 list-valued `tests[].requirements.{build,run}` + `outputs[].requirements` (multi-output) for recipe.yaml/meta.yaml.
- `requirements.run_constrained` (v0) / `requirements.run_constraints` (v1) sections are recognized ONLY to be skipped — excluded entirely from the returned components (never counted toward vuln matching or SBOM counts; no `provenance: constraint` field — the frozen `Component` contract stays untouched).
- `pixi.toml` walks base `[dependencies]`/`[pypi-dependencies]` plus every present `[feature.<name>.dependencies]`/`[feature.<name>.pypi-dependencies]`/`[target.<name>.dependencies]`/`[target.<name>.pypi-dependencies]` table, routed through 6 GENERIC static section tokens (`routing.py`'s `_ROUTES` dict stays small/fixed — the feature/target NAME is never baked into the routing key, only into `Provenance.section`, e.g. `f"feature.{name}.dependencies"`).
- `pixi.toml`/`environment.yml` conda-ecosystem values use conda matchspec syntax (`name op version`, e.g. `numpy >=1.20`, bare `python`) — parse via a simple split, mirroring `pyproject.py::_exact_pin`'s discipline (only a bare/no-operator/`==` exact version is concrete; any range withholds `RANGE_ONLY`). `pixi.toml`'s `[pypi-dependencies]` tables and `environment.yml`'s nested `- pip:` list use PEP 508 syntax — parse via `packaging.Requirement`, identical to `pyproject.py`.
- Every conda-ecosystem row consults the shared `extract/_identity.py` path (factored out of `extract/lockfiles.py`, behavior-identical for lockfiles — existing 2.6 tests must stay green byte-for-byte): only a `verified`-confidence hit sets `pypi_identity`; anything else withholds `UNMAPPED_ECOSYSTEM`.
- NFR-S5: each new extractor bounds total-file-size + per-line-byte-length BEFORE parsing (mirror `extract/lockfiles.py::_read_bounded`'s two-cap pattern exactly, including for the TOML-based `pixi.py`, which otherwise would follow `pyproject.py`'s direct-`tomllib` precedent).
- `DeptryEngine.run` unconditionally synthesizes a `name==version` temp requirements file (system temp, `tempfile.mkstemp` + `finally: os.unlink` — mirrors `OsvEngine.run`'s own input-file idiom exactly, NFR-S4) from components where `hygiene_covered and pypi_identity is not None`, and always adds `--requirements-files <path>` to the existing `deptry . -o <output> --no-ansi` argv. This is safe unconditionally: deptry's own documented rule ("if a pyproject.toml with `[project]`/`[tool.poetry.dependencies]` is found, this argument is ignored") makes the addition a no-op for every existing pyproject-native scan — verified via `deptry --help`. Apply the same NFR-S6 token-safety purity guard `vuln._synthesize_requirements` uses (mirror `_is_safe_token`).
- The oracle (`tests/conformance/test_extraction_oracle.py`) covers ONLY recipe.yaml + meta.yaml (the two templated formats with a real render step), via verified-live APIs: `rattler_build.Stage0Recipe.from_yaml(text).render(VariantConfig.from_yaml("{}"))[i].recipe.requirements.to_dict()` (v1) and `conda_build.api.render(recipe_dir, finalize=False, bypass_env_check=True)[i][0].get_value("requirements/run")` etc. (v0) — both confirmed callable against a live fixture during spec research. `pytest.skip` (NOT `test_lockfile_oracle.py`'s hard-fail convention) when either import fails — explicit divergence from 2.6, because these renderers aren't guaranteed provisioned the way `py-rattler` already was. Assertion is NAME-LEVEL coverage only (`extracted-names ⊇ rendered-names`, modulo our `NAME_ONLY`-marked entries) — never version equality (the renderer variant-pins bare deps we correctly leave unversioned, confirmed live: bare `python` rendered `python 3.14.*`).
- `environment.yml`/`pixi.toml` get NO oracle: neither format has a template/render step — `safe_load`/`tomllib` parsing IS the ground truth, same as `pyproject.py`'s existing no-oracle precedent.
- C0c/NFR-S2 socket-deny holds automatically (no socket-capable import is legal under `extract/`'s AST-denylist; the whole-suite behavioral harness in `tests/conftest.py` covers every new test transparently).

**Block If:** none identified — routing/schema/renderer-API/deptry-CLI design questions are all resolved above.

**Never:** the full supported-construct matrix (`compiler()`/`stdlib()`/`pin_subpackage()`/selector-union/expression-degrade ratcheting — Story 2.3; 2.2 only guarantees no-crash degrade for what it doesn't recognize); the corpus-scale (~1,950 recipe) 0-uncaught-exception sweep (Story 5.2); Story 1.9's full multi-manifest deterministic-selection discovery policy (this story's discovery additions stay narrow/fixed-kind, like 2.6's); a `provenance: constraint` schema field; touching `verdict.py`/`DefaultPolicy`'s rung ordering; writing the synthesized deptry front-door into the scanned tree.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| recipe.yaml common case | `context: {name: mypkg, version: "1.2.3"}`, `run: [python, numpy >=1.20]` | Literal + context-resolved components, `PARSED` | No error |
| meta.yaml common case | `{% set version = "1.2.3" %}` + `run: [{{ name }} {{ version }}]` | Same as above via v0 syntax | No error |
| `environment.yml` with nested pip | `dependencies: [python=3.11, {pip: [requests==2.31.0]}]` | conda row (ecosystem=conda) + pypi row (ecosystem=pypi, exact) | No error |
| `pixi.toml` feature/target tables | `[feature.test.dependencies]` + `[target.linux-64.dependencies]` | Both routed via generic tokens; `Provenance.section` carries the concrete `feature.test.dependencies`/`target.linux-64.dependencies` string | No error |
| `run_constrained`/`run_constraints` present | `requirements.run_constrained: [scipy >=1.0]` | Zero components from that section — never in the returned tuple | No error |
| Unresolvable Jinja construct | `{{ version.replace('.', '_') }}` in a run dep | Degrades to `NAME_ONLY`+marked (best-effort name) or `RAW_MALFORMED` | Never raised as unparsable-manifest |
| Oversized/malformed line | line exceeds NFR-S5 byte cap | `UnparsableManifestError` | Report still emitted |
| Conda-only project + adjacent Python source | no `pyproject.toml`, `src/*.py` present | Front-door synthesized, deptry's DEP001/DEP002 findings surface | No error |
| Native pyproject.toml already present | `pyproject.toml` with `[project].dependencies` | Front-door still synthesized but deptry ignores `-rf` (native behavior byte-for-byte unchanged) | No error |
| Oracle: fixture recipe.yaml | common-case fixture, `rattler_build` importable | `extracted-names ⊇ rendered-names` | Assertion failure on real gap |
| Oracle: renderer unavailable | `rattler_build`/`conda_build` not importable | `pytest.skip` | Never blocks the suite |

**Acceptance Criteria** *(from `epics.md`, preserved verbatim):*

**Given** a common-case `recipe.yaml`/`meta.yaml`/`environment.yml`/`pixi.toml`, **When** extracted, **Then** it is **parse-as-data, never rendered** — the extract module imports no execution primitive and no `jinja2` (S1 AST-denylist) — and its deps land in the inventory (**FR3**). **And** pixi extraction covers the `[feature.*]` and `[target.*]` tables (provenance-tagged) beyond the base sections. **And** `run_constrained:`/`run_constraints:` entries are **constraints, not dependencies** — excluded from vuln matching + SBOM counts. **And** the C0c socket-deny gate holds (extraction performs no egress). **And** with adjacent Python source present, deptry consumes the synthesized front-door so **hygiene findings surface for the conda-sourced project too**. **And** extraction is **line-bounded with a per-line byte cap + a total manifest-size cap**, and no compiled pattern carries nested unbounded quantifiers (NFR-S5).

**Given** the **differential-oracle**, **When** it runs on the fixture corpus, **Then** the non-rendering dep-set ⊇ the rattler-build/conda-build render (modulo name-only-marked), with 0 uncaught exceptions. **And** the oracle is **skip-if-renderer-unavailable** so 2.2 never hard-blocks on renderer provisioning.

## Design Notes

**Why `context:`/`{% set %}` capture differs by format:** recipe.yaml v1's `context:` block is itself valid YAML — `${{ name }}` is just a string scalar, so `yaml.safe_load` the WHOLE document first, then string-substitute `${{ VAR }}` occurrences on the already-parsed structure's scalar values. meta.yaml v0's `{% set name = "x" %}` lines are NOT valid YAML — they must be regex-captured into a `dict[str, str]` and STRIPPED from the text before `yaml.safe_load` runs; then `{{ VAR }}` substitutes the same way. Any leftover unresolved `{{ }}`/`${{ }}` after substitution must never be handed to `yaml.safe_load` as-is (a bare `{{ }}` can be misparsed as YAML flow-mapping syntax) — quote it defensively or fall back to a raw-text name scrape for that one entry, degrading to `NAME_ONLY`/`RAW_MALFORMED`.

**Verified renderer APIs (live-tested against the `local-recipes` pixi env during spec research, not guessed):**
```python
# v1 (recipe.yaml) — rattler_build
from rattler_build import Stage0Recipe, VariantConfig
rendered = Stage0Recipe.from_yaml(text).render(VariantConfig.from_yaml("{}"))
rendered[0].recipe.requirements.to_dict()
# -> {'host': ['python', 'pip'], 'run': ['python', 'numpy >=1.20'], 'run_constraints': [...]}

# v0 (meta.yaml) — conda_build
from conda_build import api
metas = api.render(recipe_dir, finalize=False, bypass_env_check=True)
metas[0][0].get_value("requirements/run")  # -> ['python', 'numpy >=1.20']
```
Both were exercised live against throwaway fixtures; `conda_build`'s renderer variant-pins bare `python` to `python 3.14.*` (the host's own interpreter) — confirming the oracle assertion must be name-level, not version-equality.

**Why the deptry front-door is unconditional, not conditionally detected:** duplicating deptry's own "does a pyproject.toml with declared deps exist at cwd" sniffing logic in `DeptryEngine` would be a second, driftable source of truth. `deptry --help` confirms `-rf`/`--requirements-files` is silently ignored whenever deptry's own native detection succeeds — so always synthesizing + always passing the flag is strictly simpler and can never diverge from deptry's real behavior.
