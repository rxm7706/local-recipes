## Intent

**Problem:** The gate's robustness claims (0 uncaught exceptions, a bounded unparseable rate, the differential-oracle, byte-identical determinism, parallel no-shared-state execution, engine-version discipline) are only proven at hand-authored fixture scale (4-24 files) — nowhere near the ~20k-repo fleet this tool must survive. Engines also run sequentially today despite the architecture already asserting they run in parallel, and no committed task proves the tool is clean on its own manifest.
**Approach:** Harvest+pin this repo's own `recipes/*/{recipe.yaml,meta.yaml}` (938+1041=1979 files, ~8.6MB) plus a small adversarial set into a committed corpus fixture; mature the existing fixture-scale differential-oracle and add a new extraction-layer unparseable-rate ratchet over that corpus; parallelize the 4 axis engines with a `ThreadPoolExecutor` while preserving deterministic result ordering; add a stubbed-engine p95-overhead benchmark; add a dogfood pixi task + seeded-violation test; and close the corpus-scale egress-hardening item already flagged in `deferred-work.md` as owned by this story.

## Boundaries & Constraints

**Always:**
- The corpus is a **harvested, committed snapshot** under `tests/fixtures/corpus/`, not a live glob of repo-root `recipes/` — decouples the ratchet from this repo's constant, unrelated recipe churn (recipes/ changes daily; a live-globbed corpus would make the ratchet flaky for reasons unrelated to pyforge-warden's own code). A harvest script re-runnable to refresh the pin.
- The full-corpus **differential-oracle** (rattler-build/conda-build render per file) is measurably slow: the existing 4-fixture oracle already shows meta.yaml/conda-build renders at ~0.85s each — at ~1041 meta.yaml files that is ~15 minutes serially. It runs as its **own new, slower pixi task**, separate from the fast default `pyforge-warden-test` (which stays a `--frozen`-verifiable, sub-minute loop) — never folded into the default suite unconditionally. The pure-Python extraction-only regression gate (0 uncaught exceptions + the new unparseable-rate ratchet) IS fast (no subprocess) and stays in the default suite.
- Same skip-if-renderer-unavailable convention as today's oracle (`tests/conformance/test_extraction_oracle.py`) applies at corpus scale too — never a hard fail when rattler-build/conda-build aren't installed.
- Parallelizing the 4 engines (`cli.py`'s `for factory in engines_to_run:` loop) must reassemble `engine_results`/`errors`/`rungs` in the **original registration order** (`engines_to_run`'s order), never completion order — required for NFR-R3b determinism and the existing first-registration-order-wins dedupe convention. Per-engine instantiate+run stays wrapped in the SAME try/except typed-error contract it has today (crash → `ErrorRecord`, report still emitted) — parallelizing must not weaken that.
- The only pre-existing shared state across engines is three `@lru_cache(maxsize=1)` caches (`currency.py`, `mapping.py`, `report.py`) — already thread-safe (CPython's `lru_cache` is internally lock-guarded); no new locking needed, just note it so it isn't re-litigated.
- The perf/overhead benchmark stubs all 4 engines (instant-return fakes, mirroring the existing `register_engine_for_test` + `FindingsOnlyEngine`-style pattern in `test_scan_harness.py`) so it measures orchestration/report overhead only, per NFR-P-warm's "engines-stubbed" requirement — never real deptry/osv-scanner timing. It records the machine it ran on (`platform.platform()`, `os.cpu_count()`) alongside the p95 result (the "named reference machine", NFR-P-warm) and gated on p95 over N runs, never one run.
- `architecture.md:350` already flags the P-warm p95 threshold as needing calibration once the reference corpus exists — this story IS that calibration point: measure the real p95 on this machine, commit it as the enforced regression-gate constant (same first-measurement-sets-baseline pattern `UNPARSEABLE_RATE_BASELINE` already uses in `hygiene.py`), documented as machine-relative.
- The dogfood target is `src/shared/packages/pyforge-warden`'s own `pyproject.toml` (the package's own manifest) — not repo-root `pixi.toml` (a huge multi-feature monorepo file covering unrelated environments; scanning it would produce noise with no relationship to pyforge-warden's own dependency hygiene).
- Engine version discipline (NFR-C1) is already fully shipped by Story 6.6 (`_check_engine_version`, `engines.py:364-499`, ranges pinned + range-sync tested) — this story adds only a corpus/regression-gate-level regression test citing that existing behavior, not new production code.
- The corpus-scale egress-hardening item in `deferred-work.md` ("Deferred from: code review of spec-1-4...", "owned by Story 5.2") is closed via an **egress counter** (the item's own lighter alternative to a full network namespace): `strace -e trace=network` around one `--offline` corpus-scale engine subprocess invocation, asserting zero connect/sendto syscalls. Linux-only, skip-if-`strace`-unavailable (same convention as the renderer skips) — never a hard requirement on platforms without it.
- Verification uses `pixi run --frozen -e pyforge-warden pyforge-warden-test` (confirmed working: 1931 passed in ~50s on this worktree) — omitting `--frozen` currently trips an unrelated `bmad-ui` environment solve failure (a pre-existing, out-of-scope infra issue on this branch, NOT something this story fixes).

**Block If:** No unattended-unsafe decision identified — every open question above was resolved by investigation (corpus-pin-vs-live-glob, oracle task-splitting, dogfood target, perf-stub design, egress-counter scope) and recorded as an `Always` boundary with its rationale.

**Never:**
- No change to `models.py`, `data/report-schema.json`, `REPORT_SCHEMA_VERSION`, or `verdict.py`'s exit-code ownership — this story is validation/infra, not a producer or schema change.
- No new axis, no new CLI flag, no new report field.
- No full network-namespace sandbox for engine subprocesses — the deferred item's lighter "egress counter" alternative is the scoped fulfillment.
- The corpus fixture set is never included in the built wheel/conda package (`pyproject.toml`'s `packages = ["src/pyforge"]` already excludes `tests/` — preserve this).
- The adversarial out-of-repo sample stays small (a curated subset of `prefix-dev/rattler-build-parser-tests` at a pinned commit, plus a couple of hand-authored unicode/oversized-file cases) — never a full mirror of that upstream repo.

- `tests/conformance/test_corpus_regression.py` (new) -- iterates the full committed corpus directly through `RecipeV1Extractor`/`MetaV0Extractor` (no CLI/subprocess -- fast), asserting 0 uncaught exceptions per file; computes the fraction of files that are "unparseable" (either `UnparsableManifestError` raised OR ≥1 component degraded `RAW_MALFORMED`/`NAME_ONLY` -- DELIBERATELY broader than the originally-planned "degraded component" wording alone: a whole-file manifest-level failure is a MORE severe case of the same "didn't fully extract" concept, and a ratchet that only tracked component-level degrade would blindly miss a regression that turned many more real recipes into manifest-level failures) and asserts `current <= CORPUS_UNPARSEABLE_RATE_BASELINE = 0.4686` (measured this story: 931/1987 files, ~46.85%, doc-commented the same way `hygiene.py:87-88` documents `UNPARSEABLE_RATE_BASELINE` as an NFR-R2 ratchet — a real-world number, not a design target, driven by this repo's own heavy `pin_compatible()`/`compiler()`/expression-version Jinja usage). NFR-C1 is deliberately NOT re-tested here (cited, not duplicated — see the file's own docstring): `tests/meta/test_engine_version_range_sync.py` already fully covers it and needs no corpus-scale variant (an engine's `--version` output doesn't depend on which project is scanned). Part of the default `pyforge-warden-test` suite (pure Python, fast — measured 3.28s for all 3 tests in this file).
- `tests/conformance/test_extraction_oracle.py` (modify) -- **deviation from "replace the 4 hardcoded fixture paths":** the 4 existing precision fixtures (`recipe_common`/`meta_common`/`recipe_complex`/`meta_complex`) are KEPT, not replaced — they assert EXACT excluded-name sets (e.g. "`gcc_linux-64`/`sysroot_linux-64` are excluded on both sides") no corpus-scale sweep could replicate (a real corpus recipe's `compiler()` resolves to an unpredictable variant-driven name). Two NEW tests are ADDED, walking the full committed corpus (recipes + adversarial) with two necessary generalizations spelled out in the module's own docstring: (1) name comparison is case-INSENSITIVE (a real corpus recipe declared `PyPDF2` verbatim-cased; the renderer normalizes it, our extractor correctly preserves it as authored) and (2) a file's raw text matching `compiler(`/`stdlib(`/`pin_subpackage(`, OR our OWN extraction already producing ≥1 degraded component, excludes that ONE file from the strict per-file superset assertion (not from the render/extract ATTEMPT, which must still not raise) — corpus scale can't hardcode every possible resolved compiler-package name the way the 4 curated fixtures do. Measured this story: 228/945 recipe.yaml files and 711/1042 meta.yaml files were strictly comparable, 0 violations either side. The WHOLE MODULE (not just the 2 new tests) is marked `@pytest.mark.slow` and moved out of the default `pyforge-warden-test` collection, since every test in it needs a real renderer import and the Boundaries already treat the render-based-oracle concept itself (corpus-scale or not) as never belonging in the fast default suite.
- `tests/conformance/test_corpus_determinism.py` (new) -- extends the existing `test_twice_run_stdout_is_byte_identical` pattern (`test_scan_harness.py:242`) to the full committed corpus `recipes/` directory as the scan target, asserting byte-identical stdout across two `--deterministic` runs. **Deviation:** ALSO marked `@pytest.mark.slow` (not called out explicitly in the original Code Map, but forced by the "well under a minute" default-suite acceptance criterion) — unlike `test_corpus_regression.py`, this goes through the REAL `cli.main` seam and invokes a real `osv-scanner` subprocess against the corpus's full merged inventory; measured ~7s per run, ~14s for the required twice-run, which would have pushed the default suite noticeably past budget if left in it. Lives in the same `pyforge-warden-test-corpus-oracle` task as the render-based oracle (the pixi.toml bullet's own "(and any other corpus-scale test whose cost is dominated by real renders/subprocesses...)" carve-out anticipates exactly this).
- `src/pyforge/warden/cli.py` -- `_run_scan`'s engine loop (`cli.py:1203-1275`, the `for factory in engines_to_run:` body) switches to a `ThreadPoolExecutor`-based fan-out. The per-engine instantiate+run+typed-error-catch unit is factored into a new module-level `_instantiate_and_run_engine(factory, config, target, inventory)` helper (placed just above `_run_scan`) that touches NO shared state — it returns `(EngineResult, None)` on success or `(None, <_record_error kwargs dict>)` on either a crashing constructor or a crashing `run`, so `errors`/`rungs`/`engine_results`/the `_record_error` stderr diagnostics are all mutated ONLY on the main thread, in `engines_to_run`'s own registration order (futures are collected into a list in that order, then drained via `future.result()` in the SAME order — never `as_completed()`), preserving NFR-R3b exactly as the pre-5.2 sequential loop did.

## Design Notes

**Why pin the corpus instead of live-globbing `recipes/`:** this repo's `recipes/` tree changes constantly (an active packaging factory — hundreds of PRs). A live glob would make the corpus-scale ratchet's pass/fail depend on unrelated, concurrent recipe edits rather than on pyforge-warden's own code — exactly the kind of flakiness a "committed, versioned fixture set" (epics.md's own wording) is meant to prevent. This also matches why corpus-provisioning is explicitly sequenced as 5.2's *first* task in epics.md: it decouples the harvesting spike from the regression gates that consume it.

**Why the render-based oracle gets its own pixi task:** the existing 4-fixture oracle already measures conda-build (meta.yaml/v0) renders at ~0.85s each; at ~1,041 committed meta.yaml files that is roughly 15 minutes run serially — incompatible with keeping `pyforge-warden-test` a fast, `--frozen`-verifiable default loop (currently 1931 tests in ~50s). Splitting preserves both: a fast day-to-day suite and a slower, still-committed, still-runnable full-corpus proof.

**Environment note:** `pixi run -e pyforge-warden <task>` without `--frozen` currently fails in this worktree — solving trips over an unrelated `bmad-ui` environment's missing local channel (`build_artifacts/linux64/`), a pre-existing issue on this branch unrelated to pyforge-warden. `--frozen` sidesteps it cleanly (verified: 1931 passed in 49.53s) and is already the project's documented canonical verify convention (sprint-status.yaml's repeated "canonical --frozen gate" language) — use `--frozen` for all verification in this story.

**Dogfood: what "exit 0 today" actually required (investigation, 2026-07-24):** the literal `warden scan src/shared/packages/pyforge-warden` command was empirically NOT exit-0 before this story's changes, for two independent, pre-existing reasons the original Code Map didn't anticipate:

1. `discovery.discover()` has no ignore mechanism (FR1's own full-tree-walk design) — it recursively finds every manifest under the target, including this package's OWN `tests/fixtures/projects/` (deliberately malformed/vulnerable fixtures `test_scan_harness.py` and friends exist to exercise: `sentinel`, `vuln_critical`, `vuln_kev`, ...). Live-verified: 86 findings from that tree alone, driver `indeterminate:uncovered:${{ some_undefined_filter | replace("a", "b") }}` — pure test-fixture noise, zero relationship to this package's own dependency hygiene (exactly the reasoning the Boundaries already applied to explain why repo-root `pixi.toml` isn't the target, just not carried through to this package's own `tests/`).
2. Even scoped to just `{pyproject.toml, src/}` (excluding `tests/`), `pyproject.toml` declares its 6 dependencies with NO version pins (a deliberate library convention — the file's own comment: "lean, targeted dependency set") and ships no lockfile. `classify_conda_specifier`/pyproject.py's exactness rules withhold ANY unpinned or range-only dependency from vulnerability matching (`indeterminate:no-version:`) — by design, never a bug — and the SAME unpinned state makes currency resolution impossible too (`currency:unknown:`). A bare (non-pytest) `warden scan` invocation also has no ambient OSV DB provisioned (unlike the test suite's `conftest.py` fixtures), adding `indeterminate:offline-db-unavailable:` for the same 6 deps. This is 19 stable, fully-enumerable findings — verified byte-identical across 3 repeated runs (ruling out a parallelism-introduced race in this story's own `cli.py` change).

Resolution: `scripts/dogfood_scan.py` stages `{pyproject.toml, src/}` only (closes #1), and the new committed `.warden-baseline.yaml` (`--baseline`, an EXISTING flag/mechanism, Story 6.8) grandfathers the 19 known findings (closes #2) — see that file's own header for the full per-finding rationale and the regeneration command. A THIRD, genuine bug fell out of this investigation and was fixed directly rather than grandfathered: `license.py` imports `license_expression` (deptry's DEP003, "imported but a transitive dependency") — it was already a real `pixi.toml` conda run-dependency (Story 6.2) but missing from `pyproject.toml`'s own `dependencies` list; added.
