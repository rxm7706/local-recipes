## Intent

**Problem:** pyforge-warden gates hygiene and vulnerability findings today but has no visibility into license exposure — a maintainer cannot see, let alone block, a component whose SPDX license is unresolvable or organizationally disallowed (FR32/FR33).

**Approach:** add a third `Engine` (axis `"license"`) that derives an honest `allowed | denied | unknown` verdict per component (conda `about: license:` pre-build, PyPI via `importlib.metadata` when installed) and normalizes it via `license-expression`; wire `--allow-licenses`/`--deny-licenses` into `config.py`'s policy tables; cap every license finding at the `warn` rung (real escalation is story 6.5's, not this story's); and deliver the reusable "no axis producer exceeds warn" conformance meta-test that story 6.3 will register into.

## Boundaries & Constraints

**Always:**
- Register `LicenseEngine` behind the existing `Engine` protocol (`interfaces.py:196-203`) with `axis="license"` (`AXIS_LICENSE`, `models.py:42`) — no interface changes.
- `license_rung` (new, in `license.py`) unconditionally returns `Status.WARN` for every license Finding — it must NEVER consult `config.license_policy` or produce `policy-violation`/`indeterminate`. The parameterized ceiling meta-test (new) enforces this mechanically.
- A license `Finding` is emitted ONLY for `denied`/`unknown` verdicts (never `allowed`) — the grammar `license:<spdx-expression-or-"unknown">:<pkg>@<ver>` is already enforced at construction by `Finding.__post_init__` (`models.py:379-414`); every producer-supplied id segment passes through a module-local `_sanitize_id_segment` copy (matching `hygiene.py`'s/`vuln.py`'s no-cross-import convention, not `interfaces.py`'s private helper).
- Verdict semantics (this story owns computing the verdict, not escalating it): with NEITHER flag set, every resolvable license is `allowed` (nothing restricts it) and every unresolvable one is `unknown`. With `--deny-licenses` set, a resolvable license matching an entry is `denied`. With `--allow-licenses` set, it becomes an allow-list: any resolvable license NOT in the list is `denied`. If a license matches both lists, `denied` wins (defensive default).
- `AxisCoverage` for the license axis: `deps_assessed = deps_total = inventory.count` — every component gets a real attempt this story (`license_covered` stays inert/`True`, matching 6.1's landed-inert design; no structural exclusion mechanism is activated).
- `EffectiveConfig.license_gating: bool` (new property, `True` iff `allow_licenses` or `deny_licenses` is non-empty) is a real, tested value threaded into the reported `AxisCoverage.gating` for the license axis (`report.py:285-298`) — transparency of configuration state, independent of the fact that escalation itself is deferred to 6.5.
- `EffectiveConfig.license_policy` (new `@property`, `dict[LicenseVerdict, Status]`, mirrors `vuln_severity_policy` at `config.py:261-279`) is defined this story per the architecture's ownership split, even though nothing consumes it until 6.5.
- Reuse the existing neutralize-then-load helpers for reading `about: license:` from conda manifests — `strip_jinja_comments`/`neutralize_bare_braces` (`extract/recipe_v1.py`) for `recipe.yaml`, `strip_jinja_statements`/`neutralize_unquoted_braces` (`extract/meta_v0.py`) for `meta.yaml`, dispatched by the `Component.provenance` manifest's basename — followed by `yaml.safe_load`. Never re-implement Jinja neutralization.
- `license-expression` is added to `pixi.toml`'s `[package.run-dependencies]` as `"*"` (matching `deptry`/`osv-scanner`'s existing unpinned convention; range-pinning is story 6.6's job).

**Block If:** none identified — all design ambiguities below were resolved during planning; nothing here requires human disambiguation.

**Never:**
- Never touch `verdict.py`'s lattice/exit-code logic, or `interfaces.py`'s `DefaultPolicy.evaluate` axis branches for `AXIS_HYGIENE`/`AXIS_VULNERABILITY` (sole-ownership guard, `tests/meta/test_verdict_sole_ownership.py`).
- Never implement the real denied→policy-violation / unknown→indeterminate escalation — that is story 6.5's sole ownership.
- Never perform source-level (ScanCode-class) license scanning.
- Never add a `--fail-on-license`-style blocking flag — the v1 gate activation is exactly `--allow-licenses`/`--deny-licenses` (FR33).
- Never widen `report-schema.json`/`models.py`'s frozen fields — 6.1 already added everything this story needs (`LicenseVerdict`, `LicenseInfo`, `Finding.license`, `Component.license_covered`, the `license:` id grammar).

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Conda resolvable, no flags | conda component, `about: license: MIT` | verdict `allowed`; no Finding emitted | — |
| PyPI unresolvable, no flags | bare uninstalled PyPI manifest, no flags | verdict `unknown`; Finding `license:unknown:<pkg>@<ver>` at `warn`; `AxisCoverage.deps_assessed == deps_total` | never a silent clean |
| PyPI installed, resolvable | package importable via `importlib.metadata`, PEP 639 `License-Expression` present | verdict `allowed`, normalized SPDX recorded; no Finding | falls back to legacy `License` then trove classifiers if PEP 639 absent |
| Deny-list match | `--deny-licenses GPL-3.0-only`, component license = `GPL-3.0-only` | verdict `denied`; Finding at `warn` (never higher this story) | — |
| Allow-list, non-member | `--allow-licenses MIT`, component license = `Apache-2.0` | verdict `denied` (allow-list semantics: not-listed = denied); Finding at `warn` | — |
| Both flags, overlapping match | license in both `--allow-licenses` and `--deny-licenses` | verdict `denied` (deny wins) | — |
| Malformed conda manifest | `about:` section present but license value is not a string | verdict `unknown`; never a crash | producer degrades, never raises |
| No `about:` section at all | conda recipe with no `about:` key | verdict `unknown` | — |

## Design Notes

**Verdict vs. rung split:** this story computes the *verdict* (`allowed`/`denied`/`unknown`, requiring the configured allow/deny lists) but never the *rung* above `warn` — `license_rung` is a pure warn-cap, oblivious to `config.license_policy`. Story 6.5 later swaps the `DefaultPolicy.evaluate` `AXIS_LICENSE` branch (or `license_rung` itself) to consult `license_policy` for real escalation. This split is why `EffectiveConfig.license_policy` is defined now but has no caller yet — matches the epic's explicit ownership note.

**Allow-list semantics:** an allow-list is deny-by-default for its complement (an item not in `--allow-licenses` is `denied`, not `allowed`) — this is the conventional compliance-tool interpretation and the only reading under which `--allow-licenses` actually restricts anything.

**Conda license source of truth:** `Component` intentionally carries no raw license field (`inventory.py`'s docstring: per-component verdict data lives on `Finding`, never `Component`). `license.py` re-reads the manifest at `Component.provenance[0].manifest` under the scan `target`, reusing `recipe_v1.py`'s/`meta_v0.py`'s public neutralize helpers — never a fresh Jinja/YAML pipeline, never bare-var substitution (a templated `about: license:` degrades to `unknown`, never a crash). A single manifest is re-read/re-parsed AT MOST ONCE per scan regardless of how many conda components it declares (`license_findings`'s own `conda_cache` dict, verified by `test_conda_manifest_is_read_at_most_once_per_manifest`).

**License findings compose into the overall verdict exactly like every other WARN-tier finding (correction to the original plan's Verification wording):** the plan's Verification bullet said "`status` still composes from hygiene/vuln only (license never escalates yet)" — that undersold what actually happens. `license_rung` feeds a real `Status.WARN` rung into `verdict.compose`, the SAME composition path every hygiene DEP002-005 warn and every non-critical CVSS warn already feeds — there is no per-axis exemption mechanism in this codebase, nor should there be (the Boundaries only forbid escalating ABOVE warn, not contributing warn at all). Concretely: a scan whose hygiene/vulnerability axes are both clean but which has even one component with an unresolvable/denied license now composes `warn` (exit 0, since `warn_is_error` is never set by `cli.py`) instead of `clean` — this is the intended, spec-mandated behavior ("never a silent clean," I/O matrix), not a regression. This is WHY four pre-existing test files needed updating (see Code Map) — every one of them constructed a "clean" or fixed-finding-count scan using fixture dependencies that are not genuinely installed (`leftpad`, `pdos-vuln-fixture`, a raw-malformed name, `numpy` sourced from a lockfile with no `about:` section), so the license axis now honestly surfaces an `unknown` finding for each. Two fixtures (`clean/`, `hygiene_not_applicable/`) were UNAFFECTED because their `requests`/`packaging` pins happen to already be genuinely installed (as `pyforge-warden`'s own transitive/direct dependencies) with real, resolvable Apache-2.0 licenses — proving the "allowed emits nothing" half of the design in the same motion.

**`pixi.lock` regeneration (deviation, with rationale):** a real re-solve (`pixi install -e pyforge-warden`, `pixi update -e pyforge-warden license-expression`, `pixi lock`) reliably fails in this worktree — NOT on `pyforge-warden`, but on the unrelated `bmad-ui` environment, whose `[feature.bmad-ui]` channel (`./build_artifacts/linux64`) is a LOCAL, not-yet-built conda channel this fresh worktree never populated (the exact "known, unrelated pre-existing issue" the story brief anticipated). **`family` derivation scope (deviation/clarification):** `LicenseInfo.family` is populated from a small, curated, LOCAL SPDX-id→family table (`license.py::_SPDX_FAMILY`, ~20 entries covering MIT/BSD/Apache/GPL2/GPL3/LGPL/AGPL/MPL/ISC/Unlicense/PSF/Zlib) for a single (non-compound) resolved license only — a compound (`AND`/`OR`) expression's family is `None`. This is deliberately NOT the `license-expression` package's `get_scancode_licensing()` (which vendors the full ScanCode license database, ~2,400 entries including thousands of `LicenseRef-scancode-*` ids) — using that for a SYMBOL-VALIDATION lookup would still be defensible, but a curated ~20-entry table is simpler, sufficient for the common cases the I/O matrix actually exercises, and avoids any ambiguity about whether it crosses into "ScanCode-class scanning" (the Boundaries' explicit "Never").
