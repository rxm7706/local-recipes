- (decision) Paradigm: Design-Code-Bridge with Etagged Pull Model — Single immutable Design prototype per station is source of truth (etagged .dc.html, tracked). All code-side artifacts derive via pull model. Conflicts detected by etags, never silent overwrites.
- (decision) Design Source of Truth — One .dc.html file per station (9 total) is the immutable design prototype. Tracked in git. All markdown/PPTX/narration derives from it. Design edits happen in Claude Design cloud; Code pulls etagged copies.
- (decision) Multi-Format Export Pipeline — Design → Pull (etagged) → Markdown (marp) → PPTX (deckcraft) + Narration extraction → HTML deck engine + Video scripts. Each format has specific ownership/regenerability.
- (decision) Artifact Tracking Strategy — Track source + final deliverables (design protos, markdown, PPTX, narration, SVG infographics). Gitignore intermediates (fragments.json, dist/, assets/, .mp4) as regenerable. 62% footprint reduction vs unoptimized.
- (decision) Modernist Design Tokens — Single token source (Figma variables) rounds through design-tokens.json → PPTX templates → deck engine → video production bible. Tokens enforce consistency across all 9 stations.
- (decision) Nine-Station Replication — Framework (Design-Code-Bridge, Deckcraft, Video-Scripts, Modernist-Identity) applied identically to all 9 stations. Per-station content varies (thesis, pain point, personas). No re-engineering per station.
- (decision) Narration Script Extraction — Extract speaker notes mechanically from Design protos → narration-YYYY-MM-DD.md per station. Tracked for video pipeline readiness. Enforced blacklist via linter.
- (decision) Video Pipeline Boundary — Herald orchestrates narration extraction + real screen-recording sourcing. BMad-Manticore is downstream (voice, graphics, SFX, rendering). Herald does not render video.
- (constraint) Immutability of Design Prototypes — Design .dc.html files are immutable at the Code side. All changes originate in Claude Design; Code pulls, never pushes code-side edits back to Design.
- (constraint) Etagged Round-Trip Safety — Every Design ↔ Code transfer includes etag validation. Write operations fail if etag mismatches, preventing silent overwrites. No exceptions.
- (constraint) No Fabricated Demos — All screen recordings in video output are real, recorded from actual product. No AI-generated mockups, synthetic UI, or fabricated product demos.
- (constraint) Narration Voice Identity — Narration must match published voice character (WPM, speech patterns, tone markers). Blacklist enforced by linter before any video render.
- (constraint) Modernist Token Authority — Figma is the authority for design tokens. Token updates must flow Figma → design-tokens.json → templates. Never hardcode colors/fonts in templates.
- (constraint) Multi-Surface Readiness — All artifacts must be production-ready before shipping. No "preview" or "draft" states. PPTX opens in PowerPoint; HTML renders without errors; SVG renders inline.

- (decision) AD-11 (was AD-1, from architecture-herald-moments-2-4-2026-08-02): CLI — Single Dispatcher with Subcommands. One herald entry point; subcommands progress, success, notice dispatch to Moment logic. Shared global flags: --help, --json, --date-range <start>..<end>, --station <name>. Binds: CLI structure recognizable across all three Moments; subcommand routing clean and extensible. Prevents: separate CLIs per Moment; loose argument conventions. [ADOPTED] — Herald v0.1.0 uses this pattern; extend it.
- (decision) AD-12 (was AD-2): Web Surface — Unified 4-Tab Navigation. Single Herald web app; header nav with 4 tabs: Pitch (Moment 1, external link), Progress, Success, Operations. Unified sidebar: station filter, date range selector, search box. Responsive layout. Binds: users see a coherent Herald, not disconnected surfaces; navigation conventions shared across all Moments. Prevents: separate web apps per Moment; inconsistent tab naming or layout. [ADOPTED] — Herald v0.1.0 web surface integrates existing Pitch tab; extend with Progress, Success, Operations tabs.
- (decision) AD-13 (was AD-3): Data Model — Moment-Owned Records with Evidence Links. Each Moment owns its record type — Progress (Moment 2), Claim (Moment 3), Notice (Moment 4) — with fields per its PRD. Cross-linking via evidence protocol (URL + type pairs). No shared database schema across Moments. Binds: each Moment can evolve independently; evidence links are durable. Prevents: monolithic schema; lossy evidence. [ADOPTED] — Spec defines three record types; stories implement independently.
- (decision) AD-14 (was AD-4): Automation — Webhook + Cron + Gate Dispatch. Automation rules are data, not code, stored in Herald config: per-Moment trigger rules (event type + handler name). Moment 2: on-ship webhook + Thursday 2300 UTC cron. Moment 3: on-PR-close webhook (extract) + operator gate (publish). Moment 4: manual author (no auto-trigger). Binds: operators can modify automation rules without recompiling; retries/rate limits/error handling centralized in dispatcher. Prevents: automation buried in story code; incidental inconsistency between webhook and cron handlers.
- (decision) AD-15 (was AD-5): Evidence Protocol — Shared Link Schema & Validation. Evidence links follow schema: { type: test_results|metrics|adoption|other, url, label }. Validation: sync (404 on publish) + async (weekly stale-link check). Binds: Moment 3 claims and Moment 4 notices can link to each other (bidirectional); evidence validation is consistent. Prevents: dead links in claims; ambiguous link types. Storage: evidence links stored inline (claim/notice fields), not as separate records.
- (decision) AD-16 (was AD-6): Operator Authorization — Role-Based Write Gates. Write operations require operator role (publish claim, author notice, update progress). Read operations are public. Role verified at CLI + web layer (same auth source). Binds: consistent auth across CLI and web; operators can't accidentally publish unreviewed claims. Prevents: asymmetry between CLI and web gates; silent auth failures. [ASSUMPTION]: Herald app has existing session/auth model; CLI uses implicit auth; confirm with ops team.
- (decision) AD-17 (was AD-7): Storage Strategy — Database-Backed, Archive-Friendly. Progress records and Success claims stored in database (queryable, indexed). Moment 4 notices stored as markdown files in archive folder structure (YYYY-MM/category/name.md), with database index for quick discovery. Redirects stored in database. Binds: fast queries for Moment 2 & 3; durable archive for Moment 4; simple ls inspection of archive. Prevents: pure-file storage for Progress/Claims (slow filtering); pure-database archive (hard to inspect/backup). Backup strategy: database nightly, archive files tracked in git (or synced to S3).
- (decision) AD-18 (was AD-8): State Machine — Claim/Notice Lifecycle. Progress records are immutable (once published, not edited — new record for next update). Success claims: Draft to Published to Closed (optionally versioned if thesis is edited). Notices: Draft to Published to Closed (with edit history preserved). Binds: progress audit trail is clean; operators can retract unpublished claims; closed notices stay visible. Prevents: retroactive edits confusing readers; loss of notices post-deadline.
- (decision) AD-19 (was AD-9): Resilience — Automation Reliability & Fallback. Webhook failures trigger exponential backoff + max 3 retries (configurable). If exhausted, logged to operator dashboard + alert sent. Cron jobs run in dedicated queue (no blocking web requests). If automation fails, operator can manually trigger via CLI. Binds: transient failures don't lose work; operators have fallback path; clear visibility into automation failures. Prevents: silent lost data; timeout cascades. [ASSUMPTION]: Herald has existing queue/job infrastructure (from Moment 1 or v0.1.0); reuse it, don't build new.
- (decision) AD-20 (was AD-10): Extensibility — Future Moments. Paradigm and dispatcher are extensible: new Moments add a new subcommand + handler without touching existing Moment logic or CLI structure. Evidence protocol and automation framework designed for 10+ Moments without rearchitecture. Binds: Moment 5+ can be added as stories in future epics; CLI remains stable. Prevents: revisiting dispatcher logic per new Moment.
