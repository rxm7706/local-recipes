## Intent

**Problem:** Herald's existing Marp/HTML deck pipeline exports `.pptx` files that are proven non-editable (2026-08-22 inspection: shipped exports are background-image slides with zero text runs), yet the 21-station deck program is delivered to stakeholders who need to edit slides.

**Approach:** Build a second, parallel PPTX-generation module that parses a `.potx`/`.pptx` template once into a machine-readable `spec.json` contract (layouts + placeholders), fills a `content_plan.json` into that template mechanically via python-pptx's high-level API (never hand-written OOXML), and proves the output's text runs are genuinely editable. Ships as new `herald deck pptx-spec` / `herald deck pptx-fill` subcommands alongside (never replacing) the existing Marp/bridge pipeline.

## Boundaries & Constraints

**Always:**
- Fill placeholders only through python-pptx's object model (`text_frame`, `placeholders[idx]`, `add_paragraph()`); never construct or edit raw OOXML/XML strings.
- Coexist with the existing Marp/bridge pipeline (`deck_pipeline.py`, `cli.py`'s `marp-*` pull targets) — do not modify, rename, or remove any of it.
- The "own-template question" (spec-pptx-deck-generation `open_questions`) is resolved by this story: since no operator-supplied `.potx` exists and this is an unattended run, adopt python-pptx's own built-in default Office-theme template (11 stock layouts with real inheriting placeholders) as PyForge's interim template, committed as a binary at `src/shared/packages/pyforge-herald/src/pyforge/herald/templates/pyforge-deck-template.pptx`, generated by a small, re-runnable script (never hand-edited). Record this as a dated decision (2026-08-22) in Design Notes below.
- `spec.json` is derived generically from whatever template path is given — swapping in a future PyForge-branded `.potx` requires zero pipeline code changes.

**Block If:** None identified — the one open design question (own-template) is resolved above, not deferred.

**Never:**
- Do not attempt to author new slide *layouts* inside a template via python-pptx (not supported without raw OOXML surgery — out of scope).
- Do not implement CAP-2 (custom shapes / autofit, spec-pptx-custom-shapes) — out of scope for this story; only leave the produced `Presentation`/slide reachable enough that a downstream call could add shapes to it (no specific hook required yet).
- Do not touch Epic 14's `deck_qa.py` gates — unrelated pipeline, per spec-pptx-deck-generation non-goals.

## Design Notes

**Own-template decision (2026-08-22).** Neither named option in the open question is executable unattended: a hand-derived "six-act visual system" `.potx` would require authoring custom slide layouts, which python-pptx cannot do without raw-OOXML surgery (explicitly forbidden by this epic's constraints); an operator-supplied `.potx` requires a human who isn't present in this run. Instead, this story adopts python-pptx's own bundled default Office-theme template verbatim (`pptx.Presentation()` with no path argument) as PyForge's interim "own template" — it is a genuine, PowerPoint-authored `.pptx` with 11 real layouts and inheriting placeholders, requires writing zero OOXML, and is trivially swappable later: because `extract_spec` derives `spec.json` generically from whatever template path it's given, dropping in a future branded `.potx` needs no pipeline changes, only a new template file and a `--template` flag pointing at it.

**Placeholder fill, preserving inherited formatting:**
```python
def _set_placeholder_text(placeholder, value: str | list[str]) -> None:
    lines = value if isinstance(value, list) else [value]
    placeholder.text_frame.text = lines[0]
    for line in lines[1:]:
        placeholder.text_frame.add_paragraph().text = line
```
Setting `.text_frame.text` (rather than touching XML) lets the run inherit font/size/color from the slide layout/master — this is exactly the mechanism that makes the output editable, and it's the same regression the old Marp pipeline's `<a:blip>`-based export failed.

**"Round-trip proven" test proxy.** Real PowerPoint isn't available in this environment, but `soffice` (LibreOffice 24.2, confirmed installed at `/usr/bin/soffice`) is — a genuinely independent, third-party OOXML-consuming application, not the same library that wrote the file. The test: (1) assert the freshly-written `.pptx`'s slide XML has `<a:t>` runs with the expected text and no `<p:pic>` covering those placeholders (catches the exact old-pipeline defect directly); (2) round-trip it through `soffice --headless --convert-to pptx --outdir <tmp> <file>` and re-parse *that* output with python-pptx, asserting the same text survives — this is the closer "surface-anchored" proof, since a different engine had to genuinely interpret and re-emit the OOXML rather than us re-reading our own write. Skip step 2 gracefully (log + continue) only if `soffice` is unexpectedly absent from the test environment; do not treat that as this story's failure.
