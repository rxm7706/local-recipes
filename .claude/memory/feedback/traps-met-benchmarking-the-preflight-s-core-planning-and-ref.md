Traps met benchmarking the preflight's core planning and refreshing marshal's durations (2026-11-27, PR #2442; steward Story 117.34): (1) Read the scheduler before assuming oversubscription. The preflight already sizes each xdist lane's workers at admission (steward Stories 117.3, 117.15 and 117.22). The journal (.steward/preflight-runs.jsonl) records xdist_workers, start_offset, seconds and cpu_seconds per lane, so utilisation is sum(cpu_seconds) / (total_seconds x cores): 79% on a 49-lane run. (2) Benchmark the full preflight fairly. Set PYFORGE_PREFLIGHT_REUSE=0, or a green verdict for the tree is reused. Make a local scratch commit that touches only workflow comments, so every lane is selected; spec-surface reds on it, as expected. Alternate the settings, at least two runs each. Plan for N cores with python -c "import sys, pyforge.steward.preflight as p; p._logical_core_count = lambda: N; sys.exit(p.main(['--keep-going']))"; --jobs follows the cores. (3) Planning 24 cores on this 16-core laptop used 15 to 50% more CPU for the same work and was no faster (367 and 369 s, against 277 and 367 s at 16). Back-to-back full runs slow down as the machine throttles: the same setting took 277 s, then 367 s, with CPU seconds rising run to run. Never compare a first run with a later one. (4) The session hook will not delete a branch whose tip would orphan commits, so a benchmark's scratch branch stays until the operator runs git branch -D. (5) A durations file goes stale in its weights, not only its keys. Marshal's knew all but 10 of its 13,791 tests, yet summed to 732 s where the suite now takes 239 s, because tests had got faster since. Before trusting a split, store a fresh file from empty (the lane's own task, PYTEST_XDIST_AUTO_NUM_WORKERS=4, --store-durations into a new path). Then simulate both files' splits and score them by the fresh times: 47/77/46/68 s of work became 59.5 s each. (6) Look locally before probing the runner. If the local four-worker split shows CI's pattern, the file is the cause and no runner probe is needed: marshal showed 20/28/18/24 s locally against 53/67/47/63 s on CI. If the local split is even and CI's is not, as with herald, probe the runner. (7) Read shard times over several runs before calling a shard slow: marshal's slowest shard moved between 2 and 4 from run to run (nine runs here). (8) A PR that changes only a durations file runs none of the jobs it rebalances: marshal-test did not fire on PR #2442, so the effect shows on the next PR that touches marshal.
