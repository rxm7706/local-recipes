Traps met rebalancing the live halves' CI shards and cutting the coverage gates (2026-11-27, PRs #2412 and #2413; steward 117.25 to 117.27, herald 60.1): (1) Under --dist loadgroup, xdist's worker appends @<group> to each grouped test's id (xdist/remote.py) before pytest-split, which runs last, splits. A durations file stored without xdist keys those tests by their bare ids, so on CI they count at the file's average. Store each file from empty (--store-durations merges into the file it reads, so stale keys stay), under the lane's own task with PYTEST_XDIST_AUTO_NUM_WORKERS=4 and --durations-path=<new path>. Store herald's only after docs-site-install, with HERALD_DOCS_SITE_REQUIRED=1, or 49 built-site tests skip and record nothing. (2) Reproduce CI's split offline before pushing: collect the lane once, give grouped ids the @<group> suffix, and run pytest_split.algorithms duration_based_chunks on them. With the old files this matched CI's split test for test. (3) A shard's wall time is at least its heaviest xdist group on one worker, its longest single test and its start-up; pytest-split balances sums only. A module whose cost is more than one shard's share always spans two shards, and each of them pays the module's shared fixtures (steward's trigger-map derivation, about 20 s per shard on CI). A single long test sets its shard whatever the file says (marshal's tea-architecture smoke test, 37.9 s on CI). (4) The laptop and the runner disagree per test (test_ci_status.py::test_ac6_consumers_read_master_fixture: 1.0 s here, 21.7 s on CI). To measure on the runner, push one commit that adds --durations=0 --durations-min=0 to the jobs' PYTEST_ADDOPTS, sum setup, call and teardown per id from every 'slowest durations' section of the logs, then remove the flag. Simulate before committing CI-measured files: here they left every lane's longest shard unchanged, because a fixture shared across a module is charged to whichever test each worker ran first, so the laptop files were kept. (5) Runner noise is large: the same files gave steward's third shard 77 s on one run and 42 s on the next. Read at least two runs before calling a change better or worse. (6) Herald's built-site tests fail with TMPDIR on tmpfs ('No cached compile metadata found', EXDEV), and git push runs the pre-push preflight with the shell's TMPDIR. Push with TMPDIR=$HOME/.cache/pyforge-preflight-tmp/push. main fails the same way there, so that red is the TMPDIR, not the diff. (7) A commit that adds a workflow flag and a later commit that removes it still red docs-currency on every page that lists the workflow under sources:, though the net diff against main is empty: the detector reads commit dates, not content. Re-verify the page (its verified date) with a memlog line and a scoped stamp. (8) Measure a job's anatomy before sharding it. Atlas's live half spends most of its 65 to 84 s test step starting three pytest runs: the first collects 3,396 tests to keep 370 (collection alone 8.8 s, repeated by every xdist worker), and its tests take about 17 s of wall time. A second shard would save about 10 s. The station gates were the better lever: 21 to 28 s each, 10 to 17 s of it setup-pixi. (9) A gate job that only judges uploaded reports needs no pixi environment: scripts/coverage_gates_ci.py --report imports only the standard library and calls git. Removing a setup-pixi step means lowering its workflow's hits= in scripts/pixi_version_registry.py: pixi-version-check counts exact hits, and tests/scripts/test_workflows_and_scripts_do_what_they_name.py requires every setup-pixi step to be registered. tests/scripts/test_coverage_gates_ci_driver.py now reds a gate job with setup-pixi or pixi run, and a non-standard-library import in the driver (checked in python -I -S). (10) workspace start makes no implementation-artifacts/ in the worktree. To sync a ledger there, copy the primary's sprint-status.yaml in and add the key. After the merge, copy it back, check the two match, delete the worktree's copy, then run workspace clean --delete.
