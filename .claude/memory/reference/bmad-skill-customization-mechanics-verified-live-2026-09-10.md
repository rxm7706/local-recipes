BMAD skill customization mechanics (verified live 2026-09-10 against docs.bmad-method.org/customize/customize-bmad, docs.bmad-method.org/customize/add-modules, github.com/bmad-code-org/BMAD-METHOD, bmadcode.com -- full detail at .claude/docs/bmad-skill-customization-mechanics.md). No sanctioned BMAD mechanism extends or patches an existing installed skill's step-file PROSE content. Three independent surfaces confirm this: (1) the _bmad/custom/<skill>.toml / .user.toml override layer is schema-bound to each skill's own customize.toml -- agent persona fields, workflow output/templates/toggles, [[agent.menu]]/[[workflow.review_layers]] arrays, activation_steps_prepend/_append hooks only; it deep-merges structured fields, never replaces file content, and cannot delete a base item. (2) BMAD's own suggested path for step-prose changes is to fork the skill, but BMAD provides NO formal fork mechanism -- installed skill folders are documented read-only ('never edit it; updates overwrite it'), forking is informal and self-managed with no built-in safeguards. (3) The module system (Add Modules) is purely additive/isolated -- a custom module installs as an entirely new, separate skill; it has no hook into an EXISTING skill's step files. CONCLUSION for this repo: in-place-editing an installer-owned step file (e.g. .claude/skills/bmad-build-auto/step-01-clarify-and-route.md) plus governing it via a marshal spec's surface: list + memlog (spec-surface-check drift detection) plus Story 14.8/CAP-8's automated byte-diff-scan + 3-way-merge reapplication after every BMAD update (customization-inventory.md row C5) is not merely this repo's best available option -- it is the ONLY real safety net for this class of change; BMAD upstream offers nothing equivalent.
