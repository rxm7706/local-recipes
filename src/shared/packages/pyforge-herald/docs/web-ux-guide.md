# Herald Web Surface UX Guide

Story 12.2. What the web dashboard (`src/shared/packages/pyforge-herald/web/`)
actually shows an operator, and — the single most important operational
fact about it — how to make sure it isn't showing stale data.

## The one thing to know: it's a static snapshot, not a live app

The Herald web dashboard is a plain static Vite bundle with **no backend
server, no live API**. Every panel reads a pre-generated JSON file from
`web/public/` at page load:

| Tab | Reads | Regenerated by |
|---|---|---|
| Progress | `public/progress.json` | `web/scripts/sync-progress.mjs` (copies `.herald/progress.json`) |
| Success | `public/success.json` | `scripts/export_web_snapshot.py` (reads `.herald/claims.json`) |
| Operations | `public/notices.json` | `scripts/export_notices_snapshot.py` (reads `.herald/notices-index.json`) |

None of these three exporters run automatically when you run a `herald`
CLI write command. `herald progress warden --update` writes
`.herald/progress.json`; it does **not** touch `public/progress.json`. If
you don't re-run the matching export step, the web dashboard keeps showing
whatever it last had — with no error, no warning banner, nothing visibly
wrong. This is the number one cause of "I ran the command but the
dashboard didn't update."

### Regenerating each Moment's snapshot

**Progress** — wired as a pre-step of `dev`/`build` (`predev`/`prebuild` in
`web/package.json`), or run it standalone after recording new progress
without a full rebuild:

```
cd src/shared/packages/pyforge-herald/web
npm run sync-progress
```

It resolves the source `.herald/progress.json` against this package's own
fixed location (not your shell's cwd), so it works the same regardless of
where you invoke `npm run` from. Override with `HERALD_PROGRESS_PATH` or a
positional arg for a nonstandard layout. A missing source file is not an
error — it writes `[]` so the app still builds and shows its empty state.

**Success** — not wired into any npm script; run it by hand after
publishing a claim:

```
python scripts/export_web_snapshot.py --repo-root <repo-root>
```

Defaults: `--repo-root` is cwd, `--out-dir` is `web/public/` (relative to
the package root, not your cwd — pass `--repo-root` explicitly when
running from elsewhere). Writes `success.json` containing only
**published** claims (drafts never ship to the public snapshot).

**Operations** — same story, run by hand after authoring/publishing/closing
a notice:

```
python scripts/export_notices_snapshot.py --repo-root <repo-root>
```

Writes `notices.json`, excluding drafts (published + closed only).

There is no single "sync everything" command today — each Moment's
exporter is invoked separately. If you just ran several `herald` write
commands across Progress/Success/Operations and want the dashboard
current, run all three.

## Running the dashboard locally

```
cd src/shared/packages/pyforge-herald/web
npm install
npm run dev       # http://localhost:5173, HMR, auto-syncs progress.json first
```

or a production build:

```
npm run build
npm run preview   # http://localhost:4173
```

## Tab-by-tab UX

Four tabs (`TabNav`, top of the page): **Pitch**, **Progress**, **Success**,
**Operations**. Pitch is an *external* link (opens
`https://github.com/rxm7706/local-recipes` in a new tab) — it is not an
in-app panel, so there is nothing to sync for it.

### Sidebar filters (shared across Progress/Success/Operations)

- **Station** — a dropdown of the known PyForge Guild stations (`warden`,
  `atlas`, `marshal`, `mason`, `doctor`, `scribe`, `steward`, `herald`).
- **Date range** — two free-text `YYYY-MM-DD` inputs, either can be blank
  for an open-ended range. A `?` help icon next to the label expands an
  inline explanation of the format (click or Enter/Space) — this is the
  one worked example the original UX spec (Story 7.2) called out
  explicitly.
- **Search** — free-text; scoped per-panel to whatever fields that panel
  matches against (e.g. Success matches project name + thesis).

Every input in the sidebar also carries a hover/focus tooltip
(`Tooltip.jsx`) naming what it filters, for a first-time operator who
hasn't read this guide.

### Progress tab

Card-per-station, showing the **latest** record for each station matching
the current filters. Collapsed: station, date, shipped-capability count,
total compute hours. Expanded (click the card): full capability list, the
cost breakdown (compute hours / token spend / wall-clock hours), and the
unblock narrative.

**Empty state:** "No progress recorded yet." (or "No progress recorded for
`<station>`." when a station filter is active), with a copy-paste command
hint: `herald progress <station> --update`.

**Error state** (snapshot fetch failed, e.g. `progress.json` missing or
unparseable): "Could not load progress.json." with the fix: "Run `npm run
sync-progress` (or `npm run build`) after recording progress, then
reload."

### Success tab

Card-per-claim (published only), showing project name, thesis, shipped
date, and one evidence badge per evidence item. Badge states, each with
its own tooltip:

| Symbol | Meaning | Tooltip text |
|---|---|---|
| ✓ | valid | "`<type>`: valid (valid since `<date>`) — `<url>`" |
| ✗ | broken | "`<type>`: this link may be broken (`<never/last validated>`) — `<url>`" |
| ⚠ | stale | "`<type>`: hasn't been validated recently; review it (`<...>`) — `<url>`" |

Expanded (click the card): full thesis, evidence links (clickable, open in
a new tab), edit history (each prior thesis version with its timestamp),
and status/shipped/published/closed dates.

**Empty state:** "No published claims." with the hint:
`herald success create <project> && herald success publish <claim-id>`.

**Error state:** "Could not load success claims." with the fix: "Run
`python scripts/export_web_snapshot.py` to regenerate success.json."

### Operations tab

Notice board, one card per notice (published + closed; drafts never reach
this snapshot). A **Category** dropdown local to this panel (`deprecation`
/ `fix` / `eol` / all) sits above the board; the shared sidebar's date
range filters against `created_at`. Each card header shows the category
badge, component name, status, and deadline (if any); expanding shows
what/why/migration text, the evidence link (if any), and — for a closed
notice — the close reason.

**Loading state:** "Loading notices…"

**Empty state:** "No operations notices yet." with the hint: `herald
notice author --type deprecation --component <name> --publish`.

**Error state:** "Could not load operations notices." with the fix: "Run
`herald notice list` from the CLI, or re-export web/public/notices.json."

## Responsive behavior

- **Desktop (>=1200px):** sidebar always visible.
- **Tablet (768-1200px):** sidebar collapses behind a hamburger; opening it
  overlays the content as a drawer.
- **Mobile (<768px):** everything stacks vertically (no overlay), body
  text floors at 16px, interactive targets are >=44px.
