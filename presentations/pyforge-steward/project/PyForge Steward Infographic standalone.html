The problem and the model
01

The problem

The Implementation view names Deployment & Operations a first-class stage of the lifecycle — and in the crew it fell between two chairs. The Pages console deployed by a hand-run task and a push; the pixi estate synced by convention; keys lived in environment variables with no owner and no lifecycle. The repo paid for that gap twice: _http.py attached the JFROG_API_KEY auth header to every outbound request regardless of host until a human caught it, and a committed provider key needed git history rewritten and the key rotated. Same underlying fault both times — privilege that outlived its intended scope, caught after the fact. Nothing in the Guild owned prevention until the ownership audit found the stage orphaned and adopted the Provisioner.

Privilege that outlives its scope is only ever caught after the fact — unless someone owns prevention as a duty. The Provisioner's mindset is custody: engines present before the line spins, services answered-for when they break, a credential scoped to the hosts it was issued for and retired the day its deployment ends, a ceiling declared where a machine can read it. Charter § Steward — the station is the post, not the person; a duty's evidence outlives the session that produced it.
02

Four duties — the contract at a glance

The Spec is deliberately thin: a CLI formalizing what this repo's maintainer already did by hand, cloning the already-shipped Warden packaging pattern rather than reimplementing Vault, Backstage, ArgoCD or Kubecost at a scale a one-person factory does not have. Every capability carries a success criterion written to fail when it is absent and a verified: line from a mechanical re-verification at a named HEAD. The Spec reads shipped; the Dream reads realized.

CAP-1keys
Credential lifecycle, one CLI
issue · scope · rotate · audit · inventory · record revocation. A credential declared with a host allowlist is never attached outside it; rotate re-encrypts under a fresh identity and the old one fails afterward; list never prints a raw value; the historical cross-host leak is a named regression test that fails loudly if the gating is ever removed.

Consolidation, not a platform. Domain and technical research converged on the same verdict: no Vault, Backstage, ArgoCD or Kubecost enters the dependency graph. Every duty adapter is a subprocess call or a thin import into a tool that already exists — _http.py, age, pixi, git, gh, the BMAD installer. A duty module carrying its own copy of logic that lives elsewhere is a review-blocking finding.
The counter-signals the Spec refuses to optimize. The number of duties shipped is not a score — a budget duty growing Kubecost-scale before any real spend exists is over-building. Key-rotation frequency is not a metric — more rotations is not better. What must hold: the leak pattern has a passing, named regression test, and the reconciled deploy replaces every manual build-and-push from here on.
03

The estate — what Steward wraps, and who stands on it

A hub with two rails. On the left, the tools that already existed and that Steward shells out to or thinly imports — never re-implements. On the right, the stations and surfaces that stand on what Steward provisions, deploys, keys and budgets. The hub itself is coordination: one Duty protocol, one dispatcher, one owner of the process exit code.

Duties are added by naming a new module on the same protocol, never by teaching an existing one a second job. The registered set grew from the four contract duties to sync, workspace, upgrade, suite, the machine-bootstrap family, restore and revoke — each one a thin face over a tool the estate already had.
04

The Canopy — Steward's flagship chain, the whole contract at a glance

Eight stations that each shipped as an excellent command-line tool — and stopped there. Eight terminals, eight mental models, no shared identity, no way for one station to tell another that something happened. spec-pyforge-unifying-strategy, owned by Steward, mounts all eight under one hub-and-spoke modular monolith: one ASGI process carries chrome, identity, portals and service faces; heavy work goes to Celery; infrastructure is exactly PostgreSQL + Redis + Kubernetes. The Canopy is Steward's surface, not a ninth station — the roster stays at eight.

One protocol, structurally checked. Duty is a Protocol, not a base class — a duty inherits no behaviour it did not ask for, and conformance is checked by shape. A duty not yet implemented for a subcommand returns a result carrying an explicit not-implemented status rather than raising. The NullDuty seam has existed since the first story so the protocol was exercised before any real duty landed.
Why every duty is thin. The keys module decides only host membership and whether a function's header attachment is gated — it never builds a request. The deploy module diffs and commits — it never renders a dashboard itself. The provision module reads a table and shells out — it never resolves an environment. The one place logic lives is the tool that already owned it; Steward is the grammar, the evidence and the exit code.

Persona, grammar and the skills wielded

Skills are wielded, never worn: the Smith authors and upgrades them, and the harness that governs the agent is deliberately not a skill. Steward's identity is a persona plus one content skill plus the platform surfaces it owns — and it is the station that proved the skill-plus-persona shape and built the five-tier reporter the whole roster is measured by.

Persona

bmad-agent-steward

The addressable station persona. Acts only through pyforge steward … grammar and POST /stations/steward/mcp; never freelances against the filesystem, never makes an ad-hoc HTTP call, never touches a secret value. Greets, then dispatches — a crash is exit 70, never a failed duty, in every sentence it speaks.

Content skill

pyforge-steward (SKF)

Compiled from src/shared/packages/pyforge-steward/ as an agentskills.io content skill — quick start, the duty grammar, DutyResult and the exit-code projection, "flags not nested verbs" on provision — so an agent reads documented behaviour instead of training data. Consulted, never imported: the package exports only its version.

Portal and service face

/stations/steward/

The Lane 2 portal in its own django-steward distribution — its first job the estate's own status — and the MCP face on the host ASGI. The secure-live-dashboard pattern the other portals adopt (identity at the boundary, an access declaration per board, a master-dataset cache) was built here first, behind the optional [dashboard] extra.

Craft it never replaces

conda-forge-expert

Recipe work belongs to the CFE craft, at skill version 8.90.5 with gotchas numbered to 117. Steward's prove-landed runs CFE's meta-tests as one of its gates and the air-gap rule makes a PyPI-only package Mason's feedstock work — Steward authors no recipe and edits no CLAUDE.md or AGENTS.md.

The two doors, and only two. Path B is the unified grammar — pyforge steward keys list, pyforge steward provision --verify, pyforge steward upgrade bmad-core --target … — dispatched from the repo root, never a hardcoded absolute path, never the bare steward binary as a second public contract for personas. The service face is POST /stations/steward/mcp on the Canopy host. A transcript of a completed station task shows only those two, plus the one permitted skill consult.
What the persona may never do. No direct filesystem against .steward/, pixi.toml or the chart; no curl, requests, httpx or WebFetch; no printing a secret; no second PR-gate verdict; no replacing conda-forge-expert; no scripts/bmad-switch from a fan-out. The forbidden list is the doctrine, written as a contract an agent can fail.

Three flows, one shape — reconcile, gate, prove

Three duties compose the same idea differently: deploy diffs before it mutates, provision verifies a gate the CI already enforces, upgrade proves an installer landed. Each ends in one frozen result and one documented exit code; nothing downstream re-derives what a stage already read.

The autonomy gradient — how far a duty may act on its own

Steward's autonomy runs from free observation to irreversible mutation, and the further right a verb sits the more explicit the human act that unlocks it. Reporting is free; reconciliation is diff-gated and idempotent; a mutation of keys or the BMAD core needs a flag the operator typed; the outward, irreversible steps of the estate's own cutover are ledger-blocked until the operator flips each one by hand.

Reporting is free
a report-only verb never writes: keys list prints metadata, pin-fan-out enumerates sites it will never edit, pipeline-truth probes fail-open and aborts nothing
Reconcile is idempotent
the second run with no source change produces zero commits; a webhook is a wake-up, never a value source; both sides of a sync are re-read every time
Mutation needs the flag the operator typed
--apply, rotate, revoke — each lands on a review branch or prints remediation guidance; none touches a provider API or main
Outward steps are held
opening the foundry repo, Mason's first outward submit, archiving this repo — every one a story held blocked and flipped by hand at dispatch, never auto-drained

The doctrine — nine architecture decisions the code is tested against

AD-1 · Wrap, never reimplement.
Every duty adapter is a subprocess call or a thin import into _http.py, age, pixi, git, gh or the BMAD installer. A duty module carrying its own copy of logic that already exists elsewhere is a review-blocking finding.
AD-2 · Keys have one chokepoint.
Host scoping delegates to auth_headers_for; the allowlist reads the delegate's own URL table. No duty constructs a request carrying ambient auth, and no Steward-owned URL config duplicates the one that exists.
AD-3 · Encrypted at rest, no standing service.
age and age-keygen are required external run-dependencies, never vendored. Encrypt, decrypt and rotate shell out to the CLI. No Vault-, Infisical- or OpenBao-class server enters the graph.
AD-4 · Deploy is CLI-invoked reconciliation.
A diff is computed before any git mutation; a no-diff run performs zero commits. No daemon, no scheduler, no new workflow — the operator or an existing workflow invokes the CLI against the existing Pages branch.
AD-5 · Provision wraps Marshal-owned machinery.
pixi install -e runs verbatim; the [environments] table is read for inventory and never written; loop homes are marshal init's alone — two stations never ship two ways to make the same thing.
AD-6 · Budget is declared, not enforced — yet.
budget check returns a distinct not-configured code; "no data" never collapses into a pass. No cost-SDK import exists until a real metered spend source lands — Actions minutes are named as the first.
AD-7 · One Duty protocol; missing degrades, never crashes.
Every duty exposes a protocol-conforming object; the dispatcher goes through the protocol only. A duty not yet implemented for a subcommand returns an explicit not-implemented result rather than raising.
AD-8 · The exit code has one owner.
main() alone returns a process code — catching interrupts, a duty's SystemExit and any other exception with fixed, documented values. A crash is never conflated with a duty that legitimately failed; a duty never calls sys.exit.
AD-9 · Enterprise routing inherited, never duplicated.
Any new outbound endpoint is one new row in _http.py's existing resolver convention — truststore, JFrog, GitHub and .netrc chain included — never a parallel Steward-specific mechanism.
And the conventions that ride beside them. Credential entries carry a provenance — issued or observed — and only issued ones rotate. A secret value is never printed under any flag, enforced by an invariant test. Pixi invocations are explicit, user-triggered actions, never import-time side effects. Configuration lives in the tracked repo-root .steward/ dotdir — a durable operational fact survives a switch of the active BMAD project, so it does not belong under a per-project planning tree.

The deployed estate — enterprise, air-gap, and the lines that hold there

The Canopy's deployment target is air-gapped and regulated, so this was never merely a UI project. Every artifact resolves inside the boundary; a build and deploy executed with external egress blocked must succeed end to end, and any external reference is a failing check, not a warning. Steward carries that gate and the estate's own routing chain — _http.py's truststore and JFrog / GitHub / .netrc auth — so a mirrored deployment configures once and every duty inherits it.

Infrastructure is exactly PostgreSQL + Redis + Kubernetes. A component demanding a fourth backing service has failed its design review; DuckDB is a query face, not a store. Two dated exceptions widened consumption, never self-hosting: an S3-compatible object store and managed PostgreSQL and Redis may be consumed as ops-provided endpoints — configuration-selected, beside the bundled defaults, with backup responsibility named rather than assumed away. No object-store server ever ships inside the image or chart.
Every Python dependency resolves from conda-forge. The egress-blocked build is a gate, not a warning: a PyPI-only package is new feedstock work for Mason, scheduled as such. The chain paid that price knowingly — OpenFeature feedstocks absent from the channel entirely, a Liquibase build with the JDBC driver vendored — because container images are governed separately under the internal-registry rule and neither boundary substitutes for the other.
Identity revocable, secrets delivered, schema governed. Portal authorization derives from IdP roles — revoke a role and access is gone on the next request. Pod specifications carry secret references only; go-sops and age are the in-estate vault, a vault server stays a profile adapter outside the image. Production schema change flows through one Liquibase authority enforced by database privilege: the app role provably cannot CREATE, ALTER or DROP.
Failure contained, data safe, agents bounded. A durable, memory-bounded broker on a volume that loses no queued task on restart; TLS verified on the wire; a DR contract with backup plus WAL archive and a drill; per-subject rate limits on the service faces, a per-station queue ceiling, a concurrent-run ceiling; prefixed roles with bare station names refused; deploys by digest, never latest. Every invariant has a test that fails with the mechanism absent.
The attended bring-up that made it real. The chart deployed on a local OpenShift cluster with the official database and cache images under an assigned UID, persistent volumes bound, Liquibase applied and Django reconciled with migrate --fake, the health endpoint answering; then the follow-through — the agent-runtime sidecar ready, the app role running DML-only, the MCP host sidecar up, the front door published from PostgreSQL. The one isolated migration that stays faked is recorded by name; the optional portability CI waits on Actions minutes. An honesty gap, not a stamp gate.

Integration seams — every edge, and its direction

Steward's boundaries are enforced by meta-tests and import rules, not by convention. Each seam below has a stated direction and a check that fails when the direction is violated.

steward → _http.py (import)

keys.py delegates host membership and header gating to auth_headers_for; sync.py transports through open_url. Steward decides whether a header attaches — never how a request is built. A new endpoint is one new row in the delegate's resolver table.

steward → age · pixi · git · gh · installer (subprocess)

Every mutation of the world is a thin, argv-as-list subprocess wrap of the tool that already owns it. pixi.toml is read for inventory and never written; _bmad/ has one writer, the installer; the dashboard is built by the task that already built it.

steward → the host's own commands (never Django)

restore loads the platform's backup module without importing the host; revoke drives manage.py revoke_subject through the platform interpreter named on the command line. Run state has exactly one writer — the supervisor — and Steward is never a second implementation of the platform's own work.

steward → warden (hook plugins)

Deploy-profile adapters register on pyforge.core.hooks as default plugins. publish_verdict for a Warden-owned spec raises — the plugins may never publish a PR-gate verdict. A default Warden run stays green with none of them enabled.

steward ↔ marshal (the ratified seam)

Loop homes, the build line and its worktrees are Marshal's; environments, modules, the estate and scratch worktrees are Steward's. provision --runner reports and points at marshal init; workspace cannot see a loop home by construction. The seam's obligations landed as their own epic.

The Canopy ↔ steward (import rule, with carve-outs)

src/platform/ consumes the factory's published packages and never imports pyforge.* source — an import-linter rule. Two recorded brownfield exceptions remain until their owning stories land: the project-board ingest under the platform imports pyforge.steward keys and sync, and the atlas portal's tests allow-list the steward dashboard. Exceptions are dated, never a repeal.

What the dependency graph must never contain. A Vault-, Backstage-, ArgoCD- or Kubecost-class client; a cost SDK; a Django import in the steward package itself; pyforge.doctor as a run-dependency (the suite probes reuse Doctor's shapes without importing it); a second registration mechanism beside pyforge.core.hooks. Each absence is asserted by a test or a repo-wide grep the Spec's verified: lines record.
