01

The problem

Hardened enterprises need analytics that cannot assume a writable root or a root UID. A gist architecture existed; the running stack does not. Capability counts live in the folded Atlas satellite Spec and are omitted here because this deck's glob cannot see them.

Realization dates on this ledger: 2026-04-19 · 2026-07-23.

The founding brief names three specific pains a regulated OpenShift shop runs into: Restricted SCC gives process isolation, not code isolation — a non-root, read-only pod still runs a Python process with the full language surface available to anything inside it, with no second boundary between the pipeline’s own trusted code and logic derived from a file a user just uploaded. Observability and lineage are usually bolted on after the fact, per pipeline, inconsistently, so the cost stays invisible until an audit needs a trace that was never wired end to end. And without one toolchain spanning local dev, container verification, and production, “works on my machine” and “works in the digital twin” and “works in the actual cluster” are three separate, drifting claims.

The maturity verdict is scoped, not evaded: DuckDB has no WASI build and no WASI roadmap, so the sandbox covers only the Excel upload-validation step — ingestion and transformation stay conventional hardened processes until that upstream fact changes. Everything downstream of that one honest sentence — the five capabilities, the architecture invariants named on this poster, the toolchain — is built on top of it, not around it.

What makes this worth building at all, rather than as a plain OCP-hardened pipeline with no Wasm layer: the sandboxing claim is meant to be mechanically verifiable, not aspirational. The founding PRD is explicit that it claims a narrower, provably-true thing than the architecture gist it descends from — the one place untrusted input first touches the system is sandboxed at the code level and checked by an automated gate, and everything downstream of that point runs on an already-hardened, already well-understood OCP process boundary. That is a smaller claim than the original gist made, and, per the technical research, the larger claim is not buildable with today’s ecosystem.

Nothing on the rest of this poster claims more than the folded Spec itself claims: five capabilities (CAP-27 through CAP-31), seventeen functional requirements, and ten architecture decisions, all still unimplemented. Where a number has no facts.yaml row backing it — the capability count chief among them — this poster says so in place of marking it, rather than guessing.

02

The pipeline, end to end

One seed use case, five stages, one sandbox boundary.

The upload step is OIDC-gated FastAPI; validation runs inside a genuine WASI Preview 2 component; ingestion is dlt into DuckDB Bronze; transformation is dbt-duckdb, producing schema-declared Silver and then Gold. OTel spans and OpenLineage facets tap every stage and land in Marquez, correlated end to end by one W3C trace ID minted once at ingress.

runs inside the WASI sandboxconventional trusted process

Design paradigm: pipes-and-filters, staged as a medallion pipeline — Upload → Validate → Ingest → Transform → (Serve, deferred). Each stage is a filter with one input and one output shape; stages never reach into each other’s state. Validate alone additionally follows ports-and-adapters: its WIT interface is the port, and the componentize-py-compiled component is the one adapter behind it — deliberately not a whole-system hexagonal architecture, since only the validate stage needs, or per the research can currently sustain, a real language-sandboxed boundary.

Nothing downstream of Validate is meant to call back into it, and nothing in Transform is meant to call Ingest directly — the two hand off exclusively through the shared DuckDB file, never a direct call, which is also what makes the single-writer rule in Act IV enforceable rather than aspirational.

Only the middle box runs inside the sandbox. dlt, dbt-duckdb and DuckDB itself stay conventional hardened processes in this design — not because the design flinched, but because DuckDB has nowhere to run as a WASI component today. The seed use case is deliberately narrow: an Excel upload of headcount/cost-shaped data, not a general ETL surface, because narrowness is what makes the isolation claim checkable rather than aspirational.

Every arrow on this diagram is a hand-off the architecture treats as a trust boundary: the sandbox can only ever hand validated rows forward, never partially-validated ones, and every hand-off after it is inside the same trusted process rather than a distributed call graph — a distinction that matters later when the isolation-verification gate is described in Act IV.

Six terms this poster leans on:

  • WASI Preview 2 component — a WebAssembly module compiled against the WASI 0.2/0.3 component-model spec, with an explicit WIT-defined interface rather than ambient system access.
  • Wasmtime — the Bytecode Alliance’s WASI-component host runtime; would host the validation component both in the digital twin and in OCP.
  • componentize-py — the Bytecode Alliance tool that compiles a Python application into a WASI Preview 2 component; its Python surface is restricted, which is why the denylist in Act III exists.
  • Bronze / Silver / Gold — the medallion layering convention: Bronze is raw-but-validated data, Silver is cleaned/conformed, Gold is business-ready.
  • WIT interface — the WebAssembly Interface Type definition declaring exactly what a WASI component may import or export; nothing implicit.
  • Digital twin — the local/CI verification environment running the same container images and security context as the real OCP deployment, outside a real cluster.
  • Restricted SCC — OpenShift’s Restricted Security Context Constraint: non-root UID 1001, read-only root filesystem, no privilege escalation. The hard deployment constraint for every container in this project, WASI-sandboxed or not.
  • OpenLineage facet / Marquez — a structured provenance record (who/what/when transformed which columns), emitted by dlt and dbt to Marquez, the OpenLineage-compatible lineage service this project would query for end-to-end lineage.
  • Vector sidecar — the per-pod telemetry-forwarding sidecar that aggregates OTel spans before they leave the pod, so no other container needs its own external egress.

What exists today

One architecture gist, one Realization log, zero shipped code.

The only artifact predating the Dream is an architecture README authored 2026-04-19 — the same weekend as a Sentinel point release — describing the wasm-first analytical data stack end to end: WASI-sandboxed validation, dlt/dbt-duckdb ingestion and transformation, OTel/OpenLineage tracing, one Pixi toolchain. It never landed as running code. The Dream itself was seeded 2026-07-23, distilled from an audit of that gist — three months after the architecture was first written down.

As of this poster’s own tree, a search for stack-specific code — the WASI component, the dlt/dbt-duckdb pipeline, the OTel/OpenLineage wiring — finds nothing under src/; every one of CAP-27 through CAP-31’s own verification notes says exactly that, independently re-checked rather than assumed stale. This is a planning-complete, unscheduled project, not a shipped one, and this poster says so rather than implying otherwise.

That gap is deliberate, not neglect: the technical research behind the maturity verdict in Act IV had to land first, because it is what tells anyone scheduling this Dream which corner of the architecture is buildable today and which corner is blocked on an upstream project that has not shipped a WASI build yet.

The gist itself is described as three months stale on exactly the claims that matter most by the time the Dream audited it — its Apache Arrow-across-the-Wasm-boundary step in particular has no supporting implementation anywhere the research could find. Correcting that claim, not repeating it, is why this poster keeps returning to the maturity verdict rather than treating the original gist as settled fact.

The founding PRD also names who V1 is deliberately not for: end users who want a query or dashboard interface onto Gold tables (V1 ships no read surface at all); teams whose source data isn’t file-upload-shaped (streaming, API pulls, database CDC — the WASI boundary is scoped to the file-upload trust problem specifically); and teams on Kubernetes distributions other than OpenShift, or without a Restricted-SCC-equivalent hardening requirement, since the value proposition is specific to that posture — a generic K8s deployment would carry the WASI-sandboxing cost without the OCP-hardening context that motivates it.

07

One upload’s journey

A business user’s Excel file, traced from click to Gold.

A business user hits POST /upload/excel through an OIDC-authenticated FastAPI endpoint; an unauthenticated request gets HTTP 401 before the body is even read — the authentication check happens ahead of parsing, not after.

runs inside the WASI sandboxconventional trusted process

A structurally invalid file is rejected in full — zero rows reach Bronze. A partially bad file still queues its valid rows while naming the exact column and rule each rejected row failed, never blocking the rows that passed. Both outcomes are single HTTP responses, returned synchronously in the same request — there is no polling endpoint to check back against later.

The branch point in the middle of this diagram is also the sandbox boundary: everything left of it runs as a genuine WASI Preview 2 component; everything right of it, valid or rejected, is a conventional trusted process again.

The seed journey this whole design was walked against: Marcus, a business analyst, produces a weekly headcount-and-cost Excel report by hand and needs it in the shared warehouse without filing a platform-team ticket. He uploads headcount-2026-w30.xlsx; three rows fail — a department-key typo, a negative cost value — and he sees a precise, row-level error within seconds, while the other forty-seven rows queue for ingestion independently of the three he still has to fix. He corrects the three rows, re-uploads, and this time all fifty rows pass into DuckDB Bronze. Marcus never sees or cares that any of this happened inside a Wasm sandbox — from his side it is just “the upload told me exactly what was wrong.” If his file weren’t a valid .xlsx at all — corrupted, wrong format — the WASI component would reject it before dlt or DuckDB are ever invoked; the failure is meant to be contained at the validation boundary, not discovered three stages downstream.

08

The validation boundary

The only line of code in this whole stack that actually runs inside a WASI sandbox.

The validation step compiles to a genuine WASI Preview 2 component, built with componentize-py. A build-time check blocks a fixed denylist — numpy, pandas, pyarrow, pydantic, or any other C-extension-backed or componentize-py-unproven package — from ever entering the component’s dependency closure, so the failure surfaces at pixi run build, not a later runtime crash discovered in production.

This is the only WASI-sandboxed step in the whole architecture. dlt, dbt-duckdb and DuckDB itself never run inside a WASI component in this design, because DuckDB has no WASI build to run them in — not a scoping choice made for convenience, and not one to revisit without new upstream evidence.

The denylist itself is treated as a signal, not a target: if it keeps growing as the component’s validation logic gets richer, that growth is read as a reason to reconsider whether the WASI-sandboxing bet still holds, never as a reason to quietly widen the sandbox’s allowed capability surface to make the list shorter.

The contract closes the loop on the other side, too: no row is meant to reach DuckDB Bronze via dlt without having passed this exact validation step first — there is no second, unsandboxed path a row could take around it.

The denylist is not a guess at what breaks — it follows what the domain research actually found working and not working under componentize-py: SQLite3 inside CPython-WASI, and .abi3.so-recognized native extensions in some cases, make real progress; numpy, pandas and pyarrow do not, short of depending on the unmaintained wasi-wheels project this design explicitly declines to depend on. The line the denylist draws is the line the research actually found, not a conservative guess drawn before checking.

What the validation itself checks is meant to stay self-contained to the file’s own contents, too: cross-referencing an uploaded headcount against an external HR system, for example, is explicitly out of scope for this validation step — a deliberate boundary, not an oversight, that keeps the sandboxed logic small enough to actually audit.

That smallness is the whole point of scoping the sandbox to validation alone rather than to the pipeline’s full logic: a component with a narrow, enumerable job is a component whose WIT surface a reviewer can actually read end to end, not just skim and trust.

09

Silver and Gold, traceably

dbt-duckdb owns every transform after Bronze.

dbt-duckdb transforms Bronze into schema-declared Silver and then Gold models; every model emits column-level lineage; a failing dbt test blocks promotion of that model’s output to the next layer, so a bad transform can never silently overwrite the last good Gold state that downstream consumers already read.

Each validated upload triggers exactly one dlt load followed by exactly one dbt run scoped to that load — never batched, always sequential, invoked by the same owning process. A move to concurrent or batched transforms is a scope change requiring its own architecture amendment, not a tuning knob left open for later.

Every dbt run is meant to be traceable back to the exact Bronze table state it consumed, and a lineage query for any Gold column is meant to return its full upstream column chain all the way back to Bronze — the two success conditions this capability’s contract names explicitly.

The failure case is spelled out just as precisely: a dbt run with a failing test does not update the corresponding table, and the prior good state remains queryable — a bad run is meant to leave Gold exactly as good as it was before the run started, never worse.

Silver and Gold schemas are meant to be declared in the dbt project itself, not inferred ad hoc from whatever Bronze happens to contain that week — the same discipline that makes a lineage query meaningful rather than a best-effort guess. Every date crossing a stage boundary anywhere in this pipeline is meant to be ISO 8601 UTC, with no stage-specific exceptions.

This whole stage runs on a defined schedule or trigger, not continuously — a dbt run is a discrete, traceable event tied to the specific Bronze table state and, transitively, the specific upload event that produced it, never an ambient background process nobody can point a trace ID at.

10

One trace ID, start to finish

One W3C trace ID, minted once, follows the upload from browser to Gold.

upload_trace_id is always the bare 32-hex-character W3C trace-id — never the full traceparent string, never a UUID, never dashed — minted once at FastAPI ingress, and never conflated with OpenLineage’s own separately minted runId. The trace ID returned to the client at upload time is meant to be the same one eventually attached to that upload’s Gold-table lineage record.

OTel spans and OpenLineage facets correlate across every pipeline stage to Marquez via a per-pod Vector sidecar; no other container in the pipeline holds an external telemetry egress path — the sidecar is the one and only chimney. A trace query for any upload is meant to return spans for every stage it passed through with no gap, and Marquez is meant to return the full Bronze → Silver → Gold lineage graph from that same trace.

The trace itself originates in the browser at upload time and is meant to propagate through the FastAPI endpoint, the WASI validation call, dlt ingestion, and every dbt model run that touches that data — one continuous handle, not a chain of independently-generated ids stitched together after the fact.

This is the capability the compliance-reviewer job to be done actually cashes out to: instead of taking an architecture document’s word that a pipeline is traceable, a reviewer would search Marquez by one trace ID and either see the full upload-to-Gold chain or see exactly where it breaks — a verifiable claim, not an asserted one.

12

The maturity verdict

The deck’s most valuable slide is the one that says no.

A duckdb/duckdb issue search for “WASI” returns zero results, and the only community WASI-wheel project (dicej/wasi-wheels) has been unmaintained since December 2024 and is disclaimed by its own author — with no pyarrow and no duckdb in it at all. So dlt, dbt and DuckDB cannot run inside a genuine WASI component today. The sandbox stays deliberately scoped to the pure-Python upload-validation step while ingestion and transformation stay conventional hardened processes; a future wasm32-wasi build target requires an architecture-decision amendment citing new upstream evidence, not an incremental extension of this project.

This is why the original deck leads with this verdict on its own slide, called out there as the deck’s most valuable slide — a project that told its own scope-limiting truth before anyone had to go looking for it. Two named research reports carry that verdict, treated as load-bearing rather than background reading: a technical report on Python-in-WASM maturity, and a domain report on comparable production Wasm-sandboxing deployments. Several FRs on this poster are scoped the way they are because that research showed the wider alternative is not currently buildable, not because the scope was guessed conservative.

AD-50VerificationThe isolation gate must be non-hollow from its first version: it ships with a meta-test that deliberately widens the component’s declared WIT capabilities without a matching interface change, and that must make the gate fail, on every build.
AD-51ObservabilityOne trace-ID field: the bare 32-hex W3C trace-id only, minted once at FastAPI ingress, never OpenLineage’s own runId, never a UUID, never dashed.
AD-52DeploymentOne canonical securityContext definition authored once under deploy/; the Helm chart and the Podman compose file both consume it via a generation step — neither hand-authors its own copy.
AD-53ConcurrencyDuckDB single-writer: one dlt load, one dbt run per upload, 1:1, sequential, same owning process — concurrent or batched transforms need their own amendment.
AD-54Supply chainAir-gap-routable dependency fetch: every build-time fetch — Pixi packages, DuckDB extensions, the componentize-py/Wasmtime toolchain — routes through the configured channel/mirror; no build script hardcodes a public URL.
AD-55Request modelSynchronous upload: the endpoint blocks through parsing, validation, and returns the full per-row result in one response — no V1 polling endpoint.
AD-56AuthenticationOIDC token validation happens at a sidecar/gateway boundary in front of the API application, never embedded per-request inside the application code itself.

AD-49 is real but not reproduced here — named as a gap rather than paraphrased from a text this poster has not actually read.

Three cross-cutting conventions hold underneath all of it: medallion table names are lowercase bronze_* / silver_* / gold_*; a validation failure is always a structured {row_index, column, rule, message} record, never free text alone; and DuckDB is the only stateful mutation point in the whole design — no stage keeps its own copy of pipeline state.

Authentication follows the same single-source-of-truth habit: OIDC is enforced once, at the API ingress, and no stage downstream of the API is meant to re-authenticate or re-authorize the same request — a request that reaches the WASI validator, dlt, or dbt has already cleared the only gate that matters.

The isolation-verification gate

A gate that fails on purpose, at least once, to prove it isn’t hollow.

An automated gate mechanically proves the WASI validation component cannot reach any capability beyond its WIT-declared surface. Deliberately widening the component’s declared capabilities without a corresponding WIT change must make the gate fail — the non-hollow-gate proof named as this satellite’s own success signal, SM-1. The gate is meant to fail on any host interaction beyond the component’s declared WIT imports — proving it checks something rather than always passing, which is the whole difference between a real gate and a rubber-stamp one.

the recorded proofthe deliberate-failure rungthe standing checks

Two counter-metrics guard against gaming this signal. A growing workaround list in the denylist (SM-C1) is a signal to reconsider the WASI-sandboxing bet, not a target to minimize by weakening the boundary. Upload-validation latency must never be optimized by moving checks out of the sandbox and back into the trusted process (SM-C2), which would defeat the whole point of the validation boundary described in Act III.

The project also holds itself to a stricter bar than most: it ships zero claims beyond what the technical research verified as buildable today — the same discipline that produced the maturity verdict two sections back.

15

One toolchain, three targets

Pixi builds it; the same security context runs it everywhere.

A clean checkout plus pixi install && pixi run build would produce a runnable digital twin with no manual steps outside Pixi, including the compiled WASI component; every container starts as non-root UID 1001 with a read-only root filesystem, identically under a Podman digital twin and real OpenShift Restricted SCC.

The Helm chart’s security context is meant to match Restricted SCC exactly — non-root UID 1001, readOnlyRootFilesystem: true, no privilege escalation, no anyuid or other elevated binding requested. Any component that needs writable storage is meant to get it only through an explicitly mounted volume, never the root filesystem itself. DuckDB state persists via a ReadWriteOnce PVC at a consistent mount path, so a pipeline restart never loses previously ingested Bronze, Silver or Gold data — state is meant to survive pod recreation for as long as the PVC itself persists.

The chain runs one direction: local dev produces Pixi artifacts, the digital twin consumes the same artifacts under the same container images and security context, and OCP consumes that same combination again via GitOps — both non-production environments and production mount DuckDB’s state at the same path from a ReadWriteOnce-shaped volume; only the volume’s backing implementation differs (a local bind mount, then a Podman volume, then an OCP PVC), never the mount contract itself.

Python 3.12 is the chosen stability floor for the host and pipeline processes — revisitable, since nothing in the pinned dependency set (dlt, dbt-core, dbt-duckdb, DuckDB itself all support through 3.14) actually forces that floor. It is a conservative choice, not a constrained one.

That floor is deliberately this project’s own, not the fleet’s: Atlas itself is conda-forge-only, pixi-managed, and floored at 3.14 exact-minor; Unity Data Stack targets primary 3.13/3.14 with 3.12 as legacy-consumer-only. Three different floors inside the same merged Spec is not a contradiction to resolve — each project owns its own environment and dependency closure — but it is worth stating plainly rather than letting a reader assume one floor applies across all three.

The parity check this toolchain exists to make possible: Elena, a platform engineer, runs pixi run build to compile the WASI validation component alongside the rest of the stack, then brings up the digital twin under podman --read-only --user 1001 — the exact security context Restricted SCC enforces in OCP — and re-runs Marcus’s upload scenario against it to confirm identical behavior before deploying the same artifact to the real cluster. There, she pulls up Marquez, searches for that upload by trace ID, and sees the full lineage in one query: upload, validation, Bronze row, Silver transform, Gold table, each hop timestamped and column-attributed. If the digital twin and the OCP cluster ever disagreed — a dependency resolving differently, say — that disagreement is exactly the drift this one-toolchain design exists to make visible immediately, not discover later in production.

Per-leader value

Four leaders, four reasons this is worth scheduling.

The founding PRD frames the same four leaders as jobs to be done, not personas: a platform engineer needs to let business users upload data without giving uploaded-file-derived logic the pipeline’s own trust level; the same engineer needs one command sequence that behaves identically on a laptop, in a digital twin, and in the real cluster, so “works in dev” and “works in prod” are the same claim, verified the same way; a security reviewer needs the sandboxing claim to be something an automated gate can be pointed at, not something taken on the architecture document’s word; and a future data consumer — out of this V1’s own scope, but named anyway — needs to trust that whatever reached Gold passed through a validated, traceable, lineage-recorded path.

None of the four is served by the same feature twice — the isolation gate speaks to the compliance leader, the lineage graph to the data platform leader, the one-toolchain parity to SRE, and row-level rejection reporting to whoever actually owns the uploaded data. A capability that only one leader cared about would be a weaker case for scheduling this Dream than four independent reasons converging on the same five capabilities.

The founding brief names the same ground in three ranked users instead of four peer ones: a primary platform/data-engineering team inside a regulated OpenShift shop, whose success looks like an Excel upload validated inside a real sandbox before it reaches ingestion, traced and lineage-tracked with no custom instrumentation work, using the same pixi run commands locally that CI and OCP run; a secondary security/compliance reviewer who cares that “sandboxed” is a verifiable claim, proved the same mechanical way pyforge-atlas G1’s own smoke test proves its no-backend claim, not asserted by a design document; and a tertiary future Unity Data Stack tenant, for whom this project is a candidate first “vertical application” on that platform’s shared innersource toolchain.

Enterprise and air-gap posture

Every build-time fetch is a mirror-routable fetch.

Pixi packages, DuckDB extensions, and the componentize-py/Wasmtime toolchain would all route through the configured channel/mirror at build time; no build script hardcodes a public URL — the same posture the enterprise-airgap and presenton-pixi-image kinships share, each working it from a different corner of the same regulated-enterprise problem. This project’s own version of that posture would follow the same Parquet-extension-style vendoring pattern pyforge-atlas’s own G1 already established — consulting a proven pattern rather than inventing a new one for dependency vendoring.

Restricted SCC itself is the constraint that shapes almost everything else on this poster: non-root UID 1001, a read-only root filesystem, no elevated Helm bindings — a posture that has to hold identically on a developer’s Podman digital twin and on real OpenShift, or the digital twin isn’t proving anything.

“Digital twin” is doing real work in that sentence, not just a label: it means a developer can run the exact same non-root, read-only container images locally under Podman that would later run on OCP, and catch a Restricted-SCC violation on a laptop instead of discovering it during a cluster rollout.

No specific named regulatory framework (HIPAA, PCI-DSS, SOX, GDPR) is stated anywhere upstream of this poster — the posture is described generically as “regulated enterprise.” The founding PRD treats Restricted SCC compliance and OIDC-gated access as the concrete, verifiable compliance baseline it can actually commit to today, and defers naming a specific framework rather than guessing at requirements a real framework would add.

No cost ceiling is stated in the Dream or brief either. The one data point on record is external, not this project’s own: a cited production case of WASM sandboxing for batch order processing reported roughly 60% lower compute cost — weak positive evidence that Wasm sandboxing is not inherently a cost tax, not a claim this project makes about itself.

Now, next, later

What scheduling this Dream would actually take.

Five questions stay open on purpose, not settled here — all five straight from the folded PRD’s own open-questions list, none resolved by guessing:

#Open question
1Exact maximum upload file size and expected weekly row-count/latency budget for the “within seconds” validation claim — needed before Architecture can size the validation component’s performance budget.
2Which named regulatory framework, if any, beyond Restricted SCC + OIDC (HIPAA, PCI-DSS, SOX, or none) — a named framework would likely add audit-log retention and encryption-at-rest requirements not yet captured.

5Whether the isolation-verification gate needs to run on every CI build or only on changes that touch the validation component — a build-pipeline-shape question, not a product one.

Data governance carries three more unresolved points in the same PRD: the Bronze/Silver/Gold layering is the only classification boundary that exists today, with no explicit PII or confidentiality scheme defined; OpenLineage facets would accumulate in Marquez indefinitely by default, with no retention policy specified; and Bronze/Silver/Gold data on the PVC persists until explicitly purged, also with no retention or deletion policy set. All three become load-bearing, not academic, if the seed use case’s real headcount-and-cost data turns out to carry personally identifiable information.

Marquez’s actual deployed image and version need re-verification at implementation time — its last tagged GitHub release predates its own active development, and it ships primarily via Docker and Maven rather than GitHub release tags. Pin what gets deployed at build time, not whatever GitHub happens to have tagged.

Two more items sit in the folded architecture’s own Deferred list, unresolved by design rather than by oversight: exactly which OIDC provider and gateway implementation sits at the authentication boundary is left open on purpose — the rule fixes where authentication is enforced, not which product enforces it, so two builders picking different providers still compose correctly as long as both honor that boundary. And a future migration to dbt Fusion, the Rust dbt engine, stays an explicit non-decision — a real upstream event to watch, not a scheduled item, revisited only once Fusion gains a DuckDB adapter it does not have today.

The founding brief names what would actually reshape this roadmap, not just what would complete it: if dbt Fusion gains a DuckDB adapter, the transform layer’s own WASI-portability story changes completely, since Rust compiles to WASI far more cleanly than CPython does. If DuckDB itself ever ships a WASI build — no evidence found that this is even being discussed upstream today — the entire “Bronze on DuckDB, sandboxed” claim from the original architecture gist becomes buildable as first imagined, rather than the narrower slice this poster describes. Neither is a V1 dependency; both are why an eventual architecture pass should keep the DuckDB-facing layer’s interfaces clean enough to swap later without a rewrite.

Were this Dream scheduled, it would route through the same BMAD chain and the same factory surface every other station uses today — core 6.12.0, bmad-loop 0.11.1, the conda-forge-expert skill at 8.90.5, a live snapshot of 46 MCP tools, 31 pixi environments, catalog schema v29, cf_atlas’s own 22 phases, and 117 cataloged gotchas — not a bespoke toolchain of its own.

Six items sit explicitly out of the MVP scope this poster describes, most already named elsewhere on it: any WASI-sandboxed execution of dlt, dbt, or DuckDB; Apache Arrow buffers as the host↔component interchange; a browser-side dashboard onto Gold tables (the v2 candidate that would reuse pyforge-atlas G1’s pattern directly); multi-source ingestion beyond Excel; multi-tenant Unity Data Stack integration; and the dbt Fusion migration path. All six are named choices, not gaps nobody noticed.

The concrete next step, if this Dream is picked up, is not code: it is the same Spec-→Story decomposition every other effort in this factory goes through first — a numbered Story reflecting these five capabilities into pyforge-atlas’s own epics.md and sprint ledger, before a WASI component or a dbt model gets written. Nothing on this poster substitutes for that step, and nothing here claims it has already happened.
