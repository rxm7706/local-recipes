Foundry Platform

How eight independent tools become one governed platform

PyForge is eight specialised tools, called stations, mounted on one web platform. A person signs in once and reaches all eight. An automated agent does the same through a standard protocol. Underneath, five promises hold for the regulated, offline environments this is built for: the platform is auditable, controlled, contained, honest and recoverable — and § 16 shows each promise, what enforces it, and how to check it yourself.

Fourteen words this document leans on
Station — one of the eight tools. Each owns a stage of the software lifecycle and renders its own verdict.
Foundry / estate — the foundry is the shared web platform the stations mount on; the estate is everything PyForge runs, deploys and governs.
Lane 1 · 2 · 3 — the three kinds of web surface: the public front door (1), a station's own portal (2), and analytics dashboards (3).
Five tiers — every station must exist in five forms: a command line, a portal, a service face for agents, a domain skill, and a persona.
Service face — a station's endpoint for automated agents, using MCP, the open protocol agents use to call tools.
Persona + domain skill — the skill is the written know-how an agent loads to do a station's work; the persona is the agent identity that acts through it.
Chrome — the shared page furniture every portal inherits: the app switcher, layout, theme and sign-in awareness.
Query plane — the single analytical engine every station and agent asks questions of, instead of each keeping a private database.
Hook / plugin — a hook is a named point where a process allows a swap; a plugin is what swaps in. One registration shape for all eight stations.
01 · 02 · 03 work — how much a piece of work owes: a one-off (01) stops at a spec and a script; repeating work (02) earns a skill; only a promoted station (03) owes all five tiers.
Done vs realized — done means the code merged and its tests pass. Realized means the promised effect is exercised in the running system. This document tracks both.
Consumed, never operated — the platform connects to a database, cache or object store someone else runs; it never hosts one itself in production.
Never-false-green — a check that cannot run reports "could not check", never "passed". An absent record and a clean record must never look the same.
Waiver — a recorded, dated, expiring acceptance of a known finding. It appears in every report it suppresses and re-blocks the build when it expires.

Eight stations. One foundry. Sign in once, never leave.

ACT IEight terminals
The friction
01

The problem

Before the platform, someone who needed compliance findings, package health, fleet status and build queues opened eight terminals and got no help relating them. The environment this ships into is offline and regulated, so a prettier interface was never the point.

8
separate tools, eight sign-ins, eight vocabularies, no way for one to tell another that something happened
1
sign-in, one address, one shared way of asking each station to do something
5
promises for the regulated target: auditable, controlled, contained, honest, recoverable
The governance mandate rides on it. A regulated, offline deployment needs the platform to be auditable (every change traces to a decision and a person), controlled (every access can be revoked, every secret rotated), contained (one failure, one runaway agent, one over-spend cannot take the rest down), honest (no check ever reports a green it did not earn) and recoverable (state survives any single machine). Those five promises are why this is more than a front end; § 12–15 show the mechanics and § 16 lays all of it out row by row.
02

Four users, four paths

Every surface serves a distinct person or program, and every one of them reaches the whole estate from a single entry point.

Builds the estate
Platform engineer
One command shape for everything — pyforge <station> <noun> <verb> — while each station's own command still works exactly as before.
Answers for it
Compliance auditor
Warden's portal links every finding to the package, build and fleet context behind it. § 16 lists every governance promise with the check that proves it — the auditor's index to this document.
Runs it

Deploys with Helm (Kubernetes packaging) onto OpenShift. The application's database account provably cannot change the schema; a separate, governed job does.
First-class user
Autonomous agent

The agent is a first-class user. Service faces, the shared command shape, the event backbone, domain skills and station personas make the whole estate legible to automated agents — under the same identity rules as a person.
ACT IIOne foundry
The insight — hub and spoke
03

The hub-and-spoke shape

One web platform mounts all eight stations inside a single process: sign-in, portals and service faces together; long-running work handed to background workers (Celery). Each station's own command stays a first-class entry point — the platform dispatches to the stations, it does not swallow them.

Four backing services, all consumed, never operated: in production the enterprise runs them and PyForge holds only an address and credentials. A self-hosted PostgreSQL and Redis remain the default for local development. DuckDB (the analytical engine) is a library inside the platform, not a fifth service.
For implementers: the platform imports no pyforge.* source — it consumes the factory's published conda packages. Two recorded brownfield exceptions exist and are tracked.

ACT IIIHow the mounting works
The mechanics
07

One interface for eight portals

One installable package supplies the furniture every portal mounts: the app switcher, the base layout, sign-in awareness, the Modernist theme, and page assets served from the platform itself with no outside hosts.

App switcher

Entries come from each portal's own registration, never a hardcoded list. The registration also names the owning station, a backup, the work class and a promotion date — so the console can refuse to display one-off work as if it were a station.

Base layout + theme

A sign-in-aware base page and the Modernist theme. Every portal extends it and inherits the switcher and the user context for free.

Proof, not promise

Portals render identical chrome with zero duplicated templates or assets — proven by a test that fails if a portal ships its own copy.

Portals follow Django's reusable-app convention: one distribution per station, one or more apps inside it, a compound label that names both. A data model never moves between apps — new concerns become sibling apps.
For implementers: distribution django-<station>, module django_<station>_<app>, label <station>_<app>. A model move is a governed changeset (§ 12), not a Django migration.

Wagtail (the content manager) serves the public front door. Editors publish pages from the database with no code release. The editing screen sits behind the enterprise sign-in; there is no local password form.

09

Eight portals, one session, one identity path

Every station mounts under the same address pattern. Moving between portals needs no second sign-in, and no portal ever talks to a station directly — every call goes through one trusted client that carries who is asking.

PORTAL
Renders the page
Keeps no station data of its own (one recorded exception: Warden's compliance-job record). Asks its station for data through the one client. Adding or removing a portal changes no other code.
→
THE ONLY PATH
The trusted client
First checks the user's sign-in token against the identity provider. Then issues a short-lived, cryptographically signed statement naming the user, their roles, the one station it is for, and that the platform issued it on their behalf. It expires within five minutes. A shared password was rejected: a secret on a laptop is not an identity.
→
STATION
Verifies independently
Checks the signature and that the statement was meant for it. It can prove which person the call was made for. A plain "user id" header is never trusted.
→
LONG WORK
Background job, same identity
A background job records who started it and gets its own scoped token — identity follows the work into the worker pool.
What an auditor can checkYou can check this by reading the signed statement any station receives: it names the user, the roles, the single intended station and an expiry under five minutes, and is signed with a key only the platform holds. You can confirm no portal bypasses it — a test fails the build if any portal opens a raw connection to a station. Matrix rows Co2, Co3.
For implementers: RS256 JWT; sub = the user's identity-provider subject, aud=mcp:<station>, delegated_by=pyforge-host, exp ≤ 5 min. The mint verifies the presented bearer (JWKS, iss, aud, exp) first — Story 40.1. Background jobs capture the subject at invocation (BS-3).

10

Every station has a service face

Eight agent endpoints, one per station, inside the same web process — using MCP, the open protocol agents use to call tools. One process, not a farm of eight.

Speaking every client's dialect
Accept five protocol revisions. Real agent clients are split across them; supporting only the newest or only the oldest would turn away live traffic.
Answer in the revision the client asked for. A client that hears an unfamiliar version gives up — even if that version is newer.
Decide by declared version only. The client's name or brand never changes behaviour.
Surviving a dropped connection
Two calls, start and get, over a durable store. Start returns a handle immediately; get retrieves the result later — from any replica.
The handle is the key. Opaque, unguessable, time-limited; whoever holds it can read that one result.
Keep-alives stay well under 30 seconds because the cluster's router closes idle connections at 30 and offers no per-route override.
What an auditor can checkYou can check this by running the disconnect test for any of the eight stations: it starts a multi-minute operation, severs the connection mid-way, reconnects and retrieves the completed result. Atlas's face has additionally been exercised by an operator on the laptop cluster. Matrix rows Co4, R4.
For implementers: revisions March 2025 through July 2026; official mcp 2.0 SDK; single-POST shape. The start/get pair implements SEP-2663's lifecycle without the Tasks extension (no server-side runtime exists yet); adopting it later is a wire-layer swap. Progress notifications, sticky sessions and stream replay are not used for survival.

The estate teaches agents its own work

Domain skills
How the work is actually done

Each station carries written know-how an agent can load. The model is Mason's conda-forge-expert skill — the original, and the one in daily use.

Personas
Addressable, and disciplined

Every station answers as an agent identity that acts only through the command shape and the service face — no direct file reads, no ad-hoc web calls. Language-model providers are swappable adapters behind it.

Scoped by work class
01 → 02 → 03

One-off work stops at a spec and a script. Repeating work earns a skill. Only a promoted station owes all five tiers plus a named owner — build only what value and ownership justify.

How much leash — the autonomy gradient
L1
Assistive
The agent helps; the person drives.
L2
Task-based
Discrete tasks, each approved by a person.
L3 · today
Conditional, with gates
Unattended loops inside machine-readable boundaries; anything the agent cannot safely decide escalates to a person.
L4
High-level
The person sets policy rather than driving.
L5
Self-governing
Full autonomy; the person governs intent alone.
L3 is the production ceiling and what runs here today: gated build loops, escalation on anything critical, a per-story autonomy setting, and a live escalation on record. The skill is the unit of execution; the harness that governs the agent is deliberately not a skill, so the agent never authors its own governor.

ACT IVThe governance mandate
Auditable · revocable · contained
12

Database changes are governed, not incidental

Enforcement lives in the database account itself — the one control an auditor can verify and an agent cannot bypass by accident. Developers keep their usual tools for authoring a change; production applies it through one auditable path.

AUTHOR
In Django, as usual
Developers write the change with the tools they already use.
→
EXTRACT
Reviewable SQL
The change is exported as plain SQL and filed as a Liquibase changeset (Liquibase is the schema-change tool).
→
BUILD GATE
Stale export fails
A schema change with no matching changeset fails the build. No prior art existed; this gate was built here.
→
APPLY
One deployment job
A separate migration account applies the changesets once per release — never once per replica.
→
RECONCILE
Django catches up
Django records the change as applied without touching the schema, so its bookkeeping stays consistent.
→
RUN
Read-and-write only

Revocable identity, governed secrets, runtime flags

Identity

Permissions come from roles held at the enterprise identity provider, not from a local user table. Revoke a role there and portal access is gone on the user's next request.

Secrets

Deployment manifests carry references only; no secret value appears in any of them. In-repo secrets are encrypted at rest; an enterprise vault plugs in as a deployment-profile adapter, outside the application image.

Feature flags

OpenFeature (the vendor-neutral flag standard), evaluated from a local file with no network. One flag change alters the web, service and command-line surfaces with no redeploy and no outside connection.

6
Every Python dependency ships as a conda-forge package, so the whole platform installs with the internet blocked. Six packages had to be published to conda-forge for this to be true, including the schema-change tool with its database driver bundled in. Container images are governed by a separate rule: they come from the internal registry.
What an auditor can checkYou can check this by revoking a test user's role at the identity provider and issuing one more request: it is refused. You can grep every deployment manifest for secret values and find only references. You can run the offline build with outbound traffic blocked and watch it succeed — any external fetch is a hard failure, not a warning. Matrix rows Co1, Co5, Co6, Co8.

One measured point so far: for a representative story, unaided navigation of the codebase costs about 51,800 tokens, of which about 31,100 (60%) are recoverable from a pre-built structure index. Building that index costs zero model tokens and 19 seconds; refreshing it, 4.
Five levers, one per sink
0 · Say less. The agent's working speech is compressed; verdicts, escalations and journals stay fully written. Upstream claims ~65% fewer output tokens — their benchmark, not yet ours.
1 · Read less. Tool output, logs and diffs are compressed before the model sees them, reversibly — the original is always retrievable. Upstream claims 40–95%.
2 · Ask the map, not the files. Structure questions are answered from a pre-built code graph instead of re-reading files. Measured: ~60% of navigation tokens recoverable.
3 · Recompute only what changed. Derived planning context refreshes incrementally when its sources move, never from the full document on a hunch.
4 · Retrieve the paragraph, not the book. Planning documents become a queryable graph: the ~1,500 tokens a story needs instead of the 65,000-token file they live in.
Plus the biggest lever of all: the right model for the job. Difficulty-based routing sends easy stories to economy models and hard ones to frontier models — a ~50× spread in input price and ~125× in output. Review always keeps the strongest model, because a missed review ships a false green. Flat-rate subscription pools are used before metered API. Fed on all eight stations since Story 33.6.
Guardrail
Never compress the contract
Story specs, acceptance criteria, gate verdicts and escalations cross the wire intact. Compression applies to what the agent reads along the way and says, never to what it is bound by.
Guardrail
A ceiling above every lever
Every story and every run carries a token and wall-clock ceiling; an idle ladder nudges, stops retrying, then defers before anything is killed. Spend is journaled per story in weighted tokens and, from a declared price table, in estimated dollars.
Honesty
Not "realized" until measured
All five levers are built and switched on (Epic 33). The end-to-end benchmark — same story, levers off versus on — has its off-leg recorded; the on-leg with real token counts awaits a completed run. The Dream stays "specified" until that number exists.

What the platform will not build

Design principles — the lines that hold
Eight stations, not nine. The platform is Steward's surface, not a station of its own.
One process, not a farm. Portals and service faces live in the web process; heavy work goes to background workers. No fleet of small public services.
Backing services are consumed, never operated. PostgreSQL, Redis, Kubernetes and S3 storage come from the enterprise in production. The analytical engine is a library inside the platform.
The chrome is ours. Third-party admin themes were evaluated and set aside; none offered an app switcher or worked offline.
One merge verdict: Warden's. Enterprise scanners plug into Warden as plugins; the gate stays green when a scanner is simply absent.
Agents query the plane, never production. A private analytical store or text-to-SQL against production schemas is a failing test, not a style objection.
Every station keeps its own command. The shared command shape forwards; it does not absorb.
Extension model — plug in, do not fork
Hooks — named points where a process allows a swap. A plugin implements or replaces a layer without forking the process.
Profiles — choose which plugins load. SonarQube, Checkmarx, Black Duck and GitHub Advanced Security are Warden plugins, not a second governance layer.
Identity adapters — Keycloak, Entra, Okta, Ping: configured per profile, never hardcoded.
Language-model providers — adapters behind the agent engines. The platform is model-agnostic.
Contracts — the task names, the artifact identity on the golden path, and the backing-service rule are fixed. Everything else is configurable.
Adopting PyForge means adapting it to your stack, not replacing your stack. One plugin shape, one loader, at every enterprise tool boundary.
For implementers: hooks register on the pyforge.core.hooks entry-point group; a plugin may publish a verdict only for the spec it owns (SecondVerdictError otherwise). No django-lasuite or CodeRed on the host. No services/ tree of :800x processes.
