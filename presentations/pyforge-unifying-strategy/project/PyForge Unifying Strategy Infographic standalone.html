The Canopy

pyforge-unifying-strategy · the 8-station hub-and-spoke enterprise architecture

PyForge is eight capability stations that each shipped as an excellent command-line tool — and stopped there. Eight terminals, eight mental models, no shared identity, no shared vocabulary, no way for one station to tell another that something happened. The Canopy — src/platform/ — mounts all eight under one chrome, one session, one grammar, one event backbone and one query plane, and carries a governance mandate: schema change auditable, identity revocable, failure contained.

ACT I Eight terminals
The friction
01

The problem

Each station shipped as a genuinely good CLI and stopped there. An operator who wants compliance findings, package health, fleet status and build queues holds eight terminals and gets no help from the estate in relating them. And the deployment target is air-gapped and regulated — so this was never merely a UI project.

8
terminals and eight mental models per operator — no shared identity or vocabulary
1 of 8
portals mounted before the drain — warden's, at /compliance/. The pattern worked and was simply never repeated
0
ways for one station to tell another that something happened — no events, no shared session, no shared grammar
The mandate riding on it is governance. An air-gapped, regulated deployment needs schema change to be auditable rather than incidental, identity to be revocable rather than cached, and failure to be contained rather than cascading. Those are the Dream's five RFCs and eight blind-spot directives — why this chain is more than a front end.

ACT II One canopy
The insight — hub and spoke
03

The hub-and-spoke topology

Not disconnected apps — one Platform Canopy that mounts the eight canonical stations. A modular monolith: one ASGI process carries chrome, identity, portals and service faces; heavy work goes to Celery. Not a services/ farm of nine public processes.

Infrastructure is exactly PostgreSQL + Redis + Kubernetes — a component demanding a fourth backing service has failed its design review. DuckDB is a library / query face, not a fourth kind. Each station's binary stays a first-class entry point; the Canopy dispatches to them, it does not absorb them.
04

Three lanes, one session — and two agent doors

Humans get three lanes behind one OIDC session. Agents get the same stations through the MCP faces and the unified grammar — same host, same identity discipline.

Lane 2 is HTMX, not DRF — station compute JSON stays FastAPI behind CAP-6's client; DRF JSON:API lives on the Atlas data-products kinship. Herald's React web surface is the Moments UI, not Lane 1.

ACT III How the mounting works
The mechanics
06

One chrome — django-pyforge · CAP-1

One installable Django app supplies the chrome every portal mounts. Research killed the shortcut: django-lasuite is OIDC/DRF plumbing with no app switcher and no theme, and La Suite's switcher ships as npm/React with an endpoint unreachable air-gapped — so the chrome was ours to build.

App switcher

Entries derive from each portal's registration seam (AppConfig metadata) — never a hardcoded path list. The seam also carries owner station, backup, work_class and promotion date, so the Guildhall can refuse to tile tier 01 and tier 02 work as a station surface.

Base layout + theme

An OIDC-aware pyforge/base.html, the Modernist theme, WhiteNoise-served assets — zero external CDNs. Every portal extends it and inherits the switcher and the auth context for free.

Proof, not promise

Portals render identical chrome from that one package with zero duplicated template or static files — proven by a test that fails if a portal ships its own copy. A portal that owns chrome has violated the contract.

Portals follow Django's reusable-app convention — distribution django-<station>, module django_<station>_<app>, app label <station>_<app>, one distribution per station holding one or more apps (the django-allauth shape). The compound label is required, not stylistic. And a model never moves between apps — new concerns become sibling apps; after CAP-9 a move is a governed changeset, not a Django migration.

CAP-17 — the one place the chain grew
Run state becomes a service

The console read ~/.bmad-loops, tmux and journal files off an operator's disk — which is why the published board degraded to unavailable. The operator chose to keep those surfaces and pay for them: a supervisor publishes live run state and ingests a completed run's timing, and the front door only ever queries it. Never reads a home directory; never falls back to filesystem scraping.

The replacement is held to a higher bar than the thing it replaces — deliberately.

09

Every station has a service face · CAP-4

Eight MCP endpoints on the host ASGI — POST /stations/<name>/mcp, official mcp 2.x SDK. Not a process farm; the deprecated two-endpoint /mcp/sse shape is gone (GET answers 405).

The wire rules — era discipline
Accept the whole dual-era span — the March 2025 revision through the July 2026 one — five handshake revisions. The client fleet is genuinely split; pinning either end alone rejects real traffic (Codex already sends the newest).
Echo the client's revision — never assert your own newest. A client receiving an unknown revision aborts even when it is newer; asserting the modern one is a self-inflicted rejection.
Never branch on a client's name. Only the declared revision decides. Sniffing becomes tempting mid-migration and is always wrong.
Disconnect survival — the outcome, not the extension
A start/get tool pair over a durable store — implementing SEP-2663's own lifecycle. The Tasks extension has no server-side runtime in any SDK, so binding to it would block on upstream; adopting it later is a wire-layer swap over the same store.
The task handle is a capability — opaque, high-entropy, TTL'd. Without sessions, anyone presenting the handle can read the task.
Never: progress notifications (die with their connection), sticky sessions (the modern revision removed them), or home-grown stream replay. Keep-alives stay well under 30 s — HAProxy's timeout client is cluster-wide with no per-route override.
Success criterion: an agent completes a multi-minute station operation across a simulated ingress disconnect — and still retrieves the result, from a different replica if the first one is gone.

The literal directive — "no framework emits DDL, ever" — is not implementable: post_migrate is the only supported mechanism populating content types, permissions and sites. Thirteen directives — four rewritten by research · CAP-10

Five RFCs and eight blind spots survived contact with the live pins only after Phase-2 research. The rule underneath them all: an invariant with no test that fails in its absence is not implemented — demonstrated individually, never as a suite.

RFC-1revised Two HTTP process pools → one ASGI Deployment; long work is start/get + Celery — the pool that scales independently.
RFC-2as written redis-broker (noeviction) split from redis-cache (allkeys-lru) — cache pressure provably loses no queued task.
RFC-3revised HMAC-SHA256 rejected (a laptop shared secret) → RS256 delegated JWTs, audience-bound, exp ≤ 5 min.
RFC-4revised DLQ + loop ceiling stand; bound as pyforge.events(.dlq), XAUTOCLAIM harvest, CloudEvents extension pyforgeloopdepth ≤ 8 — not an HTTP header, not 5.
RFC-5revised "Liquibase governs all DDL, frameworks prohibited" → the role-based least-bad form of § 11. Zero prior art existed for Liquibase over Django; the bridge package last released in 2016.
BS-1premise false "SQLite corrupts B-trees on RWX" — Scribe was never SQLite; it was one JSON file. Rewritten: flat-file → PostgreSQL/pgvector behind the existing store port. And "semantic search" was a new capability, not a backend swap — recall was token overlap.
BS-2revised Keep-alive + a 30 m route annotation — stale twice over: /mcp/sse deprecated, and the annotation raises timeout server, never timeout client. Bound as § 09's single-POST + start/get design.
BS-3as written Celery delegation context + scoped execution tokens; Keycloak resource-indicator support pinned as a caveat, not assumed.
BS-4revised PyBreaker's async is Tornado-era: an httpx coroutine records a false success and the circuit never trips. Bound: PyBreaker for sync + our ~40-line async wrapper over its own state storage; stale-while-revalidate HTMX badges stand.
BS-5as written One dedicated writer for the analytical store; every other handle mounts read_only=True — now generalized into CAP-19's single-writer plane.
BS-6as written Schema-versioned CloudEvents envelopes; validation in domain adapters, never at the stream boundary.
BS-7as written PydanticFormErrorBridge — HTTP 422 arrays become inline Django validation errors; lands in django-pyforge, which is ours.
BS-8revised Idempotent restart reconciliation stands; MinIO does not — an object store would be a fourth backing kind. Boot re-index runs against PostgreSQL (+ RWX media).
A pessimistic premise is as much a planning error as an optimistic one — both had been sized as risk. The corrections came from reading sources, not changelogs: PyBreaker's Redis storage was read at the source (setnx/incr, no Lua), and the FastMCP outage was reproduced, not recalled.

Revocable, delivered, flippable — and the packaging price · CAP-12 + CAP-13

Identity · CAP-12

Authorization derives from IdP roles, not locally-managed state. Revoke a role at the IdP and portal access is gone on the user's next request — nothing cached, nothing to chase.

Secrets · CAP-12

Pod specifications carry references only — no long-lived secret value in any manifest. In-estate vaulting is go-sops + age; HashiCorp Vault stays a profile adapter outside the image — never an in-process client.

Flags · CAP-13

OpenFeature via the flagd FILE resolver — the full targeting engine evaluated in-process from local JSON. One flag change flips Django, service and CLI surfaces with no egress and no redeploy.

6
conda-forge builds were the committed price — the air-gap gate is a gate, not a warning, so a PyPI-only package is feedstock work scheduled as such. Four OpenFeature feedstocks (absent from anaconda.org entirely — a global search returned zero results) + a cachebox 5.x build beside conda-forge's 6.2 line + liquibase on that 5.0 point release with the PostgreSQL JDBC driver vendored (5.0 Community stopped bundling it; LPM fetches over the network). Shape precedent: apache-tika; openjdk 25 clears the Java 17+ floor.

One HTAP query plane; stations are clients · CAP-19

The Canopy unified chrome, identity, grammar and events — but not where a question goes. Atlas ranked vectors in an in-memory DuckDB, Scribe recalled from pgvector, Langflow carried Chroma, DB-GPT spoke SQL at whatever DSN it was given, Vizro went through BSL. Five answers — and an agent that hallucinates a join can still land on OLTP.

OQ ruling
Both faces, one boot script
Library-first stands; the Mosaic duckdb-server HTTP/Arrow face is committed behind the same single boot script, raised only with the platform stack. Parity between faces is part of done.
OQ ruling
A named new pipeline
The closed seven stay sealed; the plane's cache derives downstream from their outputs. Consumers choose per call — canonical datasets direct, or the plane as the fast path. No silent 01_raw.
OQ ruling
Dual-write, for now
The plane is primary for Scribe recall; scribe_schema pgvector stays written as the safety net until the plane has operating history. Retirement becomes its own explicit decision.

What the chain refuses to build — and what it honestly left

The held lines — every one a recorded ruling
No ninth station. The Canopy is steward's surface; the roster stays at eight and Charter §5 is not amended.
No services/ farm. No nine public :800x processes — the modular-monolith trail is closed. MCP and portals ride the host ASGI; heavy work is Celery.
No fourth backing kind. PostgreSQL + Redis + Kubernetes, exactly. No MinIO-as-core, no in-app Vault, no lineage server. DuckDB is a query face.
No CodeRed, no django-lasuite on the host. One dropped on maintenance evidence; the other retracted — it contains no chrome at all.
No second PR-gate verdict. Warden is the sole Golden Path verdict; SonarQube / Checkmarx / Black Duck / GHAS register as Warden plugins on CAP-18 hooks — and the gate never fails just because a scanner is absent.
No agent on the OLTP DSN. After CAP-19, a private DuckDB, Chroma, or Text-to-SQL against production schemas is a test failure, not a style objection.
No CLI absorbed. The unified grammar dispatches; each station binary stays a first-class entry point.
