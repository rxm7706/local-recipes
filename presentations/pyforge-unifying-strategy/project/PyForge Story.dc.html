PyForge Platform Overview
Platform Narrative

PyForge

One governed, air-gap-ready enterprise platform for compliance, resiliency, and productivity.

PyForge turns a collection of open-source Python and AI tools into one governed, air-gap-ready enterprise platform that a developer, operator, or AI agent can use from a single interface to make informed decisions on compliance, resiliency, and productivity.

The problem we solve

Enterprise Python teams adopt dozens of open-source tools — packaging managers, compliance scanners, AI workflow engines, analytics frameworks, orchestration layers. Each tool has its own install story, its own CLI, its own data silo, and its own deployment contract. The result is predictable: fragmented governance, inconsistent environments, and a sprawl of bespoke integrations that break whenever any single piece upgrades.

Worse, many of these tools cannot run inside air-gapped networks without significant re-engineering. Enterprises that need the strongest security posture are forced to choose between capability and compliance.

PyForge eliminates that choice.

One platform, eight stations

PyForge organizes capability into eight purpose-built stations, each owning a distinct domain of the software lifecycle. Every station ships a CLI, a web portal, a programmatic API, a domain skill, and an agent persona — the same five tiers, the same grammar, the same governance.

The stations:

  • Warden — the sole compliance gate. Every pull request, every recipe, every dependency change passes through one verdict. Scanners are plugins, not competing governance planes.
  • Atlas — package graph intelligence. Kedro pipelines map the dependency landscape; the semantic layer makes it queryable.
  • Mason — recipe building and conda-forge packaging. The factory that turns upstream source into governed, reproducible packages.
  • Marshal — orchestration and dispatch. Loop control, run lineage, and the coordination layer for multi-agent campaigns.
  • Doctor — health diagnostics and auto-remedy. Workspace hygiene, syntax linting, and self-healing before problems reach production.
  • Herald — presentations, documentation, and narrative. Deck engines, diagram export, and the voice of the platform.
  • Scribe — team memory. Knowledge graphs, transcript mining, and compiled facts that persist across sessions and agents.
  • Steward — infrastructure, deployment, and the platform itself. The station that owns the platform's own lifecycle and carries the governance mandate.

One interface, not eight terminals

The platform mounts all eight stations under a single Django + Wagtail host. Sign in once with your enterprise identity provider — Keycloak, Entra, Okta, or Ping — and every station is one click or one command away. The CLI follows a universal grammar: pyforge <station> <noun> <verb>. The same grammar works for humans in a terminal, scripts in CI, and AI agents over MCP.

Stations share a session, an event bus (CloudEvents on Redis), and a unified query plane. When Warden blocks a non-compliant dependency, Marshal knows the run failed, Doctor can diagnose the root cause, and Scribe records the decision — all without any station importing another's code.

Air-gap first, not air-gap later

Every capability in PyForge works without internet egress. Static assets are bundled (WhiteNoise, zero CDN calls). Dependencies resolve from conda-forge packages the factory itself built and published. Container images deploy on Red Hat OpenShift under restricted-v2 security policies. Enterprise TLS certificates bind through the OS native truststore. A capability that only works online is an incomplete capability — that rule is enforced, not aspirational.

Infrastructure is exactly PostgreSQL, Redis, and Kubernetes. A component that demands a fourth piece of infrastructure has failed its design review.

The golden path

Developers, CI runners, and coding agents invoke the same Pixi task contract. The artifact that passed Warden is the artifact Steward deploys. There is no "works on my machine" — one locked environment, one image, three deployment modes:

  • Mode A — a single all-in-one container for laptops, demos, and ephemeral CI.
  • Mode B — a local Podman pod (PostgreSQL, Redis, the host) for full-stack development with production parity.
  • Mode C — multi-container OpenShift or Kubernetes for enterprise scale, with Helm charts and OCP overlays.

The same image runs all three modes. Scaling is replicating the service. Statelessness is mandatory — all state lives in PostgreSQL and Redis.

Pixi: one environment manager to rule them all

PyForge is built on Pixi, the cross-platform package and environment manager that unifies conda-forge and PyPI. The entire dependency tree — over 1,000 packages including Django, Wagtail, FastAPI, Langflow, DB-GPT, DuckDB, Kedro, Vizro, Celery, and Polars — solves cleanly across Python 3.12, 3.13, and 3.14, on Linux, macOS (Apple Silicon), and Windows. Native binaries. No Docker required for development. No virtualenv sprawl.

AI agents as first-class citizens

Every station exposes its capabilities through the Model Context Protocol (MCP). AI agents — Claude, Cursor, Antigravity, or custom orchestrators — call the same tools a human uses, through the same governance layer. Langflow and DB-GPT are mounted on the host as pluggable agentic engines, not as separate deployments to manage. The platform provides the infrastructure; the stations provide the domain intelligence.

Path A is deterministic code — Django, FastAPI, Celery. Path B is agentic work through station personas and the agentic engines. Both paths run on the same platform, under the same compliance gate, producing the same auditable artifacts.

One query plane

PyForge unifies analytical access through a single hybrid transactional/analytical query plane built on DuckDB. Live federation reads from PostgreSQL without copying data. Kedro extracts refresh a Parquet cache for dashboards and autonomous queries. Vector search runs on the same engine. Agents cannot touch production OLTP — they query the plane. Vizro dashboards sit on the Boring Semantic Layer, giving every station a governed, consistent view of the data it needs.

One engine. One writer discipline. One place a question goes.

The operating model

Every deliverable in the PyForge estate is an outcome with a spec — why it exists, what capabilities it provides, how you test success, and what it will never do. Work follows a promotion discipline:

  • Tier 01 — one-off: a spec and a script or analysis. Built because the question needed answering once.
  • Tier 02 — short-term: a spec and a skill. Expected to repeat; worth encoding.
  • Tier 03 — long-term: a spec, a capability (deterministic or agentic), an owner, and an SLA. Supported, productionized, owing all five tiers.

Promotion is earned, not assumed. Build only what value and ownership justify. Advance only when repeatability, risk, adoption, integration, and ownership justify the investment. Every change is gated by automated validation through Warden — one verdict, one gate, no competing governance planes.

Hooks and plugins, not forks

Every layer in the platform is replaceable by design. A process owns hook specifications — named points you attach to. A plugin implements or replaces a layer without forking the process. Profile settings choose which plugins load. Enterprise scanners (SonarQube, Checkmarx, Black Duck) are Warden plugins, not a second governance plane. Identity providers (Keycloak, Entra, Okta) are profile adapters, not hardcoded integrations. The same pattern governs build engines, deploy profiles, LLM providers, and storage backends.

Contracts are not plugin surfaces. Pixi task names, the golden-path artifact identity, and the three infrastructure kinds (PostgreSQL, Redis, Kubernetes) are invariants. Everything else is configurable.

The foundry destination

The lasting git root is python-foundry (workspace name pyforge). The current local-recipes monorepo is the copy source, then archive. The recipe factory lives in its own island with its own lock file, so the factory solver farm never merges into the estate lock.

Scribe, the team memory station, is built on three ports: a persist port (graph_store), a fan-in ingest port (compile_surface), and a retrieval port (recall_ranker). Ingest writes through the persist port, never beside it. Air-gap default: optional extras off.

Fleet conventions enforce consistency across stations: fully-qualified decision tags, one authoritative source per fleet status fact, and declared state-storage choices. Marshal measures horizontally; owning stations close their rows; Doctor holds the verdict on Marshal's own row.

What we are building toward

PyForge is not a product launch — it is an estate that compounds. The eight stations are live. The platform host serves traffic. The five-tier roster is complete at 40 out of 40 cells. The query plane's first slice is shipped. What comes next is depth, not breadth:

  • The query plane matures — catalog, face, and Scribe cutover bring every station's analytical needs onto one engine.
  • The Build League and Balanced Product Scorecard make contribution and quality visible across human, agent, and team dimensions — measured by published rules, never by unpublished intuition.
  • Lane 3 dashboards (Vizro over the semantic layer) give operators real-time visibility without touching production schemas.
  • The plugin architecture extends to every enterprise tool boundary — so adopting PyForge means adapting it to your stack, not replacing your stack.
  • Epic 40 resolves two red-team CRITICALs — verified assertion minting and durable bounded broker — before cutover Phase 1. Epics 41–43 address the HIGH findings.
  • The foundry cutover (phases 0–6) migrates to python-foundry as the lasting git root, with the factory as an island and the recipe universe as a working set, not a clone.

The through-line is simple: informed decisions on compliance, resiliency, and productivity — from one place, for everyone who needs them.
