ACT I
The problem and the model
friction to insight
01

The problem

The last mile of a poster is an editable brief, not a raster. Repackaging a SaaS fails the licence and air-gap bars. Deckcraft's own open item (the pymupdf licence call) is named in the README and is not a ledger number, so it is not printed as a count here.

This ledger has no Dream Realization dates. None are printed.

The requester crosses this gap most weeks already: a prompt or a source document goes into an AI assistant, a passable outline comes back, and the assistant stops at the edge of a file it cannot itself produce — the deck still gets hand-built in PowerPoint from a blank template, one text box and one manually-picked font at a time. Closing that last mile without leaving the tools already open, and without a network call the air-gapped colleague cannot make, is the whole reason this pipeline is specified the way it is. Six named jobs-to-be-done anchor the Spec (§03 below); none of them is "make me a pretty deck" in the abstract — each is a specific request a real colleague has actually made.

02

Three audiences, one gap

The Spec names three people who hit the same wall from three different directions, not one abstract "user."

The requester & colleagues

Lose 30–60 minutes per deck to manual PowerPoint formatting today — the tax this whole pipeline exists to remove.

Air-gapped enterprise colleagues

Have Copilot or MS365 already, but no path from AI-written prose to a file they can actually ship.

Technical deck authors

Every existing tool they've tried rasterizes diagrams and charts into images nobody downstream can fix.

None of the three is served by a browser-based generator that only ever opens in a tab, however good its output looks on screen: the first two need the output sitting inside a tool they already have open, and the third needs the output to still be a real diagram after it lands on the slide, not a picture of one.

05

The pipeline: three layers, four adapters

A layered architecture with strict adapter boundaries (AD A-01): surfaces consume only the Pipeline API, renderers consume only engine adapters — nothing reaches past its own layer.

The three named swap points are LLMAdapter, PptxEngineAdapter and PlatformAdapter — nothing else is a designed swap point. StyleExtractor is a format-dispatch table (one class per input format), not a swap point in that stricter sense. All inter-module data is one immutable, JSON-serializable Pydantic model family — no hidden global state, and no dataframe ever crosses a module boundary — so the same objects that pass between an outline stage and a renderer are exactly what the MCP server hands an AI caller for its tool schemas.

06

Never rasterized

The one claim the Spec treats as non-negotiable, not aspirational: every text box, autoshape, chart and diagram is native DrawingML.

Success is measured, not asserted in a README — automated structural inspection of the generated file checks that 100% of text, shapes, charts and diagrams are native, editable OOXML with zero rasterized content standing in for any of them — the acceptance bar is that the file opens clean in Microsoft PowerPoint itself, not merely in an open-source viewer that tolerates more. A vendor-fallback boundary sits underneath this claim on purpose: python-pptx has gone quiet upstream — a large, still-growing open-issue backlog behind a project that hasn't cut a release in the better part of two years — so every call into it is routed through one adapter module rather than scattered across the codebase, so a future fork-and-patch is a one-module change if it's ever needed, not a rewrite. That fork is deliberately not pre-emptive — it only triggers on a named blocker bug, a PowerPoint format change the library can't emit, or a compatibility break the upstream project leaves unpatched for thirty days; a missing nice-to-have goes through the ordinary upstream issue queue instead.

The same discipline extends to diagrams and charts: Mermaid renders offline through a headless browser bundled with the package (no CDN, no network call), and native chart types render as real PowerPoint <c:chart> elements instead of pasted images wherever the data fits a standard chart type.

07

What this pipeline studies, without depending on

Three outside projects shaped the design without becoming a runtime dependency — reference, not reuse.

The canonical PPTX engine this pipeline wraps is the same one nearly every serious PowerPoint-generation project in the ecosystem is built on — stable, permissively licensed, and exactly the reason a vendor-fallback adapter exists rather than a hard assumption that upstream keeps shipping fixes. A separate, unrelated PPTX-to-Marp converter project is studied purely as a design reference for its own element-mapping table — which PowerPoint shape types map to which Marp directives, how it scales fonts to content density, how it preserves image cropping — without ever becoming a dependency, since it depends on its own personal fork of the engine that isn't packaged for conda-forge. That same fork adds equation parsing and TIFF support the mainline engine lacks; if this pipeline ever needs either, the plan is to vendor just that patch selectively and contribute it upstream when it's worth the effort, not to inherit the whole fork.

Six renderers, no LLM inside any of them

The render half of the pipeline is deliberately dumb: text and structure go in, a file comes out — no model call happens inside a renderer.

RendererWhat it does
pptx_engineWraps python-pptx behind the vendor-fallback boundary; the only module allowed to import it
marp_engineShells to marp-cli for the human-editable Markdown round-trip, plus PDF/HTML export
chart_renderermatplotlib/plotly; native PowerPoint chart XML for bar/line/scatter/pie, SVG otherwise
mermaid_rendererBundled headless Chromium, no CDN; a persistent process keeps repeat diagrams fast
image_generatorSDXL-Turbo via diffusers — opt-in, default off, weights lazy-pulled on first real use
image_understanderA local vision model describes an existing image; a CPU-only fallback path exists

Every asset a renderer produces is content-addressed and cached by a hash of its own spec, so a second run that asks for the same chart or diagram is free — the cache exists specifically because a Mermaid cold start and a from-scratch image render are the two slowest things this pipeline ever does, and an iterative editing session hits them repeatedly.

Ten patterns, one discipline

Architecture §3's conflict-prevention rules — non-negotiable, and enforced by a dedicated test suite rather than left to review discipline alone.

P-01 pptx access only through the one engine adapter
P-02 LLM calls only through the adapter — no direct SDK imports in business code
P-03 paths only via pathlib + platformdirs — no string-built paths
P-04 subprocess calls are explicit list-form, never a shell string
P-05 inter-module data is Pydantic — no DataFrame crossing a boundary
P-06 optional capabilities fail into a warning, never a crash
P-07 no outbound call without the offline gate check first
P-08 asset rendering goes through the one pipeline, never called ad hoc
P-09 every timestamp is timezone-aware — no naive datetime
P-10 structured logging only — no stray print() in production code

A dedicated pattern-enforcement test suite greps and AST-scans the codebase for violations of all ten rules at once, with at least one positive and one intentionally-broken negative test per rule — the discipline is meant to survive contributors who never read this poster.

16

One document's journey

A single input walks the same five stations whether it started as a prompt, a PDF, or a corporate template.

Dedup runs alongside the outline stage, not after it: any two generated slides whose embeddings sit at 0.92 cosine similarity or above collapse to the first occurrence before rendering ever starts, so the deck that comes out the other end never has to be manually pruned for repeats. If the schema-validated response fails once, the pipeline retries a single time with the validation error appended to the prompt before giving up and surfacing a named error with the raw response attached — never a silent partial deck.

Hardware tiers, model picks

deckcraft init auto-detects a tier from RAM and lets the user override it; every tier has a locked default model family, not a suggestion.

TierReference machineText / code / vision models10-slide outline budget
SmallWin, 32 GB, CPU8B / 7B / 3B vision, quantized GGUFunder 15 minutes
MediumM4, 48 GB, Metal / MLX14B / 14B / 7B visionunder 4 minutes
LargeFramework laptop, 64 GB, CPU30B-class / 30B-class / 7B visionunder 10 minutes

The large-tier budget is the one that gates everything else: a pre-work spike benchmarks it against an 8-minute pass criterion before the rest of the build is allowed to start, precisely so the timeline commitment rests on a measurement instead of a guess. Detection itself uses finer-grained RAM breakpoints than the three named tiers suggest — the bottom of the small band gets an explicit "may struggle" warning rather than being silently treated the same as the middle of that band. Backend selection then layers on top of the detected tier: Apple Silicon prefers an MLX-format build of the chosen model when one exists and falls back to the same default server with Metal acceleration when it doesn't; every other platform simply runs that default server, CUDA-accelerated where an opt-in GPU feature is installed and CPU-only otherwise. A user who already runs Ollama on the standard local port is picked up automatically, with no server spawned on top of it.

18

Three real machines, one broken GPU path

The tier table in §17 isn't a spreadsheet exercise — it was written against three specific laptops the requester actually has.

The large-tier machine is a Linux laptop whose integrated GPU compute path turned out to be broken during the research pass itself — an older firmware build hangs under sustained load, so this machine currently runs the pipeline CPU-only, with a real speedup sitting behind an OS/firmware update that hadn't landed yet. The medium-tier machine is Apple Silicon, where the default local-model server auto-detects the on-board accelerator with no configuration at all, and an Apple-specific inference runtime is confirmed present on conda-forge for exactly this platform. The small-tier machine is Windows, and it drives the V1 default specifically because it has the tightest RAM budget of the three — whatever comfortably runs there is guaranteed to run on the other two as well. None of the three gaps this uncovers — the Windows NVIDIA path, the Linux GPU firmware issue, a possible Vulkan build for non-NVIDIA Windows GPUs — blocks V1; each is named and documented rather than silently worked around.

19

Graceful degradation, never a crash

Every optional capability — image generation, vision, Mermaid rendering, chart rendering — is wrapped so its failure is caught, logged, and written to a sidecar warnings file next to the deck, and the pipeline keeps going.

A broken renderer never takes the rest of the deck down with it — it becomes a placeholder plus one line in <deck>.warnings.json, never a stack trace the requester has to debug mid-generation. The same discipline applies to the offline gate: a capability that would need the network checks first and raises a named, catchable error rather than hanging or silently phoning home. Every adapter that could reach a network logs whether it actually attempted to, true or false, into a structured audit trail — the air-gapped test suite asserts that log never once reads true during a default-mode run.

20

BYO style, four sources

Bring your own branding and the generated deck, its charts and its diagrams all inherit it — no per-template hand-coding.

.potx / .pptx extracts theme, layouts, masters and brand assets directly through python-pptx; passing --as-sample keeps the same extraction but discards the source deck's own slides. .docx yields theme colors and heading/body fonts only — Word has no slide layouts, so the generated deck inherits the bundled default template's layout set instead. .pdf branches on how much text is actually extractable: enough text samples fonts, colors and heading sizes directly; too little (a scanned brand guide) falls back to OCR and samples colors from the rasterized page instead. Legacy .ppt and .doc are rejected with a "save as and retry" message rather than guessed at. .odp / .odt style sources were slipped out of the first release to keep the build inside its own committed window; the library that would read them is already installed, so the second release only owes one new module, not new environment work. A corporate template matching the requester's own employer brand on day one is treated as a deliberate stickiness lever, not an afterthought — BYO style exists specifically so nobody has to wait for a bespoke integration to get their own branding on the very first deck.

21

Layout mapping: LLM-guided, with a heuristic net

Given a template, the layout mapper runs after the outline and before rendering — the LLM picks, but a deterministic fallback catches it if it picks badly.

The template's own layouts are extracted first (name, index, and which placeholders each one carries), then handed to the LLM alongside the outline's own semantic slide types, and the LLM answers with one layout index per slide. Every answer is validated before it's trusted: the index has to exist, and the chosen layout's placeholders have to actually fit the slide's content — an image-bearing slide can't be pinned to a title-only layout just because the LLM said so.

Slide's semantic typeHeuristic fallback if the LLM's pick fails validation
titlefirst layout with a title and a subtitle placeholder
contentfirst layout with a title and a text-bearing body placeholder
two_columnfirst layout carrying two body placeholders
image_with_captionfirst layout with both an image and a text placeholder
blankthe blank or title-only layout
anything elsePowerPoint's own conventional "Title and Content" layout

A user who already knows their template can skip the LLM step entirely with an explicit alias file mapping slide types straight to layout indices — the heuristic and the LLM step both exist for the user who doesn't.

Three benchmarks, one gate

Timing is measured three times before the build trusts its own schedule — never assumed once and carried forward.

BenchmarkWhenPass criterion
Spike-0 — outline onlybefore any epic is broken into storiesunder eight minutes for a ten-slide outline on the large tier
Spike-1 — full deckafter the first wave of foundation workunder ten minutes end to end, no images
Spike-2 — every reference machineafter the renderer waveeach machine holds its own tier's budget from §17

Spike-0 is the one the whole plan actually leans on: a miss there re-tiers the large-tier model, revises the timing target upward, or gets documented as a known limitation — three named outs, decided in advance, so a bad benchmark result has a plan waiting for it instead of triggering a scramble.

Six stories carry no dependency on that gate at all and are ready to start the moment a build begins: project scaffolding, the platform adapter, the Pydantic data model, the document extractor, the LLM adapter layer, and the benchmark itself. Every other story — all twenty-two of them — waits behind the gate's result, not before it starts, but before any of them is allowed to proceed past it. A failed Spike-0 has its own contingency already written down rather than left to be improvised: re-tier the large-tier model down one size on the reference machine that missed the budget, update the timeline claim it invalidated, and record the re-tier as a formal architecture amendment rather than a quiet edit.

The doctrine band

Five constraints the Spec treats as founding, not as ordinary acceptance criteria.

  • Editable, always. Zero rasterized text, shapes, charts or diagrams — checked structurally, not by eye.
  • Air-gapped by default. Zero outbound calls after the first-run model download; every feature is re-verified inside a network-isolated test run.
  • conda-forge-only runtime. Every dependency resolves from conda-forge; only model weights are the one pre-downloadable, air-gappable exception.
  • MIT or Apache-2.0, no exceptions. The project's founding license bar — no proprietary or copyleft code, full stop.
  • Structural parity across platforms. The same prompt and tier produce the same slide, shape and chart counts on Linux, macOS and Windows — only the generated text differs.

The open ledger

One license conflict is named as blocking, not resolved away, and one story is where it actually bites.

The PDF style-extraction path leans on a PDF library that PyPI lists as dual-licensed AGPL-3.0 or Artifex-commercial — a direct conflict with the project's own MIT-or-Apache-2.0-only founding bar. Three named options sit open, undecided: accept the AGPL library for this one opt-in extraction path with a documented rationale; substitute an already-in-environment, MIT-family library at a documented quality cost; or scope the OCR-fallback depth out of the release entirely. This blocks one specific story — the PDF style loader — not the Spec as a whole, and it is a human call, not something a build session gets to decide on its own.

The success signal

A dogfooding bar, not a vanity metric: the requester ships at least one real, ship-quality deck a week for four consecutive weeks after release.

Missing that bar — more than sixty minutes of hand-editing per deck, or more than an hour a week of pipeline maintenance — triggers a documented kill decision and a rescope toward converging with the sibling presenton-pixi-image chain rather than carrying two half-finished engines forward — the kill decision is named in the Spec itself, not left for a future team to improvise under pressure. Two machine-checkable signals reinforce the dogfooding bar so it can't be eyeballed away: the zero-rasterized-content check (Act I, §06) and the network-isolated CI run described below.

A few requirement hints ride along with the core three audiences: the pipeline is specified to accept a BMAD PRD, an epics file, or an architecture document directly as input — "make a deck from this PRD" is a built-in path, not a workaround — and because the notebook-kernel package this repo already runs is present in the shared environment, the pipeline is importable from a notebook for free, without that being a committed distribution surface in its own right.

Enterprise and air-gap posture

The regulated-enterprise colleague is a named primary audience, not an afterthought bolted on later.

An environment variable gate stops every optional network path cold when set, so a laptop with no route to the internet still produces a full deck. A second variable points every model download at a pre-staged local directory, so weights can be transferred once by whatever channel an air-gapped site already trusts and never pulled live again. The whole default path — no flags, no configuration — already makes zero outbound calls after the very first model download, and CI re-runs the golden-path tests inside a network-namespace-isolated job specifically to keep that claim honest rather than assumed. A first-run setup command can also pre-pull every tier's models in one pass on a connected machine for exactly this transfer-then-air-gap workflow.

The moat moved

A minor "Option C" mentioned once at intake grew, within under eight months, to a dominant open-source entrant with real scale behind it — and it meets deckcraft's own editability bar.

Four original differentiation claims get re-scored against that one project alone: from-primitives is eroded — it compiles constrained SVG into DrawingML by its own scripts, no wrapped app in between. Always-editable native output is eroded — its shapes, masters and animations meet or exceed this Spec's own bar. Multi-surface embedding is partially eroded — it already works inside several coding-agent IDEs, though this Spec's own surface list stays broader. Air-gapped by default is not eroded — the comparable has no documented local-LLM-first or offline mode and leans on cloud-hosted models for quality. The honest read: "editable native PPTX" alone stopped being a distinguishing claim; "editable, air-gapped, and embedded beyond just a coding-agent IDE" together is what's left.
