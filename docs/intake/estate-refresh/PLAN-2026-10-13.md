# Estate refresh

**The ask.** Updating the estate's library pins and its BMAD pins is today a six-step hand
sequence the operator runs from memory, and nothing after step six is repeatable: the derived
files are regenerated by hand, the pin losses are found by reading a 21,000-line diff, the
station suites are run or not run, and the BMAD install never follows the pin. The ask is one
policy-driven, measured, repeatable path: declare the pin policy once, move the pins on it,
restore what the tool loses, regenerate every derived surface by its own generator, prove the
result in every environment and every station suite, hand a moved BMAD floor to the existing
core apply and suite advance, and land the whole batch as one reviewable PR with a journal.

**The chain.** This drop is pre-triage. The work enters the repo the way every effort does: a
dated entry on the steward station Dream (`docs/dreams/pyforge-steward.md`), `bmad-spec`
mints the CAP on `spec-pyforge-steward`, a numbered Epic lands in steward's `epics.md` with its
ledger rows, and a tracked story spec precedes code. Section 7 names the append; nothing
outside this drop changes until it exists. Ownership is steward's, whole: a capability about
the estate's own `pixi.toml`, its environments or its libraries is never split across stations
(team memory, 2026-10-06).

## 1. Baseline — the hand sequence, as run on 2026-10-13

1. `cd ~/UserLocal/Projects/Github/rxm7706/local-recipes/`
2. `pixi shell -e local-recipes`
3. `pixi upgrade --pinning-strategy latest-up --exclude …` — 28 `--exclude` flags. On `main` the
   command was a comment at `pixi.toml:48` with 20 excludes; the operator's working tree extended
   it to 28 (`asgiref`, `channels_redis`, `psycopg`, `psycopg2`, `libpq`, `pgvector`, `cachebox`,
   `pixi`), so the newest policy lived only in an uncommitted edit (corrected 2026-10-13). Two
   older generations of the same comment sit above it (`:45`, 17 excludes; `:46-47`, "19
   excludes"). The comment is the only place the "do not move" policy exists, and nothing reads it.
4. `pixi update` — the transitive re-solve.
5. `exit`
6. `pixi install -a`

Then, by hand and only when remembered: a branch, `environment.yaml` regenerated, the library
catalog's floors re-synced, the BMAD-estate catalog regenerated, the pixi-version sites
checked, station suites run, memlog lines and scoped stamps on every Spec that governs
`pixi.toml`, a PR with the `maintenance` label.

## 4. Gaps

1. **The policy is a comment.** The exclude list lives in `pixi.toml:45-48` in three
   generations; nothing renders it, checks it, or says why each package is held or until when.
2. **The losses are found by eye.** G117's specifier diff is a recipe, not a check; two more
   loss classes (a flattened channel table, a lowered floor) have no recipe at all.
3. **The derived surfaces regenerate by hand, each its own way** — `environment.yaml` by the
   exporter, the library catalog's floors by an LLM prompt, the BMAD-estate catalog by scribe,
   the env matrix by a script, the pixi-version sites by the mutator, the generated docs by
   their generators, the `bmad-suite` metapackage by `generate-bmad-suite`.
4. **Nothing proves the batch across the estate** — 36 environments, three platforms, ten
   suites; the one certain signal today is the CI run after the push.
5. **A moved pin stops at the lock.** A library whose install has a side effect beyond the pixi
   environment is not re-applied, probed or tested when its pin moves: the BMAD core
   (`_bmad/_config/manifest.yaml` at 6.12.0 against a 6.12.2 pin), the skf module and its skills,
   each bmad-suite module's wiring, `bmad-loop`'s harness range sites (CAP-12's fan-out) and loop
   homes, the caveman skill and hooks (`caveman-install --only claude --with-hooks`), the headroom
   proxy and the codegraph index (marshal's seed kit, CAP-162), the pre-commit hooks, the 16 pixi
   version sites, the CLIs warden and steward shell to (`opengrep`, `osv-scanner`, `deptry`, `age`,
   `gh`, `helm`), the local services (`postgresql`, `redis-server`, `silo`) and the import-probed
   platform libraries. Each has its own install class and its own liveness probe; none is declared
   in one place, and nothing confirms the estate is live at its pins after a refresh. (Operator
   direction 2026-10-13: "ensure bmad packages are not just updated in the pixi.toml but realized
   and implemented; the same applies for libraries like caveman, headroom etc. — all libraries that
   need to be installed and tested need to be confirmed.")
6. **The spec-surface reconcile is a ritual** — a memlog line and a scoped stamp on each of
   the seven Specs whose surface names `pixi.toml` / `pixi.lock` / `environment.yaml`, by hand.
7. **No cadence, no plan, no journal** — nothing says when a refresh is due, what it would
   move before it runs, or what the last one moved.

## 5. Solution — what it looks like when real

- **One tracked policy, `docs/governance/pin-policy.yaml`** (with a JSON Schema beside it; the
  `guild-roster.json` / `ci-surfaces.yaml` shape: governance declares, code renders and checks).
  One row per held package: `package`, `hold` (`never-move` | `cap` | `channel` | `exact` |
  `floor-only`), the clause to keep (`cap: "<3"`, `channel: SelfExplainML`, `exact: "4.2.1.*"`),
  `features` (`*` or a list), `reason`, `authority` (a Story, CAP, gotcha or fnd:CAP-12), and
  `until` (the condition or date that retires the row). Defaults: `pinning_strategy: latest-up`,
  `floors_never_lower: true`. The canonical upgrade command is **rendered** from the rows
  (`never-move` rows become `--exclude`); the three comment generations in `pixi.toml` become
  one pointer line.
- **Station pin fan-out (`pin_policy_check.py --fan-out`)**: every package-level range in
  `src/shared/packages/*/pyproject.toml` and each package `pixi.toml` `[package.run-dependencies]`
  (the reader `llms_full_check.py` already has) is compared with the locked version; a locked
  version outside a station's range is a red finding naming the station and the file, and the
  refresh refuses to land it — the move is that station's story, so no package-level pin is ever
  rewritten by the refresh and no lock-block eviction is needed.
- **One detector, `scripts/pin_policy_check.py`**, in `detectors-ci` and `pr-preflight`:
  every pin expression in `pixi.toml` that carries a cap, an inline table or an exact pin has a
  policy row (else `undeclared-hold`); every row matches a real declaration; the pointer line
  matches the rendered command; and `--diff <base-ref>` judges a change — a lost cap, a
  flattened table, a lowered floor, a moved `never-move` package — naming package, feature,
  before and after. Run over the 2026-10-13 batch it yields exactly the nine findings above.
- **One mutator, `scripts/pin_policy_restore.py`** (the `bump-pixi-version` shape): rewrites
  each named declaration back to its policy clause at the newly resolved floor, keeps the
  comment, re-locks with `pixi lock`, re-runs the check; an unsolvable restore is a refusal
  naming the row, never a silent drop.
- **One duty, `pyforge steward estate`**, behind `pyforge.steward.estate_refresh`:
  - `plan` — `pixi upgrade --dry-run --json` through the policy: what would move (package,
    feature, from, to, held-by), the BMAD table (pinned / installed / latest, from doctor's
    reader), days since the last journal; `--due` reds past 30 days.
  - `refresh` — renders the command, runs `pixi upgrade` (never `pixi update` unless
    `--transitive`, operator-only), runs the guard and the restore, re-locks, journals.
  - `reconcile` — regenerates every derived surface by its own generator (`environment.yaml`,
    the catalog floors via a new deterministic `llms_full_check.py --fix-floors`, the
    BMAD-estate catalog, the env matrix, the pixi-version sites when the `pixi` floor moved, the
    generated docs, the `bmad-suite` metapackage), runs every check, then appends the memlog
    event line to each Spec whose surface governs the moved files (read from
    `scripts/.spec-surface-baseline.json`, never a hard-coded list) and stamps each scoped.
  - `verify` — in a detached worktree (never the working tree), `pixi install --frozen` for the
    default tier (Guild, core, testing-kit, the eight station envs, `platform-ci-test`,
    `pyforge-foundry-full`) and every environment under `--all`, then the lanes CI would run for
    a `pixi.toml` change (read from the workflows, CAP-159; CAP-166's pauses honored and named),
    the laptop SBOM gate, the recipe-factory import smoke, every realization-register probe and
    each distinct test once, and the station pin fan-out; the atlas browser gate, herald's
    browser check and scribe's Postgres lane are named manual rows; one row per environment,
    lane and probe in the journal, each carrying the platform; other platforms are lock-solved,
    and the journal says so.
  - `status` — the last journal, in one read.
  - A moved `bmad-method` or `bmad-*` floor is handed to `steward upgrade bmad-core` (pre-flight
    always; `--apply-bmad` runs CAP-10/14/16) and `steward suite pipeline-truth` / `advance`;
    an installed core below the pinned floor is a journaled finding and `verify` reds on it.
- **One realization register, `docs/governance/realization-register.yaml`** (with a JSON Schema): one
  row per library whose install has a side effect beyond the environment — `package`, `env`, `class`
  (`installer-tree` | `module` | `harness` | `kit` | `hooks` | `pin-sites` | `cli` | `service` |
  `import`), `realize` (the argv that re-applies it, or none; `operator_gate: true` where it rewrites
  installer-owned or settings files), `probe` (argv and `expect`: the locked version, a kit item `ok`,
  a boot, an import), `test` (the pixi task or lane that exercises it), `owner`, `authority`. It
  generalizes the bmad-suite install-class playbook (CAP-27/28) to every realized library: `bmad-method`
  realizes through `steward upgrade bmad-core --apply` and probes the manifest; `bmad-module-skill-forge`
  through its own `update`; each suite module through `steward provision --module` and
  `suite pipeline-truth`'s `installed` / `wired` stages; `bmad-loop` through `marshal refresh` per loop
  home and `bmad-loop validate`; `caveman-installer`, `headroom-ai` and `codegraph` through their
  installers and `marshal seed check --json`'s kit items; `pre-commit` through `pre-commit install`;
  `pixi` through `bump-pixi-version`; the CLIs through `<bin> --version`; the services through a boot;
  the platform libraries through the laptop SBOM gate's import probes. A repo-scope check reds a row no
  feature declares and a `bmad-*` / `mybmad*` pin or seed-kit item with no row (both read from existing
  readers, never a list).
- **`estate realize`** — for each register row whose package moved (or `--all`): run `realize` (an
  `operator_gate` row only under `--yes`, else journaled `skipped-operator-gate`), then `probe`, and
  journal `{package, from, to, realize, probe: live | stale | missing}`; `--plan` writes nothing.
  `estate verify` runs every row's probe and each distinct test once, and reds on `stale` or `missing`
  — the estate is confirmed live at its pins, not just locked.
- **One journal**, `.steward/estate-refresh/<date>.json`, tracked: pins moved, losses restored,
  BMAD state, per-environment and per-lane verdicts, the base and result SHAs.
- **One how-to**, `docs/how-to/refresh-the-estate.md`, registered in `docs/map.yaml`, plus one
  pointer line in `AGENTS.md`, the release-cadence runbook's step 7 pointing at `estate
  refresh`, and the three comment lines in `pixi.toml` replaced by the pointer.
- **The first refresh lands through the path**, superseding the 2026-10-13 hand batch (which
  stays uncommitted on the operator's working tree until they discard it).

Steward reaches `pixi`, `gh`, `git` and every generator by subprocess (AD-1). Steward's own
code never writes `pixi.toml`: `pixi upgrade` and the policy mutator do, as subprocesses, and
the mutator is a repo script like `bump_pixi_version.py` (AD-5 as read since Story 72.1).
`main()` keeps every exit code (AD-8). No daemon, no workflow, no cron (AD-4's posture): the
operator runs `estate refresh`; agents run `plan` and, inside a worktree that lands through a
PR, `refresh` without `--transitive`.
