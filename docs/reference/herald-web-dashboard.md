# Herald web dashboard

This page lists what Herald's web dashboard (`src/shared/packages/pyforge-herald/web/`) shows an operator: its snapshot files and the exporter behind each, its tabs, filters, empty and error states, and its breakpoints (herald Stories 7.1, 7.2 and 12.2).

:::caution
The dashboard is a static snapshot, not a live app. No exporter runs when you run a `herald` write command, so the dashboard keeps showing whatever it last had, with no error and no warning banner. This is the number one cause of "I ran the command but the dashboard didn't update."
:::

## Snapshot files

The dashboard is a plain static Vite bundle with **no backend server, no live API**. Every panel reads a pre-generated JSON file from the dashboard's `public/` directory at page load. The exporters live in `src/shared/packages/pyforge-herald/scripts/`:

| Tab | Reads | Regenerated by | Contents |
|---|---|---|---|
| Progress | `public/progress.json` | `export_progress_snapshot.py` | Every progress record; `[]` when none is recorded, so the app still builds. |
| Success | `public/success.json` | `export_web_snapshot.py` | **Published** claims only; drafts never ship to the snapshot. |
| Operations | `public/notices.json` | `export_notices_snapshot.py` | Published and closed notices; drafts excluded. |

All three read `.herald/herald.db` under `--repo-root` (default: the current directory). `herald progress warden --update` writes `.herald/herald.db`; it does **not** touch `public/progress.json`.

## Exporter invocation

| Exporter | Wired into npm | Output flag and default |
|---|---|---|
| `export_progress_snapshot.py` | Yes: `npm run sync-progress`, which `predev` and `prebuild` run first | `--out-dir`, default the package's `web/public/` |
| `export_web_snapshot.py` | No: run by hand after publishing a claim | `--out-dir`, default the package's `web/public/` |
| `export_notices_snapshot.py` | No: run by hand after authoring, publishing or closing a notice | `--out`, default the package's `web/public/notices.json` |

The output defaults are relative to the package root, not your current directory. `npm run sync-progress` passes the repository root as `--repo-root`. There is no single "sync everything" command: each Moment's exporter is invoked separately. `herald scheduler run` rewrites `progress.json` too.

```
cd src/shared/packages/pyforge-herald/web
npm run sync-progress
```

The copy-paste commands for all three are in [How to record progress, claims and notices with Herald](../how-to/record-progress-claims-and-notices-with-herald.md).

## Running the dashboard locally

`npm` and a `python` that can import `pyforge.herald` must both be on `PATH`; the `pyforge-herald` pixi environment provides both.

```
cd src/shared/packages/pyforge-herald/web
npm install
npm run dev       # http://localhost:5173, HMR, auto-syncs progress.json first
```

or a production build:

```
npm run build
npm run preview   # http://localhost:4173
```

`npm run test` runs the vitest suite: tab switching, sidebar breakpoint collapse, tooltip show/hide, and panel rendering, empty and error states.

## Tabs

Four tabs (`TabNav`, top of the page): **Pitch**, **Progress**, **Success**, **Operations**. Pitch is an *external* link (opens `https://github.com/rxm7706/local-recipes` in a new tab). It is not an in-app panel, so there is nothing to sync for it.

## Sidebar filters

Shared across Progress, Success and Operations:

- **Station** — a dropdown of the known PyForge Guild stations (`warden`, `atlas`, `marshal`, `mason`, `doctor`, `scribe`, `steward`, `herald`).
- **Date range** — two free-text `YYYY-MM-DD` inputs; either can be blank for an open-ended range. A `?` help icon next to the label expands an inline explanation of the format (click or Enter/Space).
- **Search** — free-text; scoped per-panel to whatever fields that panel matches against (e.g. Success matches project name + thesis).

Every input in the sidebar also carries a hover/focus tooltip (`Tooltip.jsx`) naming what it filters.

## Progress tab

Card-per-station, showing the **latest** record for each station matching the current filters. Collapsed: station, date, shipped-capability count, total compute hours. Expanded (click the card): full capability list, the cost breakdown (compute hours / token spend / wall-clock hours), and the unblock narrative.

| State | Text |
|---|---|
| Empty | "No progress recorded yet." (or "No progress recorded for `<station>`." when a station filter is active), with the hint `herald progress <station> --update` |
| Error | "Could not load progress.json." with the fix: "Run `npm run sync-progress` (or `npm run build`) after recording progress, then reload." |

## Success tab

Card-per-claim (published only), showing project name, thesis, shipped date, and one evidence badge per evidence item. Badge states, each with its own tooltip:

| Symbol | Meaning | Tooltip text |
|---|---|---|
| ✓ | valid | "`<type>`: valid (valid since `<date>`) — `<url>`" |
| ✗ | broken | "`<type>`: this link may be broken (`<never/last validated>`) — `<url>`" |
| ⚠ | stale | "`<type>`: hasn't been validated recently; review it (`<...>`) — `<url>`" |

Expanded (click the card): full thesis, evidence links (clickable, open in a new tab), edit history (each prior thesis version with its timestamp), and status/shipped/published/closed dates.

| State | Text |
|---|---|
| Empty | "No published claims." with the hint `herald success create <project> && herald success publish <claim-id>` |
| Error | "Could not load success claims." with the fix: "Run `python scripts/export_web_snapshot.py` to regenerate success.json." |

## Operations tab

Notice board, one card per notice (published + closed; drafts never reach this snapshot). A **Category** dropdown local to this panel (`deprecation` / `fix` / `eol` / all) sits above the board; the shared sidebar's date range filters against `created_at`. Each card header shows the category badge, component name, status, and deadline (if any); expanding shows what/why/migration text, the evidence link (if any), and, for a closed notice, the close reason.

| State | Text |
|---|---|
| Loading | "Loading notices…" |
| Empty | "No operations notices yet." with the hint `herald notice author --type deprecation --component <name> --publish` |
| Error | "Could not load operations notices." with the fix: "Run `herald notice list` from the CLI, or re-export web/public/notices.json." |

## Responsive behavior

| Viewport | Behavior |
|---|---|
| Desktop (>=1200px) | Sidebar always visible. |
| Tablet (768-1200px) | Sidebar collapses behind a hamburger; opening it overlays the content as a drawer. |
| Mobile (<768px) | Everything stacks vertically (no overlay), body text floors at 16px, interactive targets are >=44px. |
